# 关键帧检测模型训练

## 知识点解析

### 概述

本文整理视频关键帧检测模型训练工作，包括业务背景、任务定义、数据构建、标注标准沉淀、bad case 归因、高优数据飞轮、基座模型与推理优化、模型部署上线和后续训练范式思考。

### 任务背景

关键帧检测服务于 UI 性能评估链路。系统需要从移动端操作录屏中找到某个性能指标对应的结束帧，再结合起始帧换算耗时。

```text
input: 操作录屏 + task_type + 起始帧/候选帧信息
output: 结束帧时间戳 / frame index + 判断依据
downstream: 性能耗时计算、智能预标、人工标注提效
```

这不是普通视频分类任务，而是带业务规则的时空证据定位任务。模型必须理解不同 `task_type` 下“什么状态才算完成”。

### 解决的问题

关键帧检测模型训练主要解决四类问题：

1. 人工标注成本高：CQC 单人标注人效约 150 条/PD，人力峰值约 1200 条/天，难以支撑持续增长的数据需求。
2. 通用模型不达业务准出：Codex + gpt5.5 在当前任务下 Acc@1 为 55.0%，Acc@3 为 69.3%，距离 Acc@3 90% 的业务要求有明显差距。
3. 标注标准不稳定：不同标注人员对“首帧出现”“页面停稳”“完全加载”等标准理解不一致。
4. 数据分布长尾：指标超过 170 个，不同业务线样本量和难度差异大，平均补数据收益低。

| 方向 | 结果 |

| 业务收益 | 标注成本下降 19%，提效贡献占比 9.5% |

### 方法总览

```text
问题定位
  -> bad case 人工归因
  -> 标注标准沉淀
  -> prompt / 训练样本规则化
  -> 高优数据飞轮
  -> 基座模型优化
  -> 推理侧 FPS / 粗筛精筛优化
  -> 部署上线和回测
```

### 标注标准沉淀

关键帧检测的难点在于不同 task_type 的完成态不同。标准需要拆成：

- 完成态：必须满足哪些 UI 状态。
- 排除条件：哪些帧一定不能选。
- 豁免条件：哪些变化不影响完成态。
- 首选证据：优先看哪个 UI 变化。
- 备选证据：首选证据不可见时如何兜底。

示例：

| 指标 | 首选证据 | 备选证据 | 容易错的点 |
| --- | --- | --- | --- |
| 购物车加购耗时 | 购物车角标数字增加 | 购物车被遮挡时看“加购成功”文案 | 只看到飞入动效或弹窗升起就提前截 |
| 商详页加载耗时 | 头图、价格、营销 Banner 清晰完整且页面停稳 | 局部异步组件可豁免 | 只看到商品主体出现就提前截 |
| 商详页头图滑动耗时 | 第一次滑动完成，头图居中高清定型 | 后续第二次滑动可证明第一滑已结束 | 跳过第一次滑动或抢跑 |

标注标准沉淀的本质是把人工经验转成模型可学习的业务先验。

### Bad Case 归因

模型效果波动不一定来自模型本身，也可能来自 GT 标注质量、业务规则冲突或评测口径不一致。

归因类型：

- 标注误差：人工标注帧本身不稳定或不符合标准。
- 标准冲突：同一 UI 元素在不同指标中的等待规则不同。
- 模型能力问题：小元素、角标、边缘区域、营销 Banner、白膜、loading 识别不足。
- 时间边界问题：低 FPS 抽帧错过“刚出现/刚稳定”的第一帧。
- 规则豁免问题：局部异步变化是否应等待，没有写清楚。

实验中人工筛查 204 个 bad case，其中标注误差 68/204。返修样本中实际 relabel 占保留返修样本约 61.45%，无变化样本约 38.55%。这说明不能默认 GT 全部正确，必须先做 bad case 归因和标注质量校验。

### 高优数据飞轮

数据飞轮流程：

```text
模型预测
  -> 筛选 bad case
  -> 人工复查和重标
  -> 归因到指标/业务线/错误类型
  -> 回流训练
  -> 分桶评测
  -> 下一轮数据选择
```

为什么不是平均补数据：

- 全量指标多，样本长尾明显。
- 高优业务线决定当前交付目标。
- 低分高价值指标更值得优先治理。
- 标注标准冲突样本比普通样本更能提升边界判断。

数据飞轮结果：

- 三轮返修 27000+ 高质量样本。
- 1 epoch 快速验证中，国际电商 ACC 从 82.479 提升到 93.927。
- 5 epoch 训练中，从 Base1 平均 ACC 75.714、国际电商 84.093，提升到 Base6 平均 ACC 84.876、国际电商 95.933。

### Prompt 与规则优化

Prompt 的作用不是简单“把问题说清楚”，而是把业务标注标准注入模型：

- 明确任务目标。
- 明确完成态和排除条件。
- 明确豁免条件。
- 明确优先级。
- 防止抢跑、防止跳过、防止等待无关组件。

实验结果显示，prompt 调整后 1 epoch 快速验证平均 ACC 从 73.886 提升到 81.54，国际电商 ACC 从 84.466 提升到 95.418。

### 基座模型与推理优化

当数据飞轮收益收敛后，瓶颈会转向模型细粒度 UI 理解和时间边界定位。

基座优化：

- 验证 Qwen3.5 等更强 [VLM](<../../06_视觉多模态与生成模型/多模态模型/VLM与Vision_Instruction_Tuning.md>)。
- 重点看 UI 小元素、边界帧、指令遵循、结构化输出稳定性。
- Qwen3.5 基座验证将全量指标 80.083 提升到 82.239。

推理优化：

- 低 FPS 容易错过关键帧第一瞬间。
- 30 FPS 思路可提高时间覆盖密度。
- 更合理的是 global-to-local：先低 FPS 粗定位候选窗口，再对候选窗口 30 FPS 精筛。
- 推理优化进一步将能力提升到 83.469。

### 训练范式思考

关键帧检测不是纯时间戳预测，而是“时间边界 + UI 区域 + 状态变化”的联合判断。

可采用：

```text
Direct SFT
  -> Structured CoT SFT
  -> RL
```

Direct [SFT](<../../03_训练优化与对齐/后训练与对齐/SFT 监督微调.md>)：

- 先保证基础关键帧判断能力。
- 避免一开始引入过长 [CoT](<../../02_大模型/应用与问题/CoT.md>) 干扰 loss。

Structured CoT SFT：

- 让模型学会稳定输出时间证据、空间证据和 UI 状态。
- CoT 必须可验证，不能只是事后解释。

RL：

```text
R = R_time + R_format + R_boundary_evidence - P_length
```

- `R_time`：时间戳是否准确。
- `R_format`：输出是否结构化可解析。
- `R_boundary_evidence`：是否绑定正确 UI 证据。
- `P_length`：惩罚冗长无效推理。

关键帧 CoT 蒸馏、Video Primitive、Evidence Chain、质量分层、隐藏校验和训练样本过滤流程见 [CoT蒸馏与RL方案.md](<CoT蒸馏与RL方案.md>)。当前 Qwen3-VL 的训练样本结构、`<video>` 与 `videos[0]` 的绑定关系，以及 `infos` 字段的实际作用见 [Qwen3-VL关键帧数据格式.md](<Qwen3-VL关键帧数据格式.md>)。

### 模型部署与上线

部署接入需要保证离线效果能稳定进入线上链路。

| 任务 | 关键问题 | 结论 |
| --- | --- | --- |
| 接口定义 | 用户输入、模型输入、模型输出字段是否对齐 | 明确 task_type、起始帧、图片 URL 列表、预测结束帧、置信度等字段 |
| 效果测试 | 线上服务效果是否和离线一致 | 通过人工二次校验 bad case 区分标注误差和模型误差 |
| 吞吐测试 | 瓶颈在下载还是推理 | 串行下载约 30s，模型推理约 3s，瓶颈主要在图片下载 |
| 压力测试 | 单卡并发和 QPM 如何设置 | 单卡并发 20 左右较合适，平均处理约 45s，QPM 约 22 |
| 全链路联调 | 上游 keyframe_type 和模型能力是否正确映射 | 维护 mapping，保证请求能正确进入服务并回传结果 |

### 常见考法与解题方法

| 考法 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 项目理解 | 关键帧检测解决什么问题 | 从人工成本、业务准出、耗时计算链路回答 |
| 数据问题 | 为什么要 bad case 归因 | 区分模型错、GT 错、标准冲突和评测口径问题 |
| 方法问题 | 为什么数据飞轮有效 | 高优样本、低分指标、标准冲突样本优先回流 |
| 训练问题 | CoT 怎么用 | 先 Direct SFT，再少量结构化 CoT，最后 RL |
| 上线问题 | 线上瓶颈怎么排查 | 拆下载、预处理、推理、后处理、队列并发 |

### 易错点

- 把关键帧检测说成普通视频分类。
- 只报平均 ACC，不看业务线和高优指标。
- 默认人工 GT 全对，忽略标注噪声。
- 把 prompt 优化说成“调话术”，没有讲业务标准注入。
- 上线只讲模型推理，不拆图片下载、队列、并发和字段映射。

## 面试应对

### 关键帧检测项目你具体做了什么？

回答思路：按问题、方法、结果、上线闭环回答。

回答模板：

我做的是视频关键帧识别能力建设，目标是从移动端操作录屏中自动定位某个性能指标的结束帧，用于替代部分人工标注并支撑性能耗时计算。这个任务难点不是简单视频理解，而是不同 task_type 的完成态不同，人工标注也有噪声。我主要做了四件事：第一，人工分析 bad case，区分模型能力问题、GT 标注误差和标准冲突；第二，把完成态、排除条件、豁免条件和首选证据沉淀成 prompt 和训练规则；第三，围绕国际电商等高优业务线做三轮数据飞轮，返修 27000+ 高质量样本；第四，参与模型上线接入和压测，拆解下载、推理和并发瓶颈。最终平均 ACC 从 75.714 提升到 84.876，国际电商 ACC 从 84.093 提升到 95.933，线上 3 帧误差回测平均达到 90.05%。

### 为什么通用多模态模型不能直接解决这个任务？

回答思路：强调业务完成态和细粒度 UI 证据。

回答模板：

通用多模态模型有基础视频理解能力，但它不知道每个业务指标下什么叫完成态。例如“首帧出现”和“完全加载”要求不同，购物车加购要优先看角标数字变化，商详页加载要等头图、价格和营销 Banner 清晰完整。通用模型容易按页面大致出现来判断，而不是按业务准出标准判断。另外任务还涉及小元素、遮挡、局部异步、低 FPS 边界帧等问题，所以必须结合真实业务数据、标注标准沉淀、bad case 归因和垂类训练来提升。

### 数据飞轮为什么比继续平均补数据更有效？

回答思路：从业务价值、长尾分布和错误类型回答。

回答模板：

因为全量指标很多，数据分布长尾明显，平均补数据会把资源稀释到大量已经表现不错或业务优先级不高的指标上。数据飞轮的核心是用模型先筛 bad case，再人工复查和重标，把样本按业务线、task_type 和错误类型归因，然后优先回流高优业务线、低分高价值指标和标准冲突样本。这样训练信号更集中，能直接提升业务准出能力，而不是只提升平均指标。

### 上线前你怎么验证模型服务？

回答思路：从接口、效果、耗时、压测和联调回答。

回答模板：

上线前我会先对齐接口字段，确认用户输入、模型输入和业务消费字段一致，例如 task_type、起始帧、图片 URL 列表、预测结束帧和置信度。然后做线上服务效果测试，对比离线评测结果，并对 bad case 做人工二次校验。性能上会拆端到端耗时，定位瓶颈是在图片下载、预处理、模型推理还是后处理。实际测试中串行图片下载约 30s，模型推理约 3s，瓶颈主要在下载；压测后单卡并发控制在 20 左右较合适，平均处理约 45s，QPM 约 22。最后再做全链路联调，保证请求能正确进入模型服务并回传结果。
