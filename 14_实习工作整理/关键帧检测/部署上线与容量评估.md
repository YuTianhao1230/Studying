# 关键帧检测：部署上线与容量评估

## 知识点解析

### 概述

本文整理关键帧检测模型从离线训练到线上服务接入的工程链路，包括接口字段、服务联调、效果回测、耗时拆解、并发压测、能力支持统计和上线风险。

### 上线链路

关键帧模型上线不是把 checkpoint 部署起来就结束，而是要接入完整业务链路：

```text
业务请求
  -> task_type / keyframe_type 映射
  -> 拉取视频帧或图片 URL
  -> 模型服务推理
  -> 输出结束帧 / 时间戳 / 证据
  -> 业务侧换算耗时
  -> 回传 CQC / 预标平台
```

每一层都可能引入错误：

- keyframe_type 不在支持集合。
- 图片 URL 不可下载。
- 起始帧和候选帧范围错位。
- 模型输出字段不可解析。
- 业务侧消费字段不一致。

### 接口字段

模型服务建议至少包含：

| 字段 | 作用 |
| --- | --- |
| `task_type` / `keyframe_type` | 指定指标类型，绑定标注标准 |
| `start_frame` / `start_timestamp` | 耗时计算起点 |
| `frame_urls` | 候选帧图片 |
| `fps` | 帧号和时间换算 |
| `prediction_frame` | 预测结束帧 |
| `prediction_timestamp` | 预测结束时间 |
| `confidence` | 置信度或可选评分 |
| `evidence` | UI 证据，便于排查 |
| `error_code` | 下载失败、能力不支持、推理失败等错误 |

### 耗时拆解

线上服务需要把端到端耗时拆开：

```text
total_latency
  = image_download
  + preprocessing
  + model_inference
  + postprocessing
  + queue_waiting
```

实测中，串行图片下载约 30s，模型推理约 3s，瓶颈主要在图片下载而不是模型本身。这种结论很关键，因为优化方向应优先考虑并发下载、缓存、帧抽样和 URL 可用性，而不是盲目压模型推理。

### 压测结论

| 指标 | 结论 |
| --- | --- |
| 单卡并发 | 20 左右较合适 |
| 平均处理耗时 | 约 45s |
| QPM | 约 22 |
| 主要瓶颈 | 图片下载和链路 IO |
| 风险点 | 高峰期队列堆积、URL 失效、能力映射缺失 |

### 线上效果回测

上线效果不能只依赖离线验证。需要看：

- 国际电商等高优业务线 3 帧误差回测。
- 线上样本分布是否和离线测试集一致。
- 失败样本是否来自模型能力、数据问题还是服务链路。
- 人工二次校验是否确认模型错。

关键结果：

- 国际电商关键帧识别 3 帧误差线上回测平均 90.05%。
- 标注成本下降 19%。
- 提效贡献占比 9.5%。

### 能力支持统计

三条业务线支持情况：

| 业务线 | 覆盖能力数 | 支持能力数 | 支持且已跑通 | 支持但数据未跑通 | 不支持能力数 |
| --- | --- | --- | --- | --- | --- |
| 国际电商 | 34 | 30 | 30 | 0 | 4 |
| 番茄系 | 40 | 40 | 33 | 7 | 0 |
| 搜索系 | 38 | 12 | 11 | 1 | 26 |

解读：

- 国际电商是当前支持最完整的核心交付线。
- 番茄系能力支持广，但存在 URL 不可下载导致未跑通的问题。
- 搜索系不支持能力较多，后续重点是 keyframe_type 扩展和标准沉淀。

### 上线风险与治理

| 风险 | 表现 | 治理方式 |
| --- | --- | --- |
| 数据链路风险 | 图片 URL 不可下载 | 增加下载重试、预检查、错误码 |
| 能力映射风险 | keyframe_type 不支持 | 建立 mapping 表和能力注册流程 |
| 输出解析风险 | 模型输出格式不稳定 | 固定 JSON schema 和 fallback parser |
| 延迟风险 | 图片下载拖慢 | 并发下载、缓存、缩帧、粗筛精筛 |
| 效果漂移风险 | 线上业务改版 | 周期回测、分桶监控、bad case 回流 |

### 常见考法与解题方法

| 考法 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 上线题 | 模型怎么接线上 | 接口、字段、映射、输出解析、业务消费 |
| 性能题 | 端到端慢怎么排查 | 下载、预处理、推理、后处理、队列分解 |
| 容量题 | QPM 怎么估 | 单请求耗时、并发数、单卡吞吐 |
| 回测题 | 线上效果怎么验证 | 3 帧误差、分桶、人工复核、链路错误归因 |

### 易错点

- 只说“模型上线”，不说接口字段和业务消费。
- 看到端到端慢就直接优化模型推理。
- URL 不可下载也算模型失败。
- 不区分能力不支持和数据未跑通。
- 没有固定错误码，导致线上问题难归因。

## 面试应对

### 你怎么把关键帧模型接到线上？

回答思路：按接口、链路、压测和回测回答。

回答模板：

上线时我先对齐业务侧和模型侧接口，确保 task_type、起始帧、图片 URL 列表、预测结束帧、时间戳、置信度和错误码都能稳定传递。然后做服务联调，确认 keyframe_type 能正确映射到模型能力，模型输出能被业务侧解析。性能上我拆了端到端耗时，发现串行图片下载约 30s，模型推理约 3s，所以瓶颈主要在下载和链路 IO，而不是模型本身。压测后单卡并发 20 左右较合适，平均处理约 45s，QPM 约 22。最后用线上回测验证效果，国际电商 3 帧误差平均达到 90.05%。
