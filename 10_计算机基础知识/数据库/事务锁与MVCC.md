# 事务锁与MVCC

## 知识点解析

### 概述

本文整理事务 ACID、隔离级别、数据库锁、MVCC、快照读与当前读，以及 undo、redo、binlog 的作用。

### ACID

- Atomicity 原子性：事务要么全部成功，要么全部失败。
- Consistency 一致性：事务前后数据满足约束。
- Isolation 隔离性：并发事务互不产生不合理干扰。
- Durability 持久性：提交后的修改可靠保存。

ACID 由多种机制共同保证：undo log 和事务回滚支撑原子性；锁与 MVCC 支撑隔离性；redo log、WAL 和刷盘策略支撑持久性。一致性是最终目标，依赖前三项提供的底层保障，也依赖数据库约束和业务校验。例如数据库可保证转账的两条更新原子提交，但“余额不得为负”仍需由约束或业务逻辑表达。

### 隔离级别

| 隔离级别 | 可能问题 |
| --- | --- |
| Read Uncommitted | 脏读、不可重复读、幻读 |
| Read Committed | 不可重复读、幻读 |
| Repeatable Read | 理论上可能幻读 |
| Serializable | 基本避免并发异常 |

脏读是读到未提交数据；不可重复读是同一行两次读取结果不同；幻读是同一范围两次查询出现新增或删除记录。

### 锁

数据库锁可按粒度分为表锁、行锁；按模式分为共享锁和排他锁。InnoDB 还涉及记录锁、间隙锁、临键锁。查询没有命中索引时，可能导致锁范围扩大。

### MVCC

MVCC 是多版本并发控制，通过版本链和 ReadView 让读操作尽量不阻塞写操作。InnoDB 中 MVCC 依赖隐藏事务 ID、undo log 和可见性判断。普通快照读通常不加锁，当前读、更新和唯一性检查仍然需要锁。

ReadView 记录创建者事务 ID `creator_trx_id`、创建时仍活跃的事务集合 `m_ids`、其中最小事务 ID `min_trx_id`，以及创建时系统将分配的下一个事务 ID `max_trx_id`。判断版本的 `trx_id` 时：

1. 等于 `creator_trx_id`，说明是本事务自己的修改，可见。
2. 小于 `min_trx_id`，说明创建视图前已提交，可见。
3. 大于等于 `max_trx_id`，说明创建视图后才开始，不可见。
4. 处于两者之间时，若在 `m_ids` 中则当时尚未提交，不可见；否则已经提交，可见。
5. 当前版本不可见时，沿 undo 版本链继续判断更早版本，直到找到可见版本或链结束。

Read Committed（RC）通常在每条快照读语句开始时创建新的 ReadView，所以同一事务的两次查询可能看到期间已提交的数据。Repeatable Read（RR）通常在事务第一次一致性快照读时创建 ReadView，并在后续快照读中复用，因此能保持可重复读；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 可在事务开始时建立一致性快照。当前读不复用上述历史快照，而是读取当前最新可用版本并参与加锁：它能看到本事务尚未提交的修改；遇到其他事务尚未结束的冲突修改时可能等待，并在对方提交或回滚后重新判断版本和查询条件。

### 日志

- undo log：用于回滚和 MVCC 版本链。
- redo log：用于崩溃恢复，保证持久性。
- binlog：记录逻辑变更，用于复制和恢复。

### 快照读与当前读

- 快照读读取符合 ReadView 的历史版本，普通 `SELECT` 通常属于快照读。
- 当前读读取当前最新可用版本并加锁，例如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`。它可见本事务未提交修改；遇到并发事务持有冲突锁时可能先等待，再根据其提交或回滚后的状态重新判断。

MVCC 主要优化快照读；当前读仍需依赖锁保证并发正确性。

### InnoDB 常见锁

| 锁 | 锁定范围 | 典型用途 |
| --- | --- | --- |
| 记录锁 | 单条索引记录 | 锁定已存在的行 |
| 间隙锁 | 两条索引记录之间的间隙 | 防止范围内插入 |
| 临键锁 | 记录锁 + 前方间隙 | Repeatable Read 下防止幻读 |
| 意向锁 | 表级标记 | 表示事务准备持有行锁 |

InnoDB 行锁依赖索引。如果查询条件无法有效使用索引，扫描和锁定范围可能扩大。

讨论锁范围必须先明确隔离级别、快照读或当前读、使用的索引及索引是否唯一。以 RR 下的当前读为例：

- 唯一索引等值查询命中已有记录时，通常只对该索引记录加记录锁，不需要为防止同键插入再锁间隙。
- 唯一索引等值查询未命中时，为阻止该键被插入，会锁住目标值所在的索引间隙。
- 非唯一索引等值查询可能匹配多条记录，通常对等值记录及阻止同值插入所需的相邻区间加临键锁；二级索引记录对应的聚簇索引记录也可能被锁定。
- 范围当前读会沿所选索引扫描并锁住命中的记录及相关间隙，扫描边界、是否包含端点和实际执行计划都会影响最终区间。

例如索引已有键 `10, 20, 30`，对不存在的 `id = 25` 做 RR 当前读，重点锁定 `(20, 30)` 间隙；对唯一索引已有的 `id = 20` 做等值当前读，通常是记录锁。若条件走非唯一索引或全表扫描，不能照搬这个简化结论。RC 下通常不使用间隙锁来防幻读，但外键检查、重复键检查等场景仍可能使用间隙锁。

### 常见考法与分析步骤

| 题型 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 并发异常 | 给出两个事务执行顺序 | 按时间线标记每次读到的版本 |
| 隔离级别 | 判断会否脏读、不可重复读、幻读 | 先区分行值变化和结果集变化 |
| MVCC 可见性 | 给事务 ID、版本链和 ReadView | 按创建者与活跃事务判断 |
| 锁范围 | 等值、范围查询会锁哪里 | 看索引、隔离级别和查询类型 |
| 死锁 | 两事务按不同顺序更新 | 画等待关系，检查环 |
| 日志恢复 | 提交前后宕机如何恢复 | 区分 undo、redo、binlog 职责 |

分析事务题时：

1. 标出事务开始、读、写、提交时间。
2. 判断读取是快照读还是当前读。
3. 确定隔离级别和 ReadView 创建时机。
4. 判断需要读取哪个版本、是否加锁、是否等待。
5. 最后判断出现哪种并发异常。

标准等待图以事务为节点；若事务 `T1` 正在等待事务 `T2` 持有的锁，就画有向边 `T1 -> T2`，即“等待事务 -> 持锁事务”。图中存在有向环表示这些事务形成死锁，数据库通常选择其中一个事务作为牺牲者回滚以打破环。

### WAL 与两阶段提交

WAL 表示数据页落盘前先持久化 redo log。这样事务提交后即使脏页尚未写入磁盘，数据库也能通过 redo 恢复。

MySQL 为保持 InnoDB redo log 与 Server 层 binlog 一致，提交事务时可概括为：InnoDB 先写 redo 并标记 `prepare`，再写 binlog，最后把 redo 标记为 `commit`。其中 binlog 事件携带事务标识 XID，崩溃恢复时可用它判断处于 `prepare` 状态的事务是否已经完整写入 binlog。

关键故障点如下：

| 宕机时点 | 恢复处理 | 原因 |
| --- | --- | --- |
| redo `prepare` 前 | 回滚未提交事务 | 两份日志都没有形成可提交依据 |
| redo 已 `prepare`，binlog 未完整持久化 | 回滚 | binlog 中找不到对应完整 XID，不能让主库出现复制端没有的事务 |
| binlog 已完整持久化，redo 尚未写 `commit` | 提交 | 可由完整 binlog/XID 确认事务应提交，保证主库与复制日志一致 |
| redo 已 `commit` | 按已提交事务恢复 | 两阶段均已完成 |

两阶段提交解决的是两个日志系统的原子一致性，不等同于跨业务库的分布式两阶段提交。实际“持久化到哪里”还受 `innodb_flush_log_at_trx_commit`、`sync_binlog` 等刷盘配置影响。

## 笔试常考

- 按事务调度时间线判断脏读、不可重复读、幻读和丢失更新，不能只看隔离级别名称。
- 给定版本 `trx_id`、`min_trx_id`、`max_trx_id` 和 `m_ids`，按 ReadView 规则逐个判断可见性；当前版本不可见时继续沿 undo 链查找。
- 区分 RC 每条快照读创建 ReadView 与 RR 首次一致性快照读后复用 ReadView；当前读读取当前最新可用版本并加锁，可见本事务未提交修改，遇到并发冲突还可能等待后重新判断。
- 判断锁区间时先看隔离级别、读类型、实际索引、唯一性、等值是否命中以及范围边界，再画记录锁、间隙锁或临键锁。
- 死锁题以事务为节点，按“等待事务 -> 持锁事务”画边；存在有向环表示死锁，数据库通常选择一个事务回滚。
- 区分 undo 的回滚与版本链、redo 的崩溃恢复、binlog 的复制与时间点恢复，并判断它们能否互相替代。
- 根据宕机发生在 redo `prepare`、binlog 持久化、redo `commit` 的哪个阶段，利用完整 binlog/XID 判断事务应回滚还是提交。

### 易错点

- MVCC 不等于完全无锁，它主要服务快照读。
- 幻读关注范围结果集变化，不只是同一行值变化。
- Repeatable Read 下 InnoDB 会结合 MVCC 和临键锁处理幻读，但具体行为取决于快照读或当前读。
- 当前读面向当前最新可用版本：它能看到本事务未提交修改，并可能等待并发事务结束后重新判断。
- 等待图的节点是事务、边是“等待事务 -> 持锁事务”，不要把锁本身画成标准节点。
- undo 用于回滚和历史版本，redo 用于崩溃恢复，binlog 用于复制和时间点恢复。
- 行锁锁的是索引记录，不命中索引可能扩大扫描与锁范围。

## 面试应对

### InnoDB 主要通过什么机制保证 ACID？

回答思路：分别映射四个特性，并强调一致性还依赖约束和业务规则。

回答模板：

InnoDB 用 undo log 和回滚机制保证事务失败时能够撤销，支撑原子性；用锁处理写冲突、用 MVCC 处理快照读，支撑隔离性；用 redo log、WAL 和刷盘保证已提交修改可恢复，支撑持久性。一致性是最终目标，除了依赖原子性、隔离性和持久性，还需要主外键、唯一约束等数据库约束以及正确的业务逻辑共同保证。

### RC 和 RR 的 ReadView 有什么区别？

回答思路：先说版本可见性的共同规则，再比较视图创建与复用时机。

回答模板：

两者都根据版本事务 ID、活跃事务集合和 ReadView 边界判断可见性，不可见时沿 undo 链找更早版本。RC 通常为每条快照读语句新建 ReadView，因此第二次查询可以看到期间已经提交的事务。RR 通常在事务第一次一致性快照读时建立 ReadView，后续快照读复用它，所以能保持可重复读。这个区别针对快照读；当前读读取当前最新可用版本并加锁，能看到本事务未提交修改，遇到并发冲突时还可能等待后重新判断。

### InnoDB 的 RR 如何处理幻读？

回答思路：分开说明快照读和当前读，避免笼统说“RR 完全没有幻读”。

回答模板：

幻读是同一事务按相同范围条件再次查询时，结果集中出现或消失了记录。在 InnoDB 的 RR 下，普通快照读复用 ReadView，通常不会看到其他事务后来提交的新行；范围当前读则通过记录锁、间隙锁或临键锁阻止相关区间插入。两条路径共同处理常见幻读，但快照读和当前读的可见性语义不同，混用时仍要按具体执行顺序分析。

### 如何判断等值查询和范围查询的锁范围？

回答思路：按隔离级别、读类型、实际索引、唯一性和命中情况逐层判断。

回答模板：

我会先确认这是快照读还是当前读，再看隔离级别和执行计划实际使用的索引。在 RR 当前读中，唯一索引等值命中通常只加记录锁；唯一等值未命中会锁住插入位置的间隙；非唯一等值可能锁住所有同值记录及防止同值插入的相邻区间；范围查询会沿索引扫描并锁定命中记录和相关间隙。最终边界还取决于端点、已有键值和扫描范围，不能只根据 WHERE 文本判断。

### 如何用等待图判断死锁？

回答思路：明确节点、边方向和成环条件。

回答模板：

标准等待图以事务为节点。如果事务 `T1` 等待事务 `T2` 持有的锁，就画边 `T1 -> T2`，也就是从等待事务指向持锁事务。图中出现有向环，说明环上的事务互相等待并形成死锁；数据库通常回滚其中一个事务来解除死锁，应用还应对死锁错误做有限重试。

### redo log 和 binlog 的两阶段提交如何处理宕机？

回答思路：说明 prepare、写 binlog、commit 三步，再按 binlog/XID 是否完整判断恢复结果。

回答模板：

MySQL 提交时先把 InnoDB redo 写到 `prepare`，再持久化 Server 层 binlog，最后把 redo 标记为 `commit`。若在 binlog 完整写入前宕机，恢复时找不到对应的完整 XID，预提交事务回滚；若 binlog 已完整写入、但 redo 还没标记 `commit`，恢复时根据 XID 提交该事务；redo 已 `commit` 则正常按已提交恢复。这样避免主库数据与用于复制、恢复的 binlog 出现一边有、一边没有。
