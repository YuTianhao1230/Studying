# SQL与关系模型

## 知识点解析

### 概述

本文整理 SQL 执行顺序、连接、聚合、窗口函数、关系模型、数据库范式和 ER 模型。

### SQL 执行顺序

SQL 逻辑执行顺序通常是：

```text
FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT
```

`WHERE` 用于分组前过滤行，`HAVING` 用于分组后过滤聚合结果。

逻辑执行顺序还解释了别名可见性：`SELECT` 中刚定义的别名通常不能在同层 `WHERE` 中使用，因为 `WHERE` 逻辑上先执行；`ORDER BY` 逻辑上晚于 `SELECT`，通常可以引用该别名。具体物理执行方式由优化器决定，不必严格按逻辑顺序逐步物化中间结果。

### 连接

| 连接 | 含义 |
| --- | --- |
| INNER JOIN | 只保留两表匹配记录 |
| LEFT JOIN | 保留左表全部记录，右表无匹配补 NULL |
| RIGHT JOIN | 保留右表全部记录 |
| FULL JOIN | 保留两边所有记录 |
| SELF JOIN | 表自己和自己连接 |

JOIN 的结果行数由连接键在两侧的重复次数决定，而不只由连接类型决定。对某个连接键值，左表有 $m$ 行、右表有 $n$ 行时，内连接会产生 $m \times n$ 行。例如左表键值 10 出现 2 次、右表出现 3 次，则该键产生 6 行。一对一连接最多匹配一行，一对多会展开左侧行，多对多会同时放大两侧重复。

`LEFT JOIN` 还会为左表完全未匹配的每一行保留一条右侧补 `NULL` 的结果。在 `WHERE` 中再写 `right_table.status = 'ok'` 会过滤这些补空行；若条件只是限制右表参与匹配的记录，应把它放入 `ON`。

### 聚合和窗口函数

聚合函数包括 `COUNT`、`SUM`、`AVG`、`MAX`、`MIN`。窗口函数在不折叠行的情况下计算分组内排名或统计，常见有 `row_number`、`rank`、`dense_rank`。

聚合会把多行折叠为分组结果，窗口函数保留原始行。需要“每个部门一行统计”时用聚合，需要“保留员工明细并附加部门排名”时用窗口函数。

`NULL` 参与比较时通常得到 `UNKNOWN`，SQL 因此具有 `TRUE`、`FALSE`、`UNKNOWN` 三值逻辑。`WHERE` 和 `HAVING` 只保留结果为 `TRUE` 的行；`NOT UNKNOWN` 仍是 `UNKNOWN`，所以 `col = NULL`、`col <> NULL` 都不能筛选空值，应使用 `IS NULL` 或 `IS NOT NULL`。聚合中 `COUNT(*)` 统计行数，`COUNT(col)`、`SUM(col)`、`AVG(col)` 等忽略 `col` 为 `NULL` 的行；若整组没有非空输入，`SUM`、`AVG` 通常返回 `NULL`。

### 集合运算

`UNION` 合并两个兼容结果集后去重，`UNION ALL` 保留全部行和重复项。两者要求列数一致，对应列的数据类型能够兼容。去重通常需要排序或哈希，因而在业务允许重复或已知分支互斥时，`UNION ALL` 往往成本更低。集合运算后的 `ORDER BY` 应放在整个语句末尾；分支内排序只有与 Top N 等语义组合时才有意义，并受具体数据库语法约束。

### 范式

1NF 要求字段原子；2NF 要求非主属性完全依赖候选键；3NF 要求非主属性不传递依赖候选键。BCNF（Boyce-Codd Normal Form，巴斯-科德范式）进一步要求每个非平凡函数依赖 $X \to Y$ 的决定因素 $X$ 都是超键，因此能处理某些已满足 3NF、但仍由非候选键属性决定其他属性而产生的冗余。

范式能减少冗余和插入、删除、更新异常，但并非级别越高越好。提高范式可能增加连接数量和查询成本；高并发读场景可在明确一致性维护方式后适当反范式，用受控冗余换取查询性能。

### 关系模型基础

- 候选键：能够唯一标识元组的最小属性集合。
- 主键：从候选键中选定的一个标识。
- 外键：引用另一关系的候选键，用于维护参照完整性。
- 实体完整性：主键不能为 NULL。
- 参照完整性：外键要么为空，要么引用已存在的记录。

关系代数常见运算：

| 运算 | 含义 | SQL 对应 |
| --- | --- | --- |
| 选择 | 按条件筛选行 | `WHERE` |
| 投影 | 选择部分列 | `SELECT column` |
| 并、交、差 | 集合运算 | `UNION`、`INTERSECT`、`EXCEPT` |
| 笛卡尔积 | 两关系任意组合 | `CROSS JOIN` |
| 连接 | 按条件组合关系 | `JOIN ... ON` |

### 范式题怎么解

1. 写出候选键和函数依赖。
2. 检查字段是否满足原子性。
3. 判断非主属性是否只依赖复合键的一部分，存在则违反 2NF。
4. 判断非主属性是否通过另一个非主属性间接依赖候选键，存在则违反 3NF。
5. 根据依赖关系分解表，并检查是否无损连接、是否保持函数依赖。

范式解决的典型问题包括数据冗余、插入异常、删除异常和更新异常。

候选键必须同时满足“能唯一确定全部属性”和“属性集合最小”。超键能够唯一标识元组，但可能含有多余属性；主键只是人为从候选键中选定的一个。

无损分解要求把分解后的关系做自然连接时，能精确还原原关系，不会丢行或产生伪元组。对二元分解 $R \to R_1, R_2$，若公共属性能函数决定 $R_1$ 或 $R_2$ 的全部属性，则该分解无损。依赖保持则要求原有函数依赖可以在各子关系内检查，不必连接子表。

例如 $R(A, B, C)$ 有 $A \to B$、$B \to C$，分解为 $R_1(A, B)$ 与 $R_2(B, C)$：公共属性 $B$ 能决定 $R_2$，所以分解无损；两条依赖也分别能在子关系内检查，所以依赖保持。无损和依赖保持是两个独立目标，不能只验证连接能还原就结束。

### ER 模型映射到关系模型

- 实体通常映射为表，实体标识符映射为主键，简单属性映射为列。
- 一对多联系把“一”方主键作为外键放在“多”方；联系自身的属性也放在多方表中。
- 一对一联系可把外键放在任一方，通常放在全参与或依赖更强的一方，并用 `UNIQUE` 保证一对一；也可在生命周期完全一致时合并实体。
- 多对多联系必须建立中间表，两侧主键作为外键，常组成联合主键，并在中间表保存联系属性。
- 多值属性通常拆成独立表，以所属实体主键和属性值标识记录；弱实体表包含所属强实体的主键，并与自身部分键组成主键。

### 常见考法与解题策略

| 题型 | 解题策略 |
| --- | --- |
| SQL 执行顺序 | 按 FROM、WHERE、GROUP BY、HAVING、SELECT、ORDER BY 推导 |
| JOIN 结果行数 | 先判断连接键是否唯一，再分析一对一或一对多 |
| NULL 判断 | 使用 `IS NULL`，注意三值逻辑 |
| 聚合题 | 先确定一行输出代表什么粒度 |
| 窗口函数 | 先确定分区字段，再确定排序和窗口范围 |
| 范式判断 | 列候选键、主属性和函数依赖 |
| ER 图转关系 | 实体建表，一对多在多方放外键，多对多建中间表 |

### 易错点

- SQL 书写顺序不等于逻辑执行顺序。
- `LEFT JOIN` 后在 `WHERE` 中过滤右表字段，可能退化成 `INNER JOIN`。
- `COUNT(*)` 与 `COUNT(column)` 对 NULL 的处理不同。
- 主键一定唯一且非空，唯一约束是否允许 NULL 取决于数据库实现。
- 反范式是有意识的工程取舍，不等于随意重复数据。

## 笔试常考

- 按 `FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT` 推导逻辑结果，并判断同层别名何时可见。
- 根据连接键重复次数计算 JOIN 行数：某键两侧分别有 $m$、$n$ 行时，内连接产生 $m \times n$ 行；外连接还保留未匹配侧。
- 判断 NULL 三值逻辑与聚合结果：`WHERE` 只保留 `TRUE`，`COUNT(*)` 计行，`COUNT(col)` 忽略空值。
- 求候选键时先验证能推出所有属性，再逐个去掉属性验证最小性；区分候选键、超键和主键。
- 判断 1NF、2NF、3NF、BCNF 时先列候选键、主属性和函数依赖，再依次检查原子性、部分依赖、传递依赖，以及每个决定因素是否为超键。
- 判断分解质量时分别验证无损连接和依赖保持，二者不能互相替代。
- ER 映射中，一对多把外键放在多方，多对多建中间表，一对一需配合唯一约束，多值属性拆表。
- `UNION` 会去重，`UNION ALL` 保留重复；结果无需去重时优先考虑后者以避免额外工作。

## 面试应对

### WHERE 和 HAVING 有什么区别？

回答思路：从过滤时机和是否能使用聚合函数回答。

回答模板：

WHERE 是分组前过滤行，作用在原始记录上，一般不能直接使用聚合函数；HAVING 是 GROUP BY 分组之后过滤聚合结果，可以使用 COUNT、SUM 这类聚合函数。简单说，过滤明细行用 WHERE，过滤分组统计结果用 HAVING。实际优化时，应尽量把能提前过滤的条件放到 WHERE，减少后续分组和聚合的数据量。

### 数据库范式有什么用？

回答思路：说明减少冗余和异常，再补工程取舍。

回答模板：

数据库范式用于规范表结构，减少数据冗余和插入、删除、更新异常。判断时我会先求候选键并列出函数依赖：1NF 要求字段不可再分，2NF 排除非主属性对候选键的部分依赖，3NF 排除非主属性的传递依赖，BCNF 进一步要求每个非平凡函数依赖的决定因素都是超键。分解后还要分别验证能否无损连接、是否保持依赖。工程上也不是范式越高越好，高并发读场景可能在可控一致性成本下适当反范式。

### 聚合函数和窗口函数有什么区别？

回答思路：说明是否折叠原始行。

回答模板：

聚合函数配合 GROUP BY 会把多行折叠成每组一行，例如统计每个部门的平均工资；窗口函数在分组范围内计算排名、累计值或聚合结果，但保留每条原始记录，例如给每个员工附加部门内排名。需要输出明细行时通常考虑窗口函数，只需要分组统计结果时使用聚合。

### LEFT JOIN 后在 WHERE 中过滤右表字段有什么风险？

回答思路：说明 NULL 行会被过滤。

回答模板：

LEFT JOIN 原本会保留左表未匹配的记录，并把右表字段补成 NULL。如果之后在 WHERE 中要求右表字段满足普通条件，这些 NULL 行会被过滤掉，效果可能变成 INNER JOIN。若条件用于限制右表参与连接的数据，通常应写在 ON 中；如果就是要过滤匹配结果，则可以保留在 WHERE 中。

### ER 图如何转换为关系表？

回答思路：按实体、不同联系基数、多值属性和约束逐类说明。

回答模板：

实体通常各建一张表，实体标识符作为主键。对一对多联系，把一方主键作为外键放到多方；对多对多联系，建立包含两侧外键和联系属性的中间表；对一对一联系，通常把外键放在全参与或依赖更强的一方，并加唯一约束。多值属性需要拆成子表，弱实体则把所属强实体主键纳入自己的主键。最后还要用非空、唯一和外键约束表达参与度与基数。
