# 同步互斥与死锁

## 知识点解析

### 概述

本文整理并发程序中的同步、互斥、锁、信号量、PV 操作、死锁条件、银行家算法和死锁处理方法。

### 同步和互斥

互斥解决“同一时刻只能有一个线程访问临界区”的问题；同步解决“多个线程之间执行顺序”的问题。互斥关注资源独占，同步关注先后依赖。

### 常见机制

| 机制 | 作用 |
| --- | --- |
| 互斥锁 | 保护临界区 |
| 读写锁 | 读多写少场景，提高并发读 |
| 自旋锁 | 忙等，不睡眠，适合极短临界区 |
| 条件变量 | 等待某个条件成立 |
| 信号量 | 控制资源数量，支持 PV 操作 |
| 原子操作 | 硬件级不可分割操作 |

条件变量必须与互斥锁配合。`wait` 会原子地释放互斥锁并阻塞当前线程，被唤醒后还要重新竞争该锁；`signal` 通常唤醒一个等待者，`broadcast` 唤醒全部等待者。等待条件必须写成 `while (!条件) wait()`，因为线程可能被伪唤醒，或者条件在它重新获得锁前已被其他线程改变。

### 死锁四条件

- 互斥：资源一次只能被一个线程占用。
- 请求并保持：持有资源时继续请求新资源。
- 不可剥夺：资源不能被强制抢走。
- 循环等待：多个线程形成等待环。

### 死锁处理

死锁处理包括预防、避免、检测和恢复。工程中常见做法是统一加锁顺序、缩小锁粒度、设置锁超时、减少嵌套锁和用工具检测等待关系。

资源分配图中，`进程 -> 资源` 表示请求边，`资源实例 -> 进程` 表示分配边。每类资源只有一个实例时，图中出现环是死锁的充分必要条件；存在多个实例时，有环只是可能死锁，必须使用多实例死锁检测算法。

检测时令 `Work = Available`；对 `Allocation[i] = 0` 的进程初始化 `Finish[i] = true`，其余进程初始化为 `false`。反复寻找满足 `Finish[i] = false` 且当前未满足请求 `Request[i] <= Work` 的进程，假设它完成并执行 `Work += Allocation[i]、Finish[i] = true`。算法结束后，只有 `Finish[i] = false` 的进程才是检测出的死锁进程。不能把所有仍在等待的进程都笼统算入死锁集合：若某进程未占有资源，只是等待被死锁进程占有的资源，它虽然会被阻塞，却不参与循环占有与等待；其 `Allocation = 0`，初始化时已被标记为可完成，不属于死锁成员。

### 常见考法与解法

| 题型 | 怎么考 | 怎么解 |
| --- | --- | --- |
| PV 操作 | 补全生产者消费者、读者写者伪代码 | 先找资源数量，再找先后关系 |
| 信号量初值 | 判断互斥量和资源量初值 | 互斥通常为 1，资源量等于可用数量 |
| 死锁判断 | 给出资源分配和等待关系 | 画资源分配图或等待图找环 |
| 银行家算法 | 判断是否安全、求安全序列 | 反复找需求不超过可用资源的进程 |
| 锁选型 | 自旋锁、互斥锁、读写锁怎么选 | 根据等待时间和读写比例判断 |
| 并发 Bug | 丢失更新、竞态、可见性问题 | 找共享状态和非原子操作 |

### PV 题解题框架

P 操作用于申请资源或等待条件，V 操作用于释放资源或通知其他执行单元。

做题时先区分：

- 互斥信号量：保护临界区，初值通常为 1。
- 资源信号量：表示可用资源数量，初值等于资源数。
- 同步信号量：表示某个前置条件是否完成，初值通常为 0。

生产者消费者模型中，若缓冲区容量为 `n`：

```text
empty = n
full = 0
mutex = 1

生产者：P(empty) -> P(mutex) -> 放入数据 -> V(mutex) -> V(full)
消费者：P(full)  -> P(mutex) -> 取出数据 -> V(mutex) -> V(empty)
```

资源信号量必须先于互斥锁申请，否则线程可能持有锁并等待资源，导致其他线程无法进入临界区释放资源。

### 读者写者方案

一种读者优先方案用 `rw_mutex = 1` 保护读者计数 `read_count`，用 `resource = 1` 控制对共享数据的访问：

```text
读者进入：P(rw_mutex) -> read_count++
          -> 若 read_count == 1，则 P(resource)
          -> V(rw_mutex)
读数据
读者退出：P(rw_mutex) -> read_count--
          -> 若 read_count == 0，则 V(resource)
          -> V(rw_mutex)

写者：P(resource) -> 写数据 -> V(resource)
```

第一个读者锁住共享资源，最后一个读者释放它，因此多个读者可并发、写者与任何读写操作互斥。该方案可能让写者饥饿；写优先方案会阻止新读者插队，公平读写锁则按队列控制进入顺序。

### 银行家算法

判断安全状态：

1. 计算每个进程的剩余需求 `Need = Max - Allocation`。
2. 令 `Work = Available`。
3. 查找满足 `Need <= Work` 的未完成进程。
4. 假设该进程完成，执行 `Work += Allocation`。
5. 重复直到所有进程完成，或再也找不到可完成进程。

能找到覆盖所有进程的顺序，说明系统处于安全状态；安全状态一定不会立即死锁，不安全状态表示未来可能死锁，但不等于当前已经死锁。

紧凑示例：两类资源下，`Available = (1, 1)`，`P0` 的 `Allocation = (1, 0)`、`Need = (0, 1)`，`P1` 的 `Allocation = (0, 1)`、`Need = (1, 0)`。先让 `P0` 完成，`Work` 从 `(1, 1)` 变为 `(2, 1)`，再让 `P1` 完成，因此 `<P0, P1>` 是安全序列。若 `P1` 请求 `(1, 0)`，先检查请求不超过 `Need` 和 `Available`；试分配后 `Available = (0, 1)`、`P1.Need = (0, 0)`，此时 `<P1, P0>` 仍安全，所以可批准。若试分配后找不到覆盖所有进程的安全序列，即使当前资源足够，也必须让请求等待。

## 笔试常考

- 补全 PV 操作，特别是生产者消费者和读者写者的 P/V 顺序。
- 根据信号量语义确定初值：互斥量为 1、资源量为资源数、前置同步量为 0。
- 用资源分配图或等待图判断死锁，并区分单实例与多实例资源。
- 用 `Need = Max - Allocation` 求银行家算法安全序列，按“检查、试分配、安全性检查”处理资源请求。
- 根据临界区长度和读写比例选择自旋锁、互斥锁或读写锁。

### 易错点

- 同步和互斥不是同义词：互斥限制同时访问，同步约束执行顺序。
- 信号量可以表示多个资源，互斥锁通常只有持有者才能解锁。
- 等待图有环在单实例资源中表示死锁，多实例资源还需进一步判断。
- 多实例检测先把 `Allocation = 0` 的进程标记为可完成；被死锁资源阻塞不等于该进程本身属于死锁集合。
- 死锁、饥饿和活锁不同：死锁互相等待，饥饿长期得不到资源，活锁持续动作却无法推进。

## 面试应对

### 如何避免锁顺序导致的死锁，并在线上诊断死锁？

回答思路：四条件、统一锁顺序、等待关系和线程栈。

回答模板：

死锁需要互斥、请求并保持、不可剥夺和循环等待同时成立。多把锁最常见的问题是不同线程按相反顺序获取锁，因此我会给锁定义全局顺序，并缩短临界区、减少嵌套，必要时使用超时和回滚。线上诊断时先抓线程栈或转储，查看每个线程持有什么锁、等待什么锁，再构造等待图找环，并结合锁等待时长和日志定位违反顺序的路径。

### 同步原语应该怎样选择？

回答思路：按临界区时长、资源数量、等待条件和读写比例选择。

回答模板：

只保护一个临界区通常用互斥锁；临界区极短且不能睡眠时才考虑自旋锁，因为忙等会消耗 CPU；读多写少可以用读写锁；表示多个同类资源用计数信号量；等待某个状态成立用“互斥锁加条件变量”；简单计数或状态更新可用原子操作。最终还要根据竞争强度、临界区耗时和公平性要求验证选择。

### 读写锁有什么收益和代价？

回答思路：并发读、写互斥、额外开销和饥饿策略。

回答模板：

读写锁允许多个读者并发，但写者必须独占，因此适合读操作明显多于写操作且临界区不太短的场景。它的状态维护和加解锁成本通常高于普通互斥锁，写频繁时未必更快。读者优先可能让写者饥饿，写者优先可能增加读延迟，工程上要根据延迟目标选择公平策略并用实际负载测试。

### 死锁、活锁和饥饿有什么区别？

回答思路：从是否阻塞、是否持续执行和能否获得资源区分。

回答模板：

死锁是多个执行单元互相等待对方持有的资源，大家都无法继续；活锁是线程没有阻塞，也在不断改变状态，但彼此反复避让，系统没有实质进展；饥饿是某个线程因为调度或资源竞争长期得不到执行机会。固定加锁顺序可以预防死锁，随机退避可以缓解活锁，公平锁和合理调度可以减少饥饿。

### PV 操作题怎么分析？

回答思路：先资源、再互斥、最后同步顺序。

回答模板：

我会先列出有限资源及其数量，确定资源信号量初值；再找临界区，设置初值为 1 的互斥信号量；最后分析线程之间的先后依赖，用初值为 0 的同步信号量连接。写伪代码时通常先申请资源、再进入互斥区，退出互斥区后再通知其他线程，并检查每个 P 是否都有对应的 V。
