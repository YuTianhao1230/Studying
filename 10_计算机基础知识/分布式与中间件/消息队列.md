# 消息队列

## 知识点解析

### 概述

消息队列用于在系统之间传递消息，核心价值是异步、解耦和削峰。它能提升系统吞吐和稳定性，但也会引入消息丢失、重复消费、顺序性、积压和一致性问题。

### 为什么使用消息队列

- 异步：非核心流程放到后台处理，降低主链路延迟。
- 解耦：生产者不直接依赖消费者。
- 削峰：把瞬时流量写入队列，消费者按能力处理。

例如下单后发送短信、更新积分、同步风控数据，都可以通过消息队列异步处理。

### 投递语义

投递语义描述消息从生产到消费的端到端效果：

| 语义 | 行为 | 代价与适用 |
| --- | --- | --- |
| 至多一次（at-most-once） | 生产端禁用发送重试，且消费端在业务处理前提交位点 | 以允许消息丢失换取失败时不重投，适合允许漏报的非关键数据 |
| 至少一次（at-least-once） | 未收到 ACK 就重试，消费者处理成功后才提交位点 | 尽量不丢但可能重复，是最常见选择，消费者必须幂等 |
| 恰好一次（exactly-once） | 在明确边界内让一条消息的可见结果只生效一次 | 需要幂等生产者、事务性消费或业务去重，成本较高 |

至多一次需要同时约束两端：生产者发送失败或确认不明时不重试，消费者先提交 offset 或 ACK 再处理。这样生产失败或消费确认后宕机都会丢消息，但不会因这些失败触发再次投递，本质是用允许丢失换取不重投。

“恰好一次”必须说明范围。例如 Broker 的事务可以原子提交“消费位点和发往另一个 Topic 的结果”，但若结果写入外部数据库，仍需数据库事务、唯一约束、幂等状态机或 Outbox 等机制配合，不能只靠消息队列配置保证全链路恰好一次。

### 消息丢失

消息丢失可能发生在生产者、Broker 或消费者：

- 生产者：必须等待 Broker 的发送确认；超时或失败时按策略重试，并记录最终失败的消息用于补偿。仅调用发送接口但不检查结果，进程退出后消息可能从未到达 Broker。
- Broker：消息应写入持久化日志并复制到足够副本后再返回成功。若只写内存、异步刷盘前就确认，或副本数不足，主节点宕机可能丢失已确认消息。持久化、副本和确认级别要一起配置。
- 消费者：业务处理和本地事务成功后再 ACK 或提交 offset。若先确认再处理，随后进程崩溃，Broker 会认为消息已完成而不再投递；若处理成功后、确认前崩溃，消息会被重投，但这是重复而不是丢失。

因此“消息不丢”不是一个开关，而是生产确认、Broker 持久化与副本、消费后确认、失败重试和补偿共同组成的链路保证。

### 重复消费

消息队列通常更容易做到至少一次投递，而不是严格只投递一次。重复既可能来自生产端，也可能来自消费端：

- 生产重试：Broker 已写入消息但确认响应丢失时，生产者看到超时会重试，同一业务消息可能被写入多次。应为消息设置稳定的业务 ID，并使用支持幂等生产的客户端；重试采用有限次数和指数退避，最终失败要记录并告警。
- 消费重投：消费者处理成功后、提交 offset 或 ACK 前宕机，Broker 会再次投递；消费超时、网络抖动和消费者重平衡也可能触发重投。

要求可靠投递时，不能通过关闭重试消除重复，否则会把重复问题变成丢失问题。消费者应按业务 ID 做幂等，常见方案包括数据库唯一索引、去重表、状态机条件更新和 Redis `SET NX`。其中 Redis 去重还要考虑 key 过期、缓存丢失以及业务操作未成功但 key 已写入的问题；对资金、订单等关键数据，优先使用数据库事务内的唯一约束或状态机。

### 事务消息与 Outbox

业务写数据库和发消息属于两个独立系统，直接依次执行会产生双写不一致：数据库提交后消息发送失败，会漏通知；消息先发送成功而数据库回滚，消费者会读到无效事件。

- 事务消息：生产者先发送对消费者不可见的半消息，再执行本地事务，最后根据事务结果提交或回滚消息。若二次确认丢失，Broker 通过事务回查确认本地事务状态。回查接口必须能根据事务 ID 幂等地判断明确结果。
- Transactional Outbox：在同一个本地数据库事务中写业务数据和 Outbox 事件表，由独立发布器扫描事件表并发送消息，发送成功后标记完成。它用本地事务避免业务数据与事件记录不一致，适用于 Broker 不支持事务消息或希望降低中间件耦合的场景。

两种方案都可能因发送确认丢失或发布器重试而产生重复消息，所以仍需稳定的事件 ID、消费者幂等、失败告警和补偿。事务消息解决的是“本地事务与消息是否一致”，并不自动保证消费者数据库也与生产者全局原子提交。

### 顺序消息

消息队列通常只保证分区内有序，不保证跨分区的全局顺序。保证同一订单、账户等业务 key 的顺序，需要同时约束生产和消费：

- 生产端：使用稳定的业务 key 路由到同一分区，避免并发发送和不受控重试导致后发消息先写入。
- Broker：只依赖同一分区日志的追加顺序；若要求全局有序，只能压到单分区或单队列，吞吐和可用性都会受限。
- 消费端：同一分区或同一 key 串行处理。前一条失败时应暂停该分区继续消费，或让重试队列保持相同 key 的顺序，否则后一条可能越过失败消息先完成。

业务状态还可携带递增版本号或序列号，消费者只接受期望版本，用于发现重复、过期和乱序消息。工程上通常选择“同一业务 key 局部有序”，而不是追求昂贵的全局顺序。

### 死信队列

消息因格式错误、业务校验失败或下游持续异常而多次消费失败时，应采用有限次数和退避策略重试；超过阈值后转入死信队列（Dead Letter Queue，DLQ），避免“毒消息”无限重试并阻塞正常消费。

死信记录应保留原消息、业务 ID、失败原因、重试次数和时间等信息，并配置监控告警。处理流程通常是定位原因、修复代码或数据，再将消息幂等地重新投递到原队列或执行人工补偿。死信队列只是隔离失败消息的兜底区，不等于问题已经解决，也不能长期无人处理。

### 消费 offset 与 lag

在日志型消息队列中，每个分区的 offset 表示消息位置，消费组提交的 offset 表示已确认的消费进度。提交时机决定丢失与重复的窗口：

- 处理前或自动提交过早：offset 已前移但业务尚未完成，消费者宕机后可能跳过消息，造成业务丢失。
- 业务处理成功后手动提交：可以避免上述丢失，但若处理成功后、提交前宕机，会产生重复，必须依赖幂等。
- 批量或并行消费：不能仅因较大 offset 已完成就跨过前面尚未完成的消息提交，否则失败消息可能被永久跳过。

消费 lag 通常等于分区最新 offset 与消费组已提交 offset 的差值，表示还有多少消息未确认。监控时应同时看各分区 lag、最大 lag、增长速度和最老消息等待时间；只看总量可能掩盖热点分区。

### 消息积压

消息积压表现为 lag 持续增长，本质是生产速率长期大于有效消费速率。排查时先区分生产流量突增还是消费能力下降，再看热点分区、消费者存活与重平衡、单条消息耗时、下游依赖、失败重试和死信数量。处理方法包括修复故障、优化或批量化消费、在分区数允许范围内扩容消费者、临时降级非核心任务；恢复后还要估算清空积压所需时间，防止直接放大流量压垮下游。

- 消息队列的作用。
- 异步、解耦、削峰分别是什么意思。
- 至多一次、至少一次和恰好一次的区别及代价。
- 如何从生产者、Broker、消费者三段排查消息丢失。
- 生产重试为什么会产生重复，消费者如何实现幂等。
- 数据库与消息队列双写为什么不一致，事务消息与 Outbox 如何解决。
- 死信队列的触发条件和处理流程。
- 如何通过业务 key 和分区保证局部顺序，全局顺序有什么代价。

- lag 的计算含义，以及消息积压如何排查和处理。

## 面试应对

### 如何保证同一业务 key 的消息局部有序？

回答思路：按生产路由、分区内消费、失败处理和业务版本兜底回答。

回答模板：

我会把同一订单或账户等业务 key 稳定路由到同一分区，利用分区日志的追加顺序；消费端对同一分区或同一 key 串行处理，避免并发执行打乱结果。前一条消息失败时，要阻塞该 key 或分区并按顺序重试，重试队列也必须保持相同路由，不能让后一条消息越过。业务数据再携带递增版本号或序列号，消费者拒绝过期版本，并对版本跳跃告警或补偿，作为重复和乱序的兜底。

### 如何保证消息不丢？

回答思路：按生产者、Broker、消费者三段回答。

回答模板：

我会分三段看。生产者侧要开启发送确认，失败要重试；Broker 侧要开启消息持久化和副本机制，避免节点故障导致消息丢失；消费者侧不能业务没处理完就 ACK，应该处理成功后再确认。如果消费失败，要允许重试或进入死信队列。严格来说，系统通常保证至少一次投递，所以消费者还必须做幂等。

### 如何处理消息重复？

回答思路：先说明生产重试和消费重投的原因，再说明业务幂等方案。

回答模板：

消息重复通常来自两处：生产者发送成功但确认丢失后重试，以及消费者处理成功但提交 offset 或 ACK 前宕机后被重新投递。不能简单关闭重试，因为那会增加消息丢失。我的做法是给每个业务事件设置稳定的唯一 ID，消费者在同一数据库事务中通过唯一索引、去重表或状态机条件更新实现幂等。Redis `SET NX` 可用于非关键场景，但要处理过期和业务失败后的原子性问题。

### 如何保证数据库与消息队列的一致性？

回答思路：先指出双写窗口，再分别说明事务消息和 Outbox，最后补充幂等。

回答模板：

直接先写数据库再发消息，可能出现数据库提交成功但消息发送失败；反过来又可能出现消息成功而数据库回滚。若中间件支持事务消息，可以先发半消息，再执行本地事务并提交或回滚，异常时由 Broker 回查事务状态。更通用的方案是 Outbox：在同一本地事务中写业务数据和事件表，再由发布器可靠投递。两种方案都可能因重试产生重复，因此消费者仍要幂等，并配合告警和补偿。

### 消费 lag 持续增长时如何排查？

回答思路：先用指标判断生产突增还是消费下降，再定位分区、消费者和下游，最后给出处置与恢复措施。

回答模板：

我会先看各分区 lag、增长速度、最老消息等待时间，以及生产和消费速率，判断是流量突增还是消费能力下降。然后检查是否存在热点分区、消费者宕机或频繁重平衡、单条消息处理变慢、下游超时、重复重试和死信增加。处理上先修复故障，再优化批处理或消费逻辑，并在分区数允许时扩容消费者；必要时限流或降级非核心任务。恢复后还要估算清空积压的时间，并控制追赶流量，避免再次压垮下游。
