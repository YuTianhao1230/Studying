# 软件工程与测试

## 知识点解析

### 概述

软件工程和测试在央国企、银行科技岗笔试中很常见，通常以选择题和简答题出现。重点是软件生命周期、开发模型、测试类型和质量保障方法。

### 软件生命周期

典型生命周期包括需求分析、概要设计、详细设计、编码、测试、部署和维护。需求分析明确做什么，设计明确怎么做，测试验证是否满足需求，维护处理缺陷和迭代。

### 开发模型

瀑布模型按阶段顺序推进，适合需求稳定、变更少的项目。敏捷开发强调短周期迭代、持续反馈和快速交付。DevOps 强调开发、测试、运维协同，通过自动化 CI/CD 提升交付效率。

### 测试类型

| 测试 | 说明 |
| --- | --- |
| 单元测试 | 测函数、类或模块 |
| 集成测试 | 测多个模块协作 |
| 系统测试 | 从完整系统角度验证 |
| 回归测试 | 验证修改没有破坏旧功能 |
| 黑盒测试 | 不关心内部实现，只看输入输出 |
| 白盒测试 | 关注代码路径、分支和覆盖率 |
| 压力测试 | 测系统极限和稳定性 |

### UML

UML 常见图包括用例图、类图、时序图、活动图、状态图。用例图描述用户和系统功能，类图描述类关系，时序图描述对象之间的调用顺序。

### 模块化设计

模块化设计的目标是把复杂系统拆成职责清晰、接口稳定的模块。评价模块设计时通常看耦合和内聚：

- 内聚：模块内部元素联系的紧密程度，通常越高越好。
- 耦合：模块之间依赖的紧密程度，通常越低越好。

常见内聚程度从低到高可以理解为偶然内聚、逻辑内聚、时间内聚、过程内聚、通信内聚、顺序内聚和功能内聚。常见耦合从强到弱包括内容耦合、公共耦合、控制耦合、标记耦合、数据耦合和非直接耦合。

### 需求与软件维护

需求工程包括需求获取、分析、规格说明、验证和管理。一个合格需求应尽量具备明确性、可验证性、可追踪性和一致性。

软件维护通常分为：

- 改正性维护：修复发现的错误。
- 适应性维护：适应操作系统、硬件、法规或外部环境变化。
- 完善性维护：增加功能、改善性能或易用性。
- 预防性维护：改善结构，降低未来维护成本。

### 配置管理和版本控制

软件配置管理关注源代码、需求、设计文档、测试用例、构建脚本和发布包等配置项。基线是经过正式评审和批准、后续变更需要受控的版本状态。

变更流程通常包括提出变更、影响分析、审批、实施、测试、发布和记录。版本控制解决多人协作和历史追踪问题，但不能代替需求管理、代码评审和发布审批。

### 项目管理基础

项目管理常见约束包括范围、进度、成本、质量、风险和资源。风险管理通常包括风险识别、分析、应对和跟踪。

- 关键路径上的活动延迟，可能直接延长项目总工期。
- 里程碑是重要阶段节点，不一定代表所有工作完成。
- 质量保证关注过程改进，质量控制关注交付物检查。
- 文档、测试和审计是银行及央国企项目的重要交付物。

### 常见考法与测试设计

| 题型 | 解题方法 |
| --- | --- |
| 开发模型选型 | 根据需求稳定性、交付周期和合规要求判断 |
| 测试阶段 | 区分单元、集成、系统、验收和回归 |
| 耦合内聚判断 | 优先选择高内聚、低耦合的设计 |
| 软件维护分类 | 根据变化原因判断改正、适应、完善或预防 |
| 黑盒用例 | 使用等价类、边界值、判定表和场景法 |
| 白盒覆盖 | 根据控制流判断语句、分支、条件和路径覆盖 |
| 缺陷处理 | 复现、定位、修复、回归、补自动化用例 |

设计输入类测试用例时：

1. 划分有效和无效等价类。
2. 覆盖最小值、最大值及边界外相邻值。
3. 补充空值、重复、非法字符和异常流程。
4. 检查错误提示、数据状态和恢复行为。
5. 根据风险增加并发、安全、性能和兼容性测试。

### 易错点

- 回归测试用于验证修改没有破坏已有功能，不只是重跑失败用例。
- 单元测试关注局部逻辑，集成测试关注模块协作。
- 覆盖率高不等于测试充分，断言错误和需求遗漏无法只靠覆盖率发现。
- 敏捷不代表没有设计和文档，而是通过短周期持续反馈。
- 高内聚、低耦合通常是模块化设计的目标。
- 适应性维护是适应外部环境变化，不是修复原有功能缺陷。

## 面试应对

### 黑盒测试和白盒测试有什么区别？

回答思路：是否关注内部实现。

回答模板：

黑盒测试不关注代码内部实现，只从输入输出和需求角度验证功能是否正确，常用于功能测试和验收测试。白盒测试关注代码内部结构、分支、路径和覆盖率，常用于单元测试和代码级质量保障。实际项目中两者会结合使用，黑盒保证业务行为，白盒保证实现路径和边界覆盖。

### 敏捷和瀑布有什么区别？

回答思路：需求稳定性、迭代方式、反馈周期。

回答模板：

瀑布模型按需求、设计、开发、测试、上线顺序推进，适合需求稳定、变更少、流程要求强的项目。敏捷开发强调小步迭代和快速反馈，把需求拆成多个短周期交付，更适合需求变化快的业务。两者不是绝对对立，金融和央国企项目可能在总体流程上偏瀑布，但在具体开发中引入敏捷迭代和持续集成。

### 如何为登录功能设计测试用例？

回答思路：从功能、边界、安全、性能和异常恢复分层回答。

回答模板：

我会先覆盖正确账号密码的主流程，再用等价类和边界值测试空值、错误密码、长度边界、非法字符和不存在账号。然后检查连续失败锁定、验证码、会话过期和找回密码。安全方面测试 SQL 注入、暴力破解、日志脱敏和 HTTPS；还要覆盖重复提交、并发登录、服务异常后的提示与恢复。
