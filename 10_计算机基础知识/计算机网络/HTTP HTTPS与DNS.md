# HTTP HTTPS与DNS

## 知识点解析

### 概述

本文整理 HTTP 方法与版本、状态码、缓存、TLS 握手、DNS 查询，以及从输入 URL 到页面展示的完整链路。

### HTTP

HTTP 是请求-响应模型的应用层协议。常见方法包括 GET、POST、PUT、DELETE。GET 通常用于获取资源，POST 通常用于提交数据。HTTP 默认无状态，需要 Cookie、Session 或 Token 维护用户状态。

GET 的参数通常放在 URL 中，便于缓存、收藏和重复获取；POST 的数据通常放在请求体中，更适合提交或修改数据。但安全性不由 GET/POST 决定，敏感数据仍然需要 HTTPS 和服务端权限校验。

### Cookie、Session 和 Token

Cookie 是浏览器保存在客户端的小段数据，会按域、路径、安全属性等规则自动随请求携带；Session 通常把会话状态保存在服务端，客户端只保存并携带 Session ID；Token 通常由服务端签发并由客户端保存，请求时显式携带，服务端据此验证身份和权限。

分布式部署中，服务端 Session 需要通过共享存储或粘性会话让不同实例读取同一状态。Token 更适合无状态服务和跨服务传递，但仍要设计有效期、刷新、吊销和泄露后的处置机制。Cookie 是存储与传输机制，Session 和 Token 是状态或凭证方案，三者不处于同一比较维度；Token 也可以存入 Cookie。

### HTTP 版本

| 版本 | 核心特点 |
| --- | --- |
| HTTP/1.0 | 短连接为主 |
| HTTP/1.1 | 长连接、Host 头、管线化；同一连接上的响应仍可能发生队头阻塞 |
| HTTP/2 | 二进制分帧、多路复用、头部压缩和服务端推送，减少连接数量和应用层队头阻塞 |
| HTTP/3 | 基于 QUIC/UDP，减少握手开销并改善传输层队头阻塞 |

### HTTPS

HTTPS = HTTP + TLS。TLS 提供身份认证、加密传输和完整性保护。客户端通过证书验证服务端身份，握手阶段协商密钥，后续用对称加密传输数据。

### DNS

DNS 把域名解析成 IP。解析链路可能经过浏览器缓存、操作系统缓存、本地 DNS、根域名服务器、顶级域名服务器和权威域名服务器。DNS 查询可分为递归查询和迭代查询。

常见 DNS 优化包括合理利用缓存、按需预解析和设置合适的 TTL。TTL 过短会增加查询压力，过长则会延缓地址变更生效。

### 状态码

| 状态码 | 含义 |
| --- | --- |
| 200 | 请求成功 |
| 301 | 永久重定向，客户端和缓存可更新长期引用 |
| 302 | 临时重定向，不应据此永久替换原地址 |
| 304 | 资源未修改，可继续使用缓存 |
| 400 | 请求格式或参数有误 |
| 401 | 未认证或认证失效 |
| 403 | 身份已知但没有权限 |
| 404 | 资源不存在 |
| 500 | 服务端内部错误 |
| 502 | 网关收到上游错误响应 |
| 503 | 服务暂不可用 |
| 504 | 网关等待上游响应超时 |

### HTTP 缓存

- 强缓存：浏览器根据 `Cache-Control` 或 `Expires` 直接使用本地副本，不发请求。
- 协商缓存：浏览器携带 `If-None-Match` 或 `If-Modified-Since`，服务端未变化时返回 304。
- `ETag` 基于资源版本，通常比只依赖修改时间更精确。

### TLS 握手怎么理解

TLS 的目标是认证服务端、协商会话密钥并验证握手未被篡改。现代 TLS 通常使用 ECDHE 协商共享密钥，证书和数字签名用于验证服务端身份，后续业务数据使用高效的对称加密。

TLS 1.3 的一次完整握手可以概括为：

1. 客户端发送 `ClientHello`，携带支持的算法、随机数和 ECDHE 密钥份额。
2. 服务端返回 `ServerHello` 并选择参数、给出自己的密钥份额；双方据此派生握手密钥。
3. 服务端在加密保护下发送证书、对握手内容的签名和 `Finished`。证书证明公钥对应受信任域名，签名证明服务端持有相应私钥。
4. 客户端验证证书链、域名、签名和 `Finished` 后发送自己的 `Finished`，随后双方使用派生出的应用密钥传输 HTTP 数据。

TLS 1.3 完整握手通常为 1-RTT；会话恢复可减少开销。`0-RTT` 数据可能被重放，因此只适合可安全重试、具有幂等性的操作。证书私钥主要用于身份签名，业务数据不是直接用证书公钥加密。

客户端验证证书时会检查：

- 是否由受信任 CA 签发。
- 域名是否匹配。
- 是否在有效期内。
- 证书链和签名是否有效。

### DNS 查询

主机通常向本地 DNS 发起递归查询，本地 DNS 再迭代查询根、顶级域和权威 DNS。缓存会显著减少查询次数，TTL 决定记录可以缓存多久。

- `A`：把域名映射到 IPv4 地址。
- `AAAA`：把域名映射到 IPv6 地址。
- `CNAME`：把一个域名指向另一个规范域名，解析器还需继续解析目标名称；同一名称通常不能再配置 `A`、`AAAA` 等其他数据。

客户端要求本地 DNS 给出最终答案属于递归查询；本地 DNS 依次向根、顶级域和权威服务器询问下一步去哪里，属于迭代查询。浏览器、操作系统和递归解析器都可能缓存结果，并在记录 TTL 到期前复用；TTL 越长越能减轻查询压力，但地址变更的传播也越慢。缓存未命中或过期后才需要重新查询，实际剩余 TTL 不会因多级缓存而重新从原值起算。

### 常见应用层协议与默认端口

| 协议 | 默认端口 | 主要用途 |
| --- | --- | --- |
| HTTP | 80 | 明文 Web 访问 |
| HTTPS | 443 | 基于 TLS 的安全 Web 访问 |
| DNS | 53 | 域名解析，通常使用 UDP，响应较大或区域传送等场景可使用 TCP |
| SSH | 22 | 加密远程登录 |
| FTP | 20/21 | 文件传输，传统主动模式分别使用数据连接和控制连接 |
| SMTP | 25 | 邮件服务器之间传输邮件 |
| POP3 | 110 | 下载式邮件接收 |
| IMAP | 143 | 服务端邮件同步与管理 |

端口是默认约定而不是协议不可更改的固定属性；加密变体、服务配置和网络代理都可能使用其他端口。

### 从输入 URL 到页面展示

典型链路如下：

1. 浏览器解析 URL，确定协议、主机、端口和资源路径。
2. DNS 把域名解析为 IP 地址。
3. 建立 TCP 连接；HTTP/3 场景则建立 QUIC 连接。
4. HTTPS 场景完成 TLS 握手。
5. 浏览器发送 HTTP 请求，服务端处理并返回响应。
6. 浏览器解析 HTML，加载 CSS、JavaScript 和图片等资源，构建 DOM 与 CSSOM。
7. 浏览器生成渲染树，完成布局、绘制与合成后展示页面。

缓存命中、连接复用、代理/CDN 和 HTTP 版本会使实际链路省略或合并部分步骤。

### 常见考法与排查

| 题型 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 协议顺序 | URL 访问时 DNS、TCP、TLS、HTTP 顺序 | 按分层和依赖关系排列 |
| 状态码 | 401/403、502/504 等区别 | 判断错误发生在哪一侧 |
| HTTP 版本 | 多路复用、队头阻塞、QUIC | 对比连接与传输机制 |
| 缓存 | 200、304、Cache-Control、ETag | 先判断强缓存，再判断协商缓存 |
| TLS | 为什么能防窃听和篡改 | 证书认证 + 密钥协商 + 对称加密 |
| DNS | 递归和迭代、缓存层级 | 按客户端、本地 DNS、权威链路分析 |

网页访问慢时按阶段排查：

```text
DNS 解析
  -> TCP/QUIC 建连
  -> TLS 握手
  -> 服务端处理
  -> 内容下载
  -> 浏览器解析与渲染
```

## 笔试常考

- URL 访问阶段排序：解析 URL 后依次考虑 DNS、TCP 建连、TLS、HTTP 请求响应、资源加载与浏览器渲染；HTTP/3 把 TLS 1.3 集成进 QUIC 握手，缓存命中也可能跳过部分网络阶段。
- 默认端口与状态保持：识别 HTTP、HTTPS、DNS、SSH、FTP、SMTP、POP3、IMAP 的常见端口，并从状态保存位置、自动携带方式和分布式部署成本区分 Cookie、Session 与 Token。
- 状态码辨析：区分 `301` 与 `302`、`200` 与 `304`、`401` 与 `403`、`502` 与 `504`，先判断是重定向、缓存、认证授权还是网关上游问题。
- 缓存判断：先检查 `Cache-Control`/`Expires` 强缓存；未命中后再用 `If-None-Match`/`ETag` 或 `If-Modified-Since`/`Last-Modified` 进行条件请求。
- TLS 证书与密钥协商：证书链和签名认证服务端，ECDHE 协商共享秘密，再派生对称会话密钥；证书私钥不直接加密业务数据。
- DNS 查询：客户端到本地 DNS 常用递归查询，本地 DNS 到各级权威链路常用迭代查询；`A`、`AAAA`、`CNAME` 记录按 TTL 缓存。
- 队头阻塞：HTTP/2 可在一个 TCP 连接中多路复用，但 TCP 丢包会阻塞该连接上的流；HTTP/3 基于 QUIC，使不同流在传输层独立推进。

### 易错点

- POST 不天然比 GET 安全，安全性主要依赖 HTTPS、认证和授权。
- 401 表示未认证或认证失效，403 表示身份已知但没有权限。
- 502 通常是网关收到上游错误响应，504 是网关等待上游超时。
- HTTP/2 解决应用层多路复用问题，但底层 TCP 丢包仍可能阻塞连接；HTTP/3 使用 QUIC 改善这一问题。
- HTTPS 不能阻止服务端自身泄露数据，也不能替代业务权限校验。

## 面试应对

### HTTPS 为什么安全？

回答思路：认证、加密、完整性。

回答模板：

HTTPS 的安全性来自 TLS。第一，通过证书验证服务端身份，降低中间人攻击风险；第二，握手阶段协商会话密钥，后续使用对称加密保护数据内容；第三，通过消息认证码或 AEAD 机制保证数据完整性，防止传输过程中被篡改。所以 HTTPS 不只是加密，还同时解决身份认证、机密性和完整性。

### 从输入 URL 到页面展示发生什么？

回答思路：DNS、TCP、TLS、HTTP、浏览器渲染。

回答模板：

浏览器输入 URL 后，先解析 URL，再通过 DNS 把域名解析成 IP。然后建立 TCP 连接，如果是 HTTPS 还要进行 TLS 握手。连接建立后发送 HTTP 请求，服务端处理并返回响应。浏览器收到 HTML 后解析 DOM，加载 CSS 和 JS，构建渲染树，执行布局和绘制，最后展示页面。实际排查性能时可以把 DNS、建连、TLS、服务端处理和下载渲染分开看。

### HTTP/1.1、HTTP/2 和 HTTP/3 有什么区别？

回答思路：从连接复用、帧、多路复用和底层传输回答。

回答模板：

HTTP/1.1 支持长连接，但同一连接上的请求处理能力有限，管线化也没有广泛使用；HTTP/2 引入二进制分帧、头部压缩和多路复用，让多个请求共享一个 TCP 连接，但 TCP 丢包仍可能造成整个连接等待；HTTP/3 基于 QUIC 和 UDP，把不同流独立处理，并把传输层与 TLS 握手结合，减少建连开销和传输层队头阻塞。

### 强缓存和协商缓存有什么区别？

回答思路：是否向服务端发送请求。

回答模板：

强缓存命中时浏览器直接使用本地资源，不向服务端发请求，常由 Cache-Control 控制；协商缓存会向服务端发送条件请求，例如携带 ETag 或 Last-Modified，资源未变化时服务端返回 304。通常先判断强缓存，未命中后再走协商缓存。

### 线上接口突然变慢，网络侧怎么排查？

回答思路：按 DNS、建连、TLS、传输、服务端和地域链路拆分总耗时，用日志、指标和抓包验证。

回答模板：

我会先通过分阶段埋点或抓包确认耗时发生在 DNS、TCP 或 QUIC 建连、TLS 握手、服务端处理还是响应下载。然后检查 DNS 解析与缓存是否异常，TCP 是否出现重传、丢包或 RTT 升高，连接池是否耗尽，以及服务端是否出现 5xx 或上游超时。如果问题只出现在部分地区或运营商，还要比较 CDN 节点、路由路径和链路质量。排查时不能只看总耗时，而要先定位变慢阶段，再用对应证据确认根因。
