# TCP与UDP

## 知识点解析

### 概述

本文整理 TCP 与 UDP 的协议特点、连接建立与关闭、可靠传输、滑动窗口、流量控制、拥塞控制和常见连接状态。

### TCP

TCP 是面向连接、可靠、有序、面向字节流的协议。它通过序列号、确认应答、重传、滑动窗口、流量控制和拥塞控制保证可靠传输。

### UDP

UDP 是无连接、尽力而为、面向数据报的协议。它不保证可靠和有序，但头部简单、延迟低，适合 DNS、实时音视频、游戏等场景。

### 三次握手

```text
第一次：客户端 -> 服务端：SYN=1, seq=x
第二次：服务端 -> 客户端：SYN=1, ACK=1, seq=y, ack=x+1
第三次：客户端 -> 服务端：ACK=1, seq=x+1, ack=y+1
```

`x` 和 `y` 分别是客户端与服务端选择的初始序列号。SYN 会占用一个序列号，所以对它的确认号是初始序列号加一。三次握手还可以协商 MSS、窗口扩大、SACK 等 TCP 选项。

状态上，客户端发送 SYN 后从 `CLOSED` 进入 `SYN_SENT`，收到 SYN+ACK 并回复 ACK 后进入 `ESTABLISHED`；服务端从 `LISTEN` 收到 SYN 后进入 `SYN_RECV`，收到第三次 ACK 后进入 `ESTABLISHED`。

三次握手的核心目的有两个：

1. 同步双方的初始序列号，后续才能通过序列号和 ACK 判断数据是否丢失、重复或乱序。
2. 让双方都确认客户端到服务端、服务端到客户端这两个方向可以通信。

| 次数 | 接收方得到的信息 | 这一步的作用 |
| --- | --- | --- |
| 第一次握手 | 服务端收到客户端的 SYN 和初始序列号 `x` | 服务端确认客户端能够发送、自己能够接收，并知道客户端希望建立连接 |
| 第二次握手 | 客户端收到服务端对 `x` 的确认、服务端的 SYN 和初始序列号 `y` | 客户端确认自己的 SYN 已到达服务端，也确认服务端能够发送、自己能够接收 |
| 第三次握手 | 服务端收到客户端对 `y` 的确认 | 服务端确认自己的 SYN 已到达客户端，即服务端到客户端方向也可用；双方进入已建立状态 |

#### 为什么不能只有两次握手？

如果服务端收到 SYN 后发送 SYN+ACK 就直接认为连接已经建立，它无法确定客户端是否收到了响应，也无法确定客户端现在是否仍想建立连接。例如，网络中滞留的旧 SYN 延迟到达服务端时，服务端可能为一个已经失效的请求建立连接并占用资源。第三次 ACK 表明客户端确实收到了本次连接的服务端序列号，并仍同意建立连接。

三次是确认双向通信和同步双方序列号所需的最少次数。通常也不需要四次，因为服务端可以把“确认客户端 SYN 的 ACK”和“发送自己的 SYN”合并在第二个报文中。

#### 握手报文丢失会怎样？

TCP 不会因为单个握手报文丢失就立即失败，而会通过定时器重传；多次重传仍得不到响应才会超时。

| 丢失的报文 | 直接结果 |
| --- | --- |
| 第一次 SYN | 服务端不知道连接请求；客户端超时后重传 SYN |
| 第二次 SYN+ACK | 客户端不知道服务端已经响应；服务端停留在 `SYN_RECV` 并重传 SYN+ACK，客户端也可能重传 SYN |
| 第三次 ACK | 客户端认为连接已建立，但服务端仍处于 `SYN_RECV`；服务端会重传 SYN+ACK，客户端收到后再次发送 ACK |

如果大量客户端只发送 SYN 而不完成第三次握手，服务端会保留大量半连接并占用半连接队列，这正是 SYN Flood 攻击的基本原理。

### 四次挥手

TCP 是全双工连接，两个方向要分别关闭。主动关闭方发送 FIN，被动关闭方先 ACK，等数据发送完再 FIN，主动关闭方再 ACK。

```text
主动方 -> 被动方：FIN=1, seq=u
被动方 -> 主动方：ACK=1, ack=u+1
被动方 -> 主动方：FIN=1, seq=v
主动方 -> 被动方：ACK=1, ack=v+1
```

FIN 和 SYN 一样会占用一个序列号，纯 ACK 不占用序列号。主动关闭方通常依次经历 `ESTABLISHED -> FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT -> CLOSED`；被动关闭方通常经历 `ESTABLISHED -> CLOSE_WAIT -> LAST_ACK -> CLOSED`。如果被动方可以立即关闭，它对第一个 FIN 的 ACK 和自己的 FIN 可能合并，报文数不一定严格是四个。

收到 FIN 只表示对端不再向本端发送数据，本端仍可继续发送剩余数据，这就是 TCP 半关闭。应用调用 `shutdown` 可以只关闭一个方向；只有两个方向都关闭后，连接才完整释放。

### TIME_WAIT

TIME_WAIT 的作用是保证最后一个 ACK 可重传，并让旧连接中的延迟报文自然消失，避免影响相同四元组的新连接。

### 可靠传输

TCP 通过序列号、确认应答、超时重传、快速重传和滑动窗口保证数据可靠、有序到达。流量控制通过接收窗口避免接收方处理不过来；拥塞控制通过慢启动、拥塞避免、快重传和快恢复调整发送速度，避免网络过载。

### CLOSE_WAIT

CLOSE_WAIT 表示对端已经发送 FIN，本端也已经回复 ACK，但应用程序还没有关闭连接。大量 CLOSE_WAIT 通常说明应用没有及时执行 close，可能存在连接泄漏。

### 序列号、ACK 与滑动窗口

TCP 面向字节流，序列号标识字节在数据流中的位置，ACK 通常表示下一个期望收到的字节序号。发送方可以在未收到每个单独确认前连续发送窗口内的数据，提高链路利用率。

- 累计确认：ACK 表示此前连续字节均已收到。
- 超时重传：超过重传定时器仍未确认则重发。
- 快速重传：收到多个重复 ACK 时，不等待超时直接重发疑似丢失报文。
- 流量控制：接收方通过接收窗口 `rwnd` 告知可接收容量。
- 拥塞控制：发送方通过拥塞窗口 `cwnd` 控制注入网络的数据量。

实际发送窗口受 `min(rwnd, cwnd)` 限制。

例如发送方下一个未确认字节为 `1001`，接收方通告 `rwnd=5000` 字节，而 `cwnd=3000` 字节，则当前最多发送 3000 字节，序列号范围为 `[1001, 4000]`。当 `[1001, 2000]` 被累计确认且两个窗口大小不变时，窗口左沿滑到 `2001`，新的可发送范围为 `[2001, 5000]`。

接收方通告零窗口时，发送方暂停普通数据发送，并启动持续计时器，定期发送零窗口探测报文，直到收到非零窗口更新，避免窗口更新报文丢失后双方永久等待。重传超时 `RTO` 则根据平滑 RTT 和 RTT 波动动态估算；发生超时重传后通常进行指数退避，不能把 RTO 固定等同于一次 RTT。

### 拥塞控制

- 慢启动：拥塞窗口从较小值开始，按确认快速增长。
- 拥塞避免：达到阈值后近似线性增长。
- 快重传：多个重复 ACK 表明可能发生单个报文丢失。
- 快恢复：不直接回到最小窗口，而是调整阈值后继续传输。

以经典 Reno 的笔试模型为例，发生丢包时通常把 `ssthresh` 调整为当前在途数据量的一半左右。超时被视为更严重的拥塞信号，`cwnd` 回到初始窗口并重新慢启动；收到 3 个重复 ACK 时执行快重传和快恢复，`cwnd` 不直接降到初始窗口，恢复后从新的 `ssthresh` 附近进入拥塞避免。具体初始窗口、下限和恢复过程依 TCP 实现与题目设定而异，CUBIC、BBR 等算法不能机械套用 Reno 曲线。

### 常见考法与排查

| 题型 | 怎么考 | 解题方法 |
| --- | --- | --- |
| 握手挥手 | 填标志位、序列号和 ACK | ACK 指向下一个期望序号 |
| TCP 状态 | 判断 TIME_WAIT、CLOSE_WAIT | 先判断谁主动关闭 |
| 滑动窗口 | 求可发送范围和吞吐 | 同时看接收窗口与拥塞窗口 |
| 拥塞控制 | 画 cwnd 变化 | 区分超时和重复 ACK |
| TCP/UDP 选型 | 可靠性、时延、消息边界 | 根据业务容错和实时性判断 |
| 网络故障 | 连接失败、重传、状态堆积 | 分建连、传输、关闭阶段排查 |

大量状态的常见原因：

- 大量 `TIME_WAIT`：本端主动关闭连接频繁，可能是短连接过多。
- 大量 `CLOSE_WAIT`：应用收到 FIN 后没有及时关闭连接。
- 大量 `SYN_RECV`：连接建立未完成，可能有网络问题、队列不足或 SYN Flood。

## 笔试常考

- 握手与挥手序列号：SYN、FIN 各占用一个序列号，ACK 指向下一个期望序号，纯 ACK 不消耗序列号。
- 状态转换：握手关注 `SYN_SENT`、`SYN_RECV`、`ESTABLISHED`；主动关闭关注 `FIN_WAIT_1/2`、`TIME_WAIT`，被动关闭关注 `CLOSE_WAIT`、`LAST_ACK`。
- 滑动窗口范围：从最早未确认字节开始，按 `min(rwnd, cwnd)` 计算可在途范围；累计 ACK 前移后窗口左、右边界随之滑动。
- 拥塞窗口变化：慢启动到 `ssthresh` 后转拥塞避免；Reno 模型中超时使 `cwnd` 回到初始窗口，3 个重复 ACK 触发快重传和快恢复。
- 状态诊断：`SYN_RECV` 多关注半连接与握手失败，`CLOSE_WAIT` 多关注应用未关闭，`TIME_WAIT` 多关注主动关闭和短连接。
- TCP/UDP 选型：可靠有序、可接受重传时延时选 TCP；强调低时延、消息边界或应用自行保证可靠性时可选 UDP，不能只按“快慢”判断。

### 易错点

- TCP 可靠不等于应用一定成功，应用仍需处理超时、重复请求和业务幂等。
- TCP 是字节流，没有消息边界，应用层需要用固定长度、分隔符或长度字段划分消息，并循环读取完整消息。
- UDP 一次发送对应一个数据报，保留消息边界，但可能丢失、重复或乱序。
- 流量控制保护接收方，拥塞控制保护网络。
- 三次握手主要确认双向收发能力和序列号，不是为了“多一次更安全”。

## 面试应对

### TCP 和 UDP 有什么区别？

回答思路：连接、可靠性、有序性、开销、场景。

回答模板：

TCP 是面向连接的可靠传输协议，会通过三次握手建立连接，并用序列号、ACK、重传、滑动窗口、流量控制和拥塞控制保证可靠有序传输。UDP 是无连接协议，不保证可靠和有序，但头部小、延迟低。可靠性要求高的场景，比如 HTTP、数据库连接、文件传输，通常用 TCP；实时性更重要且能容忍少量丢包的场景，比如 DNS、音视频、游戏，可以用 UDP。

### 为什么 TCP 需要三次握手？

回答思路：确认双向收发能力，避免历史连接。

回答模板：

三次握手用于同步双方的初始序列号，并让双方确认两个方向都可以通信。第一次 SYN 使服务端获得客户端的初始序列号；第二次 SYN+ACK 确认客户端的序列号，同时把服务端的初始序列号发给客户端；第三次 ACK 使服务端确认客户端已经收到自己的序列号。如果只有两次，服务端无法确认客户端是否收到 SYN+ACK，延迟到达的历史 SYN 还可能使服务端错误建立连接并占用资源。通常不需要四次，因为服务端可以把 ACK 和自己的 SYN 合并发送。若第三次 ACK 丢失，服务端会重传 SYN+ACK，客户端收到后会再次回复 ACK，因此不会立即判定连接失败。

### TCP 如何保证可靠传输？

回答思路：从序列号、确认、重传、窗口和拥塞控制展开。

回答模板：

TCP 通过多套机制保证可靠传输。序列号保证数据按顺序组装，累计 ACK 确认连续数据，动态 RTO 到期后超时重传，重复 ACK 可触发快速重传。滑动窗口提升吞吐，实际发送量受接收窗口和拥塞窗口共同限制。若接收方通告零窗口，发送方会用持续计时器进行零窗口探测，避免窗口更新丢失造成死锁。因此可靠性来自确认、重传、有序、窗口和拥塞控制的配合。

### TCP 挥手、半关闭和常见关闭状态怎么理解？

回答思路：全双工、FIN 状态转换、半关闭、TIME_WAIT 与 CLOSE_WAIT。

回答模板：

TCP 是全双工连接，两个发送方向需要分别关闭。主动方发送 FIN 后进入 `FIN_WAIT_1`，收到 ACK 后进入 `FIN_WAIT_2`；这时只是主动方不再发送，仍能接收对端数据，属于半关闭。对端发送 FIN 后，主动方回复 ACK 并进入 `TIME_WAIT`，以便重发最后的 ACK 并等待旧报文消失。被动方收到 FIN 后进入 `CLOSE_WAIT`，应用关闭并发送 FIN 后进入 `LAST_ACK`。因此大量 `CLOSE_WAIT` 常说明应用未及时 close，大量 `TIME_WAIT` 则常见于频繁主动关闭或短连接。

### 流量控制和拥塞控制有什么区别？

回答思路：区分接收方能力和网络容量。

回答模板：

流量控制解决接收方处理不过来的问题，接收方通过接收窗口 `rwnd` 告诉发送方还有多少缓冲区；拥塞控制解决网络承载不过来的问题，发送方根据丢包和 ACK 调整拥塞窗口 `cwnd`，实际可发送量不超过 `min(rwnd, cwnd)`。以经典 Reno 为例，慢启动达到 `ssthresh` 后转为拥塞避免；超时会降低 `ssthresh` 并让 `cwnd` 回到初始窗口，3 个重复 ACK 则触发快重传和快恢复，通常不会降得同样激进。
