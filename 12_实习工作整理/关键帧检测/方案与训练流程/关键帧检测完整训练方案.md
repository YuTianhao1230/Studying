# 关键帧检测完整训练方案：Direct SFT、CoT-SFT 与 GRPO

## 知识点解析

### 概述

关键帧检测的目标是从移动端操作录屏中定位某个业务指标的“完成态第一次成立”的时间点，用于性能耗时计算、智能预标和人工标注提效。它不是普通视频分类，而是一个由业务规则约束的时空证据定位任务。当前模型已经具备较好的基础能力，完整训练路线的重点是：先用 Direct SFT 学会稳定完成基础任务，再用结构化 CoT SFT 补充边界证据，最后在 reward 和 verifier 可靠时用 GRPO 优化困难指标。

```text
业务录屏与 GT
  -> 任务定义和数据治理
  -> Base/Prompt baseline
  -> Direct SFT
  -> 结构化 CoT 数据构造和质量过滤
  -> Structured CoT SFT
  -> 同一批 CoT 数据用于 rollout 和 reward 计算
  -> Verifier-based GRPO
  -> 固定评测、bad case 回流和上线
```

### 1. 项目目标和当前能力

输入：视频 + task_type + 完成态定义 + 排除条件和豁免条件。

输出：`<answer>{"time": 6.97}</answer>`。

当前模型效果：

| 范围 | ACC |
| --- | ---: |
| 全量平均 | 89.982 |
| 国际电商 | 97.457 |
| 番茄系 | 89.055 |
| 搜索系 | 75.977 |

这意味着 [Direct SFT](<SFT 训练方案设计.md>)、[数据治理](<../任务与数据治理/README.md>)、[Prompt](<../../../02_大模型/应用与问题/Prompt调优.md>) 和[推理优化](<../工程实现/部署上线与容量评估.md>)已经解决了大部分基础问题。后续训练重点不是让模型从零学会视频输入，而是解决：

- 低 ACC 业务线和长尾指标。
- 过早预测和过晚预测。
- 局部异步加载和小 UI 元素。
- 页面二次刷新或内容替换。
- “当前看似稳定”与“首次满足完成态”的区别。
- [CoT-SFT](<CoT-SFT 蒸馏方案设计.md>) 中的证据幻觉和边界解释不一致。

### 3. 阶段零：任务和数据先对齐

#### 3.1 完成态规则

每个 `task_type` 至少要定义：

```text
任务目标
  -> 必须满足的条件
  -> 排除条件
  -> 豁免条件
  -> 首选证据和备选证据
  -> 防抢跑规则
  -> 防跳过规则
```

例如页面加载任务不能只写“等页面加载完成”，而应写成：

```text
页面主干停稳，核心图片和价格清晰，
关键区域不再被占位内容覆盖；
局部非业务区域继续异步加载可以豁免；
如果后续发生核心内容二次替换，
以最后一次替换完成后的首次稳定帧为准。
```

详见[任务定义与标注标准.md](<../任务与数据治理/任务定义与标注标准.md>)。

#### 3.2 数据检查

视频层面：

- 文件存在且可以解码。
- FPS、时长、宽高和总帧数可读取。
- 视频没有黑屏、截断或严重损坏。

标签层面：

- `task_type` 可以映射到任务规则。
- GT 帧号和时间没有越界。
- 裁剪前后的时间坐标一致。
- 同一视频和任务不存在冲突标签。

多模态层面：

- `<video>` 和 `videos[0]` 一一对应。
- assistant 标签参与 loss。
- 输出格式可以解析。
- 训练、评测和线上使用同一时间坐标口径。

详见[Qwen3-VL关键帧数据格式.md](<../工程实现/Qwen3-VL关键帧数据格式.md>)。

### 4. 阶段一：Base 和 [Prompt](<../../../02_大模型/应用与问题/Prompt调优.md>) baseline

训练前固定三类 baseline：

```text
规则/传统 baseline
  -> Base Model baseline
  -> Prompt baseline
```

记录：

- 全量和分业务线 ACC。
- `frame_err`、`time_err`。
- PASS 率。
- 格式解析率。
- early/late 分布。
- 各 `task_type` 指标。
- bad case 类型。

没有 baseline，就无法判断收益来自模型、数据、Prompt、采样配置还是评测口径变化。

### 5. 阶段二：Direct SFT

#### 5.1 训练目标

```text
视频 + task_type + 完成态规则
  -> <answer>{"time": ...}</answer>
```

Direct SFT 先学习：

- 视频输入。
- 任务遵循。
- 明显完成态识别。
- 时间预测。
- 稳定输出格式。

#### 5.2 冷启动顺序

```text
单样本 forward
  -> 10~100 条小数据过拟合
  -> 小规模 dev 实验
  -> 一轮完整 Direct SFT
```

如果小数据都无法过拟合，优先检查：

- 视频字段和 `<video>` 是否匹配。
- assistant labels 是否为空。
- vision encoder 是否参与 forward。
- 训练参数是否真的生效。
- 是否发生严重截断。

#### 5.3 Direct SFT 的能力边界

Direct SFT 能告诉模型最终答案，但通常没有显式告诉模型：

```text
前一候选为什么不行
当前候选为什么是第一次满足
后续为什么只是稳定延续
哪个 UI 区域是必决证据
二次刷新是否推翻当前判断
```

因此 Direct SFT 之后才需要进入 CoT-SFT，而不是一开始就用长 CoT 替代全部基础训练。

详细参数和收敛排查见[SFT 训练方案设计.md](<SFT 训练方案设计.md>)。

### 6. 阶段三：Structured CoT SFT

#### 6.1 为什么使用 CoT

结构化 CoT 将单点监督升级为：

```text
任务理解
  -> 目标区域
  -> 必须满足的证据
  -> before：未完成证据
  -> current：首次满足证据
  -> after：稳定性复核
  -> 最终时间
```

它的目标不是让回答更长，而是让模型学习边界判断所需的证据。

#### 6.2 CoT 数据来源

```text
高质量人工 GT
  + Direct SFT 数据
  + 低 ACC 指标
  + bad case
  + GT 附近 hard negative
  + 强教师生成结果
```

教师生成的 CoT 必须经过：

- 视频和时间检查。
- 结构检查。
- 视觉证据检查。
- GT 泄漏检查。
- 语义一致性检查。
- 长度和重复检查。

#### 6.3 训练方式

从 Direct SFT checkpoint 开始，先单独验证：

```text
Direct SFT checkpoint
  -> clean CoT SFT
  -> 评估困难指标
```

不要把短答案和完整 CoT 以相同 Prompt 裸混。两者是不同的输出协议：

```text
direct：
  <answer>{"time": ...}</answer>

structured_cot：
  状态/事件/边界证据
  + <answer>{"time": ...}</answer>
```

如果最终线上只需要短答案，可以：

1. 使用 CoT 模型离线生成和验证困难样本。
2. 训练 direct/cot 双模式模型。
3. 或将验证后的能力蒸馏回 answer-only 模型。

详见[CoT-SFT 蒸馏方案设计.md](<CoT-SFT 蒸馏方案设计.md>)。

### 7. 阶段四：[Verifier-based GRPO](<GRPO 训练方案设计.md>)

#### 7.1 GRPO 的进入条件

只有满足以下条件才进入 GRPO：

- CoT policy 能稳定生成可解析回答。
- `answer.time` 可以稳定提取。
- verifier 与人工判断有较高一致性。
- reward 分项与真实 ACC 相关。
- group 内存在正确和错误的回答差异。
- 训练资源能够支持 rollout 和验证。

#### 7.2 训练流程

```text
CoT SFT checkpoint
  -> 同一视频/task_type 生成 G 个回答
  -> 解析 answer、segments 和 evidence
  -> 计算 time/format/boundary/evidence reward
  -> 组内标准化 advantage
  -> clipping + KL 更新 policy
  -> 固定回归集和困难集验证
```

#### 7.3 Reward

```text
R_total =
  R_time          (预测时间与 GT 的误差)
  + R_format     (输出结构和 JSON 可解析)
  + R_boundary   (before/current/after 边界正确)
  + R_evidence   (UI 区域、状态和时间证据一致)
  + R_task       (遵循 task_type 完成态规则)
  - P_length     (无效冗长、重复或循环)
  - P_hallucination (虚假 UI、事件或视觉证据)
```

核心是让 reward 能区分：

```text
6.53s：仍未完成
6.97s：首次满足
10.00s：只是后续稳定
```

详细 reward、参数和失败排查见[GRPO 训练方案设计.md](<GRPO 训练方案设计.md>)。

### 8. 阶段五：评测、回流和上线

#### 8.1 评测矩阵

每个阶段都比较：

```text
Direct SFT
  vs Structured CoT SFT
  vs RFT baseline
  vs GRPO
```

指标包括：

- 全量 ACC。
- 低 ACC 指标 ACC。
- `frame_err`、`time_err`。
- PASS 率。
- 格式解析率。
- evidence accuracy。
- early/late 分布。
- response length。
- KL、reward 分项和训练成本。

#### 8.2 Bad case 回流

```text
模型预测
  -> 按 task_type/错误类型分桶
  -> 视频、GT、规则三方复核
  -> relabel / hard negative / prompt 修正
  -> 同一批 CoT 样本按需回流 CoT-SFT 或 GRPO
  -> 固定回归集验证
```

不能把所有预测错误都当成模型能力问题。需要先区分：

```text
GT 错误
  + 标准冲突
  + 数据覆盖不足
  + 视觉输入不足
  + 模型边界能力不足
```

#### 8.3 上线检查

上线前对齐：

```text
checkpoint
  + tokenizer / processor / chat template
  + FPS / max_frames
  + 分辨率和视觉 token 预算
  + max_new_tokens
  + 采样参数
  + 输出解析规则
```

性能上拆分：

```text
视频下载
  -> 解码
  -> processor
  -> 模型推理
  -> 后处理
  -> 队列和并发
```

详见[工程实现/部署上线与容量评估.md](<../工程实现/部署上线与容量评估.md>)。

### 9. 最终方法选择

```text
模型不会遵循任务：
  -> Direct SFT

模型会答，但不会解释边界：
  -> Structured CoT SFT

模型已有 CoT，但困难样本仍有多个候选差异：
  -> Verifier-based GRPO

Reward 可靠但还不想承担 RL 成本：
  -> RFT baseline

有强教师 logits，想纠正学生自己的错误状态：
  -> OPD

线上只需要短答案：
  -> CoT 离线增强 + direct/cot 双模式或答案蒸馏
```

方法卡片：[GRPO](<../../../03_训练优化与对齐/后训练与对齐/GRPO 组相对策略优化.md>)、[RFT](<../../../03_训练优化与对齐/后训练与对齐/RFT 拒绝采样微调.md>)、[OPD](<../../../03_训练优化与对齐/后训练与对齐/On-Policy Distillation 在线策略蒸馏.md>)。

### 10. 面试回答模板

我会把关键帧训练拆成 [Direct SFT](<SFT 训练方案设计.md>)、[Structured CoT SFT](<CoT-SFT 蒸馏方案设计.md>) 和 [Verifier-based GRPO](<GRPO 训练方案设计.md>) 三阶段。Direct SFT 先让模型学会视频输入、task_type 遵循、基础完成态判断和稳定的时间 JSON 输出；CoT-SFT 再把任务理解、目标区域、before/current/after 证据和边界判断显式化，解决单点 GT 监督不足的问题；当模型能稳定生成结构化回答且 verifier 可靠后，再用 GRPO 对同一个视频采样多个候选回答，用时间误差、格式、边界和视觉证据 reward 强化更好的策略。每一阶段都用固定回归集、低 ACC 指标集和 bad case 分桶评估，不会只看 loss 或 reward。
