# Workflow 与 LangGraph 编排

## 知识点解析

### 概述

Workflow 是 Agent 的控制骨架：它定义节点、状态、分支、并行、循环、终止和失败语义。LangGraph 适合把这些控制关系显式化。D2C 视觉一致性评估场景 采用“已知问题类型走显式专家、未知问题走 ReAct 工具循环”的混合方式，既保留专项检测的稳定性，也保留开放任务的扩展能力。

### 先选编排模式

| 模式 | 适用场景 | 风险 |
| --- | --- | --- |
| 固定链 | 清洗 → 检测 → 输出，顺序稳定 | 变化时需要改图 |
| Routing | 根据问题类型选择专家 | 路由错误会把任务送到错误能力 |
| Parallelization | 多个互相独立的属性并行检测 | 资源争用、结果合并和部分失败 |
| ReAct | 工具选择和参数依赖中间结果 | 循环、幻觉工具和成本失控 |
| Evaluator-Optimizer | 初稿 → 检查 → 修正 | 延迟和重复调用增加 |
| Orchestrator-Workers | 总控拆任务，专家并行处理 | 状态聚合和冲突复杂 |

D2C 的颜色、圆角、尺寸、字号、字重和间距检测可以并行，但它们共享前置的图片和组件匹配结果，因此应把“采集与匹配”作为公共前置节点，再并行执行属性专家。

### D2C 场景的双路径编排

```text
开始
  -> 输入校验与状态收敛
      -> 任务类型明确：进入固定专项流程
      -> 任务类型不明确：进入受限规划
                              -> 选择只读工具或补充信息
                              -> 继续规划或结束
```

固定流程保证确定性检测的可回归性；受限规划负责补充信息、选择允许的能力和组织证据，并遵守输入校验、权限和输出门禁。实现时应通过配置或编排图注入 allowlist 工具，工具发现和模型可调用能力分开管理。
### 状态设计

状态是跨节点共享的事实。一个可用状态至少包含请求标识、任务标识、输入资源、当前阶段、历史事件、工具结果、最终输出、错误状态、配置版本和模型版本。字段必须使用业务中立的结构化协议，减少对某个仓库类名或字段命名的依赖。实践中还应补充阶段耗时、重试次数和证据标识，便于跨服务追踪。

状态字段要区分以下四种情况：

```text
value = None       -> 尚未产生结果
value = []         -> 有效结果为空
success = false    -> 能力执行失败
status = skipped   -> 按策略没有执行
```

如果把这几种状态都压成空列表，下游会把“采集失败”误判成“没有缺陷”。

### 节点设计原则

每个节点只做一类工作，并满足：

- 输入字段明确，缺字段立即失败。
- 输出字段稳定，成功和失败都有结构化结果。
- 副作用集中在边界节点，并有幂等键。
- 记录开始、结束、耗时、版本和关键计数。
- 不在节点内部悄悄改变全局配置或共享请求状态。

典型 D2C 图：

```text
validate_request
  -> prepare_workspace
  -> capture_or_load_resources
  -> normalize_figma_and_lynx
  -> match_components
  -> parallel:
       detect_color
       detect_corner
       detect_size
       detect_spacing
       detect_font_size
       detect_font_weight
  -> merge_results
  -> filter_false_positive
  -> build_report
  -> persist_and_publish
```

### 显式专家和 ReAct 的边界

显式专家适合：

- 问题类型已知。
- 输入字段和检测步骤稳定。
- 结果需要强一致和可回归。
- 有明确配置和阈值。

ReAct 适合：

- 用户只提供自然语言目标。
- 需要先探索可用工具或补充信息。
- 工具顺序由中间结果决定。
- 任务是分析、查询或组合多个能力。

ReAct 应通过显式专家的门禁访问能力。可以让 ReAct 负责选择“调用哪个已注册专家”，内部参数拼装和输入校验继续由专家或工具契约承担。

### 并行与合并

并行节点必须提前定义：

- 哪些输入只读共享。
- 每个分支写入哪个独立字段。
- 一个分支失败是否影响整体。
- 结果合并顺序是否稳定。
- 是否允许部分成功。
- 总体超时时间和取消策略。

D2C 属性检测可以允许部分成功，但“匹配失败”通常应阻断后续属性检测，因为没有可靠对象就没有可靠差异。合并结果时保留每个分支的 `status`、`defects`、`debug` 和 `latency`，并生成可下钻的总结果。

### 循环与终止条件

ReAct 循环至少需要：

- 最大模型轮数。
- 最大工具调用数。
- 单工具超时。
- 总预算和总耗时。
- 重复调用检测。
- 无新证据时的提前终止。

终止条件应该是结构化的，例如“已获得所有必需字段并通过校验”，由状态字段和校验结果共同决定。

### 失败分支

推荐将错误分为：

| 错误 | 是否重试 | 是否继续 |
| --- | --- | --- |
| 参数缺失 | 否 | 请求失败并提示补充 |
| 临时网络失败 | 有限重试 | 当前节点重试 |
| 资源采集失败 | 视接口幂等性 | 通常阻断 |
| 模型超时 | 一次退避重试 | 仍失败则不确定或降级 |
| 业务规则不满足 | 否 | 输出明确不通过 |
| 工具返回空结果 | 通常不重试 | 需要区分“无结果”和“失败” |
| 权限拒绝 | 否 | 进入授权或人工流程 |

### 配置与实例隔离

每个请求都应拥有隔离的配置和状态实例，使不同请求的阈值、模型、Prompt 版本和重试策略互不覆盖。无状态工具可以复用，但不能在共享对象中保存请求级图片、用户身份或可变配置。

## 落地步骤

1. 画出主流程和所有终止状态。
2. 为每个节点定义输入、输出、错误和副作用。
3. 把固定流程先写成显式图，再为必要的开放决策增加 ReAct。
4. 把共享前置结果和并行分支字段分开。
5. 加入超时、预算、最大循环次数和取消逻辑。
6. 对每个分支做成功、空结果、失败和重试测试。
7. 为每次执行记录 state snapshot、节点轨迹、工具调用和版本。
8. 用故障注入验证节点失败、部分成功和恢复行为。

### 编排图的实现原则

编排图面向控制关系，不必暴露具体代码。实现时需要明确：入口校验节点、任务路由节点、固定专项节点、受限规划节点、工具节点、结果合并节点和终止节点。每条边都应定义触发条件、可重试性、超时、取消和输出状态；工具集合通过权限 allowlist 注入。

## 失败与排障

| 现象 | 排查顺序 |
| --- | --- |
| 路由总进入 ReAct | 检查 任务类型 是否规范化、是否被入口丢失 |
| 显式专家找不到 | 检查能力注册、配置版本和可用能力清单 |
| ReAct 无限循环 | 检查 tool_calls、工具结果是否回写、最大轮数和重复参数 |
| 并行结果互相覆盖 | 检查状态 reducer、写入字段和合并节点 |
| 中间失败被吞掉 | 检查 history、错误状态和下游是否把失败重写成 completed |
| 同配置请求互相影响 | 检查全局单例是否持有请求状态，确认实例隔离 |

## 面试应对

### 常考点及考法

- LangGraph 为什么适合 Agent 编排？
- 显式 Workflow 和 ReAct 怎么选？
- 如何处理并行任务和部分失败？
- 如何防止 Agent 无限循环？

### 解法/回答思路

从状态图的节点、边、条件路由和终止条件讲起，再用 D2C 场景的双路径说明：已知问题类型走显式专家，未知目标才走 ReAct。最后补充状态隔离、失败分支和可观测性。

### 易错点

- 把 LangGraph 当作模型本身。
- 只说“有状态”，却说不清哪些字段跨节点传递。
- 并行时只考虑速度，不考虑资源、合并和部分失败。
- 没有循环上限、预算和取消机制。

### 回答模板

可直接回答：

> 我会把 Agent 编排建模成状态图：节点负责单一能力，边负责顺序和条件分支，状态保存输入、资源、工具结果、历史、错误和版本。对于问题类型明确、步骤稳定的任务走显式 Workflow；对于目标开放、需要根据中间结果选择工具的任务使用 ReAct，并设置最大轮数、工具次数、总超时和预算。互相独立的检测可以并行，但要为每个分支定义独立输出和部分失败语义，最后统一合并。每个节点都记录耗时、版本和错误，区分采集失败、空结果和真实无缺陷。
