# AI Coding 与 Spec-First Agent 协作

## 知识点解析

### 概述

AI Coding 是让 Agent 参与软件研发全过程的人机协作方式。它适合需求探索、方案整理、代码生成、测试设计、问题定位和文档沉淀；工程师负责需求、架构、质量和安全的最终判断。本卡片讲通用研发方法、协作边界和验证闭环。

### AI Coding 的正确定位

AI 负责高强度执行，人负责：

- 明确目标、边界和验收标准。
- 判断架构、数据模型和技术取舍。
- 提供最少但足够的上下文。
- 审查变更、运行测试和验证真实行为。
- 对权限、安全、数据和最终交付负责。

Vibe Coding 适合低风险原型和局部探索；复杂任务应升级为 Spec-First，先形成可验收规格，再分阶段实现。

### Spec-First 工作流

```text
需求澄清
  -> 任务规格
  -> 技术方案
  -> 任务拆分
  -> 增量实现
  -> 自动化测试
  -> 运行时验证
  -> 代码审查
  -> 经验沉淀
```

规格文档至少要明确：

- 用户目标和非目标。
- 输入、输出、数据结构和错误语义。
- 功能边界、权限边界和兼容性要求。
- 前后端或多模块的职责划分。
- 验收标准、测试范围和已知限制。
- 灰度、回滚和后续演进方式。

规格的价值是让 Agent 每次修改都有可检查的依据，并把需求、边界和验收标准沉淀成团队可复用资产。

### 上下文准备

给 Agent 的上下文应分为四层：

1. **任务上下文**：当前目标、范围、验收标准和禁止事项。
2. **系统上下文**：模块边界、数据流、依赖关系和运行方式。
3. **变更上下文**：需要修改的模块、已有约束和相邻调用方。
4. **验证上下文**：测试命令、测试数据、预期结果和失败处理。

上下文应围绕当前任务逐步加载。先让 Agent 阅读目录和关键接口，再按任务逐步加载相关模块；修改前重新确认当前文件状态，减少对过期记忆的依赖。

### 增量实现

推荐按垂直切片推进：

1. 先实现最小输入到输出路径。
2. 运行静态检查和单元测试。
3. 接入一个真实调用方或页面交互。
4. 验证错误、超时、空结果和权限边界。
5. 再扩展并发、缓存、监控和兼容逻辑。

每次修改尽量只解决一个问题，保留清晰的变更范围和回归证据。跨模块改动需要先拆分职责和验证路径。

### 测试验证

后端重点验证：

- 正常输入和边界输入。
- 参数缺失、类型错误和空结果。
- 超时、重试、幂等和并发。
- 权限拒绝、敏感数据和错误脱敏。
- 外部依赖不可用时的降级行为。

前端重点验证：

- 页面能否启动和加载。
- 关键交互后的真实 UI 状态。
- 接口请求、错误提示和加载状态。
- 不同屏幕尺寸和异常数据。
- 刷新、返回、重复点击和取消操作。

测试文件生成不等于测试完成。必须真正运行测试，并检查退出码、日志、页面状态和接口结果。

### 存量项目的处理方法

存量系统通常存在隐式约束、历史兼容、跨模块依赖和不完整文档。处理顺序应是：

1. 先做模块和依赖盘点。
2. 找到真实调用链和数据流。
3. 标记不能改变的接口和行为。
4. 为目标变更建立最小回归集。
5. 先做兼容层或局部改动。
6. 用运行时证据确认没有扩大影响面。

如果需求依赖多个模块，应使用多模块工作区，并为每个模块写清规则、启动方式、测试入口和禁止修改区域。

### 经验沉淀

重复失败应沉淀为可复用能力：

- 需求检查清单。
- 接口契约模板。
- 测试验证流程。
- 常见故障处理规则。
- 安全和权限检查项。
- 代码审查清单。

沉淀时记录“触发条件、正确动作、失败信号和验证方式”。经验变更后应补回归样例，防止规则越来越宽或与其他能力冲突。

## 落地步骤

1. 把自然语言需求改写成任务规格和验收标准。
2. 让 Agent 先总结现有系统和风险，不立即修改。
3. 将任务拆成可独立验证的增量步骤。
4. 为每一步定义输入、输出、测试和回滚方式。
5. 让 Agent 小范围实现，立即运行验证。
6. 根据真实错误定位问题，不接受未经验证的解释。
7. 做代码、数据、权限和依赖审查。
8. 保存变更摘要、测试证据和已知限制。
9. 将重复失败沉淀为规则、测试或 Skill。

## 失败与排障

| 现象 | 优先检查 |
| --- | --- |
| Agent 理解错需求 | 目标、非目标、输入输出和验收标准是否明确 |
| 改动范围失控 | 是否限定模块、任务边界和禁止修改区域 |
| 测试看似通过但功能不可用 | 是否运行了真实调用链和运行时验证 |
| 前后端结果不一致 | 接口契约、字段、错误语义和版本是否统一 |
| 修复一个问题引入多个回归 | 是否缺少最小回归集和增量变更 |
| Agent 反复犯同类错误 | 是否把失败原因沉淀为规则和测试 |

## 面试应对

### 常考点及考法

常考 Vibe Coding 的边界、Spec-First、多模块上下文、增量开发、测试验证、代码审查和人类责任。

### 解法/回答思路

先说明 Agent 承担执行加速，工程师承担最终责任，再按需求、规格、实现、验证、审查和沉淀闭环展开。

### 易错点

把自然语言生成当成交付，把测试文件生成当成测试完成，或没有阅读现有系统和运行测试就接受模型修改。

### 回答模板

可直接回答：

> 我会先把需求整理成可验收的规格，明确目标、边界、接口、错误语义、测试和回滚。然后让 Agent 理解现有模块和调用链，再按垂直切片小步实现，每一步都运行自动化测试和真实链路验证。工程师负责架构、权限、安全、代码审查和最终验收。遇到失败时依据日志和测试结果定位，重复问题再沉淀为规则、测试或 Skill，使后续任务更稳定。
