# AI Coding 与 Spec-First Agent 协作

## 知识点解析

### 概述

AI Coding 是让 Agent 参与软件研发全过程的人机协作方式。它适合需求探索、方案整理、代码生成、测试设计、问题定位和文档沉淀；工程师负责需求、架构、质量和安全的最终判断。本卡片讲通用研发方法、协作边界和验证闭环。

### AI Coding 的正确定位

AI 负责高强度执行，人负责：

- 明确目标、边界和验收标准。
- 判断架构、数据模型和技术取舍。
- 提供最少但足够的上下文。
- 审查变更、运行测试和验证真实行为。
- 对权限、安全、数据和最终交付负责。

Vibe Coding 适合低风险原型和局部探索；复杂任务应升级为 Spec-First，先形成可验收规格，再分阶段实现。

### Spec-First 工作流

```text
需求澄清
  -> 任务规格
  -> 技术方案
  -> 任务拆分
  -> 增量实现
  -> 自动化测试
  -> 运行时验证
  -> 代码审查
  -> 经验沉淀
```

规格文档至少要明确：

- 用户目标和非目标。
- 输入、输出、数据结构和错误语义。
- 功能边界、权限边界和兼容性要求。
- 前后端或多模块的职责划分。
- 验收标准、测试范围和已知限制。
- 灰度、回滚和后续演进方式。

规格的价值是让 Agent 每次修改都有可检查的依据，并把需求、边界和验收标准沉淀成团队可复用资产。

### 上下文准备

给 Agent 的上下文应分为四层：

1. **任务上下文**：当前目标、范围、验收标准和禁止事项。
2. **系统上下文**：模块边界、数据流、依赖关系和运行方式。
3. **变更上下文**：需要修改的模块、已有约束和相邻调用方。
4. **验证上下文**：测试命令、测试数据、预期结果和失败处理。

上下文应围绕当前任务逐步加载。先让 Agent 阅读目录和关键接口，再按任务逐步加载相关模块；修改前重新确认当前文件状态，减少对过期记忆的依赖。

### 增量实现

推荐按垂直切片推进：

1. 先实现最小输入到输出路径。
2. 运行静态检查和单元测试。
3. 接入一个真实调用方或页面交互。
4. 验证错误、超时、空结果和权限边界。
5. 再扩展并发、缓存、监控和兼容逻辑。

每次修改尽量只解决一个问题，保留清晰的变更范围和回归证据。跨模块改动需要先拆分职责和验证路径。

### 测试验证

后端重点验证：

- 正常输入和边界输入。
- 参数缺失、类型错误和空结果。
- 超时、重试、幂等和并发。
- 权限拒绝、敏感数据和错误脱敏。
- 外部依赖不可用时的降级行为。

前端重点验证：

- 页面能否启动和加载。
- 关键交互后的真实 UI 状态。
- 接口请求、错误提示和加载状态。
- 不同屏幕尺寸和异常数据。
- 刷新、返回、重复点击和取消操作。

测试文件生成不等于测试完成。必须真正运行测试，并检查退出码、日志、页面状态和接口结果。

### 存量项目的处理方法

存量系统通常存在隐式约束、历史兼容、跨模块依赖和不完整文档。处理顺序应是：

1. 先做模块和依赖盘点。
2. 找到真实调用链和数据流。
3. 标记不能改变的接口和行为。
4. 为目标变更建立最小回归集。
5. 先做兼容层或局部改动。
6. 用运行时证据确认没有扩大影响面。

如果需求依赖多个模块，应使用多模块工作区，并为每个模块写清规则、启动方式、测试入口和禁止修改区域。

### 经验沉淀

重复失败应沉淀为可复用能力：

- 需求检查清单。
- 接口契约模板。
- 测试验证流程。
- 常见故障处理规则。
- 安全和权限检查项。
- 代码审查清单。

沉淀时记录“触发条件、正确动作、失败信号和验证方式”。经验变更后应补回归样例，防止规则越来越宽或与其他能力冲突。

## 落地步骤

1. 把自然语言需求改写成任务规格和验收标准。
2. 让 Agent 先总结现有系统和风险，不立即修改。
3. 将任务拆成可独立验证的增量步骤。
4. 为每一步定义输入、输出、测试和回滚方式。
5. 让 Agent 小范围实现，立即运行验证。
6. 根据真实错误定位问题，不接受未经验证的解释。
7. 做代码、数据、权限和依赖审查。
8. 保存变更摘要、测试证据和已知限制。
9. 将重复失败沉淀为规则、测试或 Skill。

## 失败与排障

| 现象 | 优先检查 |
| --- | --- |
| Agent 理解错需求 | 目标、非目标、输入输出和验收标准是否明确 |
| 改动范围失控 | 是否限定模块、任务边界和禁止修改区域 |
| 测试看似通过但功能不可用 | 是否运行了真实调用链和运行时验证 |
| 前后端结果不一致 | 接口契约、字段、错误语义和版本是否统一 |
| 修复一个问题引入多个回归 | 是否缺少最小回归集和增量变更 |
| Agent 反复犯同类错误 | 是否把失败原因沉淀为规则和测试 |

## 面试应对

### Vibe Coding 和 Spec-First 分别适合什么场景？

回答思路：先按任务风险和复杂度划分适用场景，再说明从 Vibe Coding 升级到 Spec-First 的判断标准。

回答模板：

Vibe Coding 更适合低风险原型和局部探索，重点是快速验证方向；当任务涉及多个模块、接口兼容、权限、安全或明确交付责任时，我会切换到 Spec-First。Spec 至少要写清目标与非目标、输入输出、模块边界、错误语义、验收标准、测试范围和回滚方式，让 Agent 的每次修改都有可检查的依据。两者不是对立关系，而是根据风险选择协作粒度。

### 如何让 Agent 理解一个存量项目后再修改？

回答思路：按任务、系统、变更和验证四层准备上下文，强调先理解真实调用链和隐式约束，再限定改动范围。

回答模板：

我会先给 Agent 明确当前任务的目标、范围、验收标准和禁止事项，再让它阅读目录、关键接口、真实调用链和数据流，识别不能改变的兼容行为。随后只加载目标模块及相邻调用方，提供启动方式、测试入口和预期结果。修改前还要重新确认文件状态，避免依赖过期上下文；如果跨多个模块，我会分别写清各模块职责和禁止修改区域。

### AI Coding 为什么要采用增量开发？

回答思路：说明垂直切片如何缩小变更范围、快速暴露问题，并给出从最小链路到异常场景的推进顺序。

回答模板：

我会按可独立验证的垂直切片推进，先打通最小输入到输出路径，立即运行静态检查和单元测试，再接入一个真实调用方。之后逐步补充空结果、超时、权限和并发等异常场景，最后再扩展缓存、监控和兼容逻辑。每一步只解决一个问题并保留回归证据，这样出现失败时能快速定位，也能避免一次大改把多个风险混在一起。

### 如何判断 Agent 生成的代码可以交付？

回答思路：区分“生成了代码或测试”与“完成验证”，从自动化测试、真实链路、代码审查和责任边界回答。

回答模板：

代码生成只是实现开始，不代表已经交付。我会真正运行测试并检查退出码、日志、接口结果和页面状态，同时覆盖正常输入、边界输入、空结果、超时、重试、幂等、并发、权限和降级行为。随后审查架构、数据、依赖和安全边界，并在真实调用链上验收。工程师对最终结果负责；重复出现的问题再沉淀为规则、测试或 Skill，形成可复用的质量闭环。
