# 可靠性、性能、成本与可观测性

## 知识点解析

### 概述

Agent 的可靠性来自“每一步都可观察、可重试、可取消、可恢复”。D2C 任务同时包含图片下载、设备采集、结构树上传、组件检测、多个属性专家、VLM 过滤和报告写盘，任何一层变慢或返回空值都可能造成级联失败。本卡片把重试、超时、并发、幂等、缓存、资源回收、观测和容量统一起来。

### 可靠性预算

先给一次请求分配总预算：

$$
\begin{aligned}
\mathrm{total\_deadline}
  &= \mathrm{input\_validation} \\
  &+ \mathrm{resource\_prepare} \\
  &+ \mathrm{external\_calls} \\
  &+ \mathrm{model\_calls} \\
  &+ \mathrm{report\_persist} \\
  &+ \mathrm{safety\_margin}
\end{aligned}
$$

每个节点要有自己的 deadline，子调用不能无限占用父请求。达到总 deadline 后，停止新增工作，取消可取消任务，保留已完成结果并返回 `TIMEOUT` 或 `PARTIAL`，不能继续后台偷偷执行副作用。

### 重试策略

只有临时错误才重试：网络抖动、服务未就绪、短期限流和明确可重试的 5xx。参数错误、认证失败、权限拒绝、资源不存在和业务规则不满足不应盲目重试。

推荐使用指数退避和抖动：

$$
\mathrm{sleep} = \min(\mathrm{max\_delay}, \mathrm{base} \times 2^{\mathrm{attempt}}) + \mathrm{random\_jitter}
$$

重试必须记录：原错误、attempt、等待时间、是否改变输入、最终结果和幂等键。VLM 同步接口没有队列时，超时或报告缺失最多退避重试一次；更多重试通常只会放大拥塞和成本。

### 幂等

幂等键应由业务实体和版本组成，例如：

$$
\mathrm{idempotency\_key}
= \operatorname{hash}(\mathrm{case\_id}, \mathrm{input\_version}, \mathrm{model\_version}, \mathrm{prompt\_version}, \mathrm{config\_version})
$$

可重试操作必须先判断：

- 是否已经产生成功结果。
- 是否已经创建外部任务。
- 是否可以安全覆盖临时文件。
- 是否已经写入 结果数据集平台、评测集或通知系统。

读操作天然更容易重试；写操作必须用服务端幂等键或状态机保护。不要因为“模型超时”就再次触发不可撤销的外部动作。

### 并发与背压

并发需要按资源瓶颈分层设计。瓶颈可能在 CPU 图像处理、设备连接、模型服务、文件带宽或外部 API 限额。为每类资源分别设置 semaphore、队列长度和超时：

```text
请求入口 -> admission control -> 有界队列
           -> 下载并发池
           -> 模型并发池
           -> 写盘/上传并发池
```

外部视觉服务可能存在并发上限或没有排队能力，应从低并发开始压测，逐步观察 P95/P99、超时率和报告缺失率。资源下载、设备采集和模型调用应分别限流。

### 缓存

适合缓存：

- 版本化 Prompt。
- 按问题类型建立的 few-shot knowledge handle。
- 不可变的图片下载结果和结构树解析结果。
- 组件检测和标准化结果。
- 相同输入版本下的确定性规则结果。

不应盲目缓存：

- 依赖实时设备状态的截图。
- 有权限差异的外部资源。
- 会随业务数据变化的任务状态。
- 尚未验证的模型输出。

缓存键要包含输入、版本、配置和权限范围；缓存命中要记录命中版本。资源缓存必须有容量、TTL、校验和回收策略。

### 资源生命周期

一次多模态请求的资源生命周期：

```text
创建 request workspace
  -> 下载或接收资源
  -> 生成中间文件
  -> 执行检测和报告
  -> 持久化必要证据
  -> 删除临时资源
```

系统应统一管理资源创建、临时文件清理和长期证据归档，异常分支也必须执行清理；不能把用户路径、临时目录和共享缓存混用。

### 可观测性三件套

#### Logs

日志记录事件和错误上下文：`request_id`、`task_id`、stage、tool、attempt、status、latency、版本和资源计数。日志要结构化，敏感参数做摘要或哈希。

#### Metrics

至少记录：

- 请求量、成功率、失败率、部分成功率和取消率。
- 各阶段 P50/P95/P99 延迟。
- 工具调用次数、错误码、重试次数和超时率。
- 模型 token、图片大小、调用成本和并发占用。
- 组件数量、匹配数量、缺陷数量和过滤数量。
- 评测指标、人工复核率和结果回写成功率。

#### Traces

Trace 把入口、Workflow 节点、模型请求、工具、检索、外部 API 和报告写盘串起来。每个 span 带版本、输入摘要、输出摘要和 artifact ID，便于定位首次偏离点。

### 结果与证据可观测

D2C 的监控需要覆盖“任务成功”和关键过程指标：

- Figma/Lynx 组件数差异。
- 原始匹配对数与过滤后匹配对数。
- 各属性检测的候选数、缺陷数和空结果数。
- VLM 报告 7 项字段完整率和分数方差。
- 生成 JSON/HTML 的成功率。
- 研发/设计可用率与人工复核率。

这些指标能判断业务效果提升来自真实质量改进、数据分布变化还是前置链路变化。

### 性能优化顺序

1. 先消除重复下载、重复解析和重复初始化。
2. 对互不依赖的 CPU 检测做并行。
3. 限制模型输入图片尺寸和候选数量，但保留证据可追溯。
4. 将长任务拆成异步任务和可查询状态。
5. 使用批量 API 或共享缓存降低连接开销。
6. 最后再调整模型、并发和硬件规格。

### 成本估算

一次任务成本可以拆成：

$$
\begin{aligned}
\mathrm{cost}
  &= \mathrm{model\_tokens}\times\mathrm{token\_unit\_price} \\
  &+ \mathrm{image\_input\_units}\times\mathrm{image\_unit\_price} \\
  &+ \mathrm{external\_api\_calls}\times\mathrm{api\_unit\_price} \\
  &+ \mathrm{device\_minutes}\times\mathrm{device\_minute\_price} \\
  &+ \mathrm{cpu\_time}\times\mathrm{cpu\_time\_price} \\
  &+ \mathrm{storage\_bytes}\times\mathrm{storage\_unit\_price} \\
  &+ \mathrm{human\_review\_minutes}\times\mathrm{review\_minute\_price}
\end{aligned}
$$

token、调用次数、分钟和字节等不同量纲不能直接相加；必须先按各自用量乘以对应单价，统一为货币单位后再求和。

每种错误的重试成本、长图 token 成本和人工复核成本都应计入。成本优化应来自减少无效调用、复用确定性结果、控制输入规模和改进调度。

### 降级策略

按影响从低到高设计降级：

1. 复用已验证的结构化结果。
2. 跳过非关键 VLM 解释，仅输出规则结果。
3. 用轻量模型或规则替代高成本模型。
4. 输出 `PARTIAL` 并列出缺失阶段。
5. 高风险场景转人工，不自动发布。

降级结果必须带 `degraded=true`、原因和缺失证据，并和完整成功使用不同状态。

## 落地步骤

1. 为入口和每个节点定义 deadline、重试分类和取消行为。
2. 给所有可重试动作设计幂等键和状态机。
3. 为下载、设备、模型、上传和写回分别设并发上限。
4. 建立统一日志、指标、Trace 和 artifact ID。
5. 增加重复请求、超时、断连、限流、部分失败和磁盘不足测试。
6. 做基线压测，记录吞吐、P95、P99、错误率和成本。
7. 依据瓶颈逐层优化，避免把并发直接调到最大。
8. 发布前验证降级、取消、清理和回滚。

### 推荐状态机

```text
PENDING
  -> PREPARING
  -> RUNNING
  -> PARTIAL | SUCCEEDED
  -> FAILED | CANCELLED | TIMEOUT
```

状态迁移必须幂等；终态不能被迟到的重试结果覆盖。任务查询接口要能返回当前 stage、进度、最近错误、可重试性和产物位置。

## 失败与排障

| 现象 | 优先检查 |
| --- | --- |
| 延迟偶发飙升 | 哪个 span 变慢、队列等待、并发占用和上游 P99 |
| 重试越多越慢 | 是否重试不可重试错误、没有退避或没有并发上限 |
| 机器磁盘持续增长 | workspace 清理、artifact TTL、缓存和异常退出路径 |
| QPS 上升但成功率下降 | 模型限流、设备容量、队列、线程池和外部 API 配额 |
| 结果无法复现 | 输入/版本/缓存命中/随机性/外部状态是否记录 |
| 只有失败没有原因 | stage、错误码、trace、原始响应和证据是否丢失 |

## 面试应对

### Agent 系统如何设计重试和幂等？

回答思路：先按错误类型判断是否重试，再说明退避策略、幂等键和服务端状态机如何避免重复副作用。

回答模板：

我只对网络抖动、服务未就绪、短期限流和明确可重试的 5xx 做有限重试，参数错误、认证失败、权限拒绝和资源不存在不会盲目重试。重试采用指数退避和抖动，并记录原错误、次数、等待时间和最终结果。所有可重试操作都使用由 case、输入、模型、Prompt 和配置版本组成的幂等键；涉及创建任务或写回时，还要由服务端状态机阻止重复副作用，终态不能被迟到结果覆盖。

### 如何限制 Agent 的成本和并发？

回答思路：从总预算、有界队列、分资源限流、缓存和输入裁剪逐层回答，强调用压测数据调整。

回答模板：

我会先给请求设置总 deadline 和成本预算，再为下载、设备采集、模型调用和写盘分别设置 semaphore、队列长度和超时，因为它们的瓶颈不同。VLM 没有排队能力时从很小的在途数开始压测，观察 P95、P99、超时率和报告缺失率后逐步调整。成本优化优先消除重复下载、解析和初始化，复用版本化的确定性结果，并限制图片尺寸和候选数量。缓存键必须包含输入、版本、配置和权限范围，不能用缓存掩盖实时状态变化。

### 线上 Agent 需要观测哪些指标？

回答思路：按日志、指标和 Trace 三层展开，并补充 D2C 的过程指标与业务指标。

回答模板：

日志要记录 request_id、task_id、stage、tool、attempt、status、latency、版本和资源计数；指标要覆盖请求量、成功率、部分成功率、取消率、各阶段 P50/P95/P99、工具错误、重试、超时、token、成本和并发占用；Trace 要串起入口、Workflow、模型、工具、检索、外部 API 和报告写盘。D2C 还要观察组件数、匹配数、各属性候选与缺陷数、VLM 七项字段完整率、分数方差、报告生成率和人工复核率，这样才能定位首次偏离点。

### 长任务如何处理超时和部分成功？

回答思路：从分层 deadline、停止新增工作、取消传播、状态机和显式降级说明完整处理方式。

回答模板：

我会把总 deadline 分配到输入校验、资源准备、外部调用、模型调用和结果持久化，每个子调用不能无限占用父请求。达到总时限后停止新增工作，取消可取消任务并保留已经完成的结果。状态机明确区分 TIMEOUT、PARTIAL、FAILED 和 CANCELLED；如果允许部分成功，就返回缺失阶段、已有证据以及 degraded=true，不能伪装成完整成功。长任务采用异步方式，支持查询、取消和幂等重试，异常路径也要清理临时资源。
