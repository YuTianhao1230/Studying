# 评测、Harness 与 GT 回流

## 知识点解析

### 概述

Agent 评测要同时回答最终答案、路由、工具参数、证据充分性、失败恢复、成本延迟和 bad case 归因。评测 Harness 是把数据、运行、轨迹、解析、打分、并发、断点续跑、归因和版本比较固定下来的工程脚手架。D2C 视觉评估场景的离线评测思路是先拉取 GT 和线上结果，冻结本地快照，运行归因，再生成 GT vNext 和复评；正式写回平台前需要显式确认。

### 评测对象分层

| 层级 | 评测问题 |
| --- | --- |
| 输入 | case 是否完整、状态是否可比、资源是否可访问 |
| 路由 | 是否选择正确 Skill、Workflow、专家或工具 |
| 执行 | 工具参数、调用顺序、循环和权限是否正确 |
| 判定 | 缺陷识别、过滤、证据和结构化输出是否正确 |
| 系统 | 延迟、成本、失败率、并发、恢复和资源使用 |
| 业务 | 首次出图率、研发可用率、设计可用率、门禁通过率 |

### Dataset 设计

一个好的 case 是可复现的任务包：

```json
{
  "case_id": "d2c-001",
  "input": {
    "figma_node_id": "31:42",
    "design_image": "...",
    "impl_image": "...",
    "lynx_tree": "..."
  },
  "gt": {
    "status": "defect",
    "defect_type": "component_size",
    "pairs": [],
    "reason": "宽度差异超过阈值"
  },
  "metadata": {
    "page_type": "dialog",
    "difficulty": "medium",
    "labels": ["text", "button"],
    "input_version": "v3"
  }
}
```

case 应覆盖：

- 正例、负例和边界阈值。
- 简单局部组件、完整页面和二维网格。
- 重复组件、父子组件和跨状态内容变化。
- 文案、数字、图标、颜色、布局和字体差异。
- 采集失败、权限拒绝、结构树损坏、模型超时和空结果。
- 真实分布中的长尾页面，而不只是容易样本。

### Ground Truth 设计

GT 要区分：

- 真实缺陷。
- 正常差异，例如业务数据变化或可接受字体渲染差异。
- 无法判断，需要人工复核。
- 输入无效或采集失败。
- 标注不确定或存在多个合理答案。

GT 更新时保留原始标注。建立 `v1 -> v2` 版本差异，记录变更原因、标注人、证据和影响的 case。D2C 视觉评估场景的评测流程把原数据视为只读，归因后生成 GT vNext，再用固定输入复评，保证分数变化来自可解释修复。

### Harness 的运行阶段

```text
准备输入
  -> 冻结 manifest 和资源快照
  -> 运行 Agent / Workflow
  -> 保存原始 response 和 trajectory
  -> 解析结构化结果
  -> 计算 case 与 aggregate 指标
  -> 生成差异和 bad case 报告
  -> 人工归因
  -> 生成 GT vNext 或修复配置
  -> 在同一快照上复评
```

每个阶段都应支持断点续跑。结果目录可以按 `run_id/case_id/stage` 组织，保存输入摘要、版本、耗时、错误和产物路径。

### 轨迹记录

至少记录：

- 请求和任务 ID。
- Skill、Prompt、模型、代码和配置版本。
- 状态变化和节点开始/结束时间。
- 每次模型请求、工具名、参数摘要和返回状态。
- 检索命中的知识 ID 和版本。
- 图片/结构树/报告的 artifact ID。
- 重试次数、超时、取消和人工确认。
- 最终输出、GT、分数和归因标签。

敏感数据进入轨迹前要做脱敏；参数可以保留 schema、哈希和安全摘要。

### 指标设计

#### 分类指标

$$
\begin{aligned}
\mathrm{precision} &= \frac{TP}{TP + FP} \\
\mathrm{recall} &= \frac{TP}{TP + FN} \\
F_1 &= \frac{2 \times \mathrm{precision} \times \mathrm{recall}}{\mathrm{precision} + \mathrm{recall}}
\end{aligned}
$$

D2C 需要分别计算缺陷发现、缺陷类型、组件匹配和严重级别，并支持页面级与组件级下钻。

#### Agent 指标

- Task Success：最终任务是否达到业务完成条件。
- Tool Accuracy：工具选择和参数是否正确。
- Route Accuracy：是否进入正确能力路径。
- Evidence Completeness：是否保留足够证据。
- Recovery Rate：可恢复错误是否成功恢复。
- Safety Violation：越权、危险动作和未确认写操作。
- Latency、Cost、Token 和外部调用次数。

#### 业务可用指标

在 28 case 的案例分析中，首次出图率、研发可用率和设计师可用率的变化比单一 VLM 分数更能说明系统价值。指标必须能下钻到 case、阶段、缺陷、工具和模型版本。

### VLM 评测

VLM 评分应固定模型、Prompt、图像尺寸和评分 rubric，收集多次成功 run，计算 mean、std 和 range。长耗时请求应设置总超时和有界并发，超时或报告缺失只做有限的带退避重试。

报告验收分三层：

1. HTTP 2xx。
2. 业务 `ok` 和 `reportValidation` 通过。
3. 7 个子结果完整，布局 4 项、文本 3 项，分数范围为 0 到 4。

VLM 更适合提供语义解释、文本缺失和整体视觉判断；精确尺寸、圆角、颜色和间距应由 checker 提供证据。

### Bad case 归因树

```text
结果错误
  -> 输入无效？
  -> 采集或权限失败？
  -> 标准化/单位错误？
  -> 组件匹配错误？
  -> 确定性规则错误？
  -> VLM 过滤错误？
  -> 输出解析或回写错误？
  -> 评测 GT 或指标口径错误？
```

归因结果应直接映射到修复动作：

| 归因 | 常见修复 |
| --- | --- |
| 输入 | 采集 gate、字段 schema、设备状态等待 |
| 匹配 | 语义角色、层级特征、几何阈值和一对一约束 |
| 规则 | 阈值、单位、采样区域和边界条件 |
| Prompt/Skill | 约束、示例、输出格式和路由描述 |
| 工具 | schema、错误码、超时、幂等和权限 |
| 模型 | 模型版本、温度、输入裁剪和降级策略 |
| GT | 标注定义、版本和人工复核 |

### 发布和写回控制

评测工具可以读数据、生成本地报告和提出 GT vNext；写回正式 结果数据集平台、发布结果或回写 结果回写 属于外部副作用，必须在执行前展示计划并显式确认。使用 `用户身份参数` 或机器人身份时，要明确两者看到的资源、拥有的写权限和审计主体不同。

## 落地步骤

1. 设计 case schema、GT schema 和版本字段。
2. 先收集真实分布、边界、失败和安全样本。
3. 冻结输入快照、资源 checksum、代码/模型/Prompt 版本。
4. 运行 Agent 并保存完整但脱敏的轨迹。
5. 解析结果，计算分类、路由、工具、业务、成本和可靠性指标。
6. 生成 case 级差异报告，并保留平均分、分桶指标和失败样本下钻。
7. 对 bad case 做唯一主因归类，避免一个问题重复计数。
8. 修改 Skill、工具、规则、数据或模型后固定快照复评。
9. 生成 GT vNext，并在正式写回前请求确认。
10. 发布后继续采样线上长尾和人工复核结果。

### Harness 最小目录

```text
runs/
├── run_id/
│   ├── 任务清单
│   ├── 运行配置
│   ├── cases/
│   │   └── case_id/
│   │       ├── input.json
│   │       ├── 执行轨迹
│   │       ├── 原始响应
│   │       ├── 解析结果
│   │       └── artifacts/
│   ├── metrics.json
│   └── report.html
└── gt/
    ├── GT 版本数据
    └── GT 版本数据
```

## 失败与排障

| 现象 | 排查重点 |
| --- | --- |
| 指标突然提升 | 输入集是否变小、GT 是否被修改、失败 case 是否被过滤 |
| 平均分提升但用户不满意 | 长尾、严重缺陷、可用率和 case 下钻 |
| 同一 case 多次结果不同 | 模型/Prompt/输入版本、随机性和服务重试 |
| 评测无法复现 | 未冻结资源、版本和外部状态 |
| 结果不能写回 | 身份、scope、资源权限和确认流程 |
| bad case 越改越多 | 归因标签混乱、修复没有单变量回归 |

## 面试应对

### Agent Eval 和普通 LLM Eval 有什么区别？

回答思路：从评测对象说明差异，强调 Agent 不仅要看最终答案，还要检查路由、工具、状态、恢复和安全。

回答模板：

普通 LLM Eval 往往重点评估单次输入输出质量，Agent Eval 还要覆盖整个执行过程。除了最终任务是否完成，我会检查是否进入正确 Skill 或 Workflow、工具选择和参数是否正确、证据是否充分、状态迁移和失败恢复是否合理，以及是否发生越权或未确认写操作。同时记录延迟、成本、token 和外部调用次数。最终答案正确不代表过程正确，例如模型可能用了错误工具或偶然得到答案。

### 如何设计一个 Agent Harness？

回答思路：按冻结数据、运行、轨迹、解析、分层打分、归因、复评和断点续跑说明完整流水线。

回答模板：

我会先定义 case 和 GT schema，覆盖正常、边界、失败、安全和真实长尾样本，再冻结 manifest、资源 checksum 以及代码、模型、Prompt 和配置版本。Harness 负责运行 Agent，保存原始 response、状态变化、工具调用、检索命中、重试和产物，再解析结构化结果并计算 case 级与聚合指标。每个阶段支持按 run_id、case_id 和 stage 断点续跑，报告既展示平均结果，也能下钻到具体 case。修复后必须在同一快照上复评。

### 如何判断 bad case 应该修 Prompt 还是修工具？

回答思路：沿轨迹找首次偏离点，根据错误层级映射修复位置，避免把所有问题都归因给模型。

回答模板：

我会先冻结 bad case 的输入和所有版本，再沿轨迹寻找首次偏离点。输入不完整就修采集 gate 或 schema，单位和匹配错误就修标准化与算法，工具参数、错误码、超时或权限不正确就修工具契约，路由和步骤遗漏才修 Skill 或 Workflow。只有工具已经返回正确证据，但模型没有遵循判断要求或输出格式时，才考虑修改 Prompt；如果在相同输入下仍是模型能力边界，再评估模型版本、裁剪或降级策略。每个 case 只标一个主因，修复后做单变量回归。

### 如何避免评测集泄漏和指标虚高？

回答思路：从数据版本、只读原始 GT、固定快照、分层指标、case 下钻和正式写回审批回答。

回答模板：

我会把原始 GT 设为只读，任何标注修订都生成带原因、证据和标注人的 GT vNext，不能覆盖旧版本。新旧方案必须在同一输入快照、case 过滤条件和版本组合上比较，并检查是否删除了失败样本、改变了标注或只保留容易 case。除平均分外，还要看分桶指标、长尾、失败率和 case-level diff，区分修复、新增错误和共同错误。正式写回结果数据集平台或发布评测结果前，需要展示计划并经过授权和确认。
