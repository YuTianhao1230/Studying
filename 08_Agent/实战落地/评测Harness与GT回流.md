# 评测、Harness 与 GT 回流

## 知识点解析

### 概述

Agent 评测要同时回答最终答案、路由、工具参数、证据充分性、失败恢复、成本延迟和 bad case 归因。评测 Harness 是把数据、运行、轨迹、解析、打分、并发、断点续跑、归因和版本比较固定下来的工程脚手架。D2C 视觉评估场景的离线评测思路是先拉取 GT 和线上结果，冻结本地快照，运行归因，再生成 GT vNext 和复评；正式写回平台前需要显式确认。

### 评测对象分层

| 层级 | 评测问题 |
| --- | --- |
| 输入 | case 是否完整、状态是否可比、资源是否可访问 |
| 路由 | 是否选择正确 Skill、Workflow、专家或工具 |
| 执行 | 工具参数、调用顺序、循环和权限是否正确 |
| 判定 | 缺陷识别、过滤、证据和结构化输出是否正确 |
| 系统 | 延迟、成本、失败率、并发、恢复和资源使用 |
| 业务 | 首次出图率、研发可用率、设计可用率、门禁通过率 |

### Dataset 设计

一个好的 case 是可复现的任务包：

```json
{
  "case_id": "d2c-001",
  "input": {
    "figma_node_id": "31:42",
    "design_image": "...",
    "impl_image": "...",
    "lynx_tree": "..."
  },
  "gt": {
    "status": "defect",
    "defect_type": "component_size",
    "pairs": [],
    "reason": "宽度差异超过阈值"
  },
  "metadata": {
    "page_type": "dialog",
    "difficulty": "medium",
    "labels": ["text", "button"],
    "input_version": "v3"
  }
}
```

case 应覆盖：

- 正例、负例和边界阈值。
- 简单局部组件、完整页面和二维网格。
- 重复组件、父子组件和跨状态内容变化。
- 文案、数字、图标、颜色、布局和字体差异。
- 采集失败、权限拒绝、结构树损坏、模型超时和空结果。
- 真实分布中的长尾页面，而不只是容易样本。

### Ground Truth 设计

GT 要区分：

- 真实缺陷。
- 正常差异，例如业务数据变化或可接受字体渲染差异。
- 无法判断，需要人工复核。
- 输入无效或采集失败。
- 标注不确定或存在多个合理答案。

GT 更新时保留原始标注。建立 `v1 -> v2` 版本差异，记录变更原因、标注人、证据和影响的 case。D2C 视觉评估场景的评测流程把原数据视为只读，归因后生成 GT vNext，再用固定输入复评，保证分数变化来自可解释修复。

### Harness 的运行阶段

```text
准备输入
  -> 冻结 manifest 和资源快照
  -> 运行 Agent / Workflow
  -> 保存原始 response 和 trajectory
  -> 解析结构化结果
  -> 计算 case 与 aggregate 指标
  -> 生成差异和 bad case 报告
  -> 人工归因
  -> 生成 GT vNext 或修复配置
  -> 在同一快照上复评
```

每个阶段都应支持断点续跑。结果目录可以按 `run_id/case_id/stage` 组织，保存输入摘要、版本、耗时、错误和产物路径。

### 轨迹记录

至少记录：

- 请求和任务 ID。
- Skill、Prompt、模型、代码和配置版本。
- 状态变化和节点开始/结束时间。
- 每次模型请求、工具名、参数摘要和返回状态。
- 检索命中的知识 ID 和版本。
- 图片/结构树/报告的 artifact ID。
- 重试次数、超时、取消和人工确认。
- 最终输出、GT、分数和归因标签。

敏感数据进入轨迹前要做脱敏；参数可以保留 schema、哈希和安全摘要。

### 指标设计

#### 分类指标

```text
precision = TP / (TP + FP)
recall    = TP / (TP + FN)
F1        = 2 * precision * recall / (precision + recall)
```

D2C 需要分别计算缺陷发现、缺陷类型、组件匹配和严重级别，并支持页面级与组件级下钻。

#### Agent 指标

- Task Success：最终任务是否达到业务完成条件。
- Tool Accuracy：工具选择和参数是否正确。
- Route Accuracy：是否进入正确能力路径。
- Evidence Completeness：是否保留足够证据。
- Recovery Rate：可恢复错误是否成功恢复。
- Safety Violation：越权、危险动作和未确认写操作。
- Latency、Cost、Token 和外部调用次数。

#### 业务可用指标

在 28 case 的案例分析中，首次出图率、研发可用率和设计师可用率的变化比单一 VLM 分数更能说明系统价值。指标必须能下钻到 case、阶段、缺陷、工具和模型版本。

### VLM 评测

VLM 评分应固定模型、Prompt、图像尺寸和评分 rubric，收集多次成功 run，计算 mean、std 和 range。长耗时请求应设置总超时和有界并发，超时或报告缺失只做有限的带退避重试。

报告验收分三层：

1. HTTP 2xx。
2. 业务 `ok` 和 `reportValidation` 通过。
3. 7 个子结果完整，布局 4 项、文本 3 项，分数范围为 0 到 4。

VLM 更适合提供语义解释、文本缺失和整体视觉判断；精确尺寸、圆角、颜色和间距应由 checker 提供证据。

### Bad case 归因树

```text
结果错误
  -> 输入无效？
  -> 采集或权限失败？
  -> 标准化/单位错误？
  -> 组件匹配错误？
  -> 确定性规则错误？
  -> VLM 过滤错误？
  -> 输出解析或回写错误？
  -> 评测 GT 或指标口径错误？
```

归因结果应直接映射到修复动作：

| 归因 | 常见修复 |
| --- | --- |
| 输入 | 采集 gate、字段 schema、设备状态等待 |
| 匹配 | 语义角色、层级特征、几何阈值和一对一约束 |
| 规则 | 阈值、单位、采样区域和边界条件 |
| Prompt/Skill | 约束、示例、输出格式和路由描述 |
| 工具 | schema、错误码、超时、幂等和权限 |
| 模型 | 模型版本、温度、输入裁剪和降级策略 |
| GT | 标注定义、版本和人工复核 |

### 发布和写回控制

评测工具可以读数据、生成本地报告和提出 GT vNext；写回正式 结果数据集平台、发布结果或回写 结果回写 属于外部副作用，必须在执行前展示计划并显式确认。使用 `用户身份参数` 或机器人身份时，要明确两者看到的资源、拥有的写权限和审计主体不同。

## 落地步骤

1. 设计 case schema、GT schema 和版本字段。
2. 先收集真实分布、边界、失败和安全样本。
3. 冻结输入快照、资源 checksum、代码/模型/Prompt 版本。
4. 运行 Agent 并保存完整但脱敏的轨迹。
5. 解析结果，计算分类、路由、工具、业务、成本和可靠性指标。
6. 生成 case 级差异报告，并保留平均分、分桶指标和失败样本下钻。
7. 对 bad case 做唯一主因归类，避免一个问题重复计数。
8. 修改 Skill、工具、规则、数据或模型后固定快照复评。
9. 生成 GT vNext，并在正式写回前请求确认。
10. 发布后继续采样线上长尾和人工复核结果。

### Harness 最小目录

```text
runs/
├── run_id/
│   ├── 任务清单
│   ├── 运行配置
│   ├── cases/
│   │   └── case_id/
│   │       ├── input.json
│   │       ├── 执行轨迹
│   │       ├── 原始响应
│   │       ├── 解析结果
│   │       └── artifacts/
│   ├── metrics.json
│   └── report.html
└── gt/
    ├── GT 版本数据
    └── GT 版本数据
```

## 失败与排障

| 现象 | 排查重点 |
| --- | --- |
| 指标突然提升 | 输入集是否变小、GT 是否被修改、失败 case 是否被过滤 |
| 平均分提升但用户不满意 | 长尾、严重缺陷、可用率和 case 下钻 |
| 同一 case 多次结果不同 | 模型/Prompt/输入版本、随机性和服务重试 |
| 评测无法复现 | 未冻结资源、版本和外部状态 |
| 结果不能写回 | 身份、scope、资源权限和确认流程 |
| bad case 越改越多 | 归因标签混乱、修复没有单变量回归 |

## 面试应对

### 常考点及考法

- Agent Eval 和普通 LLM Eval 有什么区别？
- 如何设计一个 Agent Harness？
- 如何判断 bad case 应该修 Prompt 还是修工具？
- 如何避免评测集泄漏和指标虚高？

### 解法/回答思路

按“数据冻结、运行轨迹、分层指标、归因、回归和写回治理”回答。强调最终答案正确不代表工具调用、权限和恢复行为正确。

### 易错点

- 只看平均分或一次运行结果。
- 不保存原始 response 和轨迹。
- 修改 GT 后直接宣称模型变好。
- 将所有错误都归因给模型。

### 回答模板

可直接回答：

> 我会把评测做成 Harness。先冻结 case、资源、GT、代码、模型、Prompt 和配置版本，再运行 Agent 并记录路由、状态变化、工具调用、检索命中、重试和输出。指标分成任务成功、路由和工具正确率、组件/缺陷的 precision、recall、F1、证据完整性、安全违规、延迟和成本，并且支持下钻到具体 case。bad case 再按输入、采集、匹配、规则、Prompt、工具、模型、输出和 GT 归因。原始 GT 只读，修复后生成 GT vNext，在同一快照上复评；涉及正式 结果数据集平台 或评测结果写回时，必须明确展示计划并经过授权和确认。
