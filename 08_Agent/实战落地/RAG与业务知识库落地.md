# RAG 与业务知识库落地

## 知识点解析

### 概述

RAG 落地的重点是把当前任务需要的事实、规则、样例和证据以可控方式取出并注入上下文。真实 Agent 通常同时使用结构化查表、few-shot 记忆、关键词检索、向量检索和多轮 Agentic RAG。D2C 检测优先按 `任务类型` 加载样例数据与系统 Prompt，并通过缓存复用知识；按任务隔离的轻量知识库更利于稳定控制上下文。

### 先判断知识类型

| 知识 | 例子 | 推荐存储和读取 |
| --- | --- | --- |
| 业务规则 | 颜色、圆角、字号和字重阈值 | 版本化配置或代码，运行时显式注入 |
| 字段协议 | Figma/Lynx 节点字段、错误码 | 结构化 schema 和文档检索 |
| 正反样例 | 缺陷图、标签和原因 | JSONL、case store 或 few-shot memory |
| 长文资料 | 采集手册、排障手册 | 分块检索，按阶段加载 |
| 当前事实 | 某任务状态、某节点结果 | API/数据库实时查询，不能用旧向量替代 |
| 历史经验 | 某类 bad case 修复方式 | 带版本、时间、适用范围的经验库 |

“当前状态”必须从真实系统读取；RAG 用于补充规则和经验，缓存内容需要经过版本和时效校验后再参与判断。

### D2C 场景的 few-shot 知识路径

在视觉一致性评估场景中，可以按任务类型加载少量正反样例、判断规则和完成标准，再将它们作为当前任务的受控知识。典型流程是：

```text
任务类型
  -> 选择对应样例和规则
  -> 校验样例完整性与版本
  -> 建立当前任务的知识上下文
  -> 按版本和权限缓存
```

缓存键应包含任务类型、知识版本和模型版本；初始化需要并发保护。样例图片缺失、标签冲突、规则过期或权限不匹配时，应显式失败并返回可排查原因。
### 检索链路

```text
查询理解
  -> 判断是否需要知识
  -> 查询改写或拆分
  -> 候选召回
  -> 过滤权限、版本和时间
  -> 重排
  -> 证据压缩
  -> 注入当前上下文
  -> 生成或继续调用工具
  -> 证据校验
```

每一步都要有退出条件。没有召回到证据时，应返回“证据不足”或请求更多输入。

### 结构化知识优先

如果问题可以通过字典、SQL 或规则直接回答，就优先走结构化查询。例如：

- 根据 `任务类型` 找系统 Prompt。
- 根据组件 ID 找节点属性。
- 根据版本号找阈值配置。
- 根据 task ID 查当前状态。
- 根据错误码找固定处理动作。

向量检索适合语义相近但表达不固定的资料；结构化查询适合准确、可审计和实时的数据。

### 检索结果的最小单元

每个知识片段至少包含：

```json
{
  "id": "rule-size-v3",
  "content": "宽或高差异超过 2px 视为尺寸缺陷",
  "type": "policy",
  "scope": "d2c",
  "version": "v3",
  "valid_from": "...",
  "valid_to": null,
  "source_key": "component_size",
  "permissions": ["project:d2c"],
  "priority": 10
}
```

虽然模型不一定需要看到全部元数据，但检索器和审计系统必须保留 scope、版本、权限和有效期。正文注入时可以压缩成“规则 + 版本 + 适用范围”。

### Agentic RAG 什么时候值得用

适合：

- 问题需要多跳证据，例如先确定 case 状态，再找对应规则，再解释缺陷。
- 首次检索结果不足，需要查询改写或补充条件。
- 多份资料存在冲突，需要比较版本和可信度。
- 需要先调用实时工具，再基于结果检索历史经验。

不适合：

- 简单字段查询。
- 规则已经固定在代码中。
- 业务要求低延迟且检索结果可预测。
- 证据源权限复杂而没有清晰的访问控制。

### 查询改写与检索策略

查询改写不是任意扩写。应保留业务实体、版本、任务号和限制条件。D2C 查询可以拆成：

```text
任务事实：当前 case 的页面状态和设备是什么？
对象事实：Figma node 与 Lynx node 是否表示同一组件？
规则事实：该属性在当前版本的阈值是什么？
经验事实：类似 bad case 以前如何归因？
```

每个子查询绑定不同的数据源，让规则、实时状态和历史样例分别进入对应检索链路。

### 证据融合与冲突

证据融合应遵循：

1. 当前任务实时数据优先于历史样例。
2. 明确版本的业务规则优先于模糊经验。
3. 同一实体的新版本优先于旧版本，但必须检查生效时间。
4. 不同来源冲突时保留冲突，并进入复核，不强行平均。
5. 生成结论时把关键判断绑定到证据 ID。

### 防止 RAG 污染

常见污染包括旧规则、错误标签、跨项目样例、提示注入、重复片段和相互矛盾的结论。治理措施：

- 写入前审核、去重和标签化。
- 读取时按项目、版本、时间和权限过滤。
- 对用户提供的资料标记为不可信输入，不能直接成为系统规则。
- 对检索片段做长度、格式和指令隔离，避免其中的文本覆盖系统约束。
- 维护失效、撤销和替代关系。
- 记录命中片段，评测检索召回和答案是否真正使用了证据。

### RAG 评测

至少拆成：

- Retrieval Recall：正确证据是否被召回。
- Precision：召回中无关片段占比。
- Groundedness：结论能否由证据支持。
- Context Utility：注入后是否改善任务。
- Freshness：是否使用了最新有效版本。
- Permission Correctness：是否只召回有权访问的内容。
- Latency/Cost：检索和重排带来的额外成本。

## 落地步骤

1. 盘点业务知识、实时事实、样例和规则的来源。
2. 给每类知识确定唯一 ID、版本、范围、有效期和权限。
3. 对能结构化查询的内容先建 API、字典或 SQL。
4. 为语义资料设计分块、embedding、关键词和重排策略。
5. 定义查询改写、空召回、冲突和权限过滤行为。
6. 将检索结果压缩成“证据、适用范围、版本、结论”。
7. 记录知识命中轨迹并建立 RAG 专项评测。
8. 发生 bad case 时先判断检索错、知识错、注入错还是生成错。

### D2C 知识库分层

```text
实时层：任务状态、截图路径、结构树、当前版本
规则层：属性阈值、单位换算、状态 gate、输出契约
样例层：缺陷/非缺陷图片、标签、原因、难度
经验层：bad case 归因、修复策略、历史复评结果
```

实时层通过 API 或数据库读取；规则层需要版本化；样例层需要清晰标签；经验层需要标注适用范围和验证状态。

## 失败与排障

| 现象 | 原因方向 | 修复方式 |
| --- | --- | --- |
| 检索不到正确规则 | 查询字段缺失、分块不合理、索引未更新 | 先做结构化查询，补 metadata 和召回测试 |
| 召回了旧规则 | 没按版本和有效期过滤 | 引入生效时间、失效状态和 cache key 版本 |
| 模型被知识片段带偏 | 未做指令隔离或片段含恶意文本 | 片段作为证据注入，禁止覆盖系统约束 |
| few-shot 越多效果越差 | 样例相互冲突或超出上下文 | 按 任务类型、难度和版本筛选 |
| 初始化并发重复 | 缺少锁或缓存键不完整 | 双重检查、锁和版本化失效 |
| 证据足够但回答仍幻觉 | 生成没有强制绑定证据 | 输出 schema 加 evidence_id，并做 groundedness 校验 |

## 面试应对

### 常考点及考法

- 传统 RAG、Agentic RAG 和 few-shot memory 怎么选？
- 如何防止知识库污染？
- 如何评估 RAG 是否真的有效？
- 当前状态为什么要走实时查询？

### 解法/回答思路

先区分实时事实、结构化规则、语义资料和历史样例，再讲数据源、检索、过滤、重排、注入和证据校验。用 D2C 场景按 `任务类型` 缓存 few-shot 说明轻量知识也需要版本和并发治理。

### 易错点

- 把 RAG 等同于向量数据库。
- 不做版本、权限和有效期过滤。
- 只评估最终答案，不评估召回和证据使用。
- 把过期历史样例当作当前业务事实。

### 回答模板

可直接回答：

> 我会先按知识类型选存储方式：实时状态走 API，阈值和协议走版本化结构化配置，正反样例可以按任务类型建立 few-shot memory，长文资料再用关键词和向量混合检索。检索时按项目、权限、版本和有效期过滤，再做重排和证据压缩，生成结果必须带 evidence_id；没有证据就返回证据不足。D2C 场景可以按任务类型加载样例数据、绑定系统 Prompt 和 completion Prompt，并用缓存避免重复初始化，但缓存键还必须包含知识和模型版本。评测时分别看召回率、精确率、groundedness、新鲜度、权限正确率、延迟和成本。
