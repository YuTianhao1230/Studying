# RAG 与业务知识库落地

## 知识点解析

### 概述

本卡片聚焦 D2C Agent 的知识资产治理：知识分类、权限、版本、有效期、缓存与污染控制。查询规划、多跳检索、重排、证据融合和自我修正等通用机制见[《Agentic RAG》](<../基础概念/Agentic_RAG.md#agentic-rag>)。

### 先按业务语义分类

不同知识不能共用同一种存储和更新策略：

| 知识类型 | D2C 例子 | 权威来源与读取方式 |
| --- | --- | --- |
| 实时事实 | 当前任务状态、截图路径、节点结果 | API 或数据库实时查询 |
| 业务规则 | 颜色、圆角、尺寸、字号和字重阈值 | 版本化配置或代码 |
| 字段协议 | Figma/Lynx 节点字段、错误码、输出 schema | 结构化 schema 与版本化文档 |
| 正反样例 | 缺陷图、非缺陷图、标签和原因 | case store 或 few-shot memory |
| 长文资料 | 采集手册、排障手册 | 文档检索，按需加载 |
| 历史经验 | bad case 归因、修复策略、复评结果 | 带适用范围和验证状态的经验库 |

“当前状态”不能由历史向量或旧样例替代。业务规则能精确查表时也不应依赖语义相似度猜测。

### D2C 知识分层

```text
实时层：任务状态、截图路径、结构树、当前版本
规则层：属性阈值、单位换算、状态 gate、输出契约
样例层：缺陷/非缺陷图片、标签、原因、难度
经验层：bad case 归因、修复策略、历史复评结果
```

实时层通过 API 或数据库读取；规则层必须版本化；样例层需要稳定标签；经验层必须记录适用范围和验证状态。四层分别维护，避免历史经验覆盖实时事实或正式规则。

### 最小知识记录

每条可检索知识至少保存：

```json
{
  "id": "rule-size-v3",
  "content": "宽或高差异超过 2px 视为尺寸缺陷",
  "type": "policy",
  "scope": "project:d2c",
  "version": "v3",
  "valid_from": "2026-10-01T00:00:00Z",
  "valid_to": null,
  "source_key": "component_size",
  "permissions": ["project:d2c:read"],
  "status": "active",
  "supersedes": "rule-size-v2"
}
```

模型可以只看到压缩后的“规则 + 版本 + 适用范围”，但检索器和审计系统必须保留 ID、来源、权限、有效期、状态和替代关系。

### 权限与范围

知识读取至少同时校验：

- 调用主体：用户、服务账号或机器人。
- 租户与项目：只访问当前任务所属范围。
- 资源范围：Figma 文件、Lynx 页面、评测集或知识集合。
- 动作范围：读取、添加样例、修改规则或发布版本。
- 数据级权限：敏感字段、原始截图和人工标注是否可见。

权限过滤必须发生在召回与上下文注入之前。无权内容即使最终没有出现在答案中，也不应被模型读取。

### 版本、有效期与可复现性

一次判断应绑定代码、模型、Prompt、规则、样例集和知识索引版本。规则变更采用新版本，不原地覆盖；旧版本保留失效原因和替代关系。执行轨迹记录实际命中的知识 ID 与版本，才能复现某个 case 当时为何得到该结论。

缓存键至少包含：

```text
任务类型 + 项目范围 + 知识版本 + 模型版本 + 权限主体
```

初始化需要并发保护。版本更新、权限变化或知识撤销时必须主动失效缓存，不能只依赖 TTL。

### D2C few-shot 知识路径

视觉一致性评估按`任务类型`加载少量正反样例、判断规则和完成标准：

```text
任务类型
  -> 校验项目权限与目标版本
  -> 选择同类正反样例和规则
  -> 检查图片、标签与适用范围
  -> 构造当前任务知识上下文
  -> 按完整 cache key 复用
```

样例图片缺失、标签冲突、规则过期或权限不匹配时，应显式失败并返回可排查原因，不能回退到来源不明的旧缓存。few-shot 数量增加不等于质量提高，应优先保留同任务类型、同版本和有代表性的边界样例。

### 污染治理

常见污染包括旧规则、错误标签、跨项目样例、重复片段、相互矛盾的结论和提示注入。治理覆盖完整生命周期：

#### 写入前

- 校验来源、权限、schema 和必要字段。
- 去重并检查标签冲突。
- 区分正式规则、人工经验和用户临时材料。
- 新知识先进入草稿或待审状态。

#### 读取时

- 按项目、权限、版本、时间和状态过滤。
- 用户材料和检索片段作为不可信证据，不能覆盖系统约束。
- 规则与经验冲突时，以有效正式规则为准并保留冲突记录。
- 对文本做长度、格式和指令隔离。

#### 使用后

- 记录命中的知识 ID、版本和最终是否被采用。
- 监控旧版本命中、跨项目召回和空召回。
- bad case 先区分知识错误、标签错误、权限错误或缓存错误。

#### 失效与撤销

- 使用 `active/deprecated/revoked` 等显式状态。
- 维护 `supersedes` 或替代关系。
- 撤销后清理索引与缓存，并保留审计记录。
- 修订样例或规则时生成新版本，不静默覆盖历史。

### 简短选型

| 需求 | 优先方案 |
| --- | --- |
| 当前状态、精确字段 | API、SQL、字典 |
| 固定业务规则 | 版本化配置或代码 |
| 少量正反样例 | 按任务类型加载的 few-shot memory |
| 长文与表达不固定的资料 | 关键词 + 向量混合检索 |
| 多跳、冲突或需动态补证 | [Agentic RAG](<../基础概念/Agentic_RAG.md#agentic-rag>) |

选型标准是准确性、时效、权限、可审计性、延迟和成本。业务知识库不是“所有数据都向量化”，而是让每类知识使用可控的权威读取路径。

### 治理门禁

- **Freshness**：召回内容必须处于有效期内并指向当前生效版本；`deprecated/revoked` 内容命中率必须为 0，规则发布后需验证索引与缓存已经失效。
- **Permission Correctness**：召回与注入的每条知识都必须通过调用主体、项目、资源、动作和数据级权限校验；跨项目或无权内容命中率必须为 0。

任一门禁未通过时，不得把对应知识注入模型上下文；系统应返回明确错误或降级到有权且仍有效的权威来源，并记录被过滤的知识 ID、版本和原因。

### 上线检查

1. 为每类知识确定 owner、权威来源和更新方式。
2. 定义唯一 ID、项目范围、版本、有效期、权限和状态。
3. 建立规则发布、样例审核、撤销和缓存失效流程。
4. 验证用户、机器人和跨项目主体的权限边界。
5. 准备空知识、旧版本、标签冲突、跨项目和撤销知识 case。
6. 记录每次执行命中的知识及版本，并支持按 case 回放。

### 失败与排障

| 现象 | 首查项 | 修复方向 |
| --- | --- | --- |
| 使用旧规则 | 生效时间、状态、索引和缓存键 | 发布新版本并主动失效旧缓存 |
| 跨项目样例进入上下文 | scope 与主体权限过滤 | 在召回前做资源级权限校验 |
| few-shot 越多越差 | 标签冲突、任务类型和版本 | 精选同类边界样例并去重 |
| 用户材料改变系统规则 | 知识与指令是否分区 | 将外部内容限定为不可信证据 |
| 同一 case 无法复现 | 命中知识和组合版本未记录 | 保存知识 ID、版本与版本指纹 |
| 初始化并发重复 | 缓存键不完整或缺少锁 | 完整 cache key、双重检查和锁 |

## 面试应对

### 传统 RAG、few-shot memory 和 Agentic RAG 怎么选？

回答思路：先按知识类型选权威读取方式，再按问题复杂度决定是否使用 Agentic 机制。

回答模板：

我会先区分实时事实、固定规则、历史样例和长文资料。实时状态走 API 或 SQL，固定规则走版本化配置，少量正反样例按任务类型加载为 few-shot，长文资料才使用关键词和向量检索。只有问题需要多跳证据、来源冲突或动态补证时，才升级到 Agentic RAG。整个选择同时考虑准确性、时效、权限、可审计性、延迟和成本。

### 如何防止业务知识库污染？

回答思路：覆盖写入、读取、使用后追踪和撤销四个阶段。

回答模板：

写入前校验来源、权限、schema、重复和标签冲突，并区分正式规则、经验和临时材料；读取时按项目、权限、版本、有效期和状态过滤，外部文本只能作为证据，不能覆盖系统约束；使用后记录命中的知识 ID 和版本；规则失效时通过撤销状态、替代关系、索引清理和缓存失效完成闭环。历史内容不原地覆盖，才能审计和复现。

### 为什么任务状态不能直接放进 RAG？

回答思路：从时效性和权威来源解释实时层与知识层的边界。

回答模板：

任务状态、节点结果和资源可用性持续变化，旧向量或历史样例不能代表当前事实，所以必须从 API 或数据库实时读取。RAG 更适合规则、协议、长文和经过验证的历史经验。即使 few-shot 做了缓存，缓存键也要包含任务类型、项目、知识版本、模型版本和权限主体，版本或权限变化时主动失效。

### 如何让一次 RAG 结果可复现？

回答思路：强调输入快照、知识命中和组合版本。

回答模板：

我会保存原始问题、任务范围、权限主体、输入快照，以及代码、模型、Prompt、规则、样例集和索引版本，同时记录实际命中的知识 ID、版本和是否被采用。规则和样例变更只发布新版本，不覆盖历史。这样才能在同一权限与知识快照下重放 case，并判断变化来自知识、检索还是生成。
