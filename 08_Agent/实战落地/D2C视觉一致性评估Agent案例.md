# D2C 视觉一致性评估 Agent 实战地图

## 知识点解析

### 概述

本卡片用“设计稿与跨端页面视觉一致性评估”场景，串起 Agent 实战落地的任务定义、数据采集、Workflow、Skill、Tool/MCP、RAG、评测、可靠性、安全和 AI Coding 十一个入口。遇到问题时，先按现象定位所在层，再进入对应知识卡片深入解决。

场景采用抽象接口和通用流程描述，保留可迁移的方法论、工程边界和排障路径。

### 一张总图

```text
业务目标不清楚？
  -> 任务契约与 Agent 边界

输入无法比较？
  -> 数据采集与多模态输入

流程不知道怎么拆？
  -> Workflow 与状态编排

能力不知道怎么封装？
  -> Skill 工程化

外部系统不知道怎么接？
  -> Tool / MCP / 授权治理

规则和样例不知道放哪？
  -> RAG 与业务知识库

不知道效果是否变好？
  -> 评测、Harness 与 GT 回流

线上变慢、重复、失败？
  -> 可靠性、性能、成本与可观测性

出现越权或危险写入？
  -> 安全、权限与生产部署

具体故障无法定位？
  -> 真实问题排障手册

需要修改已有系统？
  -> AI Coding 与 Spec-First 协作
```

## 问题路由

### 入口一：先判断任务边界

**典型问题**：

- “这个需求需要 Agent 吗？”
- “为什么不能直接让模型看图并给分？”
- “哪些步骤应该写成规则？”

**先做什么**：

1. 写清输入、输出、成功标准、证据和失败语义。
2. 区分固定转换、固定流程、开放决策和高风险动作。
3. 把可验证的计算、校验和权限放到确定性程序。
4. 只把需要语义判断、候选选择或动态规划的部分交给模型。

**继续阅读**：[实战总览：从问题到生产 Agent](<实战总览：从问题到生产Agent.md>)。

### 入口二：输入无法比较

**典型问题**：

- 设计稿和实现页面内容不一致。
- 截图是空白、加载态或错误页面。
- 页面结构信息为空，或者和截图不属于同一次采集。
- 所有对象整体偏移、缩放或颜色异常。

**先判断哪一层**：

```text
页面状态
  -> 设备与 viewport
  -> 资源和权限
  -> 截图与结构信息的批次
  -> 坐标、单位和缩放
  -> 字段 schema 和版本
```

**解决顺序**：

1. 固定页面状态、设备尺寸、字体、主题和动态数据。
2. 确认设计截图、实现截图和结构信息来自同一批次。
3. 校验文件可读、字段完整、权限有效、时间对齐。
4. 统一坐标空间、box 格式、DPR 和单位。
5. 采集问题未解决前，不进入缺陷判定。

**继续阅读**：[数据采集与多模态输入工程](<数据采集与多模态输入工程.md>)。

### 入口三：不知道流程怎么拆

**典型问题**：

- 所有任务都让模型自由规划，结果不稳定。
- 固定流程和开放式任务混在一起。
- 并行检测后结果互相覆盖。
- 中间失败最后变成成功。

**推荐分层**：

```text
输入校验与状态收敛
  -> 公共数据准备
  -> 对象匹配
  -> 并行属性检测
  -> 结果合并
  -> 模型复核
  -> 报告和回流
```

固定流程负责边界和门禁；受限规划只负责选择允许的能力、补充信息和组织证据。每个节点都要定义输入、输出、错误、超时、重试、取消和终止条件。

**继续阅读**：[Workflow 与 LangGraph 编排](<Workflow与LangGraph编排.md>)。

### 入口四：同类任务反复犯错

**典型问题**：

- 每次都漏掉相同的前置检查。
- 不同人处理同一任务的步骤不一致。
- 工具参数和失败处理反复出错。
- 修复经验没有沉淀，下一次继续重复。

**解决顺序**：

1. 收集成功样例、失败样例和相邻误触发样例。
2. 提炼 Skill 的触发条件和不适用边界。
3. 写输入要求、决策步骤、工具使用和完成条件。
4. 把低频大段知识放到按需加载的资料中。
5. 为路由、步骤、工具参数和安全行为建立评测。

**继续阅读**：[Skill 工程化](<Skill工程化：设计、路由、实现与迭代.md>)。

### 入口五：需要接入外部能力

**典型问题**：

- 需要读取设计稿、页面状态、设备结果或评测任务。
- 不知道普通 Tool 和 MCP 如何选择。
- 用户、服务账号和机器人看到的数据不同。
- 工具可以读取，但不应该直接写入正式数据。

**先拆六层**：

```text
Agent 决策
  -> Tool Call
  -> Tool Adapter / MCP Client
  -> MCP Server 或业务 API
  -> 外部资源
  -> 权限、审计和结果治理
```

**解决顺序**：

1. 列出资源、动作、主体和副作用。
2. 只读能力先做 allowlist 和资源级权限。
3. 写入能力增加 dry-run、确认、幂等、审计和回滚。
4. Server 和真实后端都做二次鉴权。
5. 记录调用主体、资源、动作、版本和结果摘要。

**继续阅读**：[Tool 与 MCP 链路、授权和治理](<Tool与MCP链路、授权和治理.md>)。

### 入口六：模型缺少业务知识

**典型问题**：

- 模型不知道某类视觉差异的业务标准。
- few-shot 样例太多后效果变差。
- 旧规则影响当前判断。
- 检索结果和实时页面状态冲突。

**先分类知识**：

| 知识类型 | 正确处理方式 |
| --- | --- |
| 当前页面、任务和设备状态 | 以实时系统查询结果为准。 |
| 阈值、字段协议和权限规则 | 使用版本化结构化配置。 |
| 正反样例和缺陷原因 | 按任务类型、版本和权限筛选。 |
| 长文手册和历史经验 | 检索、重排、压缩并绑定证据。 |

**解决顺序**：

1. 先判断能否通过结构化查询解决。
2. 再设计关键词、向量或混合检索。
3. 过滤版本、有效期、项目范围和权限。
4. 没有证据时返回证据不足。
5. 记录命中知识的版本，支持复现和失效。

**继续阅读**：[RAG 与业务知识库落地](<RAG与业务知识库落地.md>)。

### 入口七：结果不可信或无法证明变好

**典型问题**：

- 只看总分，不知道具体哪里错。
- 改了 Prompt 后平均分变高，但用户体验没有改善。
- 结果无法复现。
- GT 被不断修改，指标失去意义。

**解决顺序**：

1. 固定输入、资源、GT、模型、Prompt 和配置版本。
2. 记录路由、状态、工具调用、知识命中、重试和输出。
3. 同时评估任务成功、工具正确率、缺陷 precision/recall/F1、延迟、成本和安全。
4. 做 case-level diff，区分修复、退化和新增错误。
5. 原始 GT 只读，人工修正生成新版本。
6. 正式写回外部平台前展示计划并确认。

**继续阅读**：[评测、Harness 与 GT 回流](<评测Harness与GT回流.md>)。

### 入口八：线上慢、重试多或成本高

**典型问题**：

- 外部视觉请求经常超时。
- 重试导致重复任务或重复写入。
- 并发提高后成功率下降。
- 临时文件、缓存和报告持续增长。

**解决顺序**：

1. 给入口和每个节点设置 deadline。
2. 按错误类型区分可重试和不可重试。
3. 为所有副作用设计幂等键和状态机。
4. 为下载、设备、模型、上传和写回分别设并发上限。
5. 记录阶段耗时、队列等待、重试、token、成本和资源占用。
6. 超时后返回明确的 PARTIAL 或 TIMEOUT，不伪装成完整成功。

**继续阅读**：[可靠性、性能、成本与可观测性](<可靠性性能成本与可观测性.md>)。

### 入口九：出现越权、泄露或危险写入

**典型问题**：

- 外部文本诱导 Agent 忽略系统规则。
- 当前任务读取了其他项目资源。
- 令牌出现在日志、报告或上下文中。
- Agent 自动发布结果、覆盖 GT 或修改配置。

**解决顺序**：

1. 将外部文本和检索内容视为不可信数据。
2. 按纯计算、受限读取、任务写入和正式副作用分级。
3. 在入口、Agent、MCP Server 和后端分别鉴权。
4. 使用最小权限短期凭证，禁止进入 Prompt、日志和报告。
5. 写操作默认 dry-run，要求人工确认、审计和回滚。
6. 做租户隔离、输入限制、输出脱敏和 HTML 转义。

**继续阅读**：[安全、权限与生产部署](<安全权限与生产部署.md>)。

### 入口十：具体故障不知道从哪里查

**典型问题**：

- 结果错误，但不知道是输入、工具还是模型问题。
- 同一个 case 偶发成功、偶发失败。
- 中间节点失败却被后续节点覆盖。
- 线上问题无法在本地复现。

**统一排查顺序**：

```text
请求是否进入
  -> 身份和资源权限
  -> 输入与页面状态
  -> Workflow 路由
  -> 工具调用和外部响应
  -> 知识与 Prompt 版本
  -> 规则与模型输出
  -> 状态合并与报告解析
  -> 结果回写
```

先冻结请求、资源和版本，找到最后一个成功节点与首次偏离节点，再做单变量复现。修复动作根据偏离层级选择，可能落在数据、编排、工具、知识、Prompt、规则、模型或平台侧。

**继续阅读**：[真实问题排障手册](<真实问题排障手册.md>)。

### 入口十一：需要在已有系统中实现功能

**典型问题**：

- 需求复杂，Agent 一次修改范围失控。
- 规格、接口和测试没有对齐。
- 测试文件生成了，但真实功能没有验证。
- 修改一个模块后引入其他回归。

**解决顺序**：

1. 先写任务规格、非目标、接口、错误语义和验收标准。
2. 让 Agent 先理解模块边界和调用链。
3. 按垂直切片增量修改。
4. 每一步运行自动化测试和真实链路验证。
5. 审查权限、数据、依赖、兼容性和回滚。
6. 将重复失败沉淀为规则、测试或 Skill。

**继续阅读**：[AI Coding 与 Spec-First Agent 协作](<AI_Coding与Spec_First工程实践.md>)。

## 最小解决闭环

无论遇到哪类问题，都可以先执行以下七步：

1. **定义现象**：把“效果不好”改写成具体错误和影响范围。
2. **冻结现场**：保存输入、状态、版本、权限主体和关键产物。
3. **定位层级**：数据、编排、能力、知识、规则、模型、输出或平台。
4. **找到首次偏离**：比较最后一个成功节点和第一个异常节点。
5. **选择最小修复**：只改一个边界或一个组件。
6. **固定回归**：增加对应 case、负例或故障注入。
7. **沉淀经验**：决定写入 Skill、规则、工具契约、评测集或排障手册。

## 面试应对

### 常考点及考法

- 给一个视觉质检 Agent，如何从零搭建？
- 线上结果不稳定时先查什么？
- Skill、Workflow、MCP、RAG 和评测如何组合？
- 如何把一次 bad case 转成长期能力？

### 解法/回答思路

沿“问题现象 -> 所在层级 -> 解决动作 -> 验证手段 -> 知识沉淀”回答，并用实战地图中的卡片关系说明下一步。

### 易错点

- 一上来就调 Prompt。
- 只讲主流程，不讲输入 gate、权限、失败和回归。
- 把所有问题都归因于模型。
- 只记录最终分数，不保留现场和首次偏离点。

### 回答模板

可直接回答：

> 我会先按层路由问题。业务目标不清楚时先写任务契约；输入不可比时先查状态、资源、权限、批次和坐标；流程复杂时用 Workflow 固定边界；重复错误时沉淀 Skill；需要外部能力时通过 Tool 或 MCP，并做最小权限和审计；缺少业务知识时按实时事实、规则、样例和历史经验设计 RAG；结果是否变好用固定 case、轨迹和 GT 版本评测；线上慢、重复或泄露则分别进入可靠性和安全卡片。每次都冻结现场、定位首次偏离、做最小修复、增加回归并沉淀经验。
