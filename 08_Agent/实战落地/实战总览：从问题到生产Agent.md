# 实战总览：从问题到生产 Agent

## 知识点解析

### 概述

落地 Agent 先把业务目标转成可验证的任务契约，再决定哪些步骤由确定性程序完成、哪些步骤交给模型、哪些动作必须人工确认。一个可落地的 Agent 至少要有输入契约、状态模型、Workflow、工具边界、知识来源、输出契约、评测集和运行保障。D2C 视觉还原度评估是典型例子：系统要稳定回答设计稿和渲染页面在哪些 UI 属性上不一致，并给出可复核证据。

本卡片聚焦生产设计：需求契约、架构决策、发布与运维。Agent 的定义、核心组件和最小开发闭环见[《Agent》](<../基础概念/Agent.md>)。

### 架构决策一：任务形态

先把任务按不确定性和可验证性分类：

| 类型 | 特征 | 推荐方案 |
| --- | --- | --- |
| 固定转换 | 输入输出稳定，规则明确 | 普通函数或批处理 |
| 固定流程 | 步骤顺序稳定，局部分支有限 | Workflow + 工具 |
| 开放决策 | 目标明确但路径不固定 | Agent + 受限工具 |
| 高风险动作 | 会写数据、发消息、改配置或产生外部影响 | Agent 规划 + dry-run + 人工确认 |
| 多模态判断 | 需要图像、视频、页面结构和业务知识共同判断 | 结构化预处理 + 专项模型 + VLM 辅助 |

D2C 场景适合按职责拆分。截图下载、尺寸校验、组件解析、坐标换算、颜色差异和阈值判断交给确定性代码；语义匹配、异常解释和误报过滤交给模型辅助。

### 业务目标要写成任务契约

在写 Prompt 前先回答：

1. 输入是什么，字段是否完整，允许哪些格式和尺寸。
2. 成功意味着什么，必须返回哪些字段。
3. 哪些结果是缺陷，哪些只是数据缺失或不可比。
4. 哪些判断必须有证据，证据来自图片、结构树、日志还是规则计算。
5. 错误如何区分，是否可以重试，重试会不会重复产生副作用。
6. 结果由谁消费，是机器门禁、研发报告、设计复核还是训练数据回流。

可用如下抽象描述目标：

```text
result = Judge(state, evidence, policy)
state    = 输入 + 中间结果 + 执行历史 + 版本信息
 evidence = 结构化数据 + 图像/视频 + 工具结果 + 检索片段
 policy   = 阈值 + 业务规则 + 权限 + 输出契约
```

### 通用架构分层

```text
入口层
  -> 参数校验、身份识别、请求去重、任务编号
编排层
  -> 路由、状态、显式专家、ReAct、并行和失败分支
能力层
  -> Tool、模型客户端、MCP、浏览器、代码执行
数据层
  -> 图片/视频、结构化树、知识库、few-shot、临时工作区
判定层
  -> 规则、模型判断、结果融合、置信度和人工复核
输出层
  -> JSON、报告、消息、数据库、评测系统
治理层
  -> 日志、Trace、指标、权限、成本、审计、灰度和回滚
```

### 架构决策二：设计顺序

#### 1. 先做最小可验证切片

选择一个输入类型、一个清晰指标和一个最小输出。例如先实现“两个页面中同一组件的宽高是否相差超过 2px”，再扩展到完整页面的综合评分。最小切片要能独立运行、保存中间证据并被评测。

#### 2. 定义可追踪状态

状态至少包含：`request_id`、`task_id`、`任务类型`、输入资源、工作目录、模型版本、Prompt 版本、工具结果、历史输出、当前状态、错误类型和最终结果。状态字段应区分“没有结果”“结果为空”“执行失败”和“无需执行”。

#### 3. 给每个能力定义输入输出契约

工具和专家都应有结构化 schema。输入包含必需字段、可选字段、单位和默认值；输出包含 `success`、`error`、`data`、`evidence`、`version` 和耗时。下游依据结构化字段判断上游是否成功。

#### 4. 把不确定性放在边界内

模型可以选择候选、解释差异或决定是否需要更多证据，但不能绕过权限、阈值和输出校验。确定性步骤先做，模型步骤尽量短，模型输出再经过 JSON schema 和业务规则校验。

#### 5. 让评测先于上线

先有代表性 case、正例、负例、边界例和故障例，再迭代 Prompt、工具和 Workflow。每次变更都要保存代码版本、配置版本、模型版本、输入快照和输出轨迹。

### 场景映射

D2C 视觉一致性评估场景可以映射为一套通用职责：

| 通用层 | 抽象职责 |
| --- | --- |
| 状态 | 保存请求、输入资源、中间结果、历史、错误和版本。 |
| 路由 | 根据任务类型选择固定流程，必要时进入受限的开放式规划。 |
| 能力注册 | 维护可用专家和工具的描述、权限、版本与生命周期。 |
| 工具调用 | 对图片、页面结构、外部服务和规则计算提供统一接口。 |
| Prompt | 管理版本化任务指令、变量和输出格式。 |
| 知识 | 按任务类型加载规则、样例和历史经验，并控制缓存。 |
| 报告 | 输出机器可解析结果、人类可读报告和可追溯证据。 |

这里描述的是可迁移的系统职责，不对应任何特定仓库、文件或实现。
### 自主 Agent 的适用边界

以下情况优先使用普通 Workflow 或函数：

- 步骤和分支已知，模型不会增加有效决策。
- 输入输出有严格协议，模型只会增加随机性。
- 失败代价高且没有可靠的回滚。
- 延迟和成本约束不允许多轮模型调用。
- 业务规则可以用确定性代码完整表达。

在 D2C 中，颜色 ΔE、圆角差、尺寸差、字号差和字重差应由规则计算；Agent 的价值在于选择检测策略、组织证据和帮助解释，算术判断继续由确定性逻辑承担。

### 发布决策

发布单元不是单独的 Prompt 或模型，而是一组共同决定行为的版本：

```text
代码 + Workflow + Skill + Prompt + 模型
  + Tool schema + 规则 + 知识 + State schema
```

离线发布门禁应固定 case、GT 和输入快照，比较任务成功率、缺陷 precision/recall/F1、工具正确率、证据完整性、延迟、成本和安全行为。通过后按用户、项目或 case 集灰度，先保持只读或 dry-run；涉及写回 GT、发布报告和修改配置时，再逐级开放权限。每次发布保存版本指纹和兼容性要求，确保问题出现时可以回滚整套组合，而不是只回退某一个 Prompt。

### 运行与运维

- **可靠性**：入口与节点 deadline、有限重试、幂等键、取消和部分成功语义。
- **可观测性**：日志、指标和 Trace 统一使用 `request_id/task_id/run_id/artifact_id` 关联。
- **容量**：分别限制下载、设备采集、模型调用、上传和写回的并发。
- **安全**：最小权限、短期凭证、资源级鉴权、危险动作确认和完整审计。
- **恢复**：稳定 checkpoint、外部结果查询、补偿动作和人工接管。
- **数据治理**：原始输入与 GT 只读，修订生成新版本；临时文件和缓存按保留周期清理。
- **回归**：线上 bad case 冻结现场，定位首次偏离点，并进入固定 case 集。

线上告警既看系统指标，也看业务过程指标。D2C 除请求成功率、P95/P99、重试和成本外，还要观察采集成功率、组件匹配率、各属性候选与缺陷数、报告字段完整率、人工复核率和结果写回成功率。

## 落地步骤

1. 写一页任务契约：输入、输出、成功、失败、证据和消费方。
2. 选一个最小 case，冻结输入快照和人工 GT。
3. 建立统一状态和错误模型。
4. 先实现确定性预处理与硬校验。
5. 再接入单个模型能力或工具，并记录版本和耗时。
6. 将多个能力编排成可观察 Workflow。
7. 加入重试、超时、幂等、权限和人工确认。
8. 建立离线 Harness，比较结果、轨迹和成本。
9. 用 bad case 归因决定修规则、修工具、修知识、修 Prompt 还是修模型。
10. 通过灰度和回滚进入线上，并持续回流数据。

## 失败与排障

| 现象 | 优先检查 |
| --- | --- |
| Agent 说得很好但无法执行 | 输出 schema、工具注册、参数映射和权限 |
| 结果随机变化 | Prompt/模型版本、输入是否变化、是否缺少硬规则 |
| 只在复杂页面失败 | 状态收敛、组件匹配、长图坐标和证据裁剪 |
| 重试后结果重复或数据重复 | 幂等键、任务状态机和副作用边界 |
| 评测分数提升但线上不可用 | 评测集是否覆盖真实分布、延迟/错误率/成本是否恶化 |

## 面试应对

### 你会如何从零设计一个 Agent？

回答思路：按任务契约、架构分层、最小切片、评测和生产保障展开，并说明模型与确定性程序的边界。

回答模板：

我会先把业务目标写成任务契约，明确输入、输出、成功标准、证据和失败语义，再判断任务是否真的需要 Agent。实现时先做一个可独立评测的最小切片，把系统拆成入口、编排、能力、数据、判定、输出和治理层；固定计算、权限和阈值用代码，语义判断和动态选择才交给模型。随后建立结构化状态、工具契约和完整轨迹，用正常、边界和故障 case 验证，最后补齐超时、重试、幂等、权限、灰度和回滚。

### 为什么不能把所有步骤都交给大模型？

回答思路：从确定性、可审计、成本和错误边界说明分工，并给出 D2C 示例。

回答模板：

大模型适合语义理解、候选选择和开放式解释，但不适合承担所有确定性工作。输入校验、坐标换算、颜色差计算、权限判断和状态迁移必须由程序完成，因为这些步骤需要稳定、可测试和可审计。以 D2C 为例，模型可以辅助组件语义匹配和误报复核，但尺寸阈值、资源权限和输出 schema 仍由代码控制。这样既利用模型能力，也把随机性限制在可验证边界内。

### Demo Agent 和生产级 Agent 的差别是什么？

回答思路：先概括“能力上限”和“可靠性下限”的差异，再列出生产化必备机制。

回答模板：

Demo Agent 主要证明模型在理想输入上能完成任务，生产级 Agent 还要保证真实流量下可预测、可恢复和可治理。生产系统必须有输入输出契约、状态机、超时重试、幂等、权限、人工确认、日志、Trace、成本控制、版本绑定、灰度和回滚，并明确空结果、失败和部分成功。只有能力演示而没有这些机制，无法稳定承担外部副作用和业务责任。

### 如何判断一次 Agent 改动真的有效？

回答思路：强调冻结变量、分层指标、case-level diff 和线上护栏，避免只看单次总分。

回答模板：

我会先冻结 case、GT、输入资源、代码、模型、Prompt 和配置版本，然后在同一 Harness 中比较新旧版本。指标既看任务成功率，也看路由和工具正确率、证据完整性、安全违规、延迟和成本，并做 case-level diff 区分修复、新增错误和共同错误。离线通过后再小流量灰度，观察真实业务指标和护栏指标；只有质量提升且可靠性、成本和安全没有不可接受退化，才能认为改动有效。
