# 真实问题排障手册

## 知识点解析

### 概述

Agent 排障应沿着输入、权限、编排、工具、知识、模型、输出和业务回写逐层定位。每次排障都要先冻结请求、版本和资源，再寻找首次偏离点。D2C 任务尤其要区分：页面没有采集成功、组件没有匹配成功、规则判定错误、VLM 过滤错误和报告回写错误。

### 统一排障入口

先收集以下信息：

```text
request_id / task_id
case_id / tenant / actor
任务类型 / workflow path
code / Skill / Prompt / model / tool versions
input manifest / artifact IDs / checksums
start time / deadline / retry attempts
final status / stage / error code
trajectory / raw response / parsed result
```

没有这些信息时，先把问题归为 `REPRODUCIBILITY_BLOCKED`，不要直接修改 Prompt。

### 分层排障树

```text
请求失败
  -> 请求是否进入？
  -> 身份和资源权限是否通过？
  -> 输入文件和状态是否有效？
  -> 是否走了正确 Workflow？
  -> 工具是否注册和调用成功？
  -> 外部服务是否返回有效结果？
  -> 解析和状态合并是否正确？
  -> 业务规则是否正确？
  -> VLM 过滤是否改变了结论？
  -> 结果是否正确持久化和展示？
```

### 入口和参数问题

#### 现象

- 任务一开始就失败。
- `任务类型` 找不到。
- 图片列表为空或路径不可读。
- 同时传 URL 和本地路径时重复下载。

#### 检查

1. 输入 schema 和必填字段。
2. `任务类型` 是否属于注册表，是否被空格、大小写或别名破坏。
3. `image_paths`、`img_urls`、`working_space` 是否与入口约定一致。
4. 本地路径是否位于允许工作区，文件是否可解码。
5. `request_id`、`task_id` 和幂等键是否保留。

入口应优先复用已经校验过的本地资源，只有缺少本地资源时才执行受控下载；排查时先确认是否发生重复下载、资源路径错误或远程地址不可访问。

### 采集和状态问题

#### 现象

- 设计图和实现图内容不一致。
- 截图是空白、加载态或错误页面。
- `实现结构树` 为空或和截图不匹配。
- 页面看起来一样但组件数量差异很大。

#### 检查

- 设计节点标识、实现版本和页面状态。
- viewport、DPR、字体、主题、滚动位置和动态数据。
- 截图时间、结构树时间和 batch ID。
- 设备连接、页面加载日志、动画稳定和采集工具版本。
- 结构树上传后是否能用同一身份回读。

采集失败应返回明确错误；不能因为结构树为空就让后续检测输出“无缺陷”。

### 坐标和标准化问题

#### 现象

- 所有组件整体偏移。
- 所有尺寸都放大或缩小同一比例。
- 设计节点在图外、负坐标或高度异常。
- 颜色、字号和圆角都出现系统性偏差。

#### 检查

1. 两侧 box 是否同一格式和坐标原点。
2. `logical_box`、`box`、`coordinate_info` 是否被混用。
3. viewport、设计基准宽度、DPR 和 rpx 换算。
4. 图片是否被缩放、裁剪或加 padding。
5. 清洗前后组件数、root 尺寸和最大 box。

先挑一个可人工测量的节点手算换算值，再判断是局部错误还是全局变换错误。

### 组件匹配问题

#### 现象

- 父容器匹配到内部图标。
- 同名重复卡片错配。
- 尺寸差异大的真实对应组件被漏配。
- 匹配数很多但缺陷数不可信。

#### 检查

- visual role、node type、owner kind、text preview。
- parent、children、depth、path 和顺序。
- normalized center、size、aspect ratio 和 edge flags。
- geometry score、宽高 log diff 和阈值。
- 每个 ID 是否只使用一次。
- 模型输出是否包含不存在的 ID 或重复 pair。

修复顺序通常是：先修候选清洗，再修语义字段，再调几何过滤，最后才调整模型 Prompt。否则会把候选质量问题误当作模型能力问题。

### 规则检测问题

#### 现象

- 单类指标全部误报。
- 差异值和报告里的 box 对不上。
- 阈值改了但结果不变。
- 只有某些字体、透明背景或长文本失败。

#### 检查

| 指标 | 检查项 |
| --- | --- |
| 颜色 | 颜色空间、采样区域、透明度、背景和 ΔE 计算 |
| 圆角 | 组件边界、四角顺序、检测置信度和 1px 阈值 |
| 尺寸 | box 方向、单位换算、宽高阈值和四舍五入 |
| 字号 | OCR 框、裁剪、字号估计和 2px 阈值 |
| 字重 | 字体渲染、OCR、统计特征和 100 阈值 |
| 间距 | 邻居选择、方向轴、投影重叠和 gap 计算 |

结果必须同时输出原值、差值、阈值和配置版本，否则无法判断代码是否真正使用了新配置。

### 工具和模型服务问题

#### 现象

- 工具不存在或自动发现数量变化。
- 工具返回 HTTP 成功但业务结果为空。
- VLM 报告缺字段、分数越界或只返回文本。
- 频繁超时、重试和限流。

#### 检查

1. 工具注册表快照、模块导入异常和工具 schema。
2. tool_name、args、图片路径和模型名。
3. HTTP 状态、业务 `ok`、`reportValidation` 和原始响应。
4. 单实例在途请求、请求大小、模型版本和服务配额。
5. 是否把一次失败当作“无缺陷”。

VLM 报告需要验证 7 项 0 到 4 分子结果，其中布局 4 项、文本 3 项。报告验证失败是服务契约失败，不是页面质量结论。

### 知识和 Prompt 问题

#### 现象

- 同一问题类型不同请求使用不同标准。
- few-shot 变多后效果反而下降。
- Prompt 修改后平均分提升但边界 case 变差。
- 模型引用了旧阈值或跨项目案例。

#### 检查

- prompt key、版本和实际渲染文本。
- knowledge cache key、命中版本和初始化并发。
- 样例标签、原因、图片路径和冲突。
- 是否把实时状态误放进长期知识库。
- 输出 schema 和证据要求是否仍然存在。

优先用一个固定 case 对比新旧 Prompt 的完整轨迹，同时检查最终字符串、工具调用、证据命中和状态变化。

### 状态和序列化问题

#### 现象

- 中间失败最后显示 completed。
- history 中有失败，但最终输出说无缺陷。
- Pydantic 对象、枚举或嵌套结果无法序列化。
- 部分成功被合并成整体成功。

#### 检查

- `专家输出.status`、`工具输出.success` 和 `error_message`。
- history 是否追加，合并节点是否覆盖失败。
- `None`、空列表、失败和 skipped 是否区分。
- JSON encoder、model dump 和 debug 字段。
- 终态是否允许迟到结果覆盖。

### 评测和回写问题

#### 现象

- 离线分数上涨，真实使用没有改善。
- 任务能读不能写。
- GT 回写后无法复现旧结果。
- 用户和机器人看到的 case 数量不同。

#### 检查

- 输入快照、GT 版本、运行版本和 case 过滤。
- bad case 是否被误删或标注改变。
- `用户身份参数` 与机器人身份的权限和资源范围。
- 写回前是否展示计划并取得确认。
- 结果数据集平台、评测任务系统、评测集和本地报告的版本关系。

## 落地步骤

1. 用 request_id 找到入口日志和完整 Trace。
2. 冻结输入、版本、权限主体和外部资源状态。
3. 判断首次失败 stage，不从最终答案猜原因。
4. 对比成功 case 与失败 case 的输入、状态、工具和版本。
5. 做最小复现，只改变一个变量。
6. 将修复归类为数据、编排、工具、知识、Prompt、规则、模型或平台问题。
7. 增加回归 case 和故障注入，再发布修复。
8. 对正式写回或发布动作保留人工确认和审计记录。

### 最小诊断表

```text
症状：
请求/任务：
失败阶段：
错误码与原始错误：
调用主体：
输入与资源版本：
代码/Skill/Prompt/模型/工具版本：
最后一个成功节点：
首次偏离节点：
是否可重试：
修复动作：
新增回归 case：
```

## 面试应对

### 常考点及考法

- Agent 失败如何定位？
- 如何区分模型、工具、数据和平台问题？
- UI 评估结果全部异常时先查什么？
- 如何让问题修复可验证？

### 解法/回答思路

用“冻结现场 → 首次偏离 → 分层检查 → 最小复现 → 单变量修复 → 回归”的科学流程回答。真实案例中优先查输入状态、坐标和匹配，再查模型。

### 易错点

- 看到答案不对就改 Prompt。
- 没有保存原始请求和版本。
- 把空结果当成成功。
- 一次改动多个变量，无法知道哪项生效。

### 回答模板

可直接回答：

> 我排查 Agent 问题时不会直接从最终答案猜模型原因，而是先用 request_id 冻结输入、资源、调用主体、代码、Prompt、模型和工具版本，再沿 Trace 找最后一个成功节点和首次偏离节点。D2C 场景先检查页面状态、截图与结构树是否同批次、坐标和单位是否正确，再检查候选清洗、组件匹配、确定性规则、VLM 过滤和报告回写。每次只改一个变量，把问题归类为数据、编排、工具、知识、Prompt、规则、模型或平台故障，并增加对应回归 case。空结果、执行失败、跳过和真实无缺陷必须在状态模型中分开表示。
