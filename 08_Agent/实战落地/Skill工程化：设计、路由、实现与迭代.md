# Skill 工程化：设计、路由、实现与迭代

## 知识点解析

### 概述

Skill 是把一类可复用任务封装成“触发条件、执行流程、约束、工具和验证方式”的能力包。Agent 识别到任务后，可以按需加载 Skill 中的操作规范。工程化 Skill 的核心是让路由可命中、正文可执行、工具可调用、结果可验证、版本可回滚。

### Skill 解决什么问题

当同一类任务反复出现，且成功依赖固定的业务知识、操作顺序和质量标准时，应该把经验固化为 Skill。典型信号包括：

- Agent 总是遗漏相同的前置检查。
- 不同人对同一任务的处理步骤不一致。
- 工具调用参数和失败处理需要反复解释。
- 任务需要多份资料，但每次全量加载上下文成本太高。
- bad case 已经有明确的修复套路，应该变成回归规则。

D2C 视觉一致性评估场景中可以把“D2C 组件一致性检测”“评测 case 归因”“VLM 调用与报告校验”分别封装成 Skill，由各 Skill 承载各自的流程、规则和验收标准。

### Skill 的四层结构

```text
路由层
  description、适用场景、反例和触发关键词
执行层
  操作步骤、决策树、输入输出、工具调用和错误处理
知识层
  领域规则、阈值、样例、术语、参考模板
验证层
  eval case、成功标准、负例、安全规则和版本变化
```

### 先设计触发器

`description` 决定 Skill 是否会被加载。好的描述应包含：

- 能力对象：处理什么资源或任务。
- 触发条件：用户出现哪些意图或字段。
- 适用边界：什么情况不能使用。
- 关键输出：加载后能完成什么。

示例：

```yaml
name: d2c-consistency
description: >
  当任务要求比较 Figma 设计稿与 Lynx 渲染结果，或需要分析组件尺寸、颜色、
  圆角、字号、字重、间距差异时使用。输入通常包含设计截图、实现截图、Figma
  节点或 Lynx 结构树。页面采集失败、设备连接和评测回归问题也需要先按本 Skill
  的前置检查处理；普通图片美化和无设计真值的审美评价不使用。
```

触发器要写清任务对象、触发信号、适用边界和关键输出。路由需要高召回，同时控制相邻 Skill 的误触发。

### 正文的执行结构

一张可执行 Skill 卡片通常包含：

1. 任务目标和适用边界。
2. 必需输入、可选输入、输入格式和单位。
3. 前置检查与状态 gate。
4. 标准执行流程。
5. 工具选择和参数模板。
6. 结果 schema 和完成条件。
7. 失败分类、重试条件和人工确认点。
8. 常见 bad case 与修复策略。
9. 最小 eval 和回归入口。

正文应优先写“下一步怎么做”和“出现什么信号如何处理”，少写无法驱动行为的背景介绍。

### 渐进式加载

规则和资料适合按任务阶段渐进加载。可以分为：

- 常驻层：Skill 名称、适用范围、强约束和安全规则。
- 主文档：标准流程、输入输出和关键决策树。
- references：大段协议、字段字典、阈值表、故障手册和样例。
- scripts：可重复执行的校验、转换、评测和报告生成脚本。

当任务是 D2C 颜色检测时，只加载颜色字段和颜色检测规则；需要排查设备采集时再加载采集故障手册。这样能减少上下文噪声和错误规则互相污染。

### Skill 与 Tool 的关系

- Skill 说明何时使用工具、工具之间的顺序、参数来源和结果验收。
- Tool 提供一个可调用的原子能力，并通过 schema 约束输入输出。
- Workflow 决定多个 Skill 或工具如何编排。
- MCP 解决外部工具和资源的标准接入，不替代 Skill 的业务方法。

例如 `ui_element_matcher` 负责调用模型生成候选匹配，D2C Skill 负责规定必须提供两侧组件列表、必须检查一对一、必须保留匹配证据以及匹配不确定时如何进入复核。

### Skill 设计中的关键取舍

| 问题 | 选择依据 |
| --- | --- |
| 写在 Skill 还是代码里 | 稳定算法、权限和阈值门禁放代码；操作顺序和解释规则可放 Skill。 |
| 写在主文档还是 references | 高频且决定下一步的内容放主文档；大表格和低频细节外置。 |
| 一个大 Skill 还是多个小 Skill | 触发条件、工具链和验收标准相互独立时拆分。 |
| 让模型自主决定还是固定流程 | 失败代价高、步骤稳定时固定；仅在候选选择和信息不足时开放决策。 |
| 是否加入示例 | 示例必须代表真实输入输出，并覆盖边界、失败和 happy path。 |

### 评测先行

在写正文前先列出：

- 应该触发的任务。
- 相邻任务的边界样例。
- 触发后必须执行的步骤。
- 不同输入下工具参数是否正确。
- 结果是否包含必需字段。
- 遇到权限、数据缺失和工具超时时是否正确停下。

Skill 评测至少包括路由召回、路由误触发、步骤遵循、工具调用正确率、结果完整性和安全拒答，并结合最终答案质量一起衡量。

### 版本和维护

Skill 需要像代码一样维护：

- 每次变更记录版本、变更原因和影响的 eval。
- 工具 schema 变化时同步更新参数模板和失败处理。
- 业务阈值变化时同步更新知识、代码和回归结果。
- bad case 先分类，再决定是修 description、正文、工具、数据还是模型。
- 保留旧版本以便复现历史任务，禁止静默覆盖生产行为。

## 落地步骤

1. 收集 10 到 30 个真实任务，标注成功路径和失败路径。
2. 写 Skill 的适用边界和反例，先解决路由冲突。
3. 定义输入输出 schema、前置 gate 和完成条件。
4. 把流程写成编号步骤、分支和验收条件。
5. 把工具参数、阈值和安全门禁结构化。
6. 将大段资料拆到 references，将可重复动作实现成 scripts。
7. 先跑路由和工具评测，再上线主流程。
8. 发布版本，观察误触发、漏触发、失败点和成本。
9. 用真实 bad case 迭代并保留版本差异。

### D2C Skill 的最小骨架

```text
skills/d2c-consistency/
├── 主文档
├── references/
│   ├── 字段协议
│   ├── 规则与阈值
│   ├── 采集手册
│   └── 故障手册
├── scripts/
│   ├── 输入校验
│   ├── 数据标准化
│   └── 报告生成
└── evals/
    ├── 路由样例
    ├── 正常样例
    ├── 失败样例
    └── 安全样例
```

`SKILL.md` 放路由、主流程、关键约束和 references 的加载条件；阈值表、设备操作和完整字段说明放入可按需加载的参考资料。

## 失败与排障

| 现象 | 原因方向 | 修复方式 |
| --- | --- | --- |
| Skill 不触发 | description 不含真实意图或被相邻 Skill 抢占 | 加入输入字段、业务同义词和反例，做路由评测 |
| Skill 触发但步骤遗漏 | 正文只有背景，没有动作和完成条件 | 改成编号步骤、决策树和验收清单 |
| 工具参数经常错 | schema、示例和实际接口不一致 | 以代码 schema 为准，加入参数校验和负例 |
| 上下文越来越长 | 主文档混入所有资料和历史结果 | 做 references 分层和按需加载 |
| 改 Skill 后结果变差 | 没有版本化和回归集 | 冻结 eval，记录版本，比较轨迹和错误类型 |

## 面试应对

### 常考点及考法

| 考点 | 常见问法 |
| --- | --- |
| 定义 | Skill 和 Prompt、Tool 有什么区别？ |
| 设计 | 你会如何设计一个 Skill？ |
| 路由 | description 为什么重要？ |
| 维护 | Skill 如何评测和迭代？ |

### 解法/回答思路

先区分职责，再按“触发器、流程、工具、知识、验证、版本”回答。强调 Skill 是可复用的任务协议，不是把所有资料塞给模型。

### 易错点

- 把 Skill 说成 Prompt 模板。
- 只讲目录结构，不讲路由和评测。
- 把不稳定算法、权限门禁和阈值都交给文字规则。
- 没有反例，导致 Skill 和相邻能力互相抢路由。

### 回答模板

可直接回答：

> 我把 Skill 看成一类可复用任务的操作协议。它的 description 负责路由，正文负责输入要求、前置检查、执行步骤、工具选择、输出契约和失败处理，references 与 scripts 负责按需加载大段知识和可重复动作，evals 负责验证路由、步骤遵循、工具参数、结果完整性和安全边界。设计时我会先收集真实任务和相邻反例，再写完成条件，最后版本化发布。出现 bad case 后，先根据轨迹判断是路由、知识、工具、数据、Prompt 还是模型问题，再做最小修改和回归验证。
