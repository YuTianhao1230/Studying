# Skill 工程化：设计、路由、实现与迭代

## 知识点解析

### 概述

本卡片聚焦 D2C 视觉一致性场景中的 Skill 生产落地，包括任务拆分、路由描述、目录骨架、工具接入、上线顺序和 bad case 迭代。Skill 的通用定义、渐进式加载、Skill/Tool 边界、评测和版本机制见[《Skill》](<../基础概念/Skill.md>)。

### D2C Skill 的生产拆分

D2C 视觉一致性链路不宜做成一个覆盖所有阶段的大 Skill。可以按触发对象、工具链和验收标准拆分：

- **组件一致性检测**：接收设计截图、实现截图、Figma 节点和 Lynx 结构树，输出组件级差异与证据。
- **评测 case 归因**：读取固定输入、GT、运行轨迹和报告，定位采集、匹配、规则、VLM 或回写问题。
- **VLM 调用与报告校验**：负责模型请求、超时重试和 7 个子结果完整性检查。

三个 Skill 可以共享字段协议和报告格式，但各自保留独立 description、前置 gate、工具 allowlist 和回归集，避免采集故障误触发缺陷判定流程。

### D2C 路由描述

路由描述需要同时覆盖视觉比较、结构化输入和采集前置条件，并排除没有设计真值的审美评价：

```yaml
name: d2c-consistency
description: >
  当任务要求比较 Figma 设计稿与 Lynx 渲染结果，或需要分析组件尺寸、颜色、
  圆角、字号、字重、间距差异时使用。输入通常包含设计截图、实现截图、Figma
  节点或 Lynx 结构树。页面采集失败和设备连接问题也需要先按本 Skill
  的前置检查处理；普通图片美化和无设计真值的审美评价不使用。
```

上线前分别用“设计稿与实现对比”“采集失败排查”“普通图片美化”三组样例检查命中、漏触发和相邻误触发。

### D2C 内容与工具组织

主文档只保留当前任务必须执行的状态检查、步骤、工具顺序、完成条件和失败分支。D2C 资料按使用阶段组织：

- 颜色检测只加载颜色字段、采样区域和颜色阈值。
- 组件匹配加载层级特征、几何约束和一对一规则。
- 设备采集异常时再加载采集故障手册。
- `ui_element_matcher` 只生成候选匹配；Skill 负责要求两侧组件列表、匹配证据和不确定项复核。
- 输入校验、数据标准化、阈值计算和报告生成由 scripts 或工具实现，Skill 不重复实现确定性逻辑。

## 落地步骤

1. 收集 10 到 30 个真实任务，标注成功路径和失败路径。
2. 写 Skill 的适用边界和反例，先解决路由冲突。
3. 定义输入输出 schema、前置 gate 和完成条件。
4. 把流程写成编号步骤、分支和验收条件。
5. 把工具参数、阈值和安全门禁结构化。
6. 将大段资料拆到 references，将可重复动作实现成 scripts。
7. 先跑路由和工具评测，再上线主流程。
8. 发布版本，观察误触发、漏触发、失败点和成本。
9. 用真实 bad case 迭代并保留版本差异。

### D2C Skill 的最小骨架

```text
skills/d2c-consistency/
├── 主文档
├── references/
│   ├── 字段协议
│   ├── 规则与阈值
│   ├── 采集手册
│   └── 故障手册
├── scripts/
│   ├── 输入校验
│   ├── 数据标准化
│   └── 报告生成
└── evals/
    ├── 路由样例
    ├── 正常样例
    ├── 失败样例
    └── 安全样例
```

`SKILL.md` 放路由、主流程、关键约束和 references 的加载条件；阈值表、设备操作和完整字段说明放入可按需加载的参考资料。

## 失败与排障

| 现象 | 原因方向 | 修复方式 |
| --- | --- | --- |
| Skill 不触发 | description 不含真实意图或被相邻 Skill 抢占 | 加入输入字段、业务同义词和反例，做路由评测 |
| Skill 触发但步骤遗漏 | 正文只有背景，没有动作和完成条件 | 改成编号步骤、决策树和验收清单 |
| 工具参数经常错 | schema、示例和实际接口不一致 | 以代码 schema 为准，加入参数校验和负例 |
| 上下文越来越长 | 主文档混入所有资料和历史结果 | 做 references 分层和按需加载 |
| 改 Skill 后结果变差 | 没有版本化和回归集 | 冻结 eval，记录版本，比较轨迹和错误类型 |

## 面试应对

### 如何把 D2C 能力拆成可上线的 Skill？

回答思路：从任务边界、前置状态、工具链、验收标准和独立回归集解释拆分依据。

回答模板：

我会把组件一致性检测、评测 case 归因、VLM 调用与报告校验拆成独立 Skill，因为三者的触发对象、工具链和完成条件不同。每个 Skill 都固定输入、前置 gate、工具 allowlist、结果 schema 和回归集；字段协议与报告格式可以共享，但设备采集故障、组件判定和模型报告校验不能混在一个大流程中。这样出现 bad case 时可以沿轨迹定位并只修改对应能力。

### D2C description 如何控制路由冲突？

回答思路：用设计稿、实现截图、结构树等输入信号定义正例，并用图片美化、无 GT 审美评价定义反例。

回答模板：

我会在 description 中写清比较 Figma 设计稿与 Lynx 实现这一任务对象，并列出设计截图、实现截图、Figma 节点和 Lynx 结构树等输入信号。页面采集失败属于前置检查，普通图片美化和无设计真值的审美评价则明确排除。上线前分别用视觉比较、采集排障和相邻图片任务做路由回归，检查召回、漏触发和误触发。

### D2C Skill 如何上线和迭代？

回答思路：说明只读灰度、真实 case 回归、轨迹归因、单层修改和组合版本回滚。

回答模板：

我会先用只读 D2C case 验证路由、采集 gate、组件匹配、工具参数和报告完整性，再灰度接入真实任务。出现 bad case 后查看完整轨迹，区分 description、流程、字段协议、工具、数据、Prompt 或模型问题，只修改对应层，并在原 case 与相邻负例上回归。发布记录 Skill、工具 schema、阈值和评测集版本，结果下降时按组合版本回滚。
