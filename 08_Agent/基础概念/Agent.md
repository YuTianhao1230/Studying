# Agent

## 知识点解析

### 概述

Agent 是以大模型为决策核心，围绕目标感知环境、选择行动、调用工具、观察结果并迭代到结束状态的系统。本卡片保留 Agent 的定义、组成和紧凑开发框架；需求契约、架构决策、发布与运维见[《实战总览：从问题到生产 Agent》](<../实战落地/实战总览：从问题到生产Agent.md#实战总览从问题到生产-agent>)。

### 和普通 Chatbot 的区别

普通 Chatbot 更像问答器：

```text
用户问题 -> 模型回答 -> 结束
```

Agent 更像目标驱动的执行闭环：

```text
目标
  -> 观察当前状态
  -> 决定下一步
  -> 调用工具或执行动作
  -> 读取环境反馈
  -> 判断是否完成
  -> 继续、降级、求助或结束
```

核心差异不是模型更强，而是模型能够通过外部行动改变环境，并依据新观察调整后续决策。

### 核心组成

- **LLM Core**：理解目标，进行推理、规划和行动选择。
- **Tools**：文件系统、浏览器、数据库、API、命令行等外部能力。
- **Orchestrator**：维护 agent loop、状态、重试、终止和人工接管。
- **Context Engineering**：控制每次模型调用看到的任务信息与工具结果。
- **Memory**：保存跨步骤或跨任务仍有价值的信息。
- **Guardrails**：限制权限、预算、时间、危险动作和输出格式。
- **Observability**：记录状态变化、模型调用、工具调用、错误和耗时。
- **Evaluator**：判断任务是否完成以及结果是否满足标准。

这些组件不一定由独立服务实现，但职责必须清楚。模型负责开放决策，权限与副作用边界不能只靠模型自觉遵守。

### Agent Loop

典型循环为：

```text
Observe -> Plan -> Act -> Observe -> Reflect -> ...
```

也常称为 Thought-Action-Observation 或 ReAct Loop。一次循环至少回答：

1. 当前已知事实和未解决目标是什么。
2. 下一步行动是否需要工具。
3. 工具调用的参数和权限是否有效。
4. 新观察是否改变原判断。
5. 是否满足完成、失败、降级或人工接管条件。

循环必须设置最大步数、超时、预算、重复动作检测和结构化完成条件。

### Agent、Workflow 与 Tool

| 概念 | 核心职责 | 适合处理 |
| --- | --- | --- |
| Agent | 根据目标和反馈动态决策 | 路径不固定的多步任务 |
| [Workflow](<Workflow.md#workflow>) | 固定节点、分支与安全边界 | 稳定、可复现的流程 |
| [Tool Call](<Tool_Call与Function_Calling.md#tool-call-与-function-calling>) | 结构化请求外部能力 | 查询或改变外部环境 |
| [Context Engineering](<Context_Engineering.md#contextengineering>) | 组织当前模型可见信息 | 上下文质量与成本控制 |
| Memory | 保存可复用长期信息 | 偏好、经验和跨会话状态 |
| Guardrails | 限制风险与不合规行为 | 权限、预算、确认和输出校验 |
| Trajectory | 记录完整执行过程 | 复现、审计和 bad case 归因 |
| [Agent Eval](<Agent_Eval.md#agent-evaltrajectory-与-harness>) | 验证能力与可靠性 | 离线回归和版本比较 |

生产系统通常由 Workflow 固定主链路，只在局部开放节点使用 Agent，并通过 Tool 契约访问外部系统。

### 紧凑开发框架

开发一个 Agent 可以先回答六个问题：

1. **目标**：输入、输出和可验证完成条件是什么。
2. **决策**：哪些步骤确实需要模型动态选择，哪些应固定为程序或 Workflow。
3. **行动**：需要哪些 Tool，每个 Tool 的 schema、权限和副作用是什么。
4. **状态**：模型每轮需要看到什么，哪些信息需要跨步骤保存。
5. **边界**：最大步数、预算、超时、危险动作确认和失败退出如何定义。
6. **验证**：如何记录 trajectory，并用固定 case 判断结果和过程是否正确。

最小闭环为：

```text
一个清晰任务
  -> 一个受限 Agent Loop
  -> 少量结构化 Tool
  -> 明确终止条件
  -> 可回放 trajectory
  -> 固定 case 验证
```

先证明闭环有效，再扩展工具、记忆和自主性。生产架构、灰度、回滚和运行保障不属于概念定义，统一在实战总览展开。

### 什么时候适合用 Agent

适合：

- 任务需要多步执行。
- 中间结果会改变下一步决策。
- 需要在多个工具或系统间动态选择。
- 信息不完整，需要探索、验证和纠错。
- 结果可通过环境反馈或 evaluator 验证。

不适合：

- 单轮问答。
- 单个确定性 API 调用。
- 完全固定的 ETL 或审批流程。
- 高风险且无法审计、确认或回滚的自动操作。
- 没有可验证完成条件的模糊目标。

### 常见失败模式

- 目标漂移，行动逐渐偏离原任务。
- 工具选择或参数错误。
- 工具失败未写回状态，模型继续沿错误假设行动。
- 上下文污染或过长，关键约束被淹没。
- 没有终止条件，重复调用或无限循环。
- 把固定规则交给模型自由判断，增加随机性。
- 权限边界只写在 Prompt 中，没有后端校验。
- 没有 trajectory，失败后无法定位首次偏离点。

## 面试应对

### Agent 和 Chatbot 的区别是什么？

回答思路：抓住是否进入行动与反馈闭环。

回答模板：

Chatbot 主要根据用户输入生成回复；Agent 则围绕目标观察环境、选择工具、执行动作，并根据工具结果继续调整下一步。比如用户说“修复这个测试失败”，Chatbot 可能只给建议，而 Code Agent 会读代码、运行测试、修改文件并再次验证。核心区别是 Agent 能进入可迭代的执行闭环，而不只是生成文本。

### Agent Loop 一般由哪些阶段构成？

回答思路：按观察、规划、行动、反馈和终止讲完整循环。

回答模板：

典型 Agent Loop 包括目标理解、观察当前状态、规划下一步、调用工具、读取结果、更新判断和验证是否完成。未完成就继续循环，遇到失败则重试、降级或人工接管。系统还必须有最大步数、超时、预算、重复动作检测、权限校验和结构化终止条件。

### 什么任务适合 Agent，什么任务不适合？

回答思路：对比动态决策任务和确定性流程。

回答模板：

Agent 适合多步、开放、依赖工具反馈且中间结果会改变路径的任务；单轮问答、单个确定性 API、固定 ETL 或规则明确的审批流程不适合。工程上先用 Workflow 固定稳定步骤，只把确实需要语义判断、探索和动态工具选择的局部交给 Agent。

### Agent 系统的主要失败模式有哪些？

回答思路：覆盖目标、工具、上下文、循环、权限和可观测性。

回答模板：

常见失败包括目标漂移、工具或参数选错、工具失败后状态未更新、上下文污染、重复调用和无限循环、幻觉事实以及越权副作用。控制这些问题需要结构化状态、工具 schema、硬权限、预算和终止条件，并记录完整 trajectory，沿执行链找到首次偏离点后再针对性修复。

### 如何快速搭建一个最小 Agent？

回答思路：使用六问框架，强调先闭环再扩展。

回答模板：

我会先选一个有明确输入、输出和完成条件的任务，只开放少量结构化工具。然后实现 Observe-Plan-Act 循环，加入最大步数、超时、权限和失败退出，保存每轮状态与工具结果。最后用固定成功、失败和边界 case 验证结果与 trajectory。最小闭环稳定后，再扩展工具、记忆和自主性。
