# Agent

## 知识点解析

### 概述

Agent 是以大模型为决策核心，能够感知环境、规划步骤、调用工具、观察结果并迭代完成目标的系统。

### 和普通 Chatbot 的区别

普通 Chatbot 更像“问答器”：

```text
用户问题 -> 模型回答 -> 结束
```

Agent 更像“执行者”：

```text
目标
  -> 观察当前状态
  -> 规划下一步
  -> 调用工具 / 写代码 / 访问环境
  -> 读取结果
  -> 判断是否完成
  -> 继续迭代或交付结果
```

核心差异不是模型更强，而是系统允许模型进入闭环：它可以根据中间结果动态调整行动。

### Agent 通常包含什么

- LLM Core：负责推理、决策、规划。
- Tools：文件系统、浏览器、数据库、API、命令行等外部能力。
- Orchestrator：维护 agent loop，决定何时继续、停止、重试或升级给人。
- Context Engineering 与 Memory：保存短期上下文、长期偏好、历史经验。
- Guardrails：权限、预算、超时、危险操作确认、输出校验。
- Observability：记录每一步输入、工具调用、输出、错误和耗时。
- Evaluator：判断任务是否完成、输出是否可靠。

### Agent Loop

常见执行循环：

```text
Observe -> Plan -> Act -> Observe -> Reflect -> ...
```

也可以叫：

- Thought-Action-Observation
- ReAct Loop
- Perception-Planning-Action-Reflection

### 从 0 开发 Agent 的完整流程

开发 Agent 的本质，是构建一个由大模型驱动、能够调用工具、观察反馈、受到约束并且可以被评测的任务执行系统。

#### 1. 定义任务边界

第一步不是选择框架，而是明确 Agent 要解决什么问题：

- 输入是什么：自然语言、文件、网页、数据库、代码仓库还是多模态内容。
- 输出是什么：答案、报告、代码变更、工单、执行结果还是结构化数据。
- 成功标准是什么：准确率、完成率、耗时、成本、安全合规还是用户满意度。
- 失败边界是什么：哪些事情不能做，哪些动作必须人工确认。

如果任务可以用固定规则或普通 Workflow 稳定完成，就不一定需要 Agent。Agent 更适合开放任务、多步任务和依赖外部工具反馈的任务。

#### 2. 设计外层 Workflow

Workflow 负责把任务拆成稳定节点，例如需求解析、资料检索、方案生成、工具执行、结果校验和总结输出。

常见做法是用 Workflow 固定整体边界，在局部节点引入 Agent 处理不确定问题。这样既保留流程的可控性，又利用 Agent 的动态决策能力。

#### 3. 设计 Agent Loop

Agent 内部通常由以下阶段组成：

```text
目标理解
  -> 观察当前状态
  -> 规划下一步
  -> 调用工具
  -> 读取工具结果
  -> 判断是否完成
  -> 继续、重试、降级或结束
```

Loop 必须有最大步数、超时、失败退出、重复动作检测和明确完成条件，否则容易陷入无限循环。

#### 4. 接入工具和外部系统

为每个工具定义清晰的名称、用途、输入 schema、返回格式、错误信息和使用限制。工具设计要克制，工具太多会增加上下文成本和选择错误。

删除、发消息、改权限、提交任务等高风险工具，必须配合权限控制、参数校验和人工确认。

#### 5. 组织上下文和记忆

Context Engineering 决定每次模型调用能看到什么；Memory 负责保存跨步骤、跨会话和跨任务的长期信息。

上下文应足够完成当前任务，但不能把无关资料、过期结论和全部历史轨迹都塞进去。长期记忆也不能无条件保存，应该只保留稳定、有复用价值且允许更新的信息。

#### 6. 加入安全和人工兜底

通过权限、预算、超时、输出校验、危险动作确认和审计日志控制执行边界。

不可逆、高成本、高风险动作应在执行前展示具体参数、影响范围和预期变更，由人确认后再执行。

#### 7. 建立轨迹和评测闭环

记录每一步的输入、上下文、计划、工具调用、工具返回、状态变化、错误和最终输出。用固定数据集评估任务成功率、工具调用、轨迹质量、成本、延迟、安全和恢复能力。

只有完成“执行、观测、评测、修复”的闭环，Agent 才具备持续迭代的基础。

### 概念在系统中的位置

| 概念 | 作用位置 | 解决的问题 |
| --- | --- | --- |
| Workflow | 任务编排阶段 | 固定流程和安全边界 |
| Agent | 开放决策节点 | 动态规划、工具选择和多步推理 |
| Tool Call | 执行阶段 | 让模型结构化请求外部能力 |
| Context Engineering | 每次模型调用前 | 控制模型当前看到的信息 |
| Memory | 跨步骤和跨任务 | 保存长期稳定信息 |
| Guardrails | 全流程 | 控制权限、风险和失败退出 |
| Trajectory | 执行全过程 | 记录行为并支持诊断 |
| Agent Eval | 测试和上线阶段 | 判断系统是否可靠 |
| Harness | 评测工程层 | 组织数据、运行、打分和回归 |

### 什么时候适合用 Agent

适合：

- 任务需要多步执行。
- 中间结果会影响下一步决策。
- 需要调用多个工具或系统。
- 任务边界不完全固定，需要动态探索。
- 需要持续验证和纠错。

不适合：

- 单轮问答。
- 单个确定性 API 调用。
- 完全固定的 ETL 流程。
- 高风险且无法审计的自动操作。

### 常见误区

- 把 Agent 等同于“套了工具调用的 LLM”。
- 只关注规划，不关注执行状态和失败恢复。
- 没有终止条件，导致循环失控。
- 没有审计日志，出错后无法复盘。
- 把确定性流程硬做成 Agent，增加成本和不稳定性。

### 常考点及考法

常考 Agent 定义、Agent Loop、与 Chatbot/Workflow 的边界、适用场景、失败模式和生产化设计。

### 解法/回答思路

先给任务目标和自主决策的定义，再按观察、规划、行动、验证的闭环说明运行机制，最后补工具、状态、安全、评测和恢复。

### 易错点

只讲模型能力，不讲状态、工具权限、终止条件、失败恢复和评测；或把所有固定流程都包装成 Agent。

### 回答模板

回答 Agent 题目时可按“定义与边界 -> Agent Loop -> 工具和上下文 -> 安全与评测 -> 适用场景”的顺序展开。
## 面试应对

### Agent 和 Chatbot 的区别是什么？

回答思路：抓住"是否进入闭环、能否根据中间结果调整"这个本质差异，配一个例子。

回答模板：

Agent 和 Chatbot 的核心区别在于是否能围绕目标主动执行任务。Chatbot 主要是根据用户输入生成自然语言回复；Agent 除了对话，还会观察环境、拆解任务、选择工具、执行动作，并根据工具结果继续调整下一步。比如用户说“帮我修这个测试失败”，Chatbot 可能只给建议，而 Code Agent 会读代码、运行测试、修改文件并再次验证。

### Agent Loop 一般由哪些阶段构成？

回答思路：按 Observe-Plan-Act-Observe 的循环讲，并补上失败处理和生产要素。

回答模板：

一个典型 Agent Loop 包括目标理解、观察当前状态、规划下一步、调用工具执行、读取工具返回、更新判断、验证是否完成。如果没完成，就继续循环；如果失败，则进入重试、降级或人工接管。生产系统里还会加入权限校验、超时控制和轨迹记录。

### 什么任务适合 Agent，什么任务不适合？

回答思路：适合"多步/开放/需工具反馈"的任务，不适合"单轮/确定性/固定流程"，稳定流程优先 [Workflow](<Workflow.md>)。

回答模板：

适合多步、开放、需要工具反馈和动态决策的任务，比如中间结果会影响下一步、要调用多个系统、任务边界不固定需要探索；不适合单轮问答、单个确定性 API 调用、完全固定的 ETL 这类规则明确的流程，硬做成 Agent 只会增加成本和不稳定性。稳定流程优先用 Workflow，只有确实需要动态决策的部分才交给 Agent。

### Agent 系统的主要失败模式有哪些？

回答思路：列举高频失败模式，并落到靠轨迹和评测定位。

回答模板：

常见失败模式包括：目标漂移（做着做着偏离原目标）、工具选错或参数错误、上下文污染导致后续决策被带偏、没有终止条件导致无限循环、幻觉编造事实、越权执行危险操作，以及失败后不会恢复。要控制这些问题，需要完整的轨迹记录（每步输入、工具调用、输出、错误）加评测闭环来定位是哪一环出的问题，再针对性加护栏。

### 如何设计一个可观测、可恢复的 Agent？

回答思路：从 Observability 记录什么、Recovery 靠什么机制两方面落地。

回答模板：

可观测靠记录每一步的输入、上下文、计划、工具调用、结果、错误和耗时，形成可复盘的轨迹；可恢复靠把执行建成状态机，加超时、重试、断点（checkpoint）和人工接管入口。出错时不从头再来，而是从最近一个稳定状态继续，并结合护栏（权限、预算、危险操作确认）防止错误扩大。这样出问题能定位、能回滚，是把 Agent 从 demo 做到生产的关键。
