# Skill

## 知识点解析

### 概述

Skill 是 Agent 可以按需加载的一类领域能力包，用来固化任务触发条件、操作流程、特殊规则、工具使用方式、失败处理和验证标准。它不是一段更长的 Prompt，也不是工具清单，而是可路由、可执行、可评测、可维护的任务协议。

### 为什么需要 Skill

通用模型在以下场景容易不稳定：

- 业务流程和组织规范无法从常识推断。
- 外部工具有特殊参数、权限和失败语义。
- 同类任务需要固定输出格式和验收标准。
- 相邻任务容易误触发或混淆。
- 历史 bad case 已经暴露了稳定的失败模式。

Skill 将这些经验结构化，让 Agent 在需要时加载，而不是把全部知识永久塞进上下文。

### Skill 通常包含什么

```text
skill/
├── 主文档
├── references/
├── scripts/
├── assets/
└── evals/
```

- **主文档**：适用范围、触发条件、核心流程、约束和完成条件。
- **references**：低频的大段规则、字段协议、排障手册和领域资料。
- **scripts**：可重复的确定性动作，例如校验、转换和报告生成。
- **assets**：模板、schema、样例和固定资源。
- **evals**：路由、正常、失败、边界和安全评测样例。

### Skill 的核心原则

#### Description 是触发器

description 要说明能力对象、适用场景、输入特征、关键输出和不适用的相邻场景。描述太宽会误触发，太窄会漏触发。

#### 正文要高信号

正文重点写模型容易错、业务必须遵守、工具参数特殊、结果必须验证的内容。不要重复通用常识，也不要只写背景介绍。

#### 渐进式加载

高频约束放在主文档；低频规则放 references；可重复动作放 scripts。按任务阶段加载资料，减少上下文长度、成本和知识污染。

#### 业务规则与确定性逻辑分工

阈值计算、权限校验、数据转换和安全门禁应由程序保证；Skill 负责说明何时调用、如何组合、如何判断完成和如何处理异常。

### Skill 与 Prompt、Tool 的区别

- Prompt 是一次或一类模型调用的指令。
- Tool 是可执行的原子能力。
- Skill 是一类任务的完整操作规范，可以编排多个 Tool。
- Workflow 是多个节点、Skill 和工具之间的控制流程。
- RAG 是按需获取知识和证据的机制。

Skill 可以规定“什么时候调用哪个 Tool”，但不应该把工具的权限校验交给自然语言。

### Skill 的生命周期

```text
真实任务
  -> 提炼共同目标和失败模式
  -> 设计 description 和边界
  -> 编写主流程与工具契约
  -> 建立路由和任务评测
  -> 发布版本
  -> 观察 bad case
  -> 最小修改并回归
```

发布时记录版本、变更原因、影响的评测样例和兼容性。工具 schema、业务阈值或权限变化时，Skill 必须同步更新。

## 面试应对

### 常考点及考法

常考 Skill 与 Prompt、Tool 的区别，description 路由，目录分层，渐进式加载，评测和维护。

### 解法/回答思路

先说明 Skill 是可复用任务协议，再按触发器、执行流程、知识、工具、评测和版本迭代展开。

### 易错点

只写背景和目录，不写适用边界、反例、完成条件、工具参数和回归方式；或把所有稳定算法和权限门禁都交给文本规则。

### 回答模板

可直接回答：

> 我把 Skill 看成一类可复用任务的操作协议。description 负责路由，主文档负责输入要求、前置检查、执行步骤、工具选择、输出契约和失败处理，references 与 scripts 负责按需加载资料和确定性动作，evals 负责验证路由、步骤遵循、工具参数、结果完整性和安全边界。设计时先收集真实任务和相邻反例，再版本化发布；出现 bad case 后，根据轨迹判断是路由、知识、工具、数据、Prompt 还是模型问题，再做最小修改并回归。

### 什么时候应该设计 Skill？

回答思路：判断任务是否重复、是否有稳定流程、是否依赖领域规则和是否值得长期维护。

回答模板：

当一类任务会反复出现，且成功依赖固定流程、领域规则、工具参数或质量标准时，我会设计 Skill。一次性、完全确定的函数不需要 Skill；复杂且需要多工具协作的任务可以由 Skill 描述方法，再交给 Workflow 编排。

### 如何判断 Skill 是否有效？

回答思路：分别评估是否正确触发、是否按流程执行、工具是否调用正确和结果是否满足业务标准。

回答模板：

我会用真实任务集和相邻反例做评测，分别看触发召回、误触发率、步骤遵循、工具调用正确率、结果完整性、失败恢复和安全行为。发布后继续收集 bad case，并用版本对比确认修改没有引入回归。
