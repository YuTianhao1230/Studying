# Agent Eval、Trajectory 与 Harness

## 知识点解析

### 概述

[Agent](<Agent.md>) Eval 是评估 Agent 是否能稳定完成任务的体系，不只评最终答案，还要评规划、工具调用、轨迹、成本、安全和可恢复性。

### 和普通模型评测的区别

普通模型评测常见形式：

```text
输入 -> 模型输出 -> 和标准答案比较
```

Agent 评测更复杂：

```text
目标
  -> 多轮模型调用
  -> 多次工具调用
  -> 中间状态变化
  -> 可能修改外部环境
  -> 最终结果
```

所以 Agent Eval 要评估完整执行过程。

### Trajectory 与 Observability

Trajectory 是 Agent 完成任务过程中的完整轨迹；Observability 是记录、查看和分析这条轨迹的工程能力。

一次 Agent 任务通常由一串事件组成：

```text
用户输入
  -> 模型思考 / 计划
  -> 工具调用
  -> 工具返回
  -> 再次规划
  -> 文件修改
  -> 测试执行
  -> 最终回复
```

常见记录内容：

- 每轮模型输入和输出。
- 上下文版本和计划变更。
- 工具调用名称、参数和返回。
- 错误栈、重试次数和状态变化。
- 文件 diff。
- 外部 API 状态码。
- Token、耗时和成本。
- 人工确认记录。
- 最终结果和验收状态。

Trajectory 的价值是定位失败链路中的首次偏离点。失败可能来自用户意图、上下文、规划、工具选择、工具参数、工具结果理解、执行中断或最终汇总，而不是笼统的“模型问题”。

调试过程：

```text
最终结果错误
  -> 查看 trajectory
  -> 定位首次偏离点
  -> 判断是上下文、规划、工具、执行还是验证问题
  -> 修复 Prompt、Skill、Tool、Workflow 或 Eval
```

### Harness：评测脚手架

Harness 负责把数据、模型调用、输出解析、指标计算、日志记录和结果汇总串成可复现的评测流程。

典型链路：

```text
输入数据
  -> 数据校验
  -> Prompt / Request 构造
  -> 模型调用
  -> Response 解析
  -> 规则校验 / Judge
  -> 指标统计
  -> 结果落盘
  -> bad case 分析
```

常见模块：

- Dataset Loader：读取 JSONL、CSV、Parquet、DataCard 等数据。
- Validator：检查字段、标签、图片 URL、视频路径和任务类型。
- Prompt Builder：把样本转成模型输入。
- Model Client：调用本地模型、在线服务或推理框架。
- Parser：把原始输出解析成结构化预测。
- Evaluator：计算准确率、F1、召回率、格式正确率等指标。
- Reporter：输出 summary、失败样本和版本 diff。
- Runner：处理并发、重试、断点续跑和进度管理。

一个好的 Harness 应该具备：

- 可复现：数据、模型、参数和环境可追踪。
- 可恢复：中途失败后可以断点续跑。
- 可观测：逐样本保留 request、response、耗时和错误。
- 可对比：支持模型、Prompt、Skill 和 checkpoint 版本比较。
- 可扩展：增加模型、指标和数据格式时不需要大改。
- 可审计：保留配置、版本、日志和原始输出。

Harness 和 Trajectory 的关系是：Harness 负责系统化运行评测，Trajectory 是逐 case 的关键证据。Harness 的总分告诉你系统是否变好，Trajectory 告诉你为什么成功或失败。

### 常见评测维度

#### Task Success

最终任务是否完成。

例如：

- 文件是否正确修改。
- 测试是否通过。
- 数据是否正确导出。
- 页面操作是否完成。

#### Trajectory Quality

过程是否合理。

关注：

- 是否选对工具。
- 是否读取必要上下文。
- 是否绕路过多。
- 是否及时纠错。
- 是否遵守约束。

#### Tool Use Accuracy

工具调用是否正确。

关注：

- 工具选择。
- 参数准确性。
- 错误处理。
- 返回结果理解。

#### Safety

是否触发危险行为。

关注：

- 未授权写操作。
- 敏感信息泄露。
- 越权访问。
- 不该自动执行的动作。

#### Cost and Latency

Agent 是否高效。

关注：

- token 消耗。
- 工具调用次数。
- 运行耗时。
- 重试次数。
- 并发资源占用。

### 评测样例类型

- 正例：应该成功完成的任务。
- 负例：应该拒绝或要求确认的任务。
- 边界例：容易误判、误触发、路径复杂的任务。
- 回归例：历史失败 case。
- 对抗例：诱导越权、泄露、忽略规则的任务。

### 常见评测方法

- 规则检查：文件是否存在、字段是否正确、测试是否通过。
- LLM Judge：让模型按 rubric 评分。
- Trace Review：人工或模型审查 trajectory。
- Golden Set：固定任务集回归。
- A/B Test：比较两个 Agent、Prompt、[Skill](<Skill.md>) 或模型版本。

### 常见误区

- 只评最终答案，不看执行过程。
- 没有负例和安全例。
- LLM Judge 没有明确 rubric。
- 测试集和开发集混用。
- 成功标准含糊，导致评分不可复现。
- 不记录成本，导致系统上线后不可控。
- 只记录最终答案，不保存中间状态。
- 工具调用失败被吞掉。
- 没有稳定的 case ID，无法追踪和对齐结果。
- 失败归因只写“模型问题”。
- 失败样本直接跳过，导致指标虚高。
- 解析逻辑和评测逻辑混在一起，无法判断是输出错还是解析错。
- 修改 Prompt、数据或模型参数却没有记录版本。
- 没有断点续跑，大批量评测失败后只能全部重跑。

### 评测与诊断的最低闭环

每条评测样本至少应保留：

```json
{
  "id": "case_001",
  "request": "...",
  "response": "...",
  "prediction": "...",
  "correct": true,
  "trajectory": [],
  "latency_ms": 532,
  "error": null
}
```

比较两个版本时，必须使用同一套 Golden Set，并做 case-level diff：

- 共同错误。
- 新增错误。
- 已修复错误。
- 任务类型和错误原因分布变化。

平均分提升不代表真正变好，必须确认关键指标提升且没有引入新的严重回归。

### 常考点及考法

常考 Agent Eval 与普通 LLM Eval 的区别、trajectory、工具评测、Harness、bad case 归因和版本回归。

### 解法/回答思路

从最终任务、执行过程、工具、成本、安全和恢复多个维度回答，强调固定数据、原始轨迹和 case-level diff。

### 易错点

只看最终答案或平均分，不保存原始请求、工具结果、版本和失败证据。

### 回答模板

回答评测题目时可按“固定 case -> 记录 trajectory -> 分层指标 -> 首次偏离归因 -> 回归与发布”展开。
## 面试应对

### Agent Eval 和普通 LLM Eval 有什么区别？

回答思路：核心是"评单轮输出 vs 评完整多步执行过程"。

回答模板：

普通 LLM Eval 通常是"输入过模型出输出，再和标准答案比较"，评的是单轮结果。Agent Eval 面对的是一个多轮、多工具、会修改外部环境的执行过程，所以不能只看最终答案，还要评估整个 trajectory：任务是否真完成（Task Success）、过程是否合理（是否选对工具、有没有绕路、能否纠错）、工具调用是否正确、以及成本、延迟和安全性。一句话，普通 Eval 评"答得对不对"，Agent Eval 评"做得对不对、稳不稳、贵不贵、安不安全"。

### 如何评估工具调用是否正确？

回答思路：分"选对工具 / 参数对 / 时机对 / 结果用对"四层，最后落到执行结果验证。

回答模板：

我会分四层看：一是工具选得对不对，有没有该用检索却去写文件这种选错；二是参数对不对，是否符合 schema、值是否合理；三是调用时机对不对，比如是不是在信息不足时就贸然执行了高风险操作；四是工具返回结果有没有被正确理解和使用，别出现拿到报错却当成功继续走。光看这四层还不够，最后我会用 execution-based grader 或状态检查来验证任务是否真的完成，比如文件是否被正确改动、测试是否通过，因为工具调用看起来对、结果不对的情况很常见。

### Agent trajectory 是什么？

回答思路：定义为执行全过程记录，并说明它是调试、评测和审计的核心证据。

回答模板：

Agent trajectory 是任务执行全过程记录，包括观察、计划、工具调用、工具结果、错误和最终输出。它是调试、评测、审计和复盘 Agent 行为的核心证据。

### 如何排查一个 Agent 任务失败？

回答思路：沿 trajectory 逐步定位首次偏离点，再决定修复上下文、规划、工具还是调度逻辑。

回答模板：

沿 trajectory 从目标理解、上下文、计划、工具选择、参数、工具结果和最终判断逐步定位。先判断失败发生在哪一步，再决定修 Prompt、Skill、工具还是调度逻辑。

### Agent Observability 需要记录哪些信息？

回答思路：覆盖输入、上下文、计划、工具调用、结果、成本和状态；高风险操作还要保留审计证据。

回答模板：

需要记录任务输入、上下文版本、计划、工具名、参数、返回结果、错误、耗时、Token、成本和最终状态。高风险操作还要保存证据和审计日志。

### 为什么要评估 trajectory？

回答思路：核心是"只看最终答案会漏掉过程问题和偶然成功"，再落到定位失败根因。

回答模板：

因为 Agent 是多步执行的，只看最终答案会漏掉很多问题。同样一个"成功"，可能是它一步到位，也可能是绕了一大圈、调了危险工具、误读了中间结果，甚至只是碰运气蒙对的。trajectory 记录了从目标到输出的全过程，评估它才能看出这些问题：它是不是走了弯路、有没有越权操作、纠错能力如何。更实际的价值是定位失败根因——通过 trajectory 我能判断问题出在 prompt、Skill、工具还是调度逻辑上，从而知道该修哪里，而不是只知道"这次失败了"。

### 如何从 trajectory 反推需要修 Skill 还是修工具？

回答思路：工具本身有错误、结构不清或能力缺失时修工具；模型选择错误、漏步骤或误解约束时修 Skill、Prompt 或上下文。

回答模板：

如果工具返回错误、结构不清或能力缺失，优先修工具；如果模型选错流程、漏步骤或误解约束，优先修 Skill、Prompt 或上下文组织。通过 trajectory 找到首次偏离点后再决定修复边界，避免把所有问题都归因给模型。

### 如何设计 Agent 的负例和安全测试？

回答思路：列出典型负例/对抗场景，再点出"好 Agent 该拒绝、澄清、请求确认"。

回答模板：

负例和安全测试的核心是覆盖"不该直接做"的场景。我一般设计这几类：无权限操作（让它删库、改权限）、恶意或注入输入、前后冲突的指令、工具返回失败或异常、涉及敏感数据、根本无法完成的任务，以及诱导越权或忽略规则的对抗 case。评的时候不只看它会不会做任务，更看它在这些情况下的行为是否正确：该拒绝的要拒绝、信息不确定的要主动澄清、高风险操作前要请求人工确认。一个只会闷头完成任务、不会喊停的 Agent，在生产环境里是危险的。

### 如何比较两个 Agent 版本是否真的变好？

回答思路：强调固定任务集 + 多维指标 + case-level diff，避免只看单个平均分。

回答模板：

关键是用固定的任务集，别用不同的题去比，否则分数没有可比性。我会在同一套 golden set 上跑两个版本，对比几组指标：任务成功率、工具调用正确率、平均步数、成本、延迟、安全违规率，以及 bad case 的类型分布。更重要的是做 case-level diff，一条条看新版本修好了哪些旧问题、又引入了哪些新问题——因为平均分涨了也可能是"修了 A 却弄坏了 B"。只有关键指标提升、且没有引入新的严重回归时，我才判断它是真的变好，而不是被平均分误导。

### 如何设计一个模型评测 Harness？

回答模板：

我会把 Harness 拆成数据读取、模型调用、输出解析、指标计算、错误归因、并发控制和结果落盘模块。核心要求是可复现、可断点续跑、能定位失败原因，并支持不同模型版本对比。

### 如何区分模型错误、数据错误和服务错误？

回答思路：按样本输入、服务执行和模型输出三个阶段区分，并保留原始证据。

回答模板：

数据错误通常是样本缺字段、格式错误或标注不一致；服务错误是超时、异常、限流或依赖失败；模型错误是服务正常返回但答案不符合预期。要保留原始输入、输出、异常和解析结果，才能准确归因。

### 如何比较两个模型版本的 bad case 差异？

回答思路：按稳定样本 ID 对齐，区分共同错误、新增错误和已修复错误，再按任务类型归因。

回答模板：

按样本 ID 对齐两个版本的结果，统计共同错误、新增错误和修复错误，再按任务类型、错误原因和数据分布分组分析。这样可以判断平均分变化背后是否出现了重要回归。

### 如何支持并发评测和断点续跑？

回答模板：

每条样本要有稳定 ID，结果增量落盘，启动时跳过已完成样本。并发层控制速率、超时和重试，避免压垮服务。

### 为什么要保存原始 request 和 response？

回答模板：

它们是复现、审计和 bad case 分析的最小证据。只保存指标无法判断失败来自输入、模型输出还是解析逻辑。
