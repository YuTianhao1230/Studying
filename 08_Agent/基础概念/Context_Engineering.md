# Context_Engineering

## 知识点解析

### 概述

Context Engineering 是为 [Agent](<Agent.md>) 设计“当前应该看见什么信息”的工程方法，目标是在有限上下文窗口内提供足够、准确、低噪声的信息。

### 为什么重要

Agent 的能力不只取决于模型，也取决于上下文质量。

上下文太少：

- 缺少约束。
- 错过关键文件。
- 工具选择错误。
- 输出不符合预期。

上下文太多：

- token 成本高。
- 注意力被稀释。
- 旧信息污染新判断。
- 更容易漏看关键点。

### Context Engineering 包含什么

- 信息选择：哪些内容该放进上下文。
- 信息压缩：如何总结而不丢关键事实。
- 信息分层：哪些常驻，哪些按需读取。
- 检索策略：如何从文档、代码、记忆中取相关内容。
- 上下文隔离：不同任务、不同 Agent 不互相污染。
- 过期处理：旧结论何时失效。

### 常见上下文来源

- 用户需求。
- 系统指令。
- [Skill](<Skill.md>)。
- Memory。
- 代码文件。
- 文档。
- 工具返回。
- 历史错误。
- 当前计划。

### 好的上下文应满足什么

- Relevant：与当前任务相关。
- Grounded：来自可靠来源。
- Concise：足够短。
- Structured：便于模型定位。
- Fresh：反映当前状态。
- Actionable：能指导下一步动作。

### 渐进加载

Agent 不应该一次性读取所有资料，而应按需展开：

```text
目录 / 摘要
  -> 相关章节
  -> 具体片段
  -> 必要时读取全文
```

这和 Skill 的设计逻辑一致：入口要短，细节按需加载。

### Memory：跨步骤和跨会话的信息管理

Memory 是 Agent 保存和取回历史信息的机制，用来支持跨步骤、跨会话和跨任务的连续性。Memory 只有被检索并放入当前上下文后，才会影响模型决策。

没有 Memory 的 Agent 往往：

- 只知道当前上下文。
- 不记得用户偏好。
- 不知道历史失败。
- 不能复用过往经验。
- 长任务容易丢失状态。

#### Memory 的常见类型

| 类型 | 主要内容 | 适用信息 |
| --- | --- | --- |
| Short-term Memory | 当前对话上下文 | 当前约束、最近工具结果、临时计划 |
| Working Memory | 当前任务中间状态 | TODO、当前假设、已验证事实、重试状态 |
| Long-term Memory | 跨会话长期信息 | 用户偏好、项目约定、常用路径、经验教训 |
| Episodic Memory | 过去发生过的事件 | Debug 过程、评测结论、事故复盘 |
| Semantic Memory | 抽象后的知识 | 概念解释、领域规则、常见问题答案 |

Context 是当前模型调用能看到的信息；Memory 是可长期保存、后续检索的信息。二者不能混为一谈。

#### Memory 的设计原则

- 只保存长期有价值的信息。
- 不保存秘密、Token 和密码。
- 不保存一次性中间日志。
- 写入前去噪、压缩和结构化。
- 读取时按当前任务相关性检索。
- 记录来源、时间和适用范围。
- 允许更新、失效和删除。
- 区分用户偏好、项目约定和任务进度。

常见污染方式包括什么都记、把错误结论长期保留、把敏感信息写入记忆、无关任务全量读取以及只存不取。历史失败不应只保存原始日志，而应抽象成规则、测试、Skill gotcha 或 checklist。

### 常见误区

- 把所有文档直接塞给模型。
- 只做向量检索，不做结构化导航。
- 不区分事实、假设和历史结论。
- 忘记工具结果也会占上下文。
- 上下文压缩时丢掉关键约束。

### 常考点及考法

常考 Context Engineering 与 Prompt Engineering 的区别、渐进加载、Memory 类型、上下文压缩和污染控制。

### 解法/回答思路

围绕“当前这一步应该看到什么”组织答案，说明信息筛选、优先级、版本、时间、隔离和按需检索。

### 易错点

把所有历史资料塞进上下文，忽略 token、延迟、注意力稀释、过期信息和跨任务污染。

### 回答模板

回答上下文题目时可按“信息来源 -> 选择与压缩 -> 记忆分层 -> 注入时机 -> 过期与污染治理”说明。
## 面试应对

### Context Engineering 和 Prompt Engineering 有什么区别？

回答思路：点明"写好一段指令 vs 管理整个上下文窗口该看见什么"的层次差异，再落到 Agent 场景。

回答模板：

Prompt Engineering 关注的是怎么把一段指令写好，让模型在单次调用里输出更符合预期，重点在措辞、示例、格式约束。Context Engineering 的范围更大，它关注的是在有限的上下文窗口里，Agent 每一步到底该看见哪些信息：包括信息怎么选、怎么压缩、哪些常驻哪些按需检索、不同任务之间怎么隔离、过期信息什么时候失效。可以说 Prompt 是其中一环，但 Agent 是多步执行、上下文会不断累积和污染的，所以真正决定 Agent 稳定性的往往不是某句 prompt 写得多好，而是整个上下文的组织。工程上我会优先保证上下文相关、简洁、有来源，而不是一味把资料堆进去。

### 为什么 Agent 不能把所有资料都放进上下文？

回答思路：从窗口有限、成本、注意力稀释和过期信息干扰四点讲，再给正确做法。

回答模板：

主要有几个原因：一是上下文窗口本身有限，塞不下；二是 token 越多成本越高、延迟越大；三是无关信息会稀释注意力，模型反而更容易漏看真正关键的约束；四是里面可能混入过期或不相关的信息，干扰当前决策。所以正确做法不是全塞进去，而是按当前任务只检索最相关的信息，并给这些信息标注来源和时间，让模型知道它可信、且是不是最新的。

### 如何设计长期任务的上下文管理？

回答思路：按"当前状态 / 长期记忆 / 外部资料 / 执行轨迹"四层分工来讲。

回答模板：

长期任务的关键是分层，不能把所有历史都堆在上下文里。我会分成四块：当前任务状态只放当下这一步决策需要的信息，保持精简；长期记忆（用户偏好、稳定结论）单独存，用检索按需注入；外部资料（代码、文档）也走检索，用到哪段取哪段；执行轨迹落盘保存，用于失败恢复和复盘，而不是常驻上下文。这样窗口里始终只有当前需要的信息，历史信息随时能检索回来，任务再长也不会被上下文撑爆或污染。

### 如何避免旧上下文污染当前决策？

回答思路：核心是给信息打标签、过期不默认注入、关键决策前重新验证。

回答模板：

旧上下文污染的典型场景是：早期读到的一个结论后来已经变了，但模型还拿它当事实继续用。我的做法有三点：一是给每条上下文标注来源、时间和适用范围，让模型能判断它是不是还有效；二是过期或已被推翻的信息不默认注入，必要时显式标记为"已失效"；三是在关键决策前重新检索或验证一次当前状态，比如改代码前重新读一下文件，而不是依赖几轮前的旧内容。核心就是不让模型基于过时假设继续行动。

### Skill 的 progressive disclosure 和 Context Engineering 是什么关系？

回答思路：说明 progressive disclosure 是 Context Engineering 中“按需加载、控制上下文成本”的具体落地。

回答模板：

Context Engineering 关注每一步应该给模型哪些信息，progressive disclosure 则把这个原则落到 Skill 的目录和加载方式上：入口只保留触发条件和核心规则，详细资料、脚本和模板在真正需要时再读取。这样既能提供足够上下文，又不会让所有低频内容长期占用窗口。

### Agent Memory 有哪些类型？

回答模板：

常见有短期工作记忆、长期用户或项目记忆、情节记忆、语义记忆和外部状态存储。不同记忆的写入标准不同，不能把临时信息都写进长期记忆。

### Memory 和 Context Window 的区别是什么？

回答模板：

Context Window 是模型当前能看到的有限文本；Memory 是可跨步骤或跨会话保存的信息。Memory 只有被检索并注入后，才会进入当前上下文影响模型。

### 什么信息适合写入长期记忆？

回答模板：

适合写稳定偏好、长期规则、项目约定、可复用经验和反复出现的错误教训。不应写临时状态、敏感信息或未经确认的猜测。

### 如何避免 Memory 污染？

回答模板：

写入前筛选稳定性、来源和适用范围；读取时按当前任务相关性注入，而不是全量注入。过期或错误记忆要能更新和删除。

### Agent 如何利用历史失败经验提升稳定性？

回答模板：

把失败原因抽象成规则、测试、Skill gotcha 或 checklist。下次同类任务执行前加载相关经验，提前避开已知坑，而不是只保存原始失败日志。

回答思路：说明 progressive disclosure 是 Context Engineering "按需加载"思想的具体落地。

回答模板：

progressive disclosure（渐进式披露）是 Context Engineering "按需加载、分层暴露"思想的一个具体落地。平时上下文里只放 Skill 的名字和一句简短描述，让模型知道有这个能力、什么时候该用；只有真正命中这个场景、要用的时候，才把 SKILL.md 的详细规则、references 文档或脚本加载进来。这样既保留了完整能力，又不会让一堆细节常驻上下文、稀释注意力和抬高成本。本质上就是把"能力清单"和"能力细节"分层，和 Context Engineering 追求的相关、简洁、低噪声是一致的。
