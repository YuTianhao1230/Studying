# Skill 协同工作流

## 知识点解析

### 概述

Skill 协同不是把所有能力同时加载，而是根据任务阶段选择负责设计、状态管理、实现、排障和交付检查的 Skill。核心目标是让每个 Skill 只处理自己的职责，并通过明确的输入、产物和验证条件完成交接。

### 三类能力的职责

| 能力 | 主要职责 | 典型产物 |
| --- | --- | --- |
| [Superpowers](<Superpowers.md>) | 约束软件开发流程，覆盖设计、计划、实现、测试、调试、审查和完成验证。 | 设计结论、实现计划、测试证据和审查结果。 |
| [Planning with Files](<Planning_with_Files.md>) | 持久化长任务的目标、发现、阶段状态、错误和下一步。 | `task_plan.md`、`findings.md`、`progress.md`。 |
| [No Negative Echo](<No_Negative_Echo.md>) | 根据最终接受状态整理标题、正文、元数据和交接表面。 | 与最终结果一致的文档、说明和 handoff。 |

三者解决的问题不同：Superpowers 决定开发阶段采用什么方法，Planning with Files 保存跨阶段状态，No Negative Echo 在交付前检查读者实际看到的表面。它们可以组合，但不能互相替代。

### 选择规则

1. 任务涉及创造性设计、功能新增或行为变化时，先用 Superpowers 的 brainstorming 明确目标、边界和验收标准。
2. 任务包含多个阶段、需要较多工具调用或可能跨上下文时，启用 Planning with Files 保存计划、发现和进度。
3. 设计获得确认后，根据任务类型进入实现计划、测试驱动开发或系统化调试。
4. 每个阶段都用真实命令、运行结果或文件回读验证，不能把生成测试或写下计划当成完成。
5. 交付文档、标题、索引、提交说明或 handoff 前，使用 No Negative Echo 从最终状态重新检查完整表面。

### 标准协同流程

```text
识别任务类型与风险
  -> 明确目标、范围和验收标准
  -> 长任务建立文件化计划
  -> 读取仓库和当前状态
  -> 分阶段实现或系统化排障
  -> 运行与风险相匹配的验证
  -> 回读最终文件和实际状态
  -> 整理交付表面
```

典型组合：

| 场景 | 推荐组合 |
| --- | --- |
| 小范围行为变更 | brainstorming → 实现与测试 → verification-before-completion |
| 多阶段开发 | brainstorming → Planning with Files → writing-plans/executing-plans → verification-before-completion |
| 复杂故障 | Planning with Files → systematic-debugging → test-driven-development → verification-before-completion |
| 文档或索引规范化 | Planning with Files → 增量修改 → 链接与结构检查 → No Negative Echo |
| 并行开发 | using-git-worktrees → 独立任务计划 → 分工执行 → 汇总审查 |

### 交接契约

相邻 Skill 之间至少交接以下信息：

- 当前目标、明确范围和非目标。
- 已确认的设计或问题假设。
- 已修改文件、未完成步骤和已知错误。
- 验证命令、实际输出和剩余风险。
- 需要读回的最终表面及其受众。

计划文件只记录工作状态，不自动成为最终文档；调试结论必须有运行时证据；交付检查不能替代测试。若用户明确限制提交、并行或外部操作，限制应贯穿所有阶段。

### 常见失配

- 需求尚未确认就进入实现，导致后续反复改方向。
- 简单任务套用完整长任务流程，过程成本高于收益。
- 长任务只依赖聊天记录，没有可恢复的状态文件。
- 遇到错误直接改代码，没有先稳定复现和定位根因。
- 只运行词面扫描，没有回读最终语义和实际文件。
- 多个 Agent 共享同一计划或工作区，同时写入造成覆盖。

## 面试应对

### 如何组合流程类 Skill，而不是让它们互相重复？

回答思路：先按设计、状态管理、执行验证和交付表面分工，再说明每一步的交接产物。

回答模板：

我会先按职责拆分 Skill。Superpowers 负责决定当前处于需求、设计、实现、调试还是验证阶段；Planning with Files 负责把长任务的目标、发现、进度和错误持久化；No Negative Echo 负责在交付前从最终状态检查标题、正文、元数据和 handoff。它们通过明确产物交接，例如设计结论进入计划，执行结果进入进度和验证记录，最后再回读实际文件。这样每个 Skill 只解决一类问题，不用重复维护同一套流程。

### 什么任务值得启用 Planning with Files？

回答思路：用阶段数、工具调用量、上下文持续时间和恢复需求判断，并说明简单任务不必机械启用。

回答模板：

当任务有多个阶段、需要频繁检索或工具调用、可能经历上下文压缩，或者必须记录决策和错误以便恢复时，我会启用 Planning with Files。计划文件保存目标和阶段，发现文件保存调研结论，进度文件保存执行与验证结果。一次性查询或单文件小改动通常不需要额外计划，关键是让状态管理成本与任务复杂度匹配。

### 如何证明 Agent 的流程约束真正生效？

回答思路：分别验证触发、步骤遵循、产物和最终行为，强调文件存在不等于宿主已加载。

回答模板：

我会分四层验证。第一层确认任务是否触发了正确 Skill；第二层检查关键步骤是否按约束执行；第三层核对计划、测试或审查产物是否完整；第四层运行真实命令并回读最终结果。对于本地 Skill，还要区分“文件已安装”和“当前宿主已加载”，后者必须以会话公开能力或实际触发结果验证，不能只看目录存在。
