# Java 基础

## 知识点解析

### 概述

Java 以静态类型、面向对象、字节码和 JVM 运行时为核心。面试中既要说明语言表面规则，也要解释集合、并发和内存管理的底层机制，并明确结论适用的 JDK 版本与使用边界。本文涉及的 `HashMap` 结构以 JDK 8 及之后的主流实现为准。

### 类型、对象与参数传递

Java 类型分为基本类型和引用类型。基本类型变量直接保存数值，引用类型变量保存对象引用；对象通常位于堆中，局部变量和调用帧位于线程私有的虚拟机栈中，但具体布局可被 JVM 优化。

Java 只有值传递。传递基本类型时复制数值，传递引用类型时复制引用本身，因此方法可以通过副本修改同一个对象的状态，却不能让调用方变量改为指向另一个对象。

- `==` 比较基本类型的值；用于引用类型时比较两个引用是否指向同一对象。
- `equals` 表示逻辑相等，默认实现仍等价于引用相等，值对象通常需要重写。
- 重写 `equals` 时必须同步重写 `hashCode`，保证相等对象具有相同哈希值；哈希值相同不代表对象相等。
- `String` 不可变，字符串常量池可以复用字面量对象，但不能依赖对象地址判断文本内容。

### 面向对象与多态

封装通过访问控制隐藏可变状态和实现细节，继承复用父类契约，多态允许同一接口根据对象实际类型产生不同行为。Java 类只能单继承，但可以实现多个接口；接口适合表达能力契约，抽象类还可以保存实例状态、构造逻辑和部分实现。继承会形成较强耦合，只有存在稳定的 is-a 关系时才适合使用，单纯复用实现通常优先考虑组合。

重载发生在同一类名或继承体系中，由参数列表区分，编译期根据参数的静态类型选择；仅改变返回类型不能构成重载。重写要求子类提供与父类实例方法兼容的签名和返回类型，运行时根据对象实际类型动态分派。`static` 方法按静态类型隐藏而不是重写，`private` 方法对子类不可见，`final` 方法不能被重写。使用 `@Override` 可以让编译器检查重写关系。

### JVM 执行与内存管理

Java 源码先编译为字节码，JVM 经过类加载、验证、链接和初始化后解释或即时编译执行热点代码。类初始化按需发生，静态字段赋值和静态代码块按源码顺序执行；父类通常先于子类初始化。

JVM 运行时区域常见划分如下：

| 区域 | 作用 | 线程关系 |
| --- | --- | --- |
| 堆 | 保存对象和数组，是垃圾回收的主要区域 | 共享 |
| 虚拟机栈 | 保存 Java 方法栈帧、局部变量和操作数栈 | 私有 |
| 本地方法栈 | 支持本地方法调用 | 私有 |
| 程序计数器 | 记录当前线程执行位置 | 私有 |
| 方法区 | 保存类元数据、运行时常量池等逻辑数据；HotSpot 通常由 Metaspace 实现 | 共享 |

垃圾回收器以可达性分析判断对象是否仍能从 GC Roots 到达，并按所选收集器执行标记、复制、整理或清除。GC 负责回收不可达对象占用的托管内存，不保证何时发生，也不能替代文件、套接字和数据库连接等外部资源的显式释放；这类资源应使用 `try-with-resources` 管理。

### HashMap 核心机制

JDK 8 的 `HashMap` 以数组保存桶，桶内使用链表；当同一桶中的节点达到树化阈值且数组容量至少为 64 时，可转为红黑树，以降低严重冲突时的查找成本。容量不足 64 时优先扩容，因为扩大桶数组通常比立即树化更能缓解冲突。

查找和插入先对键的 `hashCode` 做扰动，再通过 `(n - 1) & hash` 定位桶。容量保持为 2 的幂，使位运算可替代一般取模，并使扩容到两倍后节点只可能留在原桶或移动到“原下标 + 旧容量”。默认负载因子是 0.75；元素数量超过阈值后通常扩容，以空间换取较低冲突率。

`HashMap` 的平均查找和插入复杂度为 O(1)，但该结论依赖哈希分布和负载控制；链表严重冲突时会退化，树化桶的操作通常为 O(log n)。它允许一个 `null` 键和多个 `null` 值，不保证遍历顺序，也不保证并发安全。并发读写应根据场景使用 `ConcurrentHashMap`、外部同步或不可变快照，不能把快速失败迭代器当作并发正确性机制。

### Java 内存模型与同步

Java 内存模型定义线程间读写共享变量的可见性和有序性，并通过 happens-before 规则判断一个线程的写入何时对另一个线程可见。

- `synchronized` 同时提供互斥、可见性和有序性，锁是可重入的；退出监视器 happens-before 后续对同一监视器的成功加锁。
- `volatile` 保证对该变量的写入对后续读取可见，并限制相关指令重排，但不把 `count++` 这类读改写复合操作变成原子操作。
- 原子类适合单变量原子更新；多个变量需要共同维持不变量时，通常仍需锁或其他协调协议。
- 不可变对象、线程封闭和消息传递可以减少共享可变状态，往往比增加锁更容易保证正确性。

### 线程池

`ThreadPoolExecutor` 的关键参数包括核心线程数、最大线程数、空闲存活时间、任务队列、线程工厂和拒绝策略。提交任务时，典型决策顺序是：

1. 工作线程少于核心线程数时，创建工作线程执行任务。
2. 核心线程已满时，尝试把任务放入队列。
3. 队列已满且线程数小于最大线程数时，再创建非核心线程。
4. 队列已满且线程数达到最大值时，执行拒绝策略。

无界队列通常不会“满”，因此最大线程数可能失去扩容作用，积压任务还可能耗尽内存。生产环境应根据任务是 CPU 密集还是 IO 密集、下游容量、延迟目标和峰值流量选择线程数与有界队列，并明确拒绝、超时、取消、异常记录和优雅关闭策略。`Executors` 的便捷工厂适合简单场景，但隐藏的无界队列或近似无界线程数不利于容量控制。

### 泛型、异常与资源

Java 泛型主要通过类型擦除实现，编译器在编译期检查类型并插入必要的类型转换。擦除意味着运行时通常无法获得完整类型参数，不能直接创建 `new T()` 或 `new T[]`，也不能用基本类型作为类型实参。读取生产者常用 `? extends T`，写入消费者常用 `? super T`，即 PECS 原则。

受检异常要求捕获或声明，非受检异常通常表示编程错误、前置条件不满足或不可恢复状态。不要只按异常类别机械选择处理方式：应在能够恢复、补充上下文或完成边界转换的层处理异常，不能静默吞掉。`finally` 通常会执行，但进程强制终止等情况除外；释放实现 `AutoCloseable` 的资源应优先使用 `try-with-resources`。

### 核心边界与易错点

- Java 是值传递，传对象时复制的是引用值，不存在“引用传递”。
- `HashMap` 的树化同时受桶节点数和数组容量约束，不是冲突到 8 个就必然树化。
- `HashMap` 不是线程安全容器，`Collections.synchronizedMap` 和 `ConcurrentHashMap` 的并发语义也不同。
- `volatile` 不保证复合操作原子性，线程安全不能只看单次读写。
- 线程池不是越大越快；过多线程会增加调度、内存和下游竞争成本。
- GC 只管理可达性意义上的托管内存，不负责及时关闭外部资源。
- `final` 引用不能重新赋值，但其指向对象的内部状态仍可能可变。

## 面试应对

### HashMap 的底层结构、查找和扩容过程是什么？

回答思路：按“定位桶、处理冲突、扩容迁移、复杂度与边界”展开，并说明版本前提。

回答模板：

以 JDK 8 为例，HashMap 使用桶数组，桶内先用链表保存冲突节点；当桶中节点达到树化阈值且数组容量至少为 64 时，可转为红黑树。查找时先对 hashCode 做扰动，再用 `(n - 1) & hash` 定位桶，最后通过 hash 和 equals 确认键。默认负载因子为 0.75，超过阈值后容量通常翻倍；由于容量是 2 的幂，节点扩容后只会留在原位置或移动到原下标加旧容量。平均查询是 O(1)，严重冲突会退化，而且 HashMap 不保证线程安全和遍历顺序。

### Java 线程池提交任务时如何决策，参数怎么设置？

回答思路：先说任务进入路径，再结合任务类型、队列容量和过载策略说明参数不能套固定公式。

回答模板：

ThreadPoolExecutor 收到任务后，先在工作线程少于核心线程数时创建线程；核心线程已满后尝试入队；队列满且线程数未到最大值时再扩线程；线程和队列都满时执行拒绝策略。参数要根据 CPU 或 IO 密集程度、任务耗时、到达速率、下游容量和延迟目标压测确定。我会优先使用有界队列，明确拒绝或降级策略，并监控活跃线程、队列长度、完成量和拒绝量。无界队列会让最大线程数基本失效，还可能因任务积压造成内存问题。

### volatile 和 synchronized 有什么区别？

回答思路：从可见性、有序性、原子性和适用场景比较，重点说明复合操作边界。

回答模板：

volatile 保证对该变量的写入对后续读取可见，并限制相关指令重排，适合状态标志或单次独立读写，但不能让 `count++` 这类复合操作原子化。synchronized 通过同一监视器提供互斥，同时建立解锁到后续加锁的 happens-before 关系，因此还能保护多个操作或多个变量组成的不变量。单变量原子更新也可用原子类；涉及复合状态时应使用锁或更明确的并发协议。

### `==`、equals 和 hashCode 应如何配合？

回答思路：区分身份和值语义，再说明哈希容器依赖的契约。

回答模板：

对基本类型，`==` 比较数值；对引用类型，`==` 比较是否指向同一对象。equals 用于表达逻辑相等，但 Object 的默认实现仍是身份相等。值对象重写 equals 时必须同步重写 hashCode，因为哈希容器先按哈希值定位桶，再用 equals 判断键是否相等。契约要求相等对象的哈希值必须相同，但哈希值相同的对象不一定相等；对象作为哈希键期间，也不应修改参与 equals 和 hashCode 计算的字段。

### JVM 垃圾回收能否避免所有内存和资源问题？

回答思路：先限定 GC 管理对象内存，再区分内存泄漏、外部资源和回收时机。

回答模板：

不能。GC 根据对象是否可从 GC Roots 到达来回收托管内存，因此被无用集合、缓存、监听器或 ThreadLocal 持有的对象仍然可达，会形成逻辑内存泄漏。GC 也不保证立即执行，不能作为释放时机；文件句柄、套接字和数据库连接等外部资源应通过 try-with-resources 显式关闭。排查时要结合堆使用趋势、对象保留链、分配速率和 GC 日志，而不是只看是否存在垃圾回收器。
