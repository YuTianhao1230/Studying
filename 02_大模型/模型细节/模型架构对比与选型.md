# 模型架构对比与选型

## 知识点解析

### 概述

本文整理大模型选型时常见的架构对比维度，包括 Encoder-only、Decoder-only、Encoder-Decoder、Dense、MoE、长上下文、多模态连接器、推理模型、RAG、Agent 和部署成本。

### 为什么需要模型选型框架

面试中问“你了解哪些模型”时，不应该只罗列模型名。更好的回答是先建立维度：

```text
任务类型 -> 模型范式 -> 能力需求 -> 工程约束 -> 评测方式
```

例如：

- 做文本分类：BERT 类 encoder 或小型 decoder 都可以。
- 做开放生成：Decoder-only LLM 更自然。
- 做翻译摘要：Encoder-Decoder 或 Decoder-only 都可，根据生态和部署选。
- 做图文检索：CLIP/SigLIP 类双塔模型合适。
- 做视觉问答：VLM/MLLM，需要视觉编码器和 LLM。
- 做复杂代码 Agent：需要强推理、长上下文、工具调用和执行环境。

### Encoder-only、Decoder-only、Encoder-Decoder

| 架构 | 代表模型 | 输入输出方式 | 适合任务 | 局限 |
| --- | --- | --- | --- | --- |
| Encoder-only | BERT、RoBERTa、DeBERTa | 双向编码输入 | 分类、匹配、抽取、检索 rerank | 不擅长自回归生成 |
| Decoder-only | GPT、Llama、Qwen、DeepSeek | 从左到右生成 | 对话、生成、代码、推理、Agent | 输入理解通过生成式目标间接获得 |
| Encoder-Decoder | T5、BART、Flan-T5 | 编码输入，解码输出 | 翻译、摘要、结构化生成 | 通用聊天生态不如 decoder-only 主流 |

选择逻辑：

1. 如果输出是固定类别或短标签，Encoder-only 更轻。
2. 如果输出是开放文本或多轮对话，Decoder-only 更自然。
3. 如果输入和输出边界明确且需要条件生成，Encoder-Decoder 仍有价值。

### Dense 和 MoE

Dense 模型每次推理都会激活全部参数。MoE 模型有多个专家，每个 token 只路由到部分专家：

```text
token hidden state
  -> router
  -> top-k experts
  -> weighted combine
```

| 对比项 | Dense | MoE |
| --- | --- | --- |
| 参数激活 | 全部激活 | 部分专家激活 |
| 训练稳定性 | 相对简单 | 需要负载均衡和路由稳定 |
| 推理部署 | 简单 | 专家并行和通信更复杂 |
| 成本效率 | 总参数越大成本越高 | 可用较低激活参数扩大容量 |
| 代表模型 | Llama dense、Qwen dense | DeepSeek-V3/R1、Mixtral、部分 Qwen MoE |

MoE 的核心价值是“总容量大、激活成本低”，但不是免费变强。它会引入路由、专家负载不均、通信开销和服务批处理复杂度。

### 注意力与长上下文

长上下文模型常见优化：

- RoPE scaling：扩展位置编码适配更长序列。
- GQA/MQA：减少 KV head 数，降低 KV Cache。
- MLA：压缩 KV 表示，进一步降低长上下文缓存成本。
- Sliding window attention：只看局部窗口，控制复杂度。
- FlashAttention：通过 IO-aware 算法降低显存读写开销。
- RAG：不把所有知识塞进上下文，先检索再生成。

长上下文能力要区分三件事：

1. 能不能放进去：上下文窗口大小。
2. 能不能找得到：长文档定位和 needle-in-haystack。
3. 能不能用得对：引用、推理和跨段整合是否可靠。

### 多模态连接方式

| 连接方式 | 代表模型 | 架构思路 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| 双塔对比 | CLIP | 图像编码器和文本编码器各自输出 embedding | 检索、zero-shot 强 | 不能直接生成 |
| 融合编码 | ALBEF、TCL | 先单模态编码，再跨模态融合 | 理解和匹配强 | 生成能力依赖额外头 |
| Query bridge | BLIP-2 | Q-Former 从视觉特征抽取少量 query | 低成本连接冻结 LLM | 视觉信息压缩可能丢细节 |
| Projector bridge | LLaVA | CLIP 特征经 projector 接入 LLM | 简单有效、易复现 | 依赖指令数据和视觉编码器 |
| Gated cross-attention | Flamingo | LLM 层间插入视觉 cross-attention | 支持交错图文 few-shot | 训练和架构更复杂 |
| 原生多模态 | GPT-4o、Gemini、Qwen-Omni | 统一处理文本、图像、音频、视频 | 交互自然、能力完整 | 公开细节少，训练成本高 |

多模态模型选型要看任务。如果只是图文检索，CLIP 双塔高效；如果要 VQA 和对话，LLaVA/BLIP-2/Qwen-VL 更合适；如果要实时音视频交互，需要原生多模态模型。

### 推理模型和普通指令模型

普通指令模型主要学习“看到指令后直接给好答案”。推理模型通过推理时计算和可验证奖励，强化数学、代码、规划等任务中的多步探索。

| 对比项 | 普通指令模型 | 推理模型 |
| --- | --- | --- |
| 输出方式 | 快速直接回答 | 可能先进行长思考 |
| 优势 | 延迟低，适合通用问答 | 复杂推理、代码、数学更强 |
| 成本 | 较低 | 较高 |
| 风险 | 复杂题容易浅答 | 过度思考、长度偏置、成本不可控 |
| 代表 | GPT-4o、Qwen Instruct、Llama Instruct | o 系列、DeepSeek-R1、QwQ/Qwen3 thinking |

选型时不要所有任务都用推理模型。分类、抽取、简单改写和格式转换通常用小模型或普通 instruct 模型即可。

### RAG、微调、长上下文怎么选

| 场景 | 优先方案 | 原因 |
| --- | --- | --- |
| 知识频繁更新 | RAG | 避免反复训练，便于权限控制 |
| 固定输出格式和风格 | SFT | 让模型学会任务格式和领域表达 |
| 私有知识问答 | RAG + 权限过滤 | 知识可追溯，降低泄漏风险 |
| 长文档一次性分析 | 长上下文模型 | 减少切块损失 |
| 专业流程自动化 | SFT + RAG + 工具 | 知识、格式和执行都需要 |
| 数学/代码可验证任务 | RLVR/推理模型 | 可以用正确性 reward 强化 |

### 工程选型步骤

1. 定义任务输出：分类、抽取、生成、检索、推理、视觉问答还是 Agent 执行。
2. 定义约束：延迟、成本、并发、上下文、数据安全、部署方式。
3. 建立候选：强闭源 API、开源大模型、小模型、RAG、规则或传统 ML。
4. 小样本评测：用真实业务样本和 bad case，不只看公开榜单。
5. 分桶分析：按任务类型、输入长度、语言、难度、多模态类型看表现。
6. 成本评估：tokens、显存、QPS、延迟、缓存、批处理、失败重试。
7. 上线保护：监控、回滚、灰度、审计、安全策略和人工兜底。

### 常见考法与解题方法

| 考法 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 架构对比 | BERT、T5、GPT 怎么选 | 看输入输出形态和是否需要开放生成 |
| 成本题 | 为什么 MoE 便宜 | 讲总参数和激活参数区别，同时说明部署复杂性 |
| 长上下文题 | 1M context 是否替代 RAG | 讲能放、能找、能用、权限和成本 |
| 多模态题 | CLIP 和 LLaVA 怎么选 | 检索选 CLIP，生成问答选 VLM/MLLM |
| 工程题 | 业务场景如何选模型 | 任务、数据、指标、成本、安全和上线闭环 |

### 易错点

- 用排行榜替代业务评测。
- 只看模型效果，不看延迟、成本、并发和可部署性。
- 长上下文场景完全不用 RAG，忽略权限、引用和更新。
- 所有任务都上最大模型，导致成本不可控。
- 选择开源模型时只看权重，不看 tokenizer、推理框架、量化和许可证。
- 选择多模态模型时不区分 OCR、图像问答、视频理解和 GUI 操作。

## 面试应对

### BERT、T5、GPT 架构怎么选？

回答思路：按输入输出和任务目标回答。

回答模板：

BERT 是 Encoder-only，适合理解类任务，比如分类、匹配、抽取和 rerank；T5 是 Encoder-Decoder，把任务统一成 text-to-text，适合翻译、摘要、结构化生成这类输入输出边界清楚的任务；GPT 是 Decoder-only，自回归生成能力强，适合对话、开放生成、代码、推理和 Agent。实际选型不是看哪个更高级，而是看任务输出形式、数据量、延迟成本和部署生态。

### MoE 相比 Dense 模型的优势和代价是什么？

回答思路：讲清总参数、激活参数和工程复杂度。

回答模板：

Dense 模型每个 token 都激活全部参数，结构简单但模型越大推理成本越高。MoE 通过 router 为每个 token 选择少数专家，只激活部分参数，因此可以在较低激活成本下扩大总模型容量。它的代价是训练和部署更复杂，包括专家负载均衡、路由稳定性、跨卡通信、批处理和显存布局。如果业务只需要简单高频任务，小 dense 模型可能比大 MoE 更合适。

### 长上下文模型能替代 RAG 吗？

回答思路：不要绝对化，按知识更新、权限和成本回答。

回答模板：

长上下文能减少切块和检索遗漏，适合一次性分析长文档、代码库或长视频，但它不能完全替代 RAG。RAG 的价值不只是省上下文，还包括知识更新、权限过滤、引用追溯和成本控制。长上下文解决“能不能放进去”，RAG 解决“该拿哪些知识、用户有没有权限、答案依据是什么”。实际系统里常见做法是 RAG 先筛选高相关内容，再用长上下文模型做整合推理。

### 业务模型选型你会怎么做？

回答思路：给流程，不要直接报模型名。

回答模板：

我会先定义任务和指标，比如是抽取、生成、问答、检索、代码还是多模态理解；再看约束，包括延迟、成本、并发、上下文长度、私有化和安全要求。然后选几类候选模型做真实样本评测，而不是只看公开榜单，并按业务线、难度、输入长度和 bad case 分桶分析。最后结合部署成本、监控、灰度、回滚和人工兜底决定上线方案。模型选型本质上是效果、成本、风险和工程可控性的权衡。
