# RAG

## 知识点解析

### 概述

RAG（Retrieval-Augmented Generation，检索增强生成）是把外部知识检索接到大模型生成前面的一种系统架构。

它解决的问题不是“让模型参数记住更多知识”，而是：

```text
用户问题
  -> 从外部知识库找到相关证据
  -> 把证据放进上下文
  -> 让模型基于证据回答
  -> 给出引用或拒答
```

在现在的 AI 产品里，RAG 常用于企业知识库、客服、搜索问答、代码助手、数据分析助手、内部制度问答、文档/合同/论文问答和 [Agent](<../../10_Agent/基础概念/Agent.md>) 的长期记忆。

### 为什么现在 AI 产品大量使用 RAG

大模型本身有几个问题：

- **知识过期**：模型只记得训练时见过的知识。
- **私有知识缺失**：公司文档、项目代码、内部流程不在预训练数据里。
- **幻觉**：模型可能在不知道时编出合理但错误的答案。
- **不可追溯**：纯生成答案很难说明依据来自哪里。
- **更新成本高**：每次知识变更都重新训练不现实。

RAG 的价值是把知识放在模型外面：

| 问题 | RAG 的作用 |
| --- | --- |
| 知识更新快 | 重新索引文档即可，不必重训模型 |
| 私有知识 | 接入企业文档、数据库、代码库 |
| 幻觉 | 要求答案基于检索证据 |
| 可追溯 | 返回引用、文档名、段落、页码 |
| 权限 | 按用户权限过滤可检索内容 |
| 成本 | 只把相关片段放进上下文，而不是塞完整文档 |

### RAG 的完整链路

RAG 分离线索引和在线问答两条链路。

#### 离线索引链路

```text
文档接入
  -> 解析
  -> 清洗
  -> 切 chunk
  -> 元数据/权限标注
  -> embedding
  -> 写入向量索引 / 关键词索引
  -> 版本化发布
```

关键点：

- PDF、Word、Markdown、网页、表格、代码都要先解析成结构化文本。
- chunk 不能只按固定长度硬切，最好结合标题、段落、表格、代码函数边界。
- 每个 chunk 要带元数据：文档名、路径、标题层级、页码、更新时间、权限、业务标签。
- 索引要可版本化，方便回滚和复现线上答案。

#### 在线问答链路

```text
用户问题
  -> 鉴权
  -> query rewrite / query decomposition
  -> 多路召回
  -> 权限过滤
  -> rerank
  -> 去重和上下文压缩
  -> prompt 构造
  -> LLM 基于证据生成
  -> 引用校验 / 拒答
  -> 日志和反馈回流
```

这个链路里，生成模型只是最后一步。RAG 的效果经常不是模型本身决定的，而是文档解析、[召回](<../../05_推理部署与系统/系统设计/召回粗排精排重排.md>)、rerank、上下文组织和引用约束决定的。

### 召回策略

RAG 的召回目标是“把可能有用的证据找回来”，宁可多找一些，再交给 reranker 精排。

常见召回方式：

| 策略 | 适合场景 | 风险 |
| --- | --- | --- |
| BM25 / 关键词召回 | 专有名词、编号、错误码、人名、接口名 | 同义表达召回弱 |
| 向量召回 | 语义相似、自然语言问题 | 容易召回语义像但事实不相关的片段 |
| Metadata 召回 | 按部门、产品、时间、权限、文档类型过滤 | 元数据缺失会漏召回 |
| 图/关系召回 | 组织关系、代码调用链、知识图谱 | 构建和维护成本高 |
| 多路召回 | 综合关键词、向量、规则、图关系 | 需要融合、去重和调权 |

企业 RAG 常用组合：

```text
BM25 top 50
  + embedding top 100
  + metadata filter
  + 权限过滤
  -> 合并去重
  -> rerank top 5/10
```

### 为什么要 rerank

向量召回解决“语义像不像”，但不保证“能不能回答问题”。

例如用户问：

```text
A 系统生产权限怎么申请？
```

向量召回可能返回：

- A 系统介绍。
- A 系统测试环境权限。
- A 系统生产权限审批流程。
- B 系统生产权限申请。

这些都相似，但真正能回答的是“A 系统生产权限审批流程”。Rerank 会把 query 和候选 chunk 一起输入更强匹配模型，判断候选是否真正支持答案。

RAG 里常见 rerank：

- Cross-Encoder reranker。
- BGE / [Qwen](<../模型细节/Qwen千问架构.md>) Reranker。
- LLM-as-reranker。
- 规则 + reranker 混合。

### 上下文构造

Rerank 后不能把所有 chunk 原样塞进 prompt，还要做 context packing：

```text
去重
  -> 删除低相关片段
  -> 合并同文档相邻片段
  -> 保留标题层级和来源
  -> 控制 token budget
  -> 标注引用 ID
```

一个简单 prompt 模板：

```text
你只能根据下面的参考资料回答问题。
如果资料不足以回答，请说“根据现有资料无法确定”。
回答中必须标注引用编号。

[资料1] ...
[资料2] ...

问题：...
```

关键原则：

- 证据要少而准，不是越多越好。
- 每段证据要有来源 ID。
- 相互冲突的证据要提示模型比较更新时间和权威性。
- 不足以回答时允许拒答。

### RAG 和长上下文模型的关系

长上下文不能完全替代 RAG。

| 能力 | 长上下文 | RAG |
| --- | --- | --- |
| 放入大量材料 | 强 | 只放相关片段 |
| 知识更新 | 仍需输入最新材料 | 更新索引即可 |
| 权限控制 | 需要应用层保证 | 可在召回前过滤 |
| 引用追溯 | 需要额外设计 | 天然适合引用 |
| 成本 | token 越多越贵 | 先筛选再生成 |
| 抗噪声 | 长上下文会被无关内容干扰 | rerank/压缩可控 |

实际系统常见做法：

```text
RAG 先筛选高相关材料
  -> 长上下文模型整合多证据
  -> 引用校验和拒答
```

### RAG 和微调怎么选

| 目标 | 更适合 |
| --- | --- |
| 更新知识、接入公司文档 | RAG |
| 答案要引用来源 | RAG |
| 用户有权限差异 | RAG + 权限过滤 |
| 固定输出格式 | [SFT](<../../03_训练优化与对齐/后训练与对齐/SFT 监督微调.md>) |
| 改变模型风格和任务习惯 | SFT |
| 专业工具调用流程 | SFT + 工具 + RAG |
| 需要可验证指标继续优化 | [RLVR](<../../03_训练优化与对齐/后训练与对齐/RLVR 可验证奖励强化学习.md>) / [GRPO](<../../03_训练优化与对齐/后训练与对齐/GRPO 组相对策略优化.md>) |

经验判断：

```text
模型不知道最新知识 -> 先用 RAG
模型知道但不会按格式做 -> SFT
模型会做但偏好/选择不好 -> DPO/RLHF
任务有自动 reward -> RLVR/GRPO
```

### RAG 在当前 AI 产品里的典型用法

#### 企业知识库助手

```text
内部文档
  -> 权限索引
  -> 员工提问
  -> 检索有权限文档
  -> rerank
  -> 带引用回答
```

核心难点是权限、文档更新、引用准确和拒答。

#### AI Coding

```text
代码库
  -> 按文件/函数/类切片
  -> 用户提 bug 或需求
  -> 召回相关文件、调用链、测试、历史变更
  -> LLM 修改代码
  -> 跑测试验证
```

这里 RAG 不只是文档问答，而是把代码上下文准确送给模型。

#### Agent 系统

Agent 里的 [Memory](<../../10_Agent/基础概念/Memory.md>)、工具说明、历史轨迹和外部文档都可以走检索。

```text
当前任务
  -> 检索相关 memory / docs / tools
  -> 注入上下文
  -> 规划和工具调用
```

重点是不要把所有记忆都常驻上下文，而是按当前任务检索。

#### 多模态 RAG

多模态场景会把图片、视频帧、OCR、ASR、截图区域也纳入索引：

```text
视频
  -> 抽帧 / OCR / ASR / Video Primitive
  -> 建立文本和视觉索引
  -> 用户问题召回相关片段或帧
  -> VLM 精读
```

这和关键帧任务很接近：先召回候选时间窗口，再让 [VLM](<../../06_视觉多模态与生成模型/多模态模型/VLM与Vision_Instruction_Tuning.md>) 精判边界。

### RAG 评估

RAG 评估要拆层看：

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 召回 | Recall@K、Hit Rate | 正确证据有没有被找回来 |
| 排序 | MRR、NDCG、Precision@K | 正确证据是否排得靠前 |
| 上下文 | Context Precision、Context Relevance | 最终 prompt 里证据是否相关 |
| 生成 | Answer Correctness、Faithfulness | 答案是否正确、是否忠实于证据 |
| 引用 | Citation Precision / Recall | 引用是否支持答案 |
| 拒答 | Unanswerable Accuracy | 资料不足时是否拒答 |
| 系统 | p95/p99、错误率、成本 | 是否满足线上 SLA |

排查方法：

```text
先看正确证据是否召回
  -> 再看是否被 rerank 排进上下文
  -> 再看上下文是否噪声过多
  -> 最后看模型是否忠实生成
```

### 常见失败模式

- 文档解析错：表格、PDF、图片 OCR 丢信息。
- chunk 切太碎：答案跨 chunk，单片段不完整。
- chunk 切太大：召回相似但噪声太多。
- 只用向量召回：编号、专有名词、错误码召回差。
- rerank 缺失：正确证据召回了但排不进上下文。
- 权限过滤错误：用户看到不该看的内容。
- prompt 约束弱：模型脱离证据自由发挥。
- 引用不校验：答案引用的片段并不支持结论。
- 数据更新不及时：索引版本落后于原文档。

## 面试应对

### RAG 是什么？

回答思路：先定义“检索增强生成”，再强调它不改模型参数，而是把外部证据放进上下文。

回答模板：

RAG 是 Retrieval-Augmented Generation，检索增强生成。它的做法是在模型回答前，先从外部知识库、文档库、代码库或搜索系统中检索相关证据，再把证据和用户问题一起放进 prompt，让大模型基于证据生成答案。它不改变模型参数，所以特别适合企业私有知识、时效性知识、需要引用来源和权限控制的场景。简单说，RAG 让模型从“闭卷回答”变成“带资料回答”。

### 现在 AI 产品里 RAG 怎么用？

回答思路：按离线索引和在线问答两条链路回答，体现工程完整性。

回答模板：

现在 AI 产品里用 RAG，一般分离线和在线两条链路。离线先把文档、网页、代码、表格或视频转写内容解析清洗，按语义结构切 chunk，补充标题、来源、权限、更新时间等元数据，再做 embedding，写入向量库和关键词索引。在线时，用户问题先经过鉴权和 query rewrite，再做 BM25 加向量的多路召回，权限过滤后用 reranker 精排，选出少量高质量证据构造 prompt，最后让 LLM 基于证据回答并给引用。如果证据不足，系统应该拒答或提示补充信息，而不是让模型硬编。

### RAG 的核心流程是什么？

回答思路：按 indexing、retrieval、rerank、context packing、generation、evaluation 串起来。

回答模板：

RAG 的核心流程是：先做离线索引，把文档解析、切片、embedding 并写入向量库或关键词索引；用户提问后，先做 query rewrite 或 query decomposition，再用关键词和向量多路召回候选片段；然后用 reranker 精排，把最相关、最能支撑答案的片段选出来；接着做上下文压缩、去重和引用编号，拼进 prompt；最后模型基于这些证据生成答案，并通过引用校验和评测指标监控质量。

### 为什么 RAG 不能只做向量检索？

回答思路：说明向量召回语义泛化强，但专有名词、编号、精确条件和事实相关性不一定稳。

回答模板：

RAG 不能只依赖向量检索，因为向量检索擅长语义相似，但不一定擅长精确匹配。企业问答里经常有接口名、错误码、审批编号、人名、产品线、版本号，这些用 BM25 或关键词索引反而更稳。向量召回还容易找回“语义相似但不能回答问题”的片段，所以工程上通常做混合召回：BM25 保精确匹配，embedding 保语义泛化，再用 metadata 和权限过滤缩小范围，最后用 reranker 精排。

### RAG 和微调怎么选？

回答思路：用“知识更新 vs 行为塑造”区分，再说明两者可组合。

回答模板：

如果问题是模型缺少最新知识、企业私有知识，或者答案必须可追溯，我会优先用 RAG，因为知识更新只需要更新索引，不必重新训练。如果问题是模型输出格式不稳定、不会按业务流程回答、风格不符合要求，那更适合 SFT 或偏好对齐，因为这是行为能力问题。两者也可以组合：用 SFT 让模型学会基于证据回答和按格式输出，再用 RAG 提供实时知识。

### RAG 答案错了怎么排查？

回答思路：逐层定位：召回、排序、上下文、生成、引用、权限。

回答模板：

我会先看正确证据有没有进入召回 top K。如果没有，问题通常在文档解析、chunk、embedding、关键词召回、query rewrite 或权限过滤。然后看正确证据是否被 rerank 排进最终上下文，如果召回到了但没进 prompt，就是排序或 token budget 问题。第三步看上下文是否有噪声或冲突，第四步看模型是否忠实使用证据，最后检查引用是否真的支持答案。这样能区分是检索问题、排序问题、上下文问题还是生成问题，而不是笼统地说模型幻觉。

### 长上下文模型能替代 RAG 吗？

回答思路：强调长上下文解决“能放进去”，RAG 解决“该拿什么、有没有权限、能否引用、成本是否可控”。

回答模板：

长上下文不能完全替代 RAG。长上下文解决的是能不能把更多内容放进模型，但 RAG 解决的是该拿哪些内容、用户有没有权限看、答案能不能引用追溯、知识怎么更新、成本怎么控制。把整本文档塞进长上下文会增加延迟和费用，也可能引入噪声，让模型漏看关键段落。实际系统里更常见的是 RAG 先检索和精排高相关证据，再用长上下文模型做综合推理。
