# 软件工程与测试

## 知识点解析

### 概述

软件工程和测试在央国企、银行科技岗笔试中很常见，通常以选择题和简答题出现。重点是软件生命周期、开发模型、测试类型和质量保障方法。

### 软件生命周期

典型生命周期包括需求分析、概要设计、详细设计、编码、测试、部署和维护。需求分析明确做什么，设计明确怎么做，测试验证是否满足需求，维护处理缺陷和迭代。

### 开发模型

瀑布模型按阶段顺序推进，强调阶段文档、评审和基线，适合需求稳定、变更少、合规要求强的项目，但问题反馈通常较晚。敏捷开发把需求拆成短周期增量，通过持续反馈调整优先级，适合需求变化较快的业务，但不等于取消设计、文档或质量门禁。DevOps 不是单一开发模型，而是开发、测试和运维协作的文化与实践，通过自动化构建、测试、发布、监控和反馈缩短交付周期。银行项目常采用总体受控、局部迭代的混合方式。

### 测试类型

| 测试 | 说明 |
| --- | --- |
| 单元测试 | 测函数、类或模块 |
| 集成测试 | 测多个模块协作 |
| 系统测试 | 从完整系统角度验证 |
| 验收测试 | 由用户或业务代表确认系统是否满足验收标准 |
| 回归测试 | 验证修改没有破坏旧功能 |
| 黑盒测试 | 不关心内部实现，只看输入输出 |
| 白盒测试 | 关注代码路径、分支和覆盖率 |
| 性能测试 | 统称响应时间、吞吐量和资源利用率等非功能验证 |
| 负载测试 | 在预期或逐步增加的业务负载下验证性能指标 |
| 压力测试 | 超过正常容量寻找极限、瓶颈及失败后的恢复能力 |

测试级别通常按单元、集成、系统、验收逐步扩大对象范围；回归测试不是独立级别，而是代码或配置变更后按风险在多个级别重跑相关用例。

### 黑盒与白盒测试方法

等价类划分把输入域分为预期行为相同的有效类和无效类，每类选择代表值；边界值分析重点覆盖最小值、最大值及边界内外相邻值，因为缺陷常出现在比较符号和下标边界。

白盒覆盖率的常见强弱关系和边界如下：

- 语句覆盖：每条可执行语句至少执行一次，要求最低，不能保证每个判断结果都出现。
- 分支覆盖或判定覆盖：每个判定的真、假分支至少执行一次，通常强于语句覆盖。
- 条件覆盖：每个基本布尔条件至少取到一次真和一次假，但组合后未必让整个判定的真、假分支都执行。
- 条件/判定覆盖：同时满足条件覆盖和分支覆盖，仍未穷尽条件组合。
- 路径覆盖：覆盖控制流图中的执行路径，理论上更强，但循环会产生大量甚至无限路径，工程上通常只选高风险路径。

覆盖率只能说明代码被执行，不能证明断言有效、需求完整或结果正确。应结合需求风险、边界和异常用例、变异测试或缺陷发现情况评价测试质量。

### UML

UML 常见图及用途包括：

- 用例图：描述参与者与系统功能，适合澄清需求边界，不展示内部调用顺序。
- 类图：描述类、属性、方法以及关联、聚合、组合、继承和依赖等静态关系。
- 时序图：按时间顺序描述对象间消息，适合分析一次业务调用或接口协作。
- 活动图：描述流程、分支、并行和汇合，适合业务流程或算法步骤。
- 状态图：描述对象状态、触发事件和状态迁移，适合订单、账户等生命周期。
- 组件图和部署图：分别描述软件组件依赖和制品到计算节点的部署关系。

### 模块化设计

模块化设计的目标是把复杂系统拆成职责清晰、接口稳定的模块。评价模块设计时通常看耦合和内聚：

- 内聚：模块内部元素联系的紧密程度，通常越高越好。
- 耦合：模块之间依赖的紧密程度，通常越低越好。

常见内聚程度从低到高可以理解为偶然内聚、逻辑内聚、时间内聚、过程内聚、通信内聚、顺序内聚和功能内聚。常见耦合从强到弱包括内容耦合、公共耦合、控制耦合、标记耦合、数据耦合和非直接耦合。

### 需求与软件维护

需求工程包括需求获取、分析、规格说明、验证和管理。一个合格需求应尽量具备明确性、可验证性、可追踪性和一致性。

软件维护通常分为：

- 改正性维护：修复发现的错误。
- 适应性维护：适应操作系统、硬件、法规或外部环境变化。
- 完善性维护：增加功能、改善性能或易用性。
- 预防性维护：改善结构，降低未来维护成本。

### 配置管理和版本控制

软件配置管理关注源代码、需求、设计文档、测试用例、构建脚本和发布包等配置项。基线是经过正式评审和批准、后续变更需要受控的版本状态。

变更流程通常包括提出变更、影响分析、审批、实施、测试、发布和记录。版本控制解决多人协作和历史追踪问题，但不能代替需求管理、代码评审和发布审批。

### 项目管理基础

项目管理常见约束包括范围、进度、成本、质量、风险和资源。风险管理通常包括风险识别、分析、应对和跟踪。

- 关键路径是项目网络图中总持续时间最长的路径，决定理论最短工期；关键活动的总时差通常为 0。
- 里程碑是重要阶段节点，不一定代表所有工作完成。
- 质量保证关注过程改进，质量控制关注交付物检查。
- 文档、测试和审计是银行及央国企项目的重要交付物。

关键路径法采用前推和后推计算：

1. 前推：起点最早开始时间 $\mathrm{ES} = 0$；活动的 $\mathrm{ES} = \max(\text{所有紧前活动的 EF})$，$\mathrm{EF} = \mathrm{ES} + \text{工期}$。终点最大 $\mathrm{EF}$ 是项目工期。
2. 后推：终点最迟完成时间 $\mathrm{LF} = \text{项目工期}$；活动的 $\mathrm{LF} = \min(\text{所有紧后活动的 LS})$，$\mathrm{LS} = \mathrm{LF} - \text{工期}$。
3. 总时差 $\mathrm{TF} = \mathrm{LS} - \mathrm{ES} = \mathrm{LF} - \mathrm{EF}$。$\mathrm{TF} = 0$ 的活动构成关键路径，非关键活动在不影响总工期的前提下最多可延迟其总时差。

项目可能有多条关键路径；关键路径越多，进度风险越高。网络关系或活动工期变化后应重新计算，不能把原关键路径视为永久不变。

### 常见考法与测试设计

| 题型 | 解题方法 |
| --- | --- |
| 开发模型选型 | 根据需求稳定性、交付周期和合规要求判断 |
| 测试阶段 | 区分单元、集成、系统、验收和回归 |
| 耦合内聚判断 | 优先选择高内聚、低耦合的设计 |
| 软件维护分类 | 根据变化原因判断改正、适应、完善或预防 |
| 黑盒用例 | 使用等价类、边界值、判定表和场景法 |
| 白盒覆盖 | 根据控制流判断语句、分支、条件和路径覆盖 |
| 缺陷处理 | 复现、定位、修复、回归、补自动化用例 |

设计输入类测试用例时：

1. 划分有效和无效等价类。
2. 覆盖最小值、最大值及边界外相邻值。
3. 补充空值、重复、非法字符和异常流程。
4. 检查错误提示、数据状态和恢复行为。
5. 根据风险增加并发、安全、性能和兼容性测试。

### 易错点

- 回归测试用于验证修改没有破坏已有功能，不只是重跑失败用例。
- 单元测试关注局部逻辑，集成测试关注模块协作。
- 覆盖率高不等于测试充分，断言错误和需求遗漏无法只靠覆盖率发现。
- 敏捷不代表没有设计和文档，而是通过短周期持续反馈。
- 高内聚、低耦合通常是模块化设计的目标。
- 适应性维护是适应外部环境变化，不是修复原有功能缺陷。

## 笔试常考

- 软件生命周期：需求分析回答“做什么”，设计回答“怎么做”，随后进入编码、测试、部署和维护。
- 瀑布、敏捷与 DevOps：瀑布强调阶段与基线，敏捷强调短迭代反馈，DevOps 强调跨角色协作和交付自动化。
- 测试级别：单元、集成、系统、验收的对象范围依次扩大；回归测试可贯穿多个级别。
- 等价类和边界值：前者选取输入类代表值，后者检查上下界及边界内外相邻值。
- 白盒覆盖：语句覆盖弱于分支覆盖；条件覆盖与分支覆盖互不必然包含；路径覆盖最强但通常无法穷尽。
- 内聚与耦合：模块设计通常追求高内聚、低耦合。
- 维护类型：按修复缺陷、适应环境、改进功能和预防未来问题区分改正性、适应性、完善性、预防性维护。
- 关键路径：前推求 $\mathrm{ES}/\mathrm{EF}$，后推求 $\mathrm{LS}/\mathrm{LF}$，总时差 $\mathrm{TF} = \mathrm{LS} - \mathrm{ES}$，总时差为 0 的活动是关键活动。

## 面试应对

### 黑盒测试和白盒测试有什么区别？

回答思路：是否关注内部实现。

回答模板：

黑盒测试不关注代码内部实现，只从输入输出和需求角度验证功能是否正确，常用于功能测试和验收测试。白盒测试关注代码内部结构、分支、路径和覆盖率，常用于单元测试和代码级质量保障。实际项目中两者会结合使用，黑盒保证业务行为，白盒保证实现路径和边界覆盖。

### 敏捷和瀑布有什么区别？

回答思路：需求稳定性、迭代方式、反馈周期。

回答模板：

瀑布模型按需求、设计、开发、测试、上线顺序推进，适合需求稳定、变更少、流程要求强的项目。敏捷开发强调小步迭代和快速反馈，把需求拆成多个短周期交付，更适合需求变化快的业务。两者不是绝对对立，金融和央国企项目可能在总体流程上偏瀑布，但在具体开发中引入敏捷迭代和持续集成。

### 如何为登录功能设计测试用例？

回答思路：从功能、边界、安全、性能和异常恢复分层回答。

回答模板：

我会先覆盖正确账号密码的主流程，再用等价类和边界值测试空值、错误密码、长度边界、非法字符和不存在账号。然后检查连续失败锁定、验证码、会话过期和找回密码。安全方面测试 SQL 注入、暴力破解、日志脱敏和 HTTPS；还要覆盖重复提交、并发登录、服务异常后的提示与恢复。

### 代码变更后如何确定回归测试范围？

回答思路：从变更影响分析、风险分级、分层用例和自动化结果确定范围。

回答模板：

我会先分析代码、接口、数据库和配置的变更，结合调用链和依赖关系找出直接影响模块及上下游，再按业务重要性、改动复杂度和历史缺陷做风险分级。高风险变更要覆盖主流程、异常流程、数据一致性和相关端到端场景；低风险区域可侧重单元和接口回归。同时运行稳定的自动化回归集，并对支付、账务等核心链路保留固定冒烟用例。回归范围应由影响和风险决定，不能只重跑曾经失败的用例。

### 覆盖率高是否代表测试质量高？

回答思路：解释覆盖率能证明什么、不能证明什么，再给出组合评价方法。

回答模板：

覆盖率高只说明相应代码结构被执行过，不代表断言正确、需求完整或边界场景充分。语句覆盖可能漏掉判断的另一分支，分支覆盖也不一定覆盖每个基本条件的真假组合，路径覆盖则常因循环和组合爆炸无法穷尽。我会把覆盖率作为发现未测试代码的辅助指标，同时检查需求和风险覆盖、异常与边界用例、断言质量、变异测试结果以及线上缺陷反馈，避免单纯追求数字。
