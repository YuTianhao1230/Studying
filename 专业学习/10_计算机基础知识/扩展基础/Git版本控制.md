# Git 版本控制

## 知识点解析

### 概述

Git 是分布式版本控制系统，用快照和提交图记录文件历史，支持分支开发、版本回退、协作合并和问题追踪。每个完整克隆通常都包含仓库历史，因此本地可以创建提交、查看日志和切换分支；与远端协作时再交换提交和引用。

### 工作区、暂存区与本地仓库

Git 的本地操作围绕三个区域展开：

| 区域 | 含义 | 常用操作 |
| --- | --- | --- |
| 工作区 | 当前可直接编辑的文件 | 修改文件、`git restore` |
| 暂存区 | 下一次提交准备记录的快照 | `git add`、`git restore --staged` |
| 本地仓库 | 已保存的提交对象和引用 | `git commit`、`git log` |

`git add` 把指定路径的当前内容写入暂存区，不是简单地给文件打“已跟踪修改”标记。文件在暂存后再次被修改时，`git status` 会同时显示已暂存版本和未暂存版本；本次提交只记录暂存区里的内容。

一个常见流程是：

1. 用 `git status` 查看工作区和暂存区状态。
2. 用 `git diff` 查看未暂存差异，用 `git diff --staged` 查看将要提交的差异。
3. 用 `git add <path>` 精确暂存需要进入本次提交的内容。
4. 用 `git commit` 创建不可变提交，并让当前分支引用指向新提交。
5. 用 `git push` 把本地提交和分支引用更新到远端。

### 提交、分支与 HEAD

提交保存项目快照、父提交、作者、时间和提交说明，其内容由哈希标识。普通提交有一个父提交，合并提交通常有两个父提交，多个提交由父子关系组成有向无环图。

分支本质上是指向某个提交的可移动引用，而不是仓库内容的完整副本。`HEAD` 通常指向当前分支，创建新提交后当前分支向前移动。若直接检出某个提交而不是分支，会进入 detached HEAD 状态；此时可以查看和实验，但新提交若不及时创建分支引用，之后可能难以找到。

`git switch` 主要用于切换或创建分支，`git restore` 主要用于恢复文件；旧命令 `git checkout` 同时承担这两类职责，语义更容易混淆。

### merge 与 rebase

`git merge` 把两个分支的历史汇合：

- 若目标分支是当前分支的祖先，可以直接快进，让分支指针向前移动。
- 若双方都有新提交，Git 通常创建一个合并提交，保留真实分叉与汇合关系。
- 它不会改写已有提交，适合合并已经共享的公共分支。

`git rebase` 找到当前分支相对目标分支新增的提交，把这些变更依次重放到目标分支最新提交之后。重放生成的是新提交，因此提交哈希会变化，历史更线性，但冲突可能在多个提交重放时分别出现。

选择原则是：公共历史优先 merge，尚未共享的个人功能分支可用 rebase 整理。不要随意 rebase 已被他人基于其开发的公共提交，否则其他人的历史会与改写后的历史分叉，通常还需要强制推送和额外协调。

### 冲突处理

当 Git 无法自动合并同一位置的不同修改时会产生冲突。处理步骤是：

1. 用 `git status` 找到冲突文件和当前操作类型。
2. 阅读冲突标记与两边语义，手工得到正确的最终内容，而不是机械选择一侧。
3. 运行相关测试或检查，确认合并后的行为正确。
4. 用 `git add` 标记该文件冲突已解决。
5. merge 时完成合并提交；rebase 时运行 `git rebase --continue` 继续重放。

若判断当前合并或变基方向错误，可分别使用 `git merge --abort` 或 `git rebase --abort` 回到操作前状态。冲突解决验证的是最终语义，文本标记消失不代表功能一定正确。

### 撤销操作

| 目标 | 推荐操作 | 影响 |
| --- | --- | --- |
| 丢弃未暂存修改 | `git restore <path>` | 改写工作区，未保存内容会丢失 |
| 取消暂存但保留修改 | `git restore --staged <path>` | 只把内容移出暂存区 |
| 撤销已共享提交 | `git revert <commit>` | 新建一个反向提交，不改写公共历史 |
| 移动本地分支到旧提交 | `git reset` | 可能同时改变暂存区和工作区 |

`git reset --soft` 只移动分支引用并保留暂存区和工作区；默认的 `--mixed` 还重置暂存区，但保留工作区；`--hard` 同时重置三者，会丢弃未保存修改。已推送的公共提交通常使用 `revert`，因为它保留历史并能正常协作；`reset` 更适合整理尚未共享的本地历史。

### 远端协作

- `git fetch` 下载远端对象并更新远端跟踪引用，不自动修改当前工作分支。
- `git pull` 先 fetch，再按配置 merge 或 rebase 到当前分支，因此执行前应明确策略并检查本地修改。
- `git push` 把本地对象和引用发送到远端；若远端已有本地未知的新提交，普通推送会被拒绝以避免覆盖他人历史。
- 必须更新改写后的个人远端分支时，`--force-with-lease` 会检查远端引用是否仍是预期值，比无条件 `--force` 更能避免覆盖他人新提交。

协作中应让一次提交只表达一个完整意图，提交前检查差异，不把密钥、生成物或无关格式化混入。评审通过、自动化检查通过和分支保护规则都不能由 Git 本身替代。

### `.gitignore` 的边界

`.gitignore` 只影响尚未被跟踪的文件。文件已经进入版本历史后，再添加忽略规则不会自动停止跟踪；需要在确认保留本地文件的前提下，把它从索引移除并提交这次变更。忽略规则也不是保密机制：密钥一旦提交，即使后续删除，旧提交中仍可能存在，必须轮换密钥并按需要清理历史。

### 易错点

- 分支是提交引用，不是完整复制的一套目录。
- `git add` 暂存的是当时的文件内容，后续修改不会自动进入同一次提交。
- `git pull` 不只是下载，默认还会整合历史。
- rebase 会改写提交哈希，不应随意作用于共享历史。
- `reset --hard` 会丢弃工作区修改，执行前必须确认状态和备份。
- `.gitignore` 不能自动移除已跟踪文件，也不能消除历史中的敏感信息。

## 笔试常考

- 工作区、暂存区、本地仓库和远端仓库的关系，以及 `add`、`commit`、`push` 分别改变哪一层。
- `git diff` 与 `git diff --staged` 的查看范围。
- 分支、提交和 `HEAD` 的含义，detached HEAD 的风险。
- merge 保留分叉历史，rebase 重放提交并改写哈希；公共历史通常不做 rebase。
- `fetch` 只下载和更新远端跟踪引用，`pull` 还会把远端变化整合到当前分支。
- `restore`、`revert` 与 `reset` 的作用范围；撤销已推送提交优先使用 `revert`。
- `reset --soft`、`--mixed`、`--hard` 对分支引用、暂存区和工作区的影响。
- `.gitignore` 只忽略未跟踪文件，不能自动取消已经跟踪的文件。

## 面试应对

### merge 和 rebase 有什么区别？

回答思路：比较历史结构、提交哈希、适用范围和协作风险。

回答模板：

merge 把两个分支汇合，双方都有新提交时通常生成一个合并提交，保留真实的分叉历史，而且不改写已有提交。rebase 会把当前分支上的提交依次重放到目标分支之后，历史更线性，但会生成新提交并改变哈希。我通常对已经共享的公共分支使用 merge，对尚未共享的个人功能分支可以在合并前 rebase 整理历史，避免改写别人已经依赖的提交。

### 已经推送的错误提交应该如何撤销？

回答思路：先区分公共历史和个人未共享历史，再说明 `revert` 的原因。

回答模板：

如果错误提交已经推送并可能被他人拉取，我会优先使用 `git revert` 创建一个反向提交，因为它保留原历史，不要求其他人重写本地分支。只有在确认分支由我独占、团队同意改写历史时，才考虑 reset 或 rebase 后使用 `--force-with-lease` 推送。无论哪种方式，我都会先检查差异并运行回归验证，避免反向提交把后续正确修改一并撤销。

### Git 冲突应该怎样处理？

回答思路：按定位、理解、合并、验证和继续操作的顺序回答。

回答模板：

我会先用 `git status` 确认冲突文件以及当前处于 merge 还是 rebase。然后结合两边提交目的和业务语义手工整理最终内容，不能只机械选择 ours 或 theirs。删除冲突标记后要运行相关测试和静态检查，再用 `git add` 标记已解决，最后完成 merge 提交或执行 `git rebase --continue`。如果发现整合方向有误，就用对应的 abort 命令回到操作前状态。

### `git fetch` 和 `git pull` 有什么区别？

回答思路：说明是否自动改变当前分支，以及何时选择。

回答模板：

`git fetch` 只下载远端对象并更新远端跟踪引用，不会自动修改当前工作分支，所以适合先查看和比较远端变化。`git pull` 相当于先 fetch，再按配置把远端分支 merge 或 rebase 到当前分支，会直接改变当前历史。我在有本地修改或需要审查远端提交时先 fetch，确认差异后再选择合适的整合方式。
