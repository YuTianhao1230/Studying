# 银行系统安全与容灾

## 知识点解析

### 概述

银行系统处理资金、身份信息和大量敏感数据，安全与连续性是核心技术要求。银行笔试常考身份认证、权限控制、数据加密、审计追踪、备份恢复、灾难恢复、双活和 RPO/RTO。答题时要把“安全防护”和“故障恢复”区分开。

### 银行信息安全目标

银行系统的安全目标可以从 CIA 和可审计性理解：

- 机密性：只有授权主体可以读取数据。
- 完整性：交易和账户数据不能被未授权篡改。
- 可用性：核心服务在故障和高峰下仍能提供服务。
- 可审计性：关键操作可记录、可追踪、可复核。
- 不可抵赖：操作主体不能轻易否认已经执行的操作。

### 身份认证与访问控制

认证回答“你是谁”，授权回答“你能做什么”。银行系统通常结合：

- 用户名密码、短信验证码、生物特征和硬件令牌。
- 多因素认证：至少结合不同类别的认证因素。
- RBAC：根据角色授予权限。
- ABAC：根据用户、资源、动作、环境等属性判断权限。
- 最小权限：只授予完成任务所需的权限。
- 职责分离：关键操作由不同角色共同完成或复核。

前端隐藏按钮不是授权，真正的权限校验必须在服务端完成。

### 密码和密钥管理

- 传输加密：使用 TLS 等协议保护通信。
- 存储加密：对数据库、文件、备份和磁盘中的敏感数据加密。
- 哈希：用于摘要、完整性校验和密码保护，不是可逆加密。
- 数字签名：发送方用私钥对消息摘要签名，接收方用公钥验签，用于验证来源、完整性并支持不可抵赖。
- 密钥管理：包括生成、分发、存储、轮换、撤销、备份和销毁。
- HSM：用于保护和执行高敏感密钥操作的硬件安全模块。

密钥不能和业务数据明文放在同一个配置文件中。加密算法本身安全，不代表密钥管理就安全。

### PKI、CA 与数字证书

PKI 是围绕公钥、身份、证书和信任关系建立的一套基础设施。CA 对申请者身份进行核验后签发数字证书，证书把主体身份与公钥绑定；数字签名则是主体使用私钥对具体消息产生的结果。证书用于回答“这个公钥属于谁、是否可信”，签名用于回答“这段消息是否由对应私钥持有者签发、是否被篡改”。

验证服务器证书时，不能只看页面是否显示证书，应依次检查：

1. 从服务器叶子证书构建到受信任根 CA 的完整证书链，并验证各级 CA 的签名。
2. 检查证书有效期、主机名与 SAN 是否匹配，以及密钥用途和扩展密钥用途是否允许当前场景。
3. 通过 CRL 或 OCSP 等机制检查证书是否已被吊销。
4. 在 TLS 握手中验证对端确实持有证书公钥对应的私钥。

信任根必须来自受控信任库，不能因为证书“自称某个主体”就信任，也不能在生产环境中关闭主机名或证书链校验。

### 审计与数据安全

关键审计日志应记录操作者、时间、来源、对象、操作类型、结果和请求标识。日志需要防篡改、分级存储、访问控制和集中分析。

敏感数据治理通常包括：

- 数据分类分级。
- 最小化采集和目的限定。
- 脱敏、匿名化或 token 化。
- 生产和测试环境隔离。
- 数据访问审批和权限回收。
- 备份数据同样需要加密和权限控制。

### 容灾基本概念

- 备份：复制数据或系统状态，便于故障后恢复。
- 容灾：在主系统失效时切换到备用环境。
- 业务连续性：在故障、灾害或攻击下维持关键业务。
- RPO：Recovery Point Objective，可接受的数据丢失时间范围。
- RTO：Recovery Time Objective，可接受的业务恢复时间目标。

RPO 越小，意味着需要更及时的数据复制；RTO 越小，意味着备用资源、自动切换和预案要求更高。RPO 关注“最多丢多少数据”，RTO 关注“多久恢复服务”。

复制方式会直接影响 RPO 和系统性能：

- 同步复制：主站通常在备站确认写入后才返回成功。在所覆盖的故障模型内，已确认交易可实现接近 0 的 RPO，但跨地域延迟会增加交易时延，备站或链路故障也可能降低可用性。
- 异步复制：主站本地提交后即可返回，再异步发送到备站，时延和可用性较好；故障时尚未复制的数据可能丢失，实际 RPO 取决于复制延迟和积压量。
- 半同步复制：等待至少一个副本确认后返回，在一致性、时延和可用性之间折中。

RPO 是业务目标，不等于复制产品的宣传值。还要结合复制监控、故障范围、数据损坏传播和恢复验证评估实际可达水平。

### 备份分层与恢复验证

- 全量备份保存完整数据，恢复链短，但备份时间和空间开销大。
- 差异备份保存相对最近一次全量备份的变化，恢复时需要“全量 + 最新差异”。
- 增量备份保存相对最近一次备份的变化，备份快、占用小，但恢复依赖完整增量链。
- 在线备份便于快速恢复，离线或不可变备份可以降低勒索软件、误删和同源故障同时破坏副本的风险；关键备份还应跨介质、跨故障域保存。

备份策略应依据 RPO/RTO 设置频率和保留周期。校验文件存在或校验和正确，只能证明介质可读；还要定期在隔离环境执行恢复演练，验证数据库、日志链、密钥、应用版本和依赖能够共同恢复，并核对恢复后的账务与业务数据。

### 常见灾备模式

| 模式 | 特点 | 适用理解 |
| --- | --- | --- |
| 冷备 | 备用资源平时不运行或准备程度低 | 成本低，恢复慢 |
| 温备 | 备用系统部分运行，数据定期同步 | 成本和恢复时间居中 |
| 热备 | 备用系统持续运行并及时同步 | 恢复快，成本高 |
| 主备 | 主站对外服务，备站同步数据并待命 | 写入路径清晰，但存在切换时间和备用资源利用率问题 |
| 双活 | 两地或多地同时提供服务 | 资源利用率高，但要处理流量路由、写冲突、数据一致性和故障隔离 |

“两地三中心”属于数据中心和灾备布局思路，具体部署仍要结合业务等级、数据一致性和监管要求。

### 故障切换与恢复

故障切换不是简单修改 DNS，通常包括：

1. 通过多源监控确认故障范围、持续时间、复制延迟和备用站健康度，避免瞬时抖动触发误切。
2. 由自动化仲裁或授权人员按预案作出切换决定，记录决策依据和操作时间。
3. 先隔离旧主站，通过多数派仲裁、租约或 STONITH/存储隔离等 fencing 手段撤销其写权限，保证同一数据分区只有一个写主。
4. 确认备站数据位置和依赖后提升为主站，再通过负载均衡、全局流量调度或 DNS 将流量分批切换。
5. 观察错误率、交易量和数据复制状态，校验未知交易并逐步恢复非核心服务。
6. 原站修复后先作为副本追平并校验数据，再按审批窗口受控回切，不能直接以旧数据重新对外写入。

脑裂是两个站点同时认为自己是主站并接受冲突写入。仅靠心跳不足以防脑裂，需要多数派仲裁、租约、fencing 和单写约束；失去多数派的一侧应停止写服务。金融系统不能只追求“快速切换”，还要防止重复处理、数据分叉和账务不一致。

### 恢复后的交易核对

恢复服务后要确定数据恢复点和切换时间窗，核对主备复制位置、数据库完整性、总账与分户账，并将切换窗口内的交易与渠道流水、消息队列、外部清算文件逐笔匹配。对未知、单边、重复、金额或状态不一致的交易，应先查明事实状态，再通过幂等重放、冲正、补账或人工复核处理，不能直接批量重放所有请求。对账闭环后还要保留审批和审计记录，并持续观察回切后的复制与业务指标。

## 笔试常考

- 认证确认主体身份，授权判断主体能否对特定资源执行特定操作；认证通过不代表拥有全部权限。
- 数字证书绑定身份与公钥，数字签名验证具体消息的来源和完整性；证书校验包括信任链、有效期、SAN、用途和吊销状态。
- RPO 衡量可接受的数据丢失范围，RTO 衡量可接受的恢复时长；同步复制通常降低 RPO，但会增加时延和可用性压力。
- 全量、差异、增量备份的备份成本与恢复链不同；在线副本不能替代离线、不可变或跨故障域备份。
- 双活同时承载业务，资源利用率高但一致性和冲突处理复杂；主备写入路径清晰，但存在切换时间和资源闲置。
- 备份完成不等于可恢复，必须通过校验和、隔离恢复演练、应用启动和业务数据核对验证。

## 易错点

- RPO 不是恢复所需时间，RTO 才是恢复时间目标。
- 双活不代表天然强一致，也不代表不需要故障切换策略。
- 认证通过不代表拥有全部资源权限。
- 哈希通常不可逆，数字签名也不是简单“给数据加密”。
- 备份存在不代表可以恢复，必须定期做恢复演练和数据校验。

## 面试应对

### 1. 身份认证和授权有什么区别？

- 回答思路：先用“你是谁”和“你能做什么”区分，再补充服务端校验、最小权限和职责分离。
- 回答模板：认证用于确认访问者是谁，例如密码、多因素认证或证书认证；授权是在身份确认后，判断该主体能否对某项资源执行某个动作。认证成功不代表拥有全部权限，银行系统还要在服务端按 RBAC 或 ABAC 执行最小权限控制，对付款审批等关键操作采用职责分离，不能把前端隐藏按钮当成授权。

### 2. 数字签名和数字证书是什么关系？

- 回答思路：分别说明消息级签名和身份到公钥的绑定，再给出完整证书验证项。
- 回答模板：数字签名是签名者用私钥对消息摘要产生的结果，接收方用公钥验证消息来源和完整性；数字证书由 CA 签发，用来把主体身份与公钥绑定。验证证书时要检查到受信任根 CA 的证书链、有效期、SAN 主机名、密钥用途和吊销状态，并确认对端持有对应私钥。证书解决公钥是否属于可信主体的问题，签名解决具体消息是否由该私钥签发且未被篡改的问题。

### 3. RPO 和 RTO 如何影响容灾设计？

- 回答思路：定义两个指标，再将其映射到复制方式、备用资源和切换自动化，并说明成本权衡。
- 回答模板：RPO 表示最多可接受丢失多长时间的数据，RTO 表示故障后业务必须在多长时间内恢复。更小的 RPO 通常需要同步或更高频复制，但会带来跨地域时延和可用性压力；更小的 RTO 需要预置热备资源、自动化切换和充分演练。设计时要按业务等级确定目标，再用实际复制延迟和恢复演练验证，而不能只看产品标称值。

### 4. 灾备切换时如何防止脑裂？

- 回答思路：说明脑裂后果，再按仲裁、fencing、单写、流量切换和回切顺序回答。
- 回答模板：脑裂是两个站点同时认为自己是主站并接受写入，会造成数据分叉和重复交易。切换前要通过多数派仲裁或租约确认新主，并使用 STONITH、存储隔离或撤销网络和写权限等 fencing 手段先隔离旧主，保证一个数据分区只有一个写主。确认新主数据位置后再分批切换流量；原站恢复后先作为副本追平并校验，经过审批后受控回切，不能直接重新开放写入。

### 5. 故障切换后为什么还要对账，如何执行？

- 回答思路：指出切换只能恢复服务，不能自动证明交易一致，再说明确定窗口、多源核对、差异分类和审计闭环。
- 回答模板：故障切换恢复的是服务能力，但切换窗口内可能存在复制未完成、响应丢失、消息重复或单边记账，所以仍要对账。首先确定恢复点和切换时间窗，核对主备复制位置、数据库完整性以及总账和分户账；再把渠道流水、核心账、消息记录和外部清算文件逐笔匹配。对未知、重复、单边、金额或状态不一致的交易，查明事实状态后执行幂等重放、冲正、补账或人工复核，并保留审批和审计记录。
