# No Negative Echo

| 项目 | 内容 |

| 默认分支 | `main` |

## 主要做什么

No Negative Echo 是一个交付表面整理 Skill。它要求 Agent 先确定最终接受的结果、读者需要的事实和当前交付边界，再生成面向读者的标题、导语、标签、元数据、commit、PR 描述和 handoff。

它关注的是“最终产物如何表达”，适用于代码、文档、索引、报告和交接信息等多个表面。它不负责替代业务判断、代码测试或版本管理，而是帮助这些结果在交付时保持准确、聚焦和可读。

## 解决什么问题

它主要解决协作过程中最终产物表达失真的问题：

- 标题和导语继续围绕已经放弃的方案组织，读者难以理解当前结果。
- 文档、文件名、标签、元数据或交接文本带入不属于最终结果的过程信息。
- 为了说明当前选择，反复描述读者并不需要知道的比较过程。
- 修改后只检查正文，遗漏文件名、索引、提交说明和 handoff 等外层表面。
- 看到词面扫描通过就直接认为语义表达正确，没有回读最终文件和实际状态。

## 怎么解决

它采用“先确定接受状态，再生成交付文本，最后回读验证”的流程：

1. 先定义正向目标、最终状态、读者需要的事实和交付范围。
2. 区分必须保留的事实与只服务于工作过程的候选方案、比较信息和临时措辞。
3. 从最终状态重新生成标题、开头、标签、文件名、元数据和交接信息，而不是只做词语替换。
4. 只有在安全、准确性、兼容性、审计、对比或用户明确要求时，才在最终产物中保留必要的排除说明。
5. 对完整交付包做回读检查，覆盖正文、文件名、元数据、生成物和 handoff；内容改变后重新检查。
6. 对需要严格验证的场景，使用高保障参考中的基线、冻结、读回和后置检查流程。

## 怎么用

### 适合调用的时机

在以下工作之后调用：

- 用户纠正了标题、概述、索引或卡片定位。
- 丢弃了一个方案，需要整理最终文档或交接文本。
- 生成报告、commit、PR、发布说明、文件名或外部系统描述。
- 批量修改文档后，需要检查是否有过程信息残留在高可见表面。

### 典型工作流

```text
读取最终文件和任务边界
  -> 确定接受状态与读者需要的事实
  -> 生成标题、概述、标签和交接文本
  -> 检查必要事实是否保留
  -> 扫描文件名、元数据和正文
  -> 回读实际结果
  -> 重新验证并交付
```

### 精确表面检查

本地安装包提供 `scripts/check_surface.py`，用于检查指定文件和相对路径中的精确词项：

```bash
python3 -I \
  <skill-dir>/scripts/check_surface.py \
  --terms-file /path/to/terms.txt \
  --root /path/to/project \
  README.md docs/overview.md
```

`--root` 会让脚本同时检查根目录相对路径和文件内容；没有 `--root` 时主要检查文件名。词表检查只能发现精确文本，不能代替人工判断语义改写是否仍然带有过程残留。

### 高保障场景

涉及敏感信息、公开发布、不可逆外部操作、压缩后的长上下文或无法完整读回的最终表面时，读取：

```text
references/high-assurance-finalization.md
```

重点执行基线确认、最终表面冻结、实际结果读回和后置验证；无法读取的表面要明确标记为未验证。

## 适用边界

- 适合文档、索引、报告、commit、PR、发布说明、文件名和 handoff 的最终整理。
- 必须保留的 API 名称、错误信息、测试快照、安全事实、审计记录和用户要求的对比内容不能为了表达简洁而删除。
- 它不是普通的删除、弃用、迁移或排除工具；真实兼容性、准确性、安全和审计要求仍应写入最终产物。
- `check_surface.py` 的零命中结果不能证明语义层面一定正确，最终交付前仍需要人工回读。

## 面试应对

### No Negative Echo 解决的核心问题是什么？

回答思路：先说明它处理的是交付表达而非业务逻辑，再讲过程信息如何污染标题、元数据和 handoff。

回答模板：

No Negative Echo 解决的是协作过程污染最终交付表面的问题。方案讨论中被放弃的选项、临时措辞和纠正过程可能残留在标题、文件名、注释、PR 或 handoff 中，让读者误解当前结果。它要求先确定最终接受状态和读者真正需要的事实，再从这个状态生成所有交付表面。它不替代业务判断和测试，只负责让最终表达与实际结果一致。

### 如何判断一个排除说明是否应该保留？

回答思路：以独立读者是否需要为判断标准，并列出安全、准确、兼容、审计和明确比较等例外。

回答模板：

我会问一个没有参与工作过程的读者是否需要这条排除说明。通常，只有省略会导致安全风险、事实不准确、兼容性误解、审计缺失，或者用户明确要求比较和变更记录时才保留。仅仅因为讨论过某个方案，不代表最终文档需要解释为什么没选它。若没有必要，我会从正向目标重写表面，而不是换一个委婉说法继续保留对比。

### 为什么精确词面扫描不能代替最终回读？

回答思路：区分字面命中与语义残留，再说明完整表面和变更后复检。

回答模板：

词面扫描只能发现给定词项和路径中的精确匹配，无法识别同义改写、语义暗示或结构上仍围绕旧方案组织的问题。因此我会先扫描正文、文件名和元数据，再人工回读标题、导语、索引、生成物和 handoff，确认它们都从最终状态出发。内容发生变化后还要重新检查，因为后续工具可能再次生成新的交付表面。

## 与当前工作区的结合

- 检查 `Studying` 的 README、Agent 卡片、学习索引和常用 Skill 文档时，用它确认标题、概述和入口只表达当前结构。
- 用户纠正某个卡片定位后，先从最终定位重新写概述，再检查相关索引、文件名和交接文本。
- 与 Superpowers 的 `verification-before-completion` 配合：前者关注交付表面的表达和残留，后者关注验证证据是否足以支持完成结论。
- 与 Planning with Files 配合时，将计划文件视为工作记录，将最终文档、报告和 handoff 作为需要单独回读的交付表面。
