# AI安全伦理与产品判断

## 知识点解析

### 概述

AI 安全伦理与产品判断关注模型在真实产品中是否可控、合规并值得上线。风险不仅来自模型生成有害内容，还包括训练数据污染、隐私泄露、Prompt Injection、越权工具调用和错误信息进入业务链路。治理需要同时覆盖模型、数据、权限、运行环境和人工流程。

#### 高频问题

1. AI 模型有哪些常见安全风险？
2. 什么是 prompt injection？RAG 和 Agent 系统为什么更容易受影响？
3. 如何防止模型泄露隐私、密钥或训练数据？
4. 如何处理有害内容、偏见、歧视、幻觉和版权风险？
5. 安全评测应该覆盖哪些维度？
6. 什么是 guardrail？它应该放在模型前、中、后哪个位置？
7. 如何设计人工审核和自动审核结合的机制？
8. 如何在用户体验和安全限制之间做平衡？
9. 如何处理模型拒答过多的问题？
10. Agent 工具调用有哪些安全边界？
11. AI 产品上线前需要哪些评估？
12. 算法工程师如何理解业务指标，而不是只优化模型指标？

### 核心知识点

- 安全风险：隐私泄露、越权访问、提示注入、有害内容、偏见歧视、幻觉、版权、数据投毒。
- 防护机制：输入过滤、输出审核、权限校验、工具白名单、沙箱、审计日志、敏感信息脱敏。
- RAG 安全：文档权限、检索污染、恶意上下文、引用真实性、知识边界。
- Agent 安全：工具权限、确认机制、动作幂等、危险操作审批、状态隔离。
- 安全评测：红队测试、越狱测试、隐私测试、偏见测试、事实性测试、鲁棒性测试。
- 产品判断：用户价值、成本收益、延迟体验、失败兜底、可解释性、运营闭环。

#### 回答要点

- 安全不能只依赖模型拒答，应结合权限、数据、工具、审计和产品流程做系统性防护。
- Prompt injection 的本质是外部输入试图覆盖系统指令或诱导模型执行越权动作。
- RAG 系统必须保证用户只能检索到自己有权限看的内容，否则模型会成为数据泄漏通道。
- Agent 工具调用要遵循最小权限原则，高风险动作需要显式确认、审批或回滚机制。
- 产品上不能只看模型指标，还要看用户完成率、满意度、成本、延迟、投诉率和风险事件。

### 威胁建模

安全设计应先明确资产、攻击者、入口和影响：

- 资产：系统提示词、用户数据、密钥、内部文档、工具权限和业务操作。
- 攻击入口：用户输入、上传文件、网页内容、RAG 文档、工具返回值和外部 API。
- 攻击目标：获取敏感信息、覆盖指令、调用未授权工具、污染知识、扩大资源消耗。
- 影响：数据泄漏、资金或业务损失、错误决策、合规风险和服务不可用。

威胁模型决定防护优先级。只对普通聊天做内容过滤，无法防止 Agent 使用合法工具执行越权操作。

### Prompt Injection 与越狱

直接 Prompt Injection 来自用户输入，间接 Prompt Injection 藏在网页、邮件、文档或工具返回值中。模型无法可靠地仅靠自然语言区分“可信指令”和“不可信数据”，因此不能把系统安全建立在提示词优先级上。

防护需要多层组合：

1. 将外部内容标记为不可信数据，不允许其直接改变工具权限。
2. 工具层独立做身份认证、参数校验和资源权限检查。
3. 使用最小权限和短期凭证，按任务授予能力。
4. 高风险操作要求结构化预览、用户确认或人工审批。
5. 对工具参数和返回值做 schema 校验与内容过滤。
6. 记录完整审计轨迹，支持追责和回放。

越狱主要尝试绕过内容安全策略；Prompt Injection 更关注改变系统行为或工具调用。两者可能重叠，但测试集和防护目标不同。

### 数据与隐私安全

- 训练数据应有来源和授权记录，移除密钥、身份信息和受限制内容。
- 日志默认不保存完整敏感输入，必要字段应脱敏、加密并设置保留期限。
- RAG 必须在召回前或召回过程中执行权限过滤，不能先取出无权限内容再要求模型不要展示。
- 模型输出需要检测个人信息、凭证和训练数据记忆泄露。
- 删除请求需要覆盖原始数据、派生数据、索引、缓存和后续训练版本的治理流程。

差分隐私、联邦学习和安全聚合适用于特定隐私场景，但会带来精度、工程复杂度和成本，不应被当成通用替代方案。

### Agent 工具安全

工具调用风险由“模型可能犯错”和“工具具有真实副作用”共同产生。建议按风险分级：

| 风险级别 | 例子 | 控制方式 |
| --- | --- | --- |
| 低 | 搜索、读取公开信息 | 参数校验、限流、日志 |
| 中 | 修改草稿、创建临时资源 | 结果预览、幂等、可撤销 |
| 高 | 发消息、付款、删数据、改权限 | 显式确认、审批、最小权限、审计 |

系统还应限制工具调用次数、递归深度、预算和执行时间，防止死循环与资源滥用。代码执行必须使用网络、文件和进程权限受限的沙箱。

### 安全评测

安全评测应覆盖正常输入和对抗输入：

- 有害内容、偏见、歧视和误拒答。
- 直接与间接 Prompt Injection。
- 系统提示词、密钥和个人信息泄露。
- RAG 权限绕过与知识库投毒。
- 工具越权、危险参数、重复执行和确认绕过。
- 超长输入、循环调用和资源耗尽。

指标至少包括攻击成功率、误放行率、误拒答率、风险严重度和人工复核一致性。高风险场景不能只依赖 LLM Judge，应加入规则、沙箱测试和人工红队。

### 产品上线判断

是否上线不能只看平均模型分数，应综合判断：

```text
用户价值
  - 失败概率 × 失败损失
  - 推理与人工成本
  - 延迟和交互成本
  - 合规与声誉风险
```

上线前应明确允许模型做什么、不能做什么、失败时如何兜底、谁负责响应。对于高风险场景，可采用建议模式而不是自动执行，并保留人工最终决策。

## 面试应对

### Prompt Injection 应该怎么防？

回答思路：先说明模型侧无法单独根治，再从数据、权限、工具和审计分层回答。

回答模板：

Prompt Injection 不能只靠增加一条系统提示词解决，因为模型可能把外部文档中的恶意文本误当成指令。我会把网页、邮件和 RAG 文档统一视为不可信数据，工具层独立执行身份认证、最小权限和参数校验。高风险动作必须先生成结构化预览，再由用户确认或审批；执行过程限制调用次数、预算和超时，并保留审计日志。也就是说，即使模型被诱导，真正有副作用的系统仍然不会直接信任模型输出。

### 如何设计 Agent 的安全边界？

回答思路：按权限、执行、确认、监控和恢复组织。

回答模板：

我会先按工具副作用划分风险等级，默认使用最小权限和短期凭证。读取类工具可以自动执行，修改类操作要求结果预览，删除、付款、发消息和权限变更等高风险操作要求显式确认或审批。执行层使用沙箱、参数 schema、幂等键、超时和预算限制，避免越权、重复执行和死循环。最后通过审计日志、异常告警和回放机制保证问题可发现、可追责、可恢复。

### 模型误拒答和误放行哪个更严重？

回答思路：根据业务损失回答，不做脱离场景的绝对判断。

回答模板：

要根据场景的风险函数判断。医疗、金融操作或未成年人内容中，误放行可能造成不可逆损失，因此通常优先降低误放行；普通知识问答中过度拒答会严重损害可用性，可以适当提高召回。工程上我会分别统计误拒答率和误放行率，按风险等级设置不同阈值，并为高风险场景增加人工审核，而不是用一套策略覆盖所有请求。
