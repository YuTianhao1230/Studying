# 关键帧识别项目闭环复盘

## 项目定位

关键帧识别项目的目标，是把移动端 UI 操作录屏中的业务指标结束帧自动定位出来。这个任务看起来是“给视频预测一个时间戳”，但本质上是一个带业务规则的多模态时间定位问题：模型不仅要看懂视频，还要理解不同 task_type 下什么叫完成态、哪些变化应该等待、哪些变化应该豁免、哪些帧虽然看起来接近但仍不能算完成。

从面试角度看，这个项目非常适合体现大模型训练工程实战、数据工程与数据质量、评测体系和上线闭环能力。

## 项目背景

传统 UI 性能评估依赖人工从操作录屏中标注关键帧，再根据起止帧换算耗时。人工标注存在三个核心问题：

1. 标注成本高：CQC 单人标注人效约 150 条/PD，人力峰值约 1200 条/天，难以支撑持续扩张的数据规模。
2. 标准不稳定：不同业务线、不同指标对“完成态”的定义不同，人工标注容易出现前后不一致。
3. 结果难复用：如果没有把标注标准、数据版本、bad case 和模型输出结构化沉淀，每次迭代都像重新做一遍人工判断。

项目目标是构建智能预标模型：输入移动端操作视频和指标 task_type，输出完成态第一次成立的时间点。模型能力上线后可以降低人工标注成本，并把人工经验沉淀成可训练、可评测、可回流的数据资产。

## 核心结果

| 维度 | 结果 |
| --- | --- |
| 数据规模 | 沉淀 15w+ 样本，训练集 11w+ 覆盖 172 个指标，测试集 4w+ 覆盖 110 个指标 |
| 整体效果 | 平均 ACC 从 75.714 提升到 84.876 |
| 重点业务线 | 国际电商 ACC 从 84.093 提升到 95.933 |
| 数据飞轮 | 三轮返修 27000+ 高质量样本，覆盖国际电商核心 30+ 指标 |
| 上线效果 | 5 月底完成模型部署上线，国际电商关键帧识别 3 帧误差线上回测平均达到 90.05% |
| 成本收益 | 标注成本下降 19%，提效贡献占比 9.5% |
| 部署压测 | 单卡并发 20 左右较合适，平均处理时间约 45s，QPM 约 22 |

## 项目闭环

### 问题定义

关键帧识别不是通用视频理解任务，而是面向 UI 性能指标的完成态判断任务。每个样本至少包含：

- 视频路径或帧序列。
- task_type，例如商城页加载耗时、购物车加购耗时、小说内容加载耗时。
- 标注标准，包括关键帧特征、排除条件、豁免条件。
- GT 时间戳或帧号。
- 业务线、数据来源、版本、指标归属等元数据。

这里最关键的判断是：不同指标的完成态不一样。比如“购物车加购耗时”优先看购物车角标数字变化；如果角标被遮挡，才看“加购成功”文案。而“商详页加载耗时”可能要等头图、价格、营销 banner 等核心元素同时稳定。模型如果只学习“页面大致出现”，就会在业务准出上失败。

### 数据构建

项目的数据构建不是简单把视频和 GT 拼成训练样本，而是围绕真实业务链路做了数据 schema 和版本管理：

| 数据层 | 作用 |
| --- | --- |
| 原始采集数据 | 保留业务操作录屏、指标类型和原始人工标注 |
| 处理后训练数据 | 将图片合成视频，统一路径、fps、frame_count、duration、输入尺寸等字段 |
| 评测数据 | 按时间和业务线隔离，用于全量 ACC 和分指标 ACC |
| bad case 数据 | 模型预测错误样本，用于人工复查、归因和重标 |
| 回流数据 | 删除送标旧数据，拼接返修新数据，生成新版本训练集 |

这套数据链路体现的能力是：训练数据必须能追溯、能替换、能复现。否则模型效果提升后，很难判断收益来自哪里，也无法排查指标波动。

### 标注标准沉淀

关键帧识别最大的难点之一，是人工经验没有天然结构化。项目中把标注标准拆成几类：

- 完成态：必须同时满足的核心条件。
- 排除条件：一旦出现就不能判为完成，例如骨架屏、转圈、残影、错位、白膜、模糊。
- 豁免条件：不需要等待的变化，例如屏幕外亮度、Automation Running、非关键区域角标、局部小动效。
- 首选证据：最能代表完成态的 UI 元素。
- 备选证据：首选证据不可见或被遮挡时的替代判断。

这一步的价值是把“人工知道但模型不知道”的业务先验显式注入 prompt、训练数据和评测规则中。实验上，prompt 和标注标准对齐后，1 epoch 快速验证中平均 ACC 从 73.886 提升到 81.54，国际电商 ACC 从 84.466 提升到 95.418。

### 数据飞轮

项目采用“模型筛 bad case -> 人工重标 -> 回流训练”的数据飞轮，而不是平均铺数据。

核心策略：

1. 先用模型在评测集上找错例。
2. 对错例做人工复查，区分模型错误和标注错误。
3. 把高价值业务线和低分指标优先送标。
4. 对返修数据重新构建训练样本。
5. 用新数据训练并复测，观察全量、业务线和分指标收益。

这类飞轮比单纯加数据更有效，因为它把资源投向模型真正失败、业务价值高、标注标准冲突明显的样本。项目中三轮飞轮返修 27000+ 高质量样本，国际电商核心指标明显提升。

### Bad Case 归因

这个项目里很重要的结论是：模型错不一定是模型能力差，也可能是 GT 错。

人工筛查 204 个 bad case 后发现：

- 标注误差为 68/204。
- 返修样本中 relabel 占保留返修样本约 61.45%。
- 无变化样本约 38.55%。

这说明关键帧识别的优化不能默认人工 GT 全部正确。正确流程是先做 bad case 归因，再决定是修标注标准、重标数据、换模型，还是改推理策略。

### CoT 数据蒸馏

关键帧识别的 CoT 蒸馏不是为了让模型输出更长解释，而是为了让模型学习“如何判断完成态边界”。核心思想是把单点 GT 监督升级成“时间过程 + 视觉证据 + 边界判断 + 最终答案”的监督。

第一版 CoT 暴露出两个问题：

1. 时间切片不够细，模型容易只围绕 GT 前后做事后总结。
2. 没有模拟人工标注的真实判断路径。

第二版引入粗筛和精筛：

- 粗筛：低 FPS 看完整视频，定位候选完成窗口。
- 精筛：在候选窗口附近高 FPS 复查，比较 GT 前、首次完成和后续稳定。

第三版进一步拆成两阶段：

1. 视频原语理解：只描述客观状态和事件，不回答问题，不泄漏 GT。
2. 问题驱动推理：根据 task_type 和标注标准，从视频原语中判断完成态边界。

这背后的训练思想是 Direct SFT -> Structured CoT SFT -> RL：

- Direct SFT：先保证模型能直接预测关键帧。
- Structured CoT SFT：让模型学会输出稳定格式和证据引用。
- RL：用 `R_time + R_format + R_boundary_evidence - P_length` 优化时间精度、格式合法性、边界证据和推理长度。

### 模型训练工程

项目链路包含数据构建、训练、推理、评测和 case 分析：

| 阶段 | 核心动作 | 关键风险 |
| --- | --- | --- |
| 数据处理 | 图片合成视频、生成 JSON、补充英文指标 ID、过滤帧数异常样本 | 路径重复、云盘不一致、坏视频、帧数不足 |
| 训练 | 使用 msswift_scripts 在 GPU 资源上训练 Qwen 系列模型 | 资源排队、训练耗时、配置和输出路径不一致 |
| 推理 | 用训练 checkpoint 跑 video_time_grounding 推理 | 模型名和 checkpoint 对不上、输入 fps 不一致 |
| 评测 | 生成 metrics.jsonl 和 metrics_global.jsonl | 指标口径错误、业务线分桶错误 |
| case 分析 | 输出 bad_data_analysis.html | 样本映射错误、GT 错误和模型错误混淆 |
| 数据回流 | 删除送标数据、拼接重标数据、生成新版本 | 数据泄漏、重复样本、版本不可追溯 |

### 模型部署上线

上线阶段要验证的不是“模型能不能跑”，而是“服务能不能稳定被业务链路消费”。

| 环节 | 关键工作 |
| --- | --- |
| 接口定义 | 对齐用户输入到模型输入的字段映射，包括指标类型、起始帧、图片 URL 列表等 |
| 输出字段 | 对齐预测结束帧、置信度、错误码、可解释信息 |
| 效果验证 | 比较离线评测结果和线上服务测试结果 |
| 吞吐拆解 | 定位端到端耗时瓶颈，区分图片下载、预处理、模型推理、后处理 |
| 压力测试 | 验证并发、平均耗时、QPM、超时和失败率 |
| 全链路联调 | 确认业务请求能正确进入模型服务，输出能正确回传 |

项目中发现端到端耗时瓶颈主要在图片下载：串行下载约 30s，模型推理约 3s。这说明优化方向不能只盯模型推理，必须拆链路耗时。

## 面试表达

### 请介绍一下关键帧识别项目。

回答思路：用“人工标注瓶颈 -> 模型预标 -> 数据飞轮 -> 上线”的闭环讲。

回答模板：

这个项目是视频关键帧识别能力建设，目标是从移动端操作录屏中自动定位业务指标的结束帧。它不是简单的视频分类，而是要根据不同 task_type 判断页面什么时候真正进入完成态。我的工作是把人工标注经验标准化成 prompt、训练数据和评测规则，再通过 bad case 分析、数据飞轮、模型训练和上线压测形成闭环。最终沉淀了 15w+ 数据，三轮返修 27000+ 高质量样本，平均 ACC 从 75.714 提升到 84.876，国际电商 ACC 从 84.093 提升到 95.933，并支撑模型上线和标注成本下降。

### 这个项目为什么不是普通视频理解？

回答思路：强调业务规则、完成态定义和边界帧判断。

回答模板：

普通视频理解更多是回答视频里发生了什么，而关键帧识别要回答“第一次满足某个业务完成态的是哪一帧”。这个判断依赖 task_type，例如有些指标要求页面主体完全加载，有些指标只要求首帧出现，有些指标要等待购物车角标变化，有些指标要忽略顶部导航或悬浮按钮。模型必须理解完成态、排除条件和豁免条件，否则会把“页面大致出现”误判成完成。它本质上是带业务规则的 temporal grounding 和 UI 状态判断任务。

### 你怎么做数据质量治理？

回答思路：围绕标注标准、bad case 归因、relabel 和版本管理回答。

回答模板：

我没有默认人工 GT 一定正确，而是先对 bad case 做人工复查，区分模型预测错误和标注错误。比如一些样本中人工标注等待了不该等待的 UI 元素，导致 GT 偏晚；还有些样本模型漏看购物车角标这种小元素，属于模型能力问题。基于归因结果，我把样本分成可直接回流、需要重标、需要修 prompt 标准和需要提升模型能力几类。回流时删除送标旧数据，拼接重标新数据，并生成新的训练版本，保证数据可追溯。

### 为什么要做数据飞轮？

回答思路：说明平均补数据低效，高优业务线和低分指标更值得优先处理。

回答模板：

关键帧任务的指标很多，数据分布也长尾。如果平均补数据，会把大量资源花在已经高分或低价值指标上。数据飞轮的逻辑是先用模型找出 bad case，再人工归因和重标，最后把高质量返修样本回流训练。这样每一轮数据都更聚焦在模型真正短板和业务高价值场景上。项目中三轮飞轮返修了 27000+ 样本，国际电商核心指标提升非常明显，说明定向数据治理比简单堆数据更有效。

### CoT 蒸馏在这个项目里解决什么问题？

回答思路：强调 CoT 不是解释文本，而是边界判断监督。

回答模板：

这里的 CoT 蒸馏不是为了让模型说更多理由，而是让模型学习人工判断关键帧的过程。原始 GT 只告诉模型最终时间点，但不告诉它为什么前一帧不行、这一帧首次满足、后一帧没有推翻。结构化 CoT 把视频拆成未完成、首次完成、后续稳定几个阶段，并要求模型描述可见 UI 证据和边界判断。后续还可以用粗筛加精筛，让模型先低 FPS 找候选窗口，再高 FPS 检查边界，从而同时控制成本和提升精度。

### 线上部署时你重点关注什么？

回答思路：讲字段映射、离线线上一致性、耗时拆解和压测。

回答模板：

上线时我重点关注四件事。第一是接口字段对齐，确保业务传入的 keyframe_type、图片列表和起始帧能正确映射到模型输入。第二是离线线上效果一致，不能离线 ACC 很高但线上因为抽帧、图片下载或字段映射不同导致效果下降。第三是端到端耗时拆解，项目里发现图片下载约 30s、模型推理约 3s，所以瓶颈不在模型本身。第四是压测和容量评估，单卡并发控制在 20 左右比较合适，平均处理时间约 45s，QPM 约 22。

### 如果模型在某个指标上效果很差，你会怎么排查？

回答思路：按标准、数据、模型、推理、评测五层排查。

回答模板：

我会先看这个指标的标注标准是否清楚，比如到底是首帧出现还是完全加载，哪些 UI 元素必须等待，哪些可以豁免。然后抽 bad case 判断是 GT 错还是模型错；如果 GT 错，就要重标或修标准；如果模型错，再看是不是训练样本少、样本分布偏、UI 小元素看不清，还是 fps 太低漏掉边界帧。最后检查评测脚本和后处理，确认时间戳、帧号、误差阈值和业务线分桶没有问题。只有定位清楚瓶颈，才决定是补数据、改 prompt、换基座、调采样还是修评测。

## 可迁移的能力总结

这个项目最终体现的不是单点模型能力，而是完整训练工程能力：

1. 将模糊业务标准转成可训练、可评测的结构化规则。
2. 将人工标注经验转成数据 schema 和 prompt 规则。
3. 通过 bad case 归因判断模型问题和数据问题。
4. 用数据飞轮持续提升高价值指标。
5. 用 Direct SFT、Structured CoT SFT、RL 设计后续训练路线。
6. 用粗筛 + 精筛解决长视频 token 成本和边界帧精度冲突。
7. 用压测、接口定义和线上回测保证模型真实可用。
