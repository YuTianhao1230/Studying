# 大模型训练工程实战追问

## 知识点解析

### 概述

大模型训练工程实战考察的不是“会不会跑一个训练命令”，而是能否把数据、代码、资源、训练、推理、评测和产物管理成可复现链路。对于模型训练岗位，用人领导通常会追问：

- 你怎么准备训练数据？
- 训练任务在哪里跑？资源怎么选？
- 配置、代码、数据版本怎么对齐？
- 训练完怎么推理和评测？
- 指标异常怎么排查？
- 结果怎么沉淀成下一轮数据或上线依据？

关键帧识别项目可以作为训练工程实战的代表案例，因为它覆盖了从数据构建到模型上线的完整链路。

### 训练工程闭环

一个完整训练工程链路可以拆成七层：

| 层级 | 核心问题 | 关键产物 |
| --- | --- | --- |
| 资源层 | 在哪里跑、用什么 GPU、云盘和队列是否匹配 | 集群、队列、云盘、开发机、任务配置 |
| 环境层 | 依赖是否一致、是否可复现、是否和训练平台兼容 | conda/poetry 环境、requirements、镜像 |
| 数据层 | 数据从哪里来、怎么处理、怎么切分、怎么版本化 | JSON/JSONL、视频文件、数据版本、schema |
| 训练层 | 用什么基座、什么脚本、什么超参数、输出到哪里 | 训练脚本、checkpoint、训练日志 |
| 推理层 | 用哪个 checkpoint 推理、输入输出是否一致 | prediction 文件、推理配置 |
| 评测层 | 指标怎么算、全量和分桶怎么看 | metrics.jsonl、metrics_global.jsonl、报告 |
| 复盘层 | bad case 怎么归因、下一轮怎么改 | case HTML、错误 taxonomy、回流数据 |

### 关键帧识别中的工程链路

项目中的链路可以抽象为：

1. 在开发机准备 mllm-data 环境，用于数据处理和本地实验。
2. 用数据处理脚本将原始图片序列合成视频，并生成训练需要的 JSON。
3. 在数据配置中切换 version 和 disk_prefix，隔离不同实验版本。
4. 运行数据构建脚本生成训练文件。
5. 在训练平台申请 GPU 资源，使用 msswift_scripts 训练 Qwen 系列多模态模型。
6. 训练结束后用对应 checkpoint 做推理，输出 prediction。
7. 在 mllm-evaluation 中计算全量指标和分业务线指标。
8. 生成 bad case HTML，人工复查后形成数据飞轮。
9. 回流重标数据，替换旧数据，进入下一轮训练。

这个链路里最容易出错的地方不是模型代码本身，而是路径、版本、数据切分、checkpoint 对齐和评测口径。

### 资源与环境管理

训练工程里资源选择会直接影响实验节奏。关键判断包括：

- 开发机不等于训练资源，开发机用于调试和代码准备，训练任务需要平台资源。
- 任务资源和云盘要在同一个集群，否则数据读写会出问题。
- 高优实验优先使用稳定可用资源，避免排队时间影响迭代。
- Debug 任务和正式训练任务要分开，短时资源可用于 smoke test，但不适合长训练。
- 训练和推理可能都需要 GPU，最好训练脚本支持训练结束后自动推理，避免重新排队。

### 数据构建工程

关键帧识别的数据构建有几个典型工程点：

- 原始图片序列需要合成视频，处理速度较慢，必须有版本和中间产物管理。
- 数据中要保留视频元信息，例如 fps、frame_count、duration、width、height。
- 训练样本要有 task_type、answer_obj、problem_type、data_version 等字段。
- 需要过滤视频帧数小于 2 的异常数据，避免推理崩溃。
- 不同云盘路径要显式配置，避免路径重复或跨盘引用。
- 每次 debug 要有独立 version，避免覆盖正式实验产物。

### 训练与推理管理

训练脚本通常不是一次性命令，而是一组配置约束：

- 模型基座：例如 Qwen 系列多模态模型。
- 数据版本：训练集、验证集、测试集必须与实验记录一致。
- 输出路径：checkpoint、log、prediction 必须包含模型名和数据版本。
- 训练资源：GPU 型号、卡数、队列、集群、运行时间。
- 推理配置：fps、max_frames、max_pixels、batch、checkpoint 路径。
- 评测配置：task_list、mllm_type、prediction_folder、指标阈值。

一个可靠训练工程师要能回答“这次实验能不能复现”。如果代码版本、数据版本、checkpoint 和评测脚本无法对应，指标再高也不可信。

### 评测与产物管理

评测阶段要区分：

- 全量平均指标：看整体能力。
- 分业务线指标：看重点业务是否达标。
- 分 task_type 指标：看具体低分指标。
- bad case 样本：看错误模式和下一轮数据方向。
- 线上回测：看离线结果是否能迁移到真实链路。

关键帧识别中常见输出包括：

- `metrics.jsonl`：全量样本评测结果。
- `metrics_global.jsonl`：业务线或全局聚合指标。
- bad case HTML：用于人工检查模型预测和 GT 差异。
- JSON/Excel 报告：用于分析分指标 ACC 和回流优先级。

## 面试应对

### 你做过的大模型训练工程链路是什么样的？

回答思路：按数据、训练、推理、评测、回流讲完整链路。

回答模板：

我做过关键帧识别模型的训练工程链路。整体流程是先在 mllm-data 中处理原始标注数据，把图片序列合成视频并生成训练 JSON；然后在数据配置里管理 version、disk_prefix 和 train/test 文件；再到训练平台申请 GPU 资源，用 msswift_scripts 训练 Qwen 系列多模态模型；训练完成后用对应 checkpoint 跑推理；最后在 mllm-evaluation 中计算全量 ACC、业务线 ACC 和分指标 ACC，并生成 bad case HTML 做人工复查。复查结果会进入数据飞轮，删除旧送标数据、拼接重标数据，再进入下一轮训练。

### 训练任务开始前你会检查什么？

回答思路：从代码、数据、资源、配置和输出路径五方面回答。

回答模板：

训练前我会先检查代码分支和 commit，确认训练脚本对应当前实验目标；然后检查数据版本、训练集和测试集路径、样本量、字段 schema 和是否存在坏视频。资源上要确认 GPU 队列、云盘和任务所在集群一致，避免跨盘读写问题。配置上要确认基座模型、batch、learning rate、fps、max_frames、输出路径和实验 version。最后我会先跑小样本 smoke test，确认数据加载、前向、loss、保存 checkpoint 和评测入口都能跑通，再提交正式训练。

### 训练结束后你怎么验证结果可信？

回答思路：先看指标，再看配置一致性和 bad case。

回答模板：

我不会只看一个平均 ACC。首先要确认训练使用的数据版本、checkpoint、推理配置和评测脚本是对应的。然后看全量指标、分业务线指标和分 task_type 指标，判断提升是否集中在目标场景。接着抽样看 bad case，区分模型错、GT 错、解析错还是评测口径错。如果离线指标提升但 bad case 显示是数据泄漏或标注标准变化导致的，就不能认为模型真实变强。可信结果必须能通过配置复现、分桶解释和 case 证据支撑。

### 如果训练和推理结果对不上，你会怎么排查？

回答思路：按 checkpoint、数据版本、推理配置、后处理和指标实现排查。

回答模板：

我会先确认推理用的 checkpoint 是否就是这次训练产物，模型名和路径有没有配错。然后检查推理数据版本是否和评测数据一致，尤其是 train/test 文件、disk_prefix、视频路径和 task_type 映射。第三步看推理配置，比如 fps、max_frames、max_pixels 是否和训练或评测预期一致。第四步检查后处理，确认模型输出的时间戳能被正确解析，并映射到原视频时间。最后检查指标脚本，比如 1 帧/3 帧误差阈值、业务线聚合和无效样本过滤是否正确。

### 训练平台资源怎么选？

回答思路：说明不同资源适合 debug、正式训练和推理，不要只说“用更多卡”。

回答模板：

我会根据任务阶段选择资源。debug 阶段优先用排队快、成本低的资源，只验证环境、数据加载和小样本前向。正式训练需要稳定 GPU 和足够运行时长，避免任务中途被抢占或强杀。训练数据和云盘最好在同一个集群，减少 IO 和权限问题。如果训练结束后还要推理，我会尽量把训练和推理串在同一个任务里，避免训练完成后重新排队。资源选择的目标不是盲目用最多卡，而是让实验能稳定完成、产物可复现。

### 训练工程里最容易被忽略的风险是什么？

回答思路：强调路径、版本、评测和数据污染。

回答模板：

最容易被忽略的是版本错配。比如训练数据版本换了，但推理仍然用旧 checkpoint；评测脚本路径指向旧 prediction；云盘切换后读到另一份数据；bad case 回流时没有删除旧送标样本，导致重复或泄漏。这些问题不会一定报错，但会让指标失真。我的习惯是每次实验记录代码版本、数据版本、模型路径、推理路径、评测路径和关键配置，并把输出路径设计成包含实验名和 version，降低混淆概率。

### 如果数据处理很慢，你会怎么优化？

回答思路：先确认瓶颈是 IO、解码、编码还是模型调用。

回答模板：

我会先拆分耗时：读原始文件、图片解码、视频编码、JSON 处理、网络盘 IO 哪一步最慢。像关键帧项目里图片合成视频每 10000 条可能需要 8-10 小时，这类任务要做并行分片、断点续跑和中间产物缓存。对于已经处理过的数据，不应该重复生成；对于失败样本，要单独记录错误原因并跳过或重试。优化目标是提高吞吐，同时保证数据版本可追溯，不能为了快把异常样本静默丢掉。

### 你如何理解训练工程和算法研究的关系？

回答思路：强调工程保证实验可信，算法决定优化方向。

回答模板：

算法研究提供优化方向，但训练工程决定实验结论是否可信。比如同一个模型结构，如果数据版本、评测口径、checkpoint 或推理配置不一致，得到的指标就没有可比性。反过来，工程链路稳定后，算法改动才能被准确评估。我的理解是，模型训练岗位需要同时具备两种能力：一方面能提出合理的模型和数据优化假设，另一方面能把训练、推理、评测和回流链路做成可复现系统。

## 高频追问清单

### 如果训练任务排队很久怎么办？

回答模板：

我会先判断实验优先级和资源需求。低优或 debug 实验可以换更容易排到的队列，或者降低卡数和样本量做 smoke test。高优正式实验要选择稳定资源，确认云盘和资源集群匹配，并尽量把训练和推理串起来，减少二次排队。如果资源长期不可用，还要拆出 CPU 可跑的数据构建、评测和报告任务，避免等待期间完全停滞。

### 为什么要做 smoke test？

回答模板：

Smoke test 是为了在低成本下提前暴露路径、依赖、数据格式、显存和脚本参数问题。大模型训练任务排队和运行成本都很高，如果直接全量跑，可能几个小时后才发现一个字段缺失或路径错误。小样本跑通数据加载、前向、loss、checkpoint 保存和评测解析后，再启动全量训练，整体效率更高。

### 如何防止实验产物混乱？

回答模板：

我会给每次实验定义唯一 version，并让数据、checkpoint、prediction、metrics 和报告路径都带上这个 version。实验记录里保存代码分支、关键参数、数据版本、资源配置和输出路径。对于回流数据，要保留原始数据、删除列表、追加数据和最终合并数据，避免无法追溯。产物管理的核心是让别人能根据记录复现同一个结果。

### 模型上线前为什么还要压测？

回答模板：

离线评测只能说明模型效果，不能说明线上服务能稳定承接流量。上线前要压测并发、QPM、平均耗时、p95/p99、失败率和资源利用率。关键帧项目里端到端耗时主要来自图片下载而不是模型推理，如果不做压测，很容易把优化方向误判成换模型或加卡。压测的价值是找到真实瓶颈，并给出可执行的并发和容量配置。
