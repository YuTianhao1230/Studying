# 数据工程与数据质量项目追问

## 知识点解析

### 概述

模型训练岗位里，数据工程和数据质量经常比模型结构更能区分候选人。面试官不会只问“你用了多少数据”，而会追问：

- 数据从哪里来，为什么可信。
- schema 怎么设计，后续能不能复现。
- 标注规则是否一致，GT 是否一定正确。
- 训练集、验证集、测试集如何隔离。
- bad case 如何变成下一轮高质量数据。
- 合成数据和 CoT 数据如何过滤。
- 数据回流后如何保证不引入泄漏和重复。

关键帧识别项目非常适合回答这类问题，因为它不是简单收集数据，而是构建了围绕真实业务指标的数据飞轮。

### 数据 schema 设计

一个关键帧识别样本不应该只包含视频和答案。为了支持训练、评测、归因和回流，至少需要保留：

| 字段 | 作用 |
| --- | --- |
| `id` | 样本唯一标识，用于追踪、去重、回流和 bad case 对齐 |
| `video` | 视频路径或视频资源地址 |
| `gt_time` / `answer_obj` | 标注时间点或标准答案 |
| `task_type` | 指标类型，决定完成态定义 |
| `data_version` | 数据版本，支持复现和对比 |
| `video_metadata` | fps、frame_count、duration、width、height |
| `visual_input` | 输入模式、抽帧 fps、max_frames、精筛窗口等 |
| `source_sample` | 原始样本追踪，用于回查标注和业务来源 |
| `cot` | 可选，结构化思维链或证据链 |
| `validation_warnings` | 数据校验警告 |

schema 的目标是让样本可训练、可评测、可追溯、可修复。只保留模型输入和输出，会让后续 bad case 归因非常困难。

### 标注质量问题

关键帧识别中，GT 不一定天然正确。常见标注问题包括：

- 标注人员等待了不该等待的非关键元素。
- 不同 task_type 对同一 UI 元素的等待规则不一致。
- 首帧出现和完全加载的定义混淆。
- 页面过渡残影、白膜、骨架屏、局部小动效被误判。
- 视频 fps 或抽帧粒度导致时间边界不精确。
- 新手引导、Automation Running、屏幕外亮度变化等豁免项被错误纳入判断。

因此，数据质量治理必须从标注标准开始，而不是只做格式清洗。

### Bad Case 归因

bad case 不是简单的“错题集”，而是数据飞轮的入口。一次 bad case 分析应该区分：

| 类型 | 判断标准 | 处理方式 |
| --- | --- | --- |
| GT 错误 | 模型预测更符合标注标准，人工 GT 偏早或偏晚 | relabel，修正 GT |
| 标准冲突 | 同一元素在不同指标中等待规则不一致 | 重写 task_type 标准 |
| 模型漏看 | 小元素、角标、头像、价格、banner 等未识别 | 补充高质量样本或引入 UI primitive |
| 时间粒度不足 | 低 FPS 漏掉边界帧 | 提高局部 fps 或粗筛+精筛 |
| 后处理错误 | 模型输出正确但解析或映射错误 | 修评测脚本或输出 parser |
| 数据映射错误 | 视频、label、task_type 或业务线错配 | 修数据构建链路 |

关键帧项目中，人工筛查 204 个 bad case 发现 68 个标注误差，返修样本中 relabel 占约 61.45%。这个结论说明：模型优化前必须先确认评测数据是否可信。

### 数据飞轮

数据飞轮的核心不是“把错题重新训练一遍”，而是让每一轮数据回流都更高质量：

1. 用当前模型预测全量评测集。
2. 筛选 bad case，优先覆盖高价值业务线和低分指标。
3. 人工复查并归因，区分模型错和标注错。
4. 修正 GT、补充标注标准、生成返修样本。
5. 删除旧送标数据，拼接回流数据，生成新版本训练集。
6. 重新训练和评测，观察全量、业务线、分指标收益。
7. 固化有效标准和失败类型，进入下一轮。

这个过程的关键是优先级：不是所有错误都值得修，优先修业务价值高、样本量足、错误模式集中、能带来泛化收益的错误。

### 合成数据与 CoT 数据质量

CoT 数据蒸馏有两个核心风险：

1. GT 泄漏：教师模型在推理过程中直接看到或引用 GT，生成的 CoT 只是答案的事后合理化。
2. 证据漂移：CoT 说某个 UI 元素已经加载，但对应时间帧实际上看不到这个元素。

因此，CoT 数据需要满足：

- 推理过程只基于视频帧和 task_type 标准，不把 GT 写进推理。
- `<time>`、`<caption>`、`<think>` 和 `<answer>` 格式可解析。
- 首次完成态片段必须说明相对前一段新增了什么证据。
- 后续稳定片段必须说明是否存在二次刷新、内容替换或异常跳转。
- CoT 中提到的 UI 元素必须能在对应帧看到。
- 对脏 GT 样本，模型可给出 relabel 判断，但需要人工抽检。

### 数据切分与泄漏

关键帧任务尤其容易出现隐性泄漏：

- 同一视频或相邻帧同时出现在训练集和测试集。
- 同一业务采集批次高度相似，随机切分导致 train/test 同源。
- prompt 或 CoT 中泄漏 GT 时间。
- bad case 回流后没有从评测集中隔离。
- 人工返修时直接参考模型预测，导致评测 GT 被模型污染。

更合理的切分方式是按时间、业务线、视频 ID 或采集批次做隔离，并维护独立回归集。

## 面试应对

### 为什么你说数据质量比模型结构更重要？

回答思路：结合关键帧项目说明标签噪声和标准冲突会直接限制模型上限。

回答模板：

在关键帧识别项目里，模型效果不好不一定是模型结构不够强，很多时候是数据和标注标准的问题。比如同一个页面，有的指标应该等待营销 banner 加载，有的指标应该忽略购物车角标；如果标准没有结构化，模型会学到混乱边界。另外，我在 bad case 复查中发现相当一部分错误其实来自人工 GT 偏早或偏晚。如果不先治理数据，继续换模型或加训练轮数只会把错误标注学得更牢。因此我会先做标注标准沉淀、bad case 归因、重标回流，再考虑模型结构升级。

### 关键帧识别的数据 schema 你会怎么设计？

回答思路：强调训练、评测、追溯和回流都要支持。

回答模板：

我会让 schema 同时服务训练和排查。基础字段包括样本 id、视频路径、task_type、GT 时间、数据版本和视频元信息，比如 fps、duration、frame_count。为了支持模型输入复现，还要记录抽帧 fps、max_frames、max_pixels 和 refine window。为了支持质量治理，要保留原始样本来源、业务线、标注批次、validation_warnings 和 bad case 归因结果。如果是 CoT 数据，还要保存时间片段、视觉证据、边界判断和最终 answer。这样每个样本出问题时都能回查来源和处理链路。

### 如何判断一个 bad case 是模型错还是标注错？

回答思路：按 task_type 标准复查视频，而不是只比较预测和 GT。

回答模板：

我会先拿到该样本的 task_type 和标注标准，明确完成态、排除条件和豁免条件。然后按时间轴看 GT 前、GT 附近和 GT 后的帧，判断 GT 是否真的是第一次满足完成态。如果模型预测帧更早，但该帧已经满足所有核心条件且后续稳定，说明可能是人工 GT 偏晚；如果模型预测帧缺少关键元素，比如购物车角标没更新或 banner 仍是白膜，那就是模型错。最后把错误归到标注问题、模型感知问题、时间粒度问题或评测解析问题，再决定下一步处理。

### 为什么不能把所有 bad case 直接回流训练？

回答思路：说明 bad case 中有 GT 错、脏样本和分布偏移，直接回流会污染训练。

回答模板：

bad case 不能直接回流，因为里面混合了多种情况。有些是模型真的错了，有些是人工 GT 错了，有些是标注标准冲突，有些是视频本身异常。如果把这些样本不加区分地加入训练，模型可能学到错误边界，甚至把评测集污染进训练集。正确做法是先归因和重标，只把标准明确、证据充分、能代表目标错误类型的样本加入下一轮训练，同时保留独立评测集做回归。

### CoT 数据怎么避免 GT 泄漏？

回答思路：区分教师推理输入和后验筛选，不让 GT 进入推理过程。

回答模板：

我会把 GT 只作为后验验证信号，而不是教师模型推理时可见的信息。教师模型应该只看到视频、task_type 和标注标准，先输出时间线证据、候选窗口和最终时间。然后再用 GT 判断该样本是否可用、是否需要 relabel 或人工复查。如果在 prompt 或 CoT 中直接出现“人工 GT 是 3.47s，所以这里正确”，模型学到的是事后解释，不是真正的视频证据推理，这样的数据不适合训练。

### 如何设计 CoT 数据的质量过滤？

回答思路：从格式、答案、证据、边界和长度五类校验回答。

回答模板：

我会做五类过滤。第一是格式校验，确保 `<time>`、`<caption>`、`<think>`、`<answer>` 都可解析。第二是答案校验，`answer time` 要和首次完成态片段的起点一致，并和 GT 在误差阈值内。第三是证据校验，CoT 提到的 UI 元素必须能在对应帧看到。第四是边界校验，必须解释为什么前一段未完成、当前段首次完成、后一段没有推翻。第五是长度校验，避免推理过长、重复或过短。只有通过这些检查的 CoT 才能进入训练。

### 数据飞轮怎么决定优先级？

回答思路：按业务价值、样本量、当前准确率和错误集中度排序。

回答模板：

我会优先处理业务价值高、当前准确率低、样本量足够、错误类型集中的指标。比如国际电商是高优业务线，某些指标有几百到上千样本且 ACC 低于准出线，这类样本返修收益最大。对于训练量很少的长尾指标，可能先补采数据；对于标注标准冲突明显的指标，先修标准再重标；对于模型漏看小元素的指标，考虑补细粒度样本或引入 UI primitive。数据飞轮的目标是让每轮返修都能解释收益来源。

### 如何处理标注标准变更后的历史数据？

回答思路：不要直接混用新旧标准，要做版本和影响面管理。

回答模板：

标注标准变更后，历史数据不能直接和新数据混在一起用。我会先给标准打版本，记录变更内容和影响的 task_type；然后抽样评估旧数据中有多少会被新标准推翻。如果影响面小，可以只重标受影响样本；如果影响面大，需要重建该指标训练集和评测集。训练和评测报告里也要写清楚使用的是哪一版标准，否则新旧模型指标不可比。

### 如何判断数据飞轮开始收益收敛？

回答思路：看新增数据边际收益、错误类型变化和瓶颈迁移。

回答模板：

如果连续几轮回流后，全量 ACC 和核心业务线 ACC 提升变小，bad case 不再集中在标注标准和脏数据，而是集中在小元素识别、低 FPS 漏帧或复杂页面理解，就说明单纯数据飞轮的边际收益在下降。这时优化方向要从补数据转向模型能力、输入表示和推理策略，比如更强基座、提高局部 fps、引入 UI primitive 或粗筛加精筛。

### 训练集、测试集和回归集应该怎么划分？

回答思路：强调时间、业务、视频 ID 和采集批次隔离。

回答模板：

我会避免简单随机切分，因为视频任务里同源样本很容易泄漏。更稳妥的做法是按采集时间、视频 ID、业务线或批次切分，保证同一视频、相邻帧或高度相似录屏不会同时出现在训练和测试中。测试集用于衡量泛化，回归集用于固定关键业务场景和历史 bad case。bad case 进入训练后，原测试集如果被污染，就要新建干净评测集。

### 如何把数据质量讲成项目贡献？

回答思路：不要只说“清洗数据”，要说数据质量如何改变模型和业务结果。

回答模板：

我会把数据质量讲成模型能力建设的一部分，而不是辅助工作。关键帧项目里，我通过 bad case 归因发现人工 GT 和标注标准本身存在问题，于是把标准拆成完成态、排除条件和豁免条件，再通过三轮数据飞轮返修高价值样本。这个过程让模型从学习混乱边界，变成学习明确的业务完成态，最终带来国际电商 ACC 和线上回测指标提升。所以数据质量贡献不是“整理数据”，而是把训练目标变得可信、可复现、可持续迭代。
