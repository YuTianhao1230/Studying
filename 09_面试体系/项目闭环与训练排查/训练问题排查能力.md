# 训练问题排查能力

## 知识点解析

### 概述

训练问题排查能力是模型训练岗位最核心的面试考察点之一。面试官通常不是想听“我会调 learning rate”，而是想判断你是否有系统定位问题的框架：先确认现象，再缩小影响范围，再提出假设，用实验或日志验证，最后修复并回归。

一个可靠的排查流程应该遵循：

1. 现象确认：问题是否真实存在，是否可复现。
2. 影响范围：只影响某个任务、某批数据、某个模型，还是全量影响。
3. 最近变更：代码、数据、配置、环境、依赖、资源是否变化。
4. 分层定位：数据、模型、优化器、精度、分布式、评测、线上链路逐层排查。
5. 最小复现：用小样本、单卡、固定 seed、固定 batch 复现。
6. 修复验证：用原问题 case 和回归集确认修复有效。
7. 复盘沉淀：记录原因、检测方法和预防措施。

## 常见问题

### Loss 突然 spike

可能原因：

- 数据中出现异常样本、空样本、极长样本或错误 label。
- learning rate 过大，warmup 不足，scheduler 配置错误。
- 混合精度溢出，梯度 scaler 异常。
- 梯度爆炸，缺少 gradient clipping。
- batch 组成变化太大，例如某些 batch 全是长序列或难样本。
- 分布式训练中某个 rank 数据异常。

排查顺序：

1. 找 spike 对应 step、global batch、数据 shard 和样本 ID。
2. 回放该 step 的 batch，检查输入长度、label、mask、loss 分布。
3. 看 gradient norm、learning rate、loss scale、NaN/Inf 日志。
4. 用单卡小 batch 复现，看是否和分布式相关。
5. 临时降低 learning rate 或开启 gradient clipping，判断是否优化问题。
6. 如果只在特定样本触发，先隔离数据，再决定清洗还是修数据处理逻辑。

### Loss 变 NaN

可能原因：

- fp16 溢出，softmax/log/exp 数值不稳定。
- 输入中有 NaN/Inf。
- label 越界或 mask 全空。
- learning rate 过大导致参数发散。
- 自定义 loss 分母为 0。
- 梯度裁剪、AMP、optimizer state 出现异常。

排查顺序：

1. 打开 anomaly detection 或在关键 tensor 后检查 NaN/Inf。
2. 检查输入、label、attention mask、loss mask 是否合法。
3. 定位第一次出现 NaN 的 step，而不是只看最终报错。
4. 临时切换 bf16 或 fp32 验证是否是精度问题。
5. 降低 learning rate、加 gradient clipping、检查 warmup。
6. 排查自定义算子或自定义 loss 的除零、log(0)、exp overflow。

### 训练 loss 正常下降，但验证指标不升

可能原因：

- 训练集和验证集分布不同。
- 训练目标和评测指标不一致。
- 模型学到了格式或表面模式，但没有提升真实能力。
- 数据标签噪声大，训练 loss 下降只是拟合噪声。
- 过拟合，验证集开始退化。
- 评测脚本或解析逻辑有 bug。

排查顺序：

1. 对比 train/valid loss 曲线和关键业务指标。
2. 做分桶评测：任务类型、长度、来源、难度、业务线。
3. 抽样看 bad case，判断错误类型是否变化。
4. 检查评测 parser，确认模型输出格式是否被正确解析。
5. 做小规模人工复核，判断验证集 GT 是否可信。
6. 做 ablation，确认新增数据或训练策略是否真的带来收益。

### 显存 OOM

可能原因：

- batch size、sequence length、image/video token 数过大。
- KV cache 或 activation 占用过高。
- 没有正确使用 gradient checkpointing。
- 梯度累积实现错误，计算图被保留。
- 日志或评测时把 tensor 存在列表里，没有 detach。
- 分布式配置不合理，参数、梯度、optimizer state 没有正确切分。

排查顺序：

1. 记录 OOM 发生在 forward、backward、optimizer step 还是 evaluation。
2. 打印 batch 中最大长度、图片数、视频帧数、max_pixels。
3. 降低 batch size 或 max_frames，确认是否和输入规模线性相关。
4. 开启 gradient checkpointing、bf16、ZeRO/FSDP 等策略。
5. 检查是否保存了带计算图的 loss、logits、hidden states。
6. 用显存快照或逐段注释定位显存增长点。

### 吞吐突然下降

可能原因：

- 数据加载慢，CPU 或网络盘 IO 成为瓶颈。
- 视频解码或图片下载耗时增加。
- batch 中长序列比例升高。
- GPU 利用率低，等待数据。
- 分布式通信瓶颈，all-reduce 或 all-to-all 变慢。
- 日志、保存 checkpoint、评测频率过高。
- 线上服务中请求排队、限流或依赖服务变慢。

排查顺序：

1. 拆分端到端耗时：数据读取、预处理、模型推理、后处理、网络请求。
2. 看 GPU utilization、CPU、内存、磁盘 IO、网络 IO。
3. 统计 batch 长度分布和样本类型分布。
4. 关闭额外日志或降低 checkpoint 频率验证影响。
5. 对线上服务看 p50/p95/p99、队列长度、超时率和失败率。
6. 如果瓶颈在 IO，优先做缓存、并发下载、预处理离线化和数据本地化。

### 多机训练 hang 住

可能原因：

- 某个 rank 数据加载失败或提前退出。
- batch 数不一致，某些 rank 没有进入 collective。
- NCCL 通信异常。
- 网络或机器故障。
- dataloader worker 卡死。
- 保存 checkpoint 时所有 rank 协调不一致。

排查顺序：

1. 看所有 rank 日志，找第一个异常 rank。
2. 确认每个 rank 的 step 是否一致。
3. 开启 NCCL debug 日志，检查 collective 卡在哪一步。
4. 用更小 world size 或单机复现。
5. 检查 DistributedSampler、drop_last、数据长度和异常样本。
6. 确认 checkpoint 保存只在主 rank 或有正确 barrier。

### Checkpoint 恢复后指标异常

可能原因：

- 没有恢复 optimizer、scheduler、scaler。
- global step 或 epoch 计数错乱。
- 数据 shuffle 状态不同。
- 模型结构或 tokenizer 版本变化。
- LoRA/adapter 权重加载不完整。
- eval 使用了错误 checkpoint。

排查顺序：

1. 确认 checkpoint 包含 model、optimizer、scheduler、scaler、step。
2. 对比恢复前后同一 batch 的 loss 和输出。
3. 检查 tokenizer、config、adapter、特殊 token 是否一致。
4. 看学习率是否从正确 step 恢复。
5. 固定 seed 和数据顺序复现恢复流程。
6. 确认评测路径没有指向旧 checkpoint。

### 离线指标提升，线上效果下降

可能原因：

- 线上输入分布和离线评测集不同。
- 线上字段映射、预处理、抽帧策略与离线不一致。
- 评测指标和业务指标不一致。
- 线上延迟、超时和失败重试影响用户体验。
- 模型输出解析或后处理在线上发生变化。
- 数据泄漏导致离线指标虚高。

排查顺序：

1. 固定一批线上请求，离线复放同一输入。
2. 对比线上和离线的输入字段、图片/视频帧、fps、max_frames。
3. 对比模型输出原文、parser 结果和最终业务字段。
4. 分桶看业务线、设备、网络、视频长度、指标类型。
5. 检查线上延迟、超时、失败率、fallback 比例。
6. 抽样人工复核，判断是线上分布问题还是离线评测污染。

## 面试应对

### 如果一个训练实验效果突然变差，你会怎么排查？

回答思路：先确认现象，再按数据、代码、配置、训练、评测逐层收敛。

回答模板：

我会先确认效果变差是否可复现，比如同一 checkpoint、同一评测集、同一评测脚本下是否稳定下降。然后看最近变更，包括数据版本、代码 commit、模型基座、超参数、推理配置和评测口径。接着分层排查：数据层看样本量、标签、分布和泄漏；训练层看 loss、学习率、梯度、精度和 checkpoint；评测层看 parser、指标阈值和分桶结果。最后抽 bad case 做人工归因，判断是模型能力下降、数据噪声、标准变化还是评测实现问题。

### Loss 正常下降但验证集指标不涨怎么办？

回答思路：强调训练目标和评测目标可能不一致。

回答模板：

这种情况我会先判断模型是不是只学到了训练目标中的表面模式。比如 SFT loss 下降可能说明模型更会模仿训练答案格式，但不代表关键帧边界更准。接着我会看分桶指标，找出哪些 task_type 或业务线没有提升，再抽 bad case 看是 GT 噪声、输出格式解析失败，还是模型确实没学会关键能力。如果验证集标签本身有噪声，loss 下降和指标不涨并不矛盾；这时要先清洗验证集或建立更可信的回归集。

### 如果训练出现 NaN，你会怎么定位？

回答思路：先找第一次 NaN，再区分数据、精度、学习率和 loss 实现。

回答模板：

我会先定位第一次出现 NaN 的 step，而不是只看最后崩溃的位置。然后检查该 batch 的输入、label、mask 和长度是否异常，尤其是空 mask、label 越界、坏样本。接着看是不是混合精度溢出，可以临时切 bf16 或 fp32 验证；再检查 learning rate、warmup 和 gradient norm。如果有自定义 loss，还要检查 log(0)、除零、exp overflow 等数值问题。修复后要用同一批样本复现，确认 NaN 不再出现。

### 如果显存 OOM，你会怎么处理？

回答思路：先定位 OOM 发生阶段，再区分输入规模、activation、optimizer state 和缓存问题。

回答模板：

我会先看 OOM 发生在 forward、backward、optimizer step 还是 evaluation。如果是 forward，通常和 batch、sequence length、image/video token 或 max_frames 有关；如果是 backward，activation 和梯度占用更关键；如果是 optimizer step，可能是 optimizer state 太大。处理上可以降低 batch 或用 gradient accumulation，开启 activation checkpointing，使用 bf16，采用 ZeRO/FSDP 切分参数、梯度和 optimizer state。还要检查代码是否把带计算图的 tensor 存进列表，比如日志里保存 loss 没有 detach。

### 如果训练吞吐低，你会怎么排查？

回答思路：拆耗时，不要只盯 GPU。

回答模板：

我会把耗时拆成数据读取、预处理、模型前向/反向、通信、日志和 checkpoint 保存。关键帧项目里就发现端到端服务耗时主要在图片下载，而不是模型推理本身。训练中如果 GPU 利用率低，通常先看 DataLoader、网络盘 IO、视频解码和 batch 构造；如果 GPU 利用率高但吞吐低，再看模型计算、序列长度和通信。分布式下还要看 all-reduce 或 all-to-all 是否成为瓶颈。

### 多机训练卡住怎么办？

回答思路：按 rank、step、数据和通信定位。

回答模板：

我会先看所有 rank 的日志，确认是否有某个 rank 先报错或卡在数据加载。然后看各 rank 的 step 是否一致，如果某些 rank 数据数量不同或提前结束，就可能导致 collective hang。接着开启 NCCL debug，判断卡在通信还是计算。为了缩小范围，我会用单机或更小 world size 复现，并检查 DistributedSampler、drop_last、异常样本和 checkpoint barrier。多机 hang 的关键是找第一个异常点，而不是只看所有进程最后停在哪里。

### 离线和线上效果不一致怎么办？

回答思路：先复放同一请求，检查输入、模型、后处理和分布。

回答模板：

我会先抓一批线上请求做离线复放，确保输入完全一致。然后对比线上和离线的预处理，比如抽帧 fps、图片下载、resize、max_pixels、prompt、task_type 映射。接着检查模型 checkpoint、输出 parser 和后处理是否一致。如果同一输入离线线上输出一致，但整体指标不同，那就看线上分布是否和离线评测集不同；如果同一输入输出不一致，那通常是服务链路、配置或版本问题。

### 如果 bad case 很多，你怎么决定先修什么？

回答思路：按影响面、业务价值、可修复性和泛化收益排序。

回答模板：

我会先做错误 taxonomy，把 bad case 分成标注错误、标准冲突、模型漏看、时间粒度不足、格式解析失败、数据映射错误等类别。然后结合业务价值和影响面排序：高优业务线、样本量足、当前 ACC 低、错误模式集中的问题优先修。对于标注错误，先重标；对于标准冲突，先统一规则；对于模型漏看小元素，补高质量样本或引入 UI primitive；对于低 FPS 漏帧，改采样和推理策略。这样每次修复都能对应明确收益。

### 如果 checkpoint 恢复后指标异常，你会怎么排查？

回答思路：检查恢复内容、模型配置、数据顺序和评测路径。

回答模板：

我会先确认 checkpoint 是否完整恢复了 model、optimizer、scheduler、scaler 和 global step。然后用同一个 batch 比较恢复前后的 loss 和输出，判断模型状态是否一致。接着检查 tokenizer、config、LoRA adapter 或特殊 token 是否变化。训练继续时还要确认学习率从正确 step 恢复，数据 shuffle 状态合理。最后确认评测使用的是恢复后的 checkpoint，而不是旧路径或错误模型名。

### 如何把训练问题排查讲得像做过真实项目？

回答思路：用具体链路和真实现象，不背抽象步骤。

回答模板：

我会结合项目讲排查闭环，而不是只背“看数据、看模型、看参数”。比如关键帧项目里，模型效果异常时我会先看分业务线和分指标 ACC，再抽 bad case 判断是 GT 错还是模型错；如果是购物车角标这类小元素漏看，就归为细粒度感知问题；如果是人工等待了不该等待的元素，就归为标注标准问题；如果线上耗时高，就拆图片下载和模型推理耗时。这样每个排查动作都有证据和下一步决策。

## 快速记忆

训练问题排查可以记成一句话：

先确认现象，再锁定范围；先查数据和版本，再查模型和参数；先做最小复现，再做全量回归；最终沉淀到规则、脚本、数据和监控里。
