# 召回、粗排、精排与重排

## 知识点解析

### 概述

召回、粗排、精排、重排是一套分层筛选机制，用来从海量候选中逐步选出最相关、最可靠、最适合展示或送入大模型上下文的内容。

一句话：

```text
召回解决“找得到”，粗排解决“先筛掉明显不相关”，精排解决“排得准”，重排解决“最终可用”。
```

在传统搜索推荐里，候选可能是商品、视频、广告、网页；在 AI 产品里，候选也可以是文档 chunk、代码片段、工具、[Skill](<../08_Agent/基础概念/Skill.md>)、历史记忆、视频帧或 OCR 区域。

分层的本质是计算预算分配：候选规模逐层缩小，单个候选可使用的特征和模型复杂度逐层增加。四个名称描述的是职责，不绑定固定候选量或固定模型；同一个双塔或浅层网络在不同规模、延迟预算下可能用于召回，也可能用于粗排。

| 阶段 | 输入与输出 | 核心目标 | 常见模型或策略 | 主要权衡 |
| --- | --- | --- | --- | --- |
| 召回 | 全量库到百级/千级候选 | 高覆盖、低延迟 | 倒排/BM25、协同过滤、图召回、双塔向量 ANN、规则与热门召回 | 召回率与噪声、索引新鲜度、ANN 精度与时延 |
| 粗排 | 百级/千级到十级/百级候选 | 在少误杀的前提下快速压缩候选 | LR、GBDT、浅层 DNN、蒸馏模型、预计算特征与轻量规则 | 保留率与压缩率、特征丰富度与计算成本 |
| 精排 | 小候选集到有序 Top-K | 精确估计相关性、点击、转化或任务价值 | Learning to Rank、Wide & Deep、DeepFM、DCN、DIN/序列模型、Cross-Encoder、Transformer/LLM reranker | 精度与 p95/p99 延迟、多目标收益与模型复杂度 |
| 重排 | 已打分列表到最终展示/上下文 | 优化整页效用并满足硬约束 | 规则、MMR、多目标打分、约束优化、去重与配额控制 | 单项相关性与多样性、公平性、安全、商业目标 |

### 召回是什么

召回是从海量候选中快速找出一批“可能相关”的内容。它优先保证正确候选进入后续链路，而不是追求最终顺序最优。

它的目标不是最终排序最精确，而是尽量不漏掉正确候选：

```text
海量候选
  -> 快速召回 top 100 / top 1000
  -> 保证正确候选在里面
```

不同 AI 场景里的召回对象：

| 场景 | 召回对象 |
| --- | --- |
| [RAG](<../02_大模型/应用与问题/RAG.md>) | 文档 chunk、网页、知识片段 |
| AI Coding | 文件、函数、类、测试、历史错误 |
| [Agent](<../08_Agent/基础概念/Agent.md>) | 工具、Skill、Memory、历史轨迹 |
| 多模态 | 图片、视频片段、关键帧、OCR 区域 |
| 搜索推荐 | 网页、商品、帖子、视频、广告 |

### 常见召回策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 关键词召回 | BM25、倒排索引 | 精确匹配强，适合术语、编号、错误码、人名 | 语义泛化弱 |
| 向量召回 | 双塔/Embedding + ANN | 物品向量可预计算，语义泛化强 | 两侧交互有限，ANN 近似检索会损失召回 |
| 协同过滤 | 用户-物品交互或相似邻域 | 能利用群体行为发现兴趣 | 冷启动和稀疏交互明显 |
| 规则召回 | 根据权限、标签、类型、业务规则过滤 | 稳定、可控 | 覆盖有限 |
| 图召回 | 基于用户、物品、代码调用、知识图谱扩展 | 适合关系型候选 | 构建和维护成本高 |
| 热门/探索召回 | 热门兜底或为新候选分配探索流量 | 缓解冷启动并采集反馈 | 个性化弱，探索会产生机会成本 |
| Query Rewrite | 改写、扩展、拆解 query 后再检索 | 改善召回覆盖 | 改写错会引入噪声 |
| 多路召回 | BM25 + 向量 + 规则 + 图/热门 | 覆盖更全 | 需要融合、去重和调权 |

RAG 常见组合：

```text
BM25 top 50
  + embedding top 100
  + metadata / 权限过滤
  -> 合并去重
  -> rerank
```

### 粗排是什么

粗排是在召回结果上做快速筛选，目标是在显著压缩候选量时尽可能保住后续精排需要的正例和多样候选。

召回结果可能有几百到几千个，如果全部交给复杂 reranker 或 LLM，成本和延迟太高。粗排通常用轻量规则或轻量模型先筛掉明显不相关的候选。

常见粗排信号：

- 关键词命中数。
- embedding 相似度。
- 文档更新时间。
- 权限和业务标签。
- 用户上下文匹配。
- 文件路径或标题匹配。
- 候选长度是否过长。

常见实现包括 LR、GBDT、浅层 DNN、蒸馏后的排序模型，以及只使用可批量计算或预缓存特征的轻量打分。粗排不能只追求候选压缩率，还要测量“精排正例保留率”，否则会把不可逆的信息损失隐藏到后续阶段。

典型规模变化：

```text
召回 top 1000
  -> 粗排 top 100
```

### 精排是什么

精排是用更强模型和更丰富的交叉特征对小候选集做细粒度打分。目标因场景而异，可以是相关性、pCTR/pCVR、观看时长、成交价值或证据支持度，也可以是这些目标的联合优化。

常见精排模型：

- Learning to Rank、GBDT/LambdaMART。
- Wide & Deep、DeepFM、DCN 等特征交叉模型。
- DIN/DIEN、Transformer 等行为序列模型。
- Cross-Encoder、BGE/[Qwen](<../02_大模型/模型细节/Qwen千问架构.md>) Reranker。
- LLM-as-reranker。
- 规则 + 模型混合打分。

为什么精排比向量召回更准：

```text
向量召回：
  query 和 doc 分别编码，再算相似度。

Cross-Encoder 精排：
  query 和 doc 一起输入模型，让模型直接判断相关性。
```

后者能理解更细粒度条件，例如“生产权限”不能匹配成“测试权限”，“Qwen3-VL 视频输入”不能匹配成普通 Qwen 文本模型。

精排的边界是只能在上游留下的候选中比较，无法补回召回或粗排已经丢失的结果。模型更复杂也不必然更好：在线系统还要共同评估特征实时性、吞吐、尾延迟、成本以及训练与服务特征一致性。

### 重排是什么

重排是在精排结果基础上优化整个列表，而不是再次独立预测每个候选。它把模型分数与展示约束、跨候选关系和硬规则结合，输出真正可展示或可送入上下文的结果。

它不只看相关性，还看最终可用性：

- 去重：同一文档相邻 chunk 合并。
- 多样性：避免全是同一来源。
- 安全：过滤敏感、过期、低可信内容。
- 业务规则：优先官方文档、最新版本、用户所在部门文档。
- 长度预算：控制进入 prompt 的 token 数。
- 引用顺序：按答案组织而不是按分数机械排列。
- 广告约束：预算、频控、行业安全和用户体验；竞价与流量分配发生在价值排序之后，不属于重排本身。

在 RAG 里：

```text
精排 top 10
  -> 去重 / 合并相邻 chunk
  -> 过滤冲突或低可信来源
  -> 按答案逻辑组织 top 5
  -> 放入 prompt
```

### 跨场景的阶段映射

| 场景 | 候选与主要目标 | 召回/精排侧重点 | 重排侧重点 |
| --- | --- | --- | --- |
| 搜索 | Query 对网页、商品或服务 | 词面与语义相关性、内容质量、时效 | 去重、来源多样性、安全与商业规则 |
| 推荐 | 用户/会话对动态物品池 | 兴趣覆盖、点击/转化/时长等多目标 | 多样性、新鲜度、探索、频控与长期体验 |
| 广告 | 合格广告与曝光机会 | pCTR/pCVR、质量和预期价值；价值排序后进入拍卖/分配 | 预算 pacing、频控、合规与用户体验 |
| RAG | 已通过租户/ACL/scope 预过滤的文档 chunk | 证据覆盖与答案支持度 | 冲突消解、token budget 与引用组织 |

搜索、推荐和广告各自的 Query/用户意图、库存、反馈与延迟边界，分别见[搜索系统基础](<搜索系统基础.md>)、[推荐系统基础](<推荐系统基础.md>)和[广告排序与 CTR 预估](<广告排序与CTR预估.md>)。

### RAG 里的完整链路

```text
知识库全量 chunk
  -> 租户 / ACL / scope 预过滤
  -> 多路召回 top 200
  -> 粗排过滤 top 50
  -> cross-encoder / LLM reranker 精排 top 10
  -> 重排：去重、压缩、质量/时效过滤、引用组织
  -> top 5 放入 prompt
  -> LLM 基于证据回答
```

这个链路里，每层解决的问题不同：

| 层级 | 目标 | 更关注 |
| --- | --- | --- |
| 召回 | 不漏正确证据 | Recall@K、覆盖率、速度 |
| 粗排 | 快速降候选量 | 延迟、明显错误过滤 |
| 精排 | 把正确证据排前面 | MRR、NDCG、Precision@K |
| 重排 | 最终上下文可用 | 去重、冲突消解、引用、token budget |

### 精排为什么重要

向量召回只看 embedding 相似，不等于能回答问题。

例子：

```text
用户问：如何申请 A 系统的生产权限？

向量召回可能找回：
- A 系统介绍
- A 系统测试环境权限
- A 系统生产权限审批流程
- B 系统生产权限流程
```

这些都“语义相似”，但真正能回答的是“A 系统生产权限审批流程”。精排模型会把 query 和候选文档一起看，判断哪个片段真正支持答案。

### 在 AI Coding 里的对应

```text
用户说：帮我修这个测试失败

召回：
  搜相关错误日志、测试文件、被测函数、最近改动。

粗排：
  排除明显无关文件和依赖目录。

精排：
  选择最可能导致失败的函数、配置和测试断言。

重排：
  按阅读/修改顺序组织上下文，避免把无关大文件塞给模型。
```

### 在多模态关键帧里的对应

```text
视频任务
  -> 召回候选时间窗口 / 候选帧 / OCR 区域 / Video Primitive
  -> 粗排去掉明显未加载或无关片段
  -> 精排比较边界前、当前、后帧
  -> 重排/组织证据，输出关键帧时间和理由
```

对关键帧任务，召回漏掉正确时间窗口，后面 [VLM](<../02_大模型/视觉多模态与生成模型/多模态模型/VLM与Vision_Instruction_Tuning.md>) 再强也没用；精排不准，就会把“相似但不是首次完成”的帧排在前面。

### 评估指标

各阶段只选择与职责相符的指标，定义、计算边界、线上线下差异和 A/B 解释统一见[排序指标与 A/B 测试](<排序指标与A_B测试.md>)。

| 阶段 | 常用指标 |
| --- | --- |
| 召回 | Recall@K、Hit Rate、覆盖率、延迟 |
| 粗排 | 过滤后 Recall@K、候选压缩率、延迟 |
| 精排 | AUC/GAUC、MRR、NDCG、Precision@K、Pairwise Accuracy |
| 重排 | 去重率、多样性、约束违规率、上下文 token 数 |
| 端到端 | CTR/CVR、任务成功率、Faithfulness、p95/p99、成本 |

排查顺序：

```text
答案错
  -> 正确证据是否被召回？
  -> 是否被粗排误杀？
  -> 是否被精排排进 top K？
  -> 重排后是否仍在 prompt 里？
  -> 模型是否忠实使用证据？
```

### 常见错误

- 召回和精排混为一谈。
- 只用向量召回，不做 BM25，导致编号、术语、错误码召回差。
- 召回 top K 太小，正确证据根本进不来。
- rerank 模型和业务 query 分布不匹配。
- 把权限校验拖到召回后，导致无权候选进入中间链路或占用 Top-K。
- 重排只看相关性，不看时效、冲突和 token budget。
- 只看端到端答案，不拆分 Recall@K、NDCG、Faithfulness。
- 把阶段名称绑定到某个固定模型，忽略候选规模和服务预算变化。
- 只优化当前层指标，不测量正确候选在层间的不可逆损失。

## 面试应对

### 召回、粗排、精排、重排有什么区别？

回答思路：按候选规模逐层缩小讲，强调召回重覆盖、精排重准确。

回答模板：

召回从全库快速找出可能相关的候选，优先保证覆盖和速度；粗排用轻量模型压缩候选，同时避免误杀后续正例；精排在小候选集上使用更丰富的交叉特征和复杂模型，优化相关性、点击、转化或任务价值；重排则面向整个列表加入去重、多样性、安全、预算等约束。候选规模逐层减少，单候选计算逐层增加，具体模型归属取决于规模和延迟预算，而不是由模型名称固定决定。

### 为什么 RAG 里通常要做 rerank？

回答思路：说明向量相似不等于能回答问题，rerank 用更强匹配模型纠正排序。

回答模板：

RAG 里做 rerank 是因为第一阶段召回通常追求速度和覆盖，尤其向量召回只看语义相似，可能把“看起来相关但不能回答问题”的片段排在前面。Reranker 会把用户问题和候选文档放在一起做更细粒度匹配，判断这个片段是否真的能支撑答案。这样可以把正确证据排进最终上下文，减少噪声和幻觉。工程上常见做法是 BM25 加向量多路召回 top 100 或 top 200，再用 reranker 精排到 top 5 到 top 10 放进 prompt。

### 多路召回为什么比单一路召回更稳？

回答思路：关键词保精确匹配，向量保语义泛化，规则保业务约束。

回答模板：

多路召回更稳，是因为不同召回方式覆盖的问题不一样。BM25 和倒排索引擅长精确匹配，适合错误码、接口名、人名、版本号；向量召回擅长语义匹配，可以处理同义表达和自然语言问题；规则和 metadata 过滤能保证权限、业务线、时间范围这些硬约束。单一路召回容易有盲区，多路召回先提高覆盖，再通过去重、融合和 rerank 控制噪声。

### 如果正确证据没进最终上下文，怎么排查？

回答思路：按召回、粗排、精排、重排逐层定位。

回答模板：

我会先看正确证据有没有进召回 top K。如果没有，问题在文档解析、chunk、关键词索引、embedding、query rewrite 或权限过滤。召回到了但粗排后没了，就看粗排规则是不是误杀，比如时间、标签、长度过滤过严。粗排保住但 rerank 排得靠后，说明 reranker 和业务相关性不匹配，或者 query-doc 匹配特征不足。rerank 排前但最终 prompt 没有，就看重排、去重、上下文预算和引用组织是否把它挤掉。这样能把“RAG 答错”拆成具体链路问题。
