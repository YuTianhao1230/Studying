## 问题 3：为什么用的是 GRPO？为什么没有用 DPO？

### 优化目标

将原来约 5 分 30 秒的回答压缩到 2～3 分钟，按照“先给结论—统一维度对比—结合项目说明—补充适用边界”组织。

原回答需要修正以下口径：

- DPO 不是“简单版 GRPO”，两者的数据形式和优化目标不同。
- DPO 使用 `chosen/rejected` 偏好对，不需要单独训练 Reward Model 或 Critic，但通常仍需要冻结的 Reference Model 作为约束。
- GRPO 的优势不只是“一次生成多个答案”，而是能够利用同一输入下多个候选的连续、多维 reward 计算组内相对 advantage。
- 不能因为没有做 DPO 对照实验，就声称 GRPO 的实际效果一定优于 DPO；准确说法是 GRPO 的训练信号与当前任务更匹配。
- “其他视频理解工作也使用 GRPO”只能作为调研参考，不能作为方法选择的核心依据。

### 回答框架

1. 先给结论：DPO 可以用，但当前任务更适合 GRPO。
2. 对比训练信号：DPO 使用离线偏好对；GRPO 使用当前策略在线生成的多个候选及可验证 reward。
3. 结合项目：关键帧任务能够计算时间误差、格式、early/late 边界和视觉证据得分。
4. 说明边界：如果 rollout 成本过高或已有成熟偏好对，DPO 可以作为更简单的离线 baseline。

### 优化版本

我们选择 GRPO，并不是因为 DPO 不能用于这个任务，而是因为关键帧任务的监督信号与 GRPO 更匹配。

DPO 是离线偏好优化，需要预先构造同一输入下的 `chosen` 和 `rejected`。它不需要单独训练 Reward Model，也不需要在线 rollout，工程链路简单稳定，但训练信号依赖固定偏好对的覆盖范围和质量。

GRPO 则由当前策略对同一个视频和任务类型在线生成多条候选，通过 verifier 分别打分，再根据组内相对 reward 更新模型。关键帧任务有明确lable和可执行的标注标准，我们可以计算时间误差、输出格式以及视觉证据的一致性，形成连续的多档 reward，区分“差一帧”和“差很多帧”，同时持续暴露当前模型最新的边界错误。

标准 DPO 也可以把误差较小的回答设为 `chosen`、误差较大的设为 `rejected`，但这样需要把候选固定成偏好对，会压缩同组多个候选的完整分数信息，也缺少训练过程中的在线探索。因此，我们选择 GRPO 直接优化可验证的时间和证据 reward。

不过我们没有做 DPO 与 GRPO 的完整对照实验，因此不能声称 GRPO 一定更好。如果 rollout 成本过高，或者已有大量稳定的边界偏好对，DPO 仍然可以作为更简单的离线 baseline。这里的选择依据是任务匹配和工程取舍。

### 可能追问：为什么没有使用 PPO？

PPO 同样可以优化这些业务 reward，但通常需要额外训练 Critic。在视频多模态场景下，Critic、rollout 和调参会带来更高的显存与工程成本。GRPO 使用同组候选的相对 reward 构造 advantage，不需要单独的 Critic，因此更符合当前任务“结果可验证、同题可以采样多个候选、视频 rollout 成本较高”的特点。

## 问题 4：你这里的数据 bad case 是怎么筛选的？以及你的数据飞轮是怎么判定它的收益的？

### 优化目标

将原来约 5 分钟的回答压缩到 2～3 分钟，分成“候选筛选—人工归因—数据回流—收益验证”四步。

原回答需要修正以下口径：

- 模型不能直接判定一条数据是不是 bad case。模型预测与原 GT 不一致，只能说明它是高价值复核候选。
- 模型 ACC 为 80% 时，不能直接断言剩余 20% 都是脏数据；其中可能包含模型错误、GT 错误、标准冲突或数据链路异常。
- 回流样本不能同时加入训练集和固定测试集，否则会造成数据泄漏，使收益不可比较。
- “每轮解决一半问题”只能作为实际观察或阶段目标，不能写成数据飞轮必然达到的固定比例。
- 数据飞轮轮数不应仅由季度排期决定，还应综合固定评测集上的边际收益、标签改动比例以及人工重标的时间成本。

### 回答框架

1. 候选怎么筛：模型与 GT 的帧误差、多模型分歧、低 ACC 指标和高优业务样本。
2. 候选怎么确认：人工按数据层、标准层和模型层进行复核归因。
3. 数据怎么回流：GT 错误修标签，真实模型错误进入训练，链路异常单独修复。
4. 收益怎么判断：固定测试集和训练配置，从模型效果、数据效率、业务价值三层比较。

### 优化版本

bad case 筛选分为模型初筛和人工确认两步。我们不会把模型与 GT 不一致直接定义成模型错误，而是把它作为高价值复核候选。

初筛时，我们会让固定模型或多个模型预测同一批数据，根据预测与 GT 的帧误差、多模型分歧、低 ACC 指标以及高优业务线优先级筛选候选集。比如模型 ACC 约为 80% 时，剩余约 20% 可以作为重点复核范围，但其中不一定都是脏数据或模型错误。

候选样本进入人工复核后，我们按三层归因：第一层检查视频、FPS、时间坐标和帧索引等数据链路；第二层检查 GT 是否符合当前任务的完成态、排除条件和豁免条件；前两层都可靠后，才判断是否是真实模型错误。GT 错误先修正标签，标准冲突先统一规则，真实模型错误再作为 hard case 回流训练。

数据飞轮的收益不能只看回流后的训练集准确率。我们会冻结独立测试集、评测脚本和训练配置，只改变回流训练数据，比较本轮与上一轮的增量。模型效果看全量 ACC、业务线和任务分桶、帧误差以及同类 bad case 是否减少；数据效率看重标后真正修改标签的比例、单位标注量带来的提升；业务价值看线上回测、人工复核时长和标注成本。

项目实际进行了六轮数据飞轮，执行节奏大约是一个季度三轮，但总轮数不会提前写死。“每轮消解约一半 bad case”只能作为阶段观察，不能当作固定规律。每轮结束后，我们会比较相邻两轮在固定测试集上的指标增量、重标后的标签改动比例以及投入的人力和时间成本。如果连续两轮提升很小、标签改动比例趋于稳定，或者单位标注成本带来的收益已经很低，就停止继续回流；如果候选主要变成 GT、标准或链路问题，则转向规则和链路治理。

## 问题 6：全量 ACC 从 75.71% 提升到 89.98%，各阶段分别贡献了多少？怎么证明提升来自数据飞轮、SFT、CoT 或 GRPO，而不是评测集变化？

### 优化目标

按照“先区分基线—再讲全量收益—再讲专项收益—最后说明归因方法”组织，避免把不同阶段、不同评测集上的数字直接相加。

原回答需要补充以下边界：

- 基座模型约 35%、初始 SFT 约 70% 和简历中的 75.71% 不是同一个 baseline。回答时必须说明 35% 和 70% 属于早期探索结果，75.71% 是后续固定口径下的项目基线。
- 数据飞轮的收益不能通过“同一个模型评估不同批次数据”证明，因为不同数据难度不可比。正确做法是用相同训练配置训练不同数据版本，再在同一固定测试集上比较。
- 如果没有完成严格的单变量消融，只能说“按阶段实验观察，主要收益来自哪些环节”，不能精确声称每个阶段存在独立、可相加的贡献。
- CoT 和 GRPO 的全量增益不足 1%，但困难指标从约 60% 提升到约 90%，这两种口径必须分开汇报。
- 如果没有分别执行 `SFT → CoT` 和 `CoT → GRPO` 的独立对照，只能汇报 CoT 与 GRPO 的组合收益，不能拆成两个未经验证的贡献值。

### 回答框架

1. 区分三个基线：原始基座、初始 SFT、简历固定项目基线。
2. 全量收益：SFT 建立基础能力，数据飞轮和标准治理贡献主要全量提升。
3. 专项收益：CoT 和 GRPO 主要优化少数细粒度、高难指标。
4. 归因方法：固定测试集、评测脚本、训练配置和推理参数，逐阶段做对照。

### 优化版本

这个问题需要先区分不同阶段的 baseline。Qwen3-VL-8B 基座模型直接做任务时，早期实验 ACC 约为 35%；使用初始数据做 SFT 后，能够提升到约75% ，并后续固定评测口径下的项目基线。

从阶段收益看，SFT 主要建立视频理解、任务遵循和稳定输出的基础能力。项目基线从 75.71% 提升到最终 89.98% 的主要贡献，来自多轮数据飞轮、数据质量治理和标注标准沉淀。

CoT 和 GRPO 的目标不是显著抬高全量平均值，而是解决少数细粒度、高难指标。它们在全量 ACC 上的组合增益不到 1%，但在个别困难指标上，ACC 可以从约 60% 提升到约 90%。因此这部分需要同时看全量回归集和困难指标分桶，不能只看平均值。

为了证明收益不是评测集变化造成的，我们会冻结测试集、评测脚本、模型初始化、训练和推理配置。评估数据飞轮时，只替换训练数据版本，在同一固定测试集上比较；评估标准沉淀时，使用同一模型和同一批样本，对比规则调整前后的结果；评估 CoT 和 GRPO 时，则沿同一 checkpoint 路线比较 SFT、CoT 和 GRPO，并同时检查全量集和困难集。

如果这些实验没有做到完全单变量控制，我会把数字表述为阶段性观察，而不会声称每个模块都有精确且可相加的独立贡献。

## 问题 7：结构化 CoT 数据是怎么构造和质检的？怎样避免教师幻觉、GT 泄漏以及推理过程与最终答案不一致？

### 优化目标

按照“数据怎么生成—质量怎么过滤—GT 怎么隔离—推理与答案怎么校验”组织，把原来约 5 分 30 秒的回答压缩到 2～3 分钟。

原回答需要修正以下口径：

- 当前方案中的视频原语主要参考 `Thinking with Visual Primitives` 的思路，不应表述为 DeepSeek-R1 提出的视频原语。
- 第一阶段本身就负责生成完整的 State/Event 视频原语；第二阶段是在原语基础上结合任务规则做边界判断。
- 第二阶段可以把 GT 作为内部候选边界进行校准，但不能把 GT 来源或参考答案直接写入学生训练文本。
- 仅在 Prompt 中要求“答案出现在推理中”不能保证一致性，还需要校验原语引用、时间边界、视觉证据和最终答案是否相互支持。
- 删除显式 GT 字样只能防止表面泄漏，不能防止教师围绕已知答案事后编造理由；证据不足或推翻候选边界时必须拒收或转人工复核。

### 回答框架

1. 第一阶段：任务无关地生成完整 State/Event 原语时间轴。
2. 第二阶段：结合任务规则，引用 2～3 个相关原语做边界判断。
3. 质量门禁：视频、时间、视觉证据、格式和来源五类检查。
4. GT 防泄漏：只作内部校准，不进入训练文本；证据不足不强行围绕 GT 生成。
5. 一致性校验：推理引用、首次完成边界和 `answer.time` 必须相互一致。

### 优化版本

我们的结构化 CoT 数据采用两阶段生成。

第一阶段只做任务无关的视频理解。教师模型输入完整视频、视频元信息和原语输出格式，不提供任务规则和 GT，然后按时间顺序生成 State 和 Event 原语，描述每段时间内的页面状态及状态变化，形成完整的客观时间轴。

第一阶段通过质量过滤后，第二阶段再输入任务类型、完成态规则和过滤后的原语。教师从中选择 2～3 个与答案直接相关的原语，按照 before、current、after 说明前面为什么未完成、当前为什么首次满足、后面为什么只是稳定延续，最后输出关键时间。

GT 只在第二阶段作为内部候选边界做校准，不会把“ground truth”“参考答案”或标签来源写入学生训练文本。如果视觉证据不支持 GT，样本不会被强行解释，而是标为 ambiguous 或 reject，进入重生成或人工复核。这样可以降低围绕已知答案事后合理化的风险。

质检分为五类：视频是否可解码；原语时间是否递增、连续且不重叠；描述的 UI 状态是否真实存在；引用时间是否与原语一致；最终 `answer.time` 是否等于首次满足完成态的时间。格式上还会检查 JSON/XML 是否可解析、是否存在 GT 泄漏以及推理是否引用了有效原语。

项目中会结合质量评分做过滤，例如低于 0.8 的样本重生成或拒收；通过自动检查的样本仍会进行人工抽检。只有时间、证据、推理和答案一致的样本进入 clean CoT 训练集。

## 问题 8：GRPO 的 reward 具体包含哪些部分？各部分如何加权？你们怎样防止模型只学格式或利用 reward 漏洞？

### 优化目标

按照“主奖励—过程奖励—辅助奖励与惩罚—防 reward hacking”组织，明确各分项职责及第一版起始权重。

原回答需要修正以下口径：

- 最终答案不是简单的二元 label，而是根据预测时间与 GT 的误差计算平滑奖励，并叠加业务容忍范围内的命中奖励。
- 两段式 CoT 是否符合 schema 属于格式奖励；before/current/after 是否真的支持首次完成边界属于边界奖励，二者不能混为一项。
- 与教师 CoT 相似只能作为辅助 anchor，不能代表视觉证据一定正确，否则模型可能复制教师噪声。
- 只在训练结束后看总 ACC 不足以防止 reward hacking，还要监控每个 reward 分项、KL、输出长度和高 reward bad case。
- 方案中的权重是第一版实验起点，不是已经证明的全局最优参数。

### 回答框架

1. 主奖励：时间答案是否准确。
2. 过程奖励：格式合法、首次完成边界正确、视觉证据真实。
3. 辅助奖励与惩罚：CoT anchor、组内一致性、多样性、长度和幻觉惩罚。
4. 权重原则：答案和边界高于格式，参考 CoT 只作辅助。
5. 防漏洞：分项监控、人工抽检、固定真实指标回归和 KL 约束。

### 优化版本

我们的 reward 分为三层。第一层是最终答案，按预测时间与 GT 的误差计算平滑奖励，并叠加业务容忍范围内的命中奖励，这是最重要的信号。

第二层是过程质量。格式 reward 检查 JSON、State/Event 和最终 `answer` 是否可解析；边界 reward 检查 before 未完成、current 首次满足、after 没有二次刷新；证据 reward 检查 CoT 中的 UI 区域、状态和时间是否与视频一致。参考 CoT 只作为辅助 anchor，不能等同于证据正确。

第一版起始权重是：时间 `1.00`、格式 `0.25`、边界 `0.35`、CoT anchor `0.20`、组内一致性 `0.08`、多样性 `0.05`，长度惩罚 `0.10`。这些只是 baseline 起点，不是固定最优值。

为了防止模型只学格式，我们让格式权重明显低于时间和边界，并分别记录各项 reward。如果格式分数上升但困难集 ACC 不升，就降低格式权重，加强时间、边界和视觉证据信号。同时加入长度、重复和幻觉惩罚，用 KL 约束模型不要偏离 CoT-SFT checkpoint，并人工抽检高 reward 样本。

最终准出同时看全量回归集、困难指标、early/late、格式解析率和输出长度。只有 reward 上升与真实 ACC 和 bad case 改善一致，才能认为没有利用奖励漏洞。

## 问题 9：为什么选择 Qwen3-VL-8B？为什么做全参数 SFT，而不是 LoRA、Prompt 调优或直接使用更大的通用多模态模型？

### 优化目标

从“模型能力、线上吞吐、资源成本、训练方式”四个维度回答，避免只说显存不够。

原回答需要补充以下边界：

- 8B 不是绝对最优规模，而是在现有 GPU、吞吐和上线成本约束下可落地的选择。
- 更大模型可能提高能力上限，但也会降低并发和吞吐，并增加显存、部署卡数和服务成本。
- Prompt 调优能够明确规则和格式，但不能稳定地把细粒度 UI、视频状态变化和首次完成边界沉淀为模型能力。
- LoRA 成本更低，适合作为快速验证方案；选择全参数 SFT 的原因是希望视觉编码器、对齐模块和语言模型共同适配任务。
- 如果没有完成同预算下的 LoRA 和大模型对照实验，不能声称全参数 8B 的效果一定更好，只能说明它更符合当时的工程约束。

### 回答框架

1. 为什么是 Qwen3-VL：具备视频多模态能力，并能接入现有训练与推理链路。
2. 为什么是 8B：在效果、显存、吞吐和线上成本之间折中。
3. 为什么 Prompt 不够：规则可表达，但能力无法只靠 Prompt 内化。
4. 为什么不用 LoRA：任务需要视觉、对齐和语言模块共同适配。
5. 说明边界：这是工程选型，不是对所有方案完成穷举实验后的绝对结论。

### 优化版本

选择 Qwen3-VL-8B，核心不是单纯因为显存不足，而是综合考虑模型能力、现有 GPU 资源、线上吞吐和部署成本。

这个任务需要理解视频状态变化和细粒度 UI，Qwen3-VL 能够接入我们已有的多模态数据、ms-swift 训练和推理链路。在既定机器资源和线上吞吐要求下，8B 左右是能够完成全参数训练并满足服务容量的规模。更大的模型可能提高能力上限，但会降低单卡并发和吞吐，或者需要增加部署卡数，整体成本不符合当时的上线约束。

只做 Prompt 调优可以把完成态、排除条件和输出格式表达清楚，但很难稳定解决小 UI 元素、跨帧状态变化和首次完成边界，所以仍然需要训练把这些规则沉淀成模型能力。

LoRA 更省显存，适合快速验证或主要调整输出格式；但这个任务不只改语言输出，还希望视觉编码器、视觉语言对齐模块和语言模型共同适配，因此采用了全参数 SFT。训练中通过 BF16、ZeRO-3、FlashAttention 和 gradient checkpointing 控制显存。

全参数训练的代价是成本更高，也有通用能力退化风险，所以必须用固定回归集选择 checkpoint。我们没有把所有模型规模和 LoRA 配置做完整穷举，因此准确表述是：Qwen3-VL-8B 的全参数 SFT 最符合当时的能力目标和工程约束，而不是它在所有条件下都一定最优。

## 问题 12：标注成本下降 19.00% 和提效贡献占比 9.50% 是怎么计算出来的？分母和统计周期是什么？

### 优化目标

按照“先说明数据来源—分别定义两个指标—交代可比口径—说明待核实边界”组织，避免把模型 ACC 提升直接换算成业务收益。

当前资料只记录了 `19.00%` 和 `9.50%` 两个结果，没有保存对应的基准周期、观察周期、任务量和工时明细。因此，面试前必须回查业务看板或项目复盘材料，不能现场编造分母和统计周期。

### 指标口径

标注成本下降率应使用同口径的人工标注成本作为分母：

$$
\text{标注成本下降率}
=
\frac{\text{基准期单位任务人工成本}-\text{上线期单位任务人工成本}}
{\text{基准期单位任务人工成本}}
\times 100\%
$$

如果两个周期的任务量不同，应先按有效任务量归一化，比较单位样本成本或单位视频成本，不能直接比较总成本。

`提效贡献占比` 不是通用指标，必须以业务看板定义为准。如果项目使用的是“节省工时贡献”口径，则计算方式为：

$$
\text{提效贡献占比}
=
\frac{\text{关键帧模型节省的有效人工工时}}
{\text{同期全部提效措施节省的有效人工工时}}
\times 100\%
$$

如果看板实际使用的是模型处理量占比、自动化覆盖率或其他口径，应按真实定义替换，不能把上述公式直接当成项目事实。

### 优化版本

这两个数字不是由模型 ACC 直接换算出来的，而是来自上线后的业务统计口径。

标注成本下降 19.00%，核心是比较模型上线前后同一业务范围内的人工标注成本。分母应该是基准周期内的人工标注成本；如果前后任务量不同，就先除以有效任务量，比较单位视频或单位样本的人工成本。模型上线后能够先给出关键帧预标结果，人工从逐帧查找变成复核和修正，因此单位任务的平均标注时长下降，对应的人力成本下降 19.00%。

提效贡献占比 9.50% 需要严格按照业务看板定义解释。如果当时采用的是节省工时口径，那么分子是关键帧模型在观察周期内节省的有效人工工时，分母是同期所有提效措施节省的总工时，关键帧项目贡献了其中的 9.50%。它表示的是这个项目对整体提效的贡献比例，不是模型准确率，也不等于自动化覆盖率。

目前我能确认的是这两个结果值，但现有材料没有保存具体的基准周期、观察周期、任务量和工时分母。正式面试前我会从业务看板补齐起止日期、样本量、单位标注时长和异常样本剔除规则；如果现场无法确认，我会明确说明统计口径以业务复盘数据为准，不会给出未经核实的数字。

### 面试前必须补齐

- 基准周期与上线观察周期的准确起止日期。
- 两个周期覆盖的业务线、有效任务量和异常样本剔除规则。
- 上线前后单位视频或单位样本的平均人工标注时长。
- 人力成本是按工时折算，还是直接使用业务侧结算成本。
- `9.50%` 的真实分子与分母，确认它是节省工时贡献、处理量占比还是其他业务口径。

## 问题 13：数据飞轮中的 Agent 自动化具体做了什么？哪些环节已经落地，哪些仍需要人工确认？

### 优化目标

先区分“已经落地的流水线自动化”和“规划中的 Agentic Model Optimization”，避免把批处理脚本包装成完整自主 Agent，也不能把尚未落地的训练策略搜索描述成项目成果。

### 回答框架

1. 先给结论：当前是自动化流水线加人工门禁，不是完全无人值守的 Agent。
2. 已落地：批量推理、候选筛选、指标统计、分桶评测和结果汇总。
3. Agent 辅助：前后帧摘要、错误聚类和候选归因，可用于降低人工检索成本。
4. 人工门禁：GT 修改、标准冲突、样本重标、训练数据准入和模型上线。
5. 后续规划：让 Agent 在受限策略空间内选择数据或训练动作，但不能修改真值和评测门槛。

### 优化版本

严格来说，我们当前落地的是自动化数据飞轮加人工门禁，还不是完全无人值守的 Agent。

已经落地的自动化包括：批量推理并计算模型与 GT 的帧误差；根据模型分歧、低 ACC 指标和业务优先级筛选候选；按业务线、`task_type` 和 early/late 自动分桶；训练后在固定回归集上汇总 ACC、帧误差和格式解析率。Agent 可以进一步生成前后帧摘要、聚类 bad case，并给出数据、GT、标准或模型能力问题的候选归因。

涉及业务真值的环节仍由人工确认，包括修改 GT、处理标准冲突、确认模糊样本、执行最终重标以及决定训练数据和模型是否准入。完整的 Agentic 优化闭环仍是后续规划，Agent 只能在固定数据、实验预算和评测门禁内选择策略，不能自行修改业务标准、评测集或准出阈值。因此，准确表述是我们实现了可追踪的半自动闭环，而不是全自主模型优化。

## 问题 14：这个项目中最难或最失败的一次尝试是什么？你如何定位原因并完成修复？

### 优化目标

用一次具体的目标错配说明“现象—定位—修复—沉淀”，重点体现问题诊断能力。不能只说模型效果不好，也不能虚构未经记录的量化收益。

### 回答框架

1. 失败现象：GRPO 总 reward 和格式分上升，但真实 ACC 没有同步提升，部分困难指标回退。
2. 定位过程：拆分 reward 分项，检查 early/late、输出长度和高 reward bad case。
3. 根因：格式奖励过强，时间与视觉证据校验不足，模型利用了 verifier 漏洞。
4. 修复：降低格式权重，强化时间、边界和证据奖励，并增加惩罚、KL 与人工抽检。
5. 工程沉淀：reward 不能单独作为准出指标，必须通过固定业务回归集验证。

### 优化版本

最有代表性的一次失败，是早期做 GRPO 时出现了 reward 与真实业务目标错配。训练中总 reward 和格式解析率上升，但困难集 ACC 没有同步提升，部分样本甚至回退。模型学会了输出规范结构，却没有真正学会正确的时间边界。

定位时，我先把总 reward 拆成时间、格式、边界和证据分项，再按 `task_type`、early/late 和输出长度检查高 reward bad case。结果发现格式分太容易获得，而 verifier 对首次完成边界和视觉证据检查不足，模型利用模板获得了高分。

修复时，我降低格式权重，把时间误差作为主奖励，并增加 before/current/after 边界检查、视觉证据一致性、长度和幻觉惩罚，同时用 KL 限制策略漂移。之后不再用总 reward 单独准出，而是要求 reward 与困难集 ACC 同向、全量能力不退化，并人工抽检高 reward 样本。这次经历让我认识到，强化学习最危险的不是 reward 不涨，而是 reward 上涨但业务指标不涨。
