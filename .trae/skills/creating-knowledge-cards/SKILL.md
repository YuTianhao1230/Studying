# 创建知识卡片

## 核心原则

把 `知识卡片防劣化规范.md` 视为唯一权威规范。每次触发后先从工作区根目录完整读取该文件，再执行任务；不要依赖记忆、摘要或本 Skill 代替原文。

默认交付是已经写入正确目录、加入最近一级索引并完成验证的知识卡片，而不是聊天中的提纲。只有用户明确要求只讨论、只规划或只给草稿时才保持只读。

## 执行流程

### 1. 冻结现场

1. 运行 `git status --short`，识别原有未提交改动。
2. 阅读目标目录的 `README.md`、上级索引、目标卡片和必要的关联卡片。
3. 使用 `rg` 搜索主题名称、英文名、缩写、近义词和交叉概念。
4. 判定任务是新增、增量补充、纠错、合并、拆分、迁移还是审计。
5. 不覆盖、回滚或格式化掉来源不明的现有改动。

用户已经给出主题或材料时直接执行。只有无法从仓库和可靠来源判断、且不同答案会显著改变卡片归属或事实内容时才提问。

### 2. 确定唯一归属

按照规范第 4.2 节的目录职责，把正文放进最具体的知识目录：

- 先搜索是否已有权威卡片；存在时增量补充，不新建第二份正文。
- 通用原理只保留一个权威版本，其他目录使用相对链接。
- 不把新卡片直接放在仓库根目录。
- `07_面试体系` 只做跨目录索引，不复制技术正文。
- `12_实习工作整理` 只记录可确认的项目事实，通用方法链接到对应知识域。
- 不为少量内容创建新目录；优先使用现有最具体分支。

文件名遵循规范第 9 节。名词型技术卡优先采用“英文缩写或英文术语 + 中文翻译”，综合专题使用能准确概括主题的中文名。

### 3. 收集和核验材料

用户要求自动收集、从链接整理或补充前沿知识时：

1. 优先使用官方文档、标准、原始论文、官方源码或技术报告。
2. 博客、机构文章和社区讨论只用于发现线索或补充解释，不能通过相互转载形成“交叉验证”。
3. 逐项核验定义、公式、数字、版本、模型配置、实验口径和题目来源。
4. 区分公开事实、可复算推导、第三方结论和经验建议。
5. 对快速变化的信息写明版本或核验日期。

公开资料没有披露的层数、维度、训练数据、指标或实现细节必须写明未知、未公开或版本差异；不能用“业内常见配置”补成目标对象的事实。用户要求“完整”或赶时间，不改变真实性要求。

普通卡片以自包含正文为主，不额外创建检索日志、证据清单或来源过程文档。只有真题、时效性数据、论文特有结论、厂商声明或争议事实才保留必要来源。

### 4. 写成可独立复习的卡片

正文必须回答：

1. 它是什么，输入输出、术语和研究对象是什么。
2. 为什么需要它，原理、机制、不变量或因果链是什么。
3. 它如何工作，结构、流程、公式、代码或可复核示例是什么。
4. 何时使用，选择依据、适用条件和替代方案是什么。
5. 边界在哪里，限制、失败模式、风险和常见误区是什么。
6. 面试如何组织回答；需要笔试内容时，题目如何识别和求解。

结构按规范第 5 至 8 节和卡片类型调整：

- `10_计算机基础知识` 的独立卡片必须包含准确标题 `## 知识点解析`、`## 笔试常考`、`## 面试应对`。
- 除 `10_计算机基础知识`、`12_实习工作整理` 外，独立卡片必须包含 `## 面试应对`。
- 面试题写成真实问法，每题包含“回答思路”和可直接口述的“回答模板”。
- 算法与数学卡补齐成立前提、推导或正确性原因、复杂度、可复核算例和边界条件。
- 工程类卡补齐组件职责、数据流或时序、设计原因、失败现象和排查顺序。
- 模型与论文卡区分论文设定、版本差异、工程实现和公开边界。

不要用定义、优缺点、关键词或问答清单代替机制解释。笔试和面试中的每个知识点都必须由正文支撑。

首次出现的技术缩写按 `缩写（English Full Name，中文译名）` 展开，多义缩写按当前语境解释。默认使用中文，保留必要英文。

### 5. 维护索引和链接

1. 新增卡片后更新最近一级 `README.md`，加入相对链接和一句话说明。
2. README 只保留一至两个短段落的目录简介和内容索引，不在其中新增知识正文。
3. 如果 README 已含与本次主题直接重叠的独有知识，先迁入权威卡片，再精简对应索引；不丢失有效内容。
4. 移动、重命名、合并或删除文件后，使用 `rg` 搜索旧路径并更新全部引用。
5. 图片放在卡片同级的 `assets/` 中并使用标准相对路径；没有必要时不为凑格式添加图片。

### 6. 验证后交付

至少执行：

```bash
git diff --check
git status --short
git diff -- <本次修改文件>
```

并按改动检查：

- 对未跟踪的新文件，普通 `git diff -- <文件>` 不会显示内容；使用 `git diff --no-index -- /dev/null <文件>` 或完整读取文件审阅。
- 新卡片已出现在最近一级 README 中，没有孤立文件。
- 新增或修改的本地相对链接和图片路径存在。
- 标题层级、代码围栏、题号、答案、公式和示例相互一致。
- 缩写首次出现已展开，正文没有空章节、占位符、聊天残留或审计过程。
- 最终 diff 只包含本次应有改动，没有覆盖用户原有内容。

除非用户明确要求，不创建提交，不推送远端。

最终回复只需说明修改文件、核心内容、验证结果和仍无法核实的事项。

## 常见失败

| 失败做法 | 正确处理 |
| --- | --- |
| 为了快而跳过 `git status`、查重或 README | 缩小正文范围，但保留完整执行闭环 |
| 把卡片放在仓库根目录 | 按知识本质选择最具体的现有目录 |
| 只写定义、优缺点和几个问答 | 补齐机制、流程、边界、示例和正文支撑 |
| 多篇博客说法一致就当作事实 | 追溯共同原始来源，按证据等级写作 |
| 用常见参数补齐未公开模型配置 | 明确未公开，不把参考实现冒充目标事实 |
| 新建单独的检索记录或来源卡片 | 普通知识直接内化到正文，仅保留必要引用 |
| 只生成聊天草稿，没有写入文件 | 默认完成落盘、索引和验证 |
| 为统一格式重写整篇或清理已有改动 | 在现有正确内容上做最小、聚焦的增量修改 |
