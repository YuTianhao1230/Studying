# 全栈_AI_Coding最佳实践工作流

## 知识点解析

### 概述

资料来源：ByteTech《全栈 AI Coding 最佳实践工作流探索》

### 核心结论

AI Coding 的关键不是“让 AI 多写代码”，而是把研发流程重构为：需求先行、全局感知、测试驱动、持续沉淀。AI 负责高强度执行，人负责需求定义、架构判断、质量验收和经验沉淀。

### 背景

文章来自一个从 0 到 1 搭建 AI 短视频生成平台的实践。早期主要依赖 Vibe Coding，效果不错；但随着项目复杂度上升，出现了典型问题：

- AI 生成代码缺少自动化验证。
- 复杂功能频繁返工。
- 前后端接口需要人工反复对齐。
- 上下文变长后，AI 容易丢失关键需求。

因此，实践从“即时对话式 Vibe Coding”转向“Spec-First + 多仓库 Workspace + 测试验证 Skill”的工程化工作流。

### 核心工作流

```text
需求输入
  -> Prompt 梳理
  -> Spec 文档
  -> Tasks 拆解
  -> Checklist 验收
  -> AI 编码
  -> 自动化测试验证
  -> 失败修复
  -> 经验沉淀为 Skill / AGENTS.md / 规则文档
```

可以概括为四句话：

- 需求先行：先用 Spec 对齐需求，再让 AI 写代码。
- 全局感知：前后端、多仓库放进同一 Workspace。
- 测试驱动：用自动化测试替代“凭感觉 Review”。
- 持续沉淀：把重复操作、坑点和测试流程固化成 Skill。

### Spec-First：需求即文档

### Spec 模式三件套

使用 Spec Coding 时，通常需要三类文档：

- `spec.md`：需求规格，包含功能描述、技术方案、API 接口定义、前后端分工。
- `tasks.md`：任务拆解，按优先级和依赖关系组织。
- `checklist.md`：验收清单，明确每个任务的完成标准和测试要点。

### 为什么 Spec 很关键

很多问题不是“代码实现错了”，而是“Spec 没对齐”。

典型问题：

| 现象 | 本质原因 | 解决方式 |
| --- | --- | --- |
| 部分功能没实现 | Prompt 没说清楚，Spec 自然缺失 | 在 Prompt 阶段补齐细节 |
| Spec 理解偏差 | 历史代码结构不规范，AI 误解边界 | 重构或补充项目规则 |
| 前后端接口对不上 | Spec 没写到参数级细节 | 前后端在同一 Workspace 中协同 |
| AI 改坏代码 | 上下文太多，关键需求丢失 | 拆小需求，逐步实现 |

### 多仓库 Workspace

全栈需求常涉及前端、后端、接口、任务调度等多个仓库。只打开单仓库会导致 AI 缺少全局信息。

推荐做法：

1. 在同一个 Trae Workspace 中加入前端和后端仓库。
2. 为每个仓库写清楚 workspace rules。
3. 明确告诉 AI 哪个目录是前端、哪个目录是后端。
4. 在 Spec 中写清楚接口参数、数据流和前后端分工。

价值：

- 减少前后端来回手动对齐。
- 让 AI 能同时修改调用方和被调用方。
- 更容易做端到端验证。

局限：

- 多仓库上下文更大，性能和上下文管理压力更高。
- Spec 文档可能只生成在某一个仓库。
- 大型存量系统仍需要额外知识库和规则文档。

### 测试驱动：AI Review 的抓手

文章中最重要的实践判断是：

```text
不要让 AI 猜“对不对”，要给它明确输入、期望输出和可执行测试。
```

### 后端测试验证

适合场景：

- 纯函数逻辑。
- 数据解析。
- 接口参数转换。
- 不依赖外部服务的业务规则。

做法：

- 给定样例输入。
- 给定期望输出。
- 明确通过标准。
- 让 AI 自动运行测试。
- 失败后让 AI 根据测试结果修复。

示例标准：

- 文本正确率 > 95%。
- 图片召回率 > 95%。
- 结构化字段完全匹配。

### 前端测试验证

前端更适合用 Playwright 这类真实浏览器测试，而不是只让 AI 静态检查。

正确流程：

```text
部署后端
  -> 启动前端
  -> 编写 Playwright 测试
  -> 操作真实页面
  -> 监听请求和响应
  -> 校验 UI 状态或接口返回
  -> 失败后修复
```

关键点：

- 测试脚本必须真正执行，不是只生成。
- 需要明确测试数据和文件路径。
- 需要等待关键请求完成。
- 需要检查最终 UI 状态或接口返回。

### Skill 迭代

高频重复动作应沉淀为 Skill。

文章提到的典型 Skill：

- `prompt-optimizer`：提示词规范与优化。
- `backend-test-verification`：后端测试验证。
- `frontend-test-verification`：前端测试验证，通常结合 Playwright。
- `cloud-edit-doc`：云编辑接口参考。
- 外部 RPC 接口接入 Skill：沉淀接口接入重复经验。
- 表生成 gorm：数据库模型代码生成。

Skill 不是一次写好的，而是由失败 case 驱动迭代：

```text
一次 AI Coding 失败
  -> 总结失败原因
  -> 抽象为规则 / gotcha / 测试流程
  -> 写入 Skill
  -> 下次自动复用
```

### 存量业务的深水区挑战

从 0 到 1 项目中，AI Coding 效果通常更好，因为：

- 代码库干净。
- 业务逻辑清晰。
- 历史包袱少。
- 团队协作简单。
- 本地可闭环验证。

存量业务系统更难，因为：

- 代码规模大，超过上下文窗口。
- 业务逻辑复杂且耦合。
- 隐性知识散落在会议、飞书消息和口头共识中。
- 外部依赖多，例如离线任务、MQ、OneService API、ABase。
- 修改影响面大。
- 很多逻辑必须在线上、PPE 或 BOE 环境验证。

### 对不同角色的建议

| 角色 | 建议 |
| --- | --- |
| 后端开发 | 优先沉淀后端测试验证 Skill，给定明确输入输出样例 |
| 前端开发 | 编写 Playwright 测试用例，比泛化 CUA/MCP 更稳定 |
| QA | 将测试场景结构化，沉淀为可复用测试 Skill |
| 全栈开发 | 多仓库 Workspace + Spec 模式是标配 |

### 和 Agent 工程的关系

这篇文章的重点不是单纯 AI Coding，而是 Agent 工程化：

- Spec 是任务规划和上下文约束。
- Workspace 是上下文工程。
- 测试脚本是 Agent 的外部验证工具。
- Skill 是经验沉淀和复用机制。
- AGENTS.md 是仓库级长期上下文。
- Playwright 是前端验证工具，也是 Agent 的可执行观察能力。

### 面试回答要点

如果被问“如何让 AI Coding 从玩具变成生产力”，可以这样回答：

```text
我不会直接让 AI 写代码，而是先把需求整理成可验收的 Spec，再拆成 tasks 和 checklist。
如果涉及前后端或多仓库，我会把相关仓库放进同一 Workspace，并补充仓库级规则。
实现阶段让 AI 小步修改，每一步都通过自动化测试验证，后端用明确输入输出，前端用 Playwright 跑真实交互。
每次失败都沉淀为 Skill、AGENTS.md 或测试用例，让下一次同类任务更稳定。
```

### 常见误区

- 把 Vibe Coding 当成“自然语言直接生成代码”。
- Prompt 没写清楚，却期待 Spec 自动正确。
- 只生成测试文件，不真正运行测试。
- 前后端不在同一上下文，导致接口对不齐。
- 复杂需求一次性塞给 AI，导致上下文丢失。
- 临时脚本散落在仓库根目录，没有归档到测试目录。
- 对存量系统缺少业务知识库和 AGENTS.md。
## 面试应对

### 全栈 AI Coding 工作流是什么？

回答思路：先定位概念，再说明它解决的具体问题。

回答模板：

全栈 AI Coding 工作流是把需求拆解、技术设计、代码生成、运行验证、错误修复和交付整理串成闭环的开发方式。它不是让模型一次性写完整项目，而是让 AI 参与每个工程节点，并通过测试、代码审查和版本管理约束输出质量。

### 核心节点有哪些？

回答思路：按关键组件或流程拆解，不停留在名词解释。

回答模板：

典型节点包括需求澄清、任务拆分、接口和数据结构设计、增量实现、自动化测试、浏览器或运行时验证、问题回归和文档整理。每个节点都要有可检查产物，避免只看模型回答是否顺眼。

### 有什么风险？

回答思路：结合工程落地讲适用边界和风险。

回答模板：

主要风险是需求理解偏差、生成代码不可维护、测试覆盖不足和错误被包装成合理解释。实践中要小步提交、保留人工审查、优先运行测试，并让 AI 基于真实报错修复。
