# Skill

## 知识点解析

### 概述

Skill 是给 Agent 动态加载的领域能力包，通常由指令、脚本、参考文档、模板和配置组成，用来让通用 Agent 在特定任务上表现得更稳定。

### 为什么需要 Skill

大模型本身具备通用知识，但在这些场景下容易不稳定：

- 企业内部流程模型不知道。
- 某个工具调用有特殊参数和坑点。
- 团队有固定输出格式或工程规范。
- 相邻任务容易混淆，需要明确边界。
- 同类任务经常失败，需要沉淀 gotchas。

Skill 的价值是把这些经验变成 Agent 可复用的上下文。

### Skill 通常包含什么

```text
skill-name/
├── SKILL.md
├── scripts/
├── references/
├── assets/
└── config.json
```

- `SKILL.md`：触发条件和核心执行规则。
- `scripts/`：确定性逻辑，供 Agent 调用而不是重写。
- `references/`：大文档，只在需要时读取。
- `assets/`：模板、schema、样例。
- `config.json`：用户配置或环境配置。

### Skill 的核心原则

#### Description 是触发器

description 不是介绍“这个 Skill 很厉害”，而是告诉 Agent “什么时候应该加载它”。

好的 description 应该：

- 短。
- 具体。
- 覆盖真实用户意图。
- 避免和其他 Skill 抢路由。

#### 正文要高信号

不要把 Skill 写成人类教程。模型已经知道的通用知识不需要写进去。

应该写：

- 特殊规则。
- 工具坑点。
- 输出约束。
- 失败恢复。
- 禁止行为。

#### 渐进加载

常驻上下文很贵，所以要分层：

- Skill Index：只放名字和描述。
- `SKILL.md`：只放核心规则。
- references/scripts/assets：按需读取。

### Skill 和 Prompt 的区别

- Prompt：一次任务内的临时指令。
- Skill：可复用、可维护、可评测的长期能力包。

如果一条指令只服务于当前任务，用 Prompt 即可；如果它会被重复使用、需要稳定执行、涉及工具或特殊流程，就适合沉淀为 Skill。

### 常见误区

- 把 Skill 写成长篇知识库。
- 把命令清单原样塞进 Skill。
- description 写得太宽，导致误触发。
- 没有 eval，无法判断是否该加载。
- 没有 gotchas，无法从失败中进化。

## 面试应对

### Skill 和普通 Prompt 有什么区别？

回答思路：抓住"一次性临时指令 vs 可复用可维护的长期能力包"这个本质差异。

回答模板：

Prompt 是一次任务里的临时指令，用完就过去了，不沉淀、不复用。Skill 是一个可复用、可维护、可评测的长期能力包，通常由触发描述、核心执行规则、脚本、参考文档和模板组成，目的是把某类任务的经验和坑点固化下来，让通用 Agent 在这类任务上表现稳定。区别的判断标准很简单：如果一条指令只服务当前这次任务，用 Prompt 就够了；如果它会被反复使用、需要稳定执行、还涉及特殊工具或流程，就该沉淀成 Skill。而且 Skill 支持渐进加载——平时只暴露描述，用到时才加载细节，这是单纯写 Prompt 做不到的。

### Skill 的 description 为什么重要？

回答思路：点明 description 是"触发器"，太宽误触发、太窄漏触发。

回答模板：

因为 description 本质上是一个触发器，决定模型什么时候加载这个 Skill，而不是介绍这个 Skill 有多厉害。它写得太宽，就会在不相关的任务上被误触发，白白占上下文、还可能和别的 Skill 抢路由；写得太窄或太抽象，又会该用的时候没被加载，能力形同虚设。所以好的 description 要短、要具体、要覆盖真实的用户意图，明确说清"什么场景该用、什么场景不该用"，让模型能准确判断该不该加载。

### 如何设计 Skill 的目录结构？

回答思路：按 SKILL.md / references / scripts / assets 的分工讲，核心是渐进加载。

回答模板：

我一般分成四块，核心思路是渐进加载、按需读取。SKILL.md 放触发条件、核心执行流程和必须遵守的规则，尽量短、信号高；references/ 放较长、低频、按场景才需要读的资料，比如详细规范和长文档；scripts/ 放确定性逻辑的脚本，让 Agent 直接调用而不是每次自己重写，既稳又省 token；assets/ 放模板、schema、样例这类可复用资源。这样上下文里默认只有 SKILL.md 的核心规则，细节和资料只在真正用到时才加载进来。

### 什么内容应该放 `SKILL.md`，什么内容应该放 references？

回答思路：按"高频必守 vs 低频按需"的划分讲，落到上下文成本。

回答模板：

判断标准是频率和是否必须常驻。高频、短小、每次执行都必须遵守的内容放 SKILL.md，比如触发条件、核心流程、硬性规则和常见坑点，保证它们默认就在上下文里；篇幅长、低频、只在特定场景才需要查的内容放 references，比如完整的接口规范、详细文档、边界 case 说明，用到时再让 Agent 去读。这样做的核心目的是控制上下文成本：常驻的东西越少越精，注意力才不会被稀释，同时又不丢失完整能力。

### 如何评测一个 Skill 是否有效？

回答思路：不能只看"有没有被加载"，要用真实任务集看触发准确率和任务效果。

回答模板：

评一个 Skill 有没有用，不能只看它有没有被加载，要用真实任务集去跑几个指标：一是触发准确率，该加载时加载、不该加载时不误触发；二是任务成功率，加载后任务是不是真的完成得更好；三是步骤遵循率和错误率，看它有没有让 Agent 更守规则、少犯同类错误；四是上下文成本，加载它带来的 token 开销划不划算。最关键的一条是看它能不能减少重复出现的失败 case——如果同类问题反复犯，说明这个 Skill 的 gotchas 还没沉淀到位。
