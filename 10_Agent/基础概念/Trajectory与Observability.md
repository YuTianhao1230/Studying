# Trajectory与Observability

## 知识点解析

### 概述

Trajectory 是 Agent 完成任务过程中的完整轨迹；Observability 是记录、查看和分析这条轨迹的工程能力。

### Trajectory 包含什么

一次 Agent 任务通常不是单次模型调用，而是一串事件：

```text
用户输入
  -> 模型思考 / 计划
  -> 工具调用
  -> 工具返回
  -> 再次规划
  -> 文件修改
  -> 测试执行
  -> 最终回复
```

这些中间步骤组成 trajectory。

### 为什么需要 Observability

Agent 失败时，如果只看最终答案，很难知道问题在哪里。

可能原因包括：

- 用户意图理解错。
- 检索到错误上下文。
- 计划不合理。
- 工具选错。
- 工具参数错。
- 工具结果被误读。
- 执行中断。
- 最终汇总丢信息。

Observability 要帮助定位这些问题。

### 常见记录内容

- 每轮模型输入和输出。
- 计划变更。
- 工具调用名称、参数、返回。
- 错误栈和重试次数。
- 文件 diff。
- 外部 API 状态码。
- token、耗时、成本。
- 人工确认记录。
- 最终结果和验收状态。

### Agent 调试思路

```text
最终结果错
  -> 看 trajectory
  -> 定位首次偏离点
  -> 判断是上下文、规划、工具、执行还是验证问题
  -> 修 prompt / skill / tool / workflow / eval
```

关键不是只问“模型为什么错”，而是定位系统链路里第一个错误环节。

### 和 Harness 的关系

Harness 负责系统化跑评测；Trajectory 是评测中的关键证据。

对 Agent 来说，逐 case 的 trajectory 比单个最终分数更重要，因为它能解释：

- 为什么成功。
- 为什么失败。
- 失败发生在哪一步。
- 是否可以通过工具、上下文或流程修复。

### 常见误区

- 只记录最终答案。
- 工具调用失败被吞掉。
- 不保存中间状态。
- 没有 case id，无法追踪。
- 只看总准确率，不看路径质量。
- 失败归因只写“模型问题”。

## 面试应对

### Agent trajectory 是什么？

回答思路：先给一句话定义，再说明它解决什么问题，最后补一个工程例子或常见风险。

回答模板：

Agent trajectory 是任务执行全过程记录，包括观察、计划、工具调用、工具结果、错误和最终输出。它是调试、评测、审计和复盘 Agent 行为的核心证据。

### 如何排查一个 Agent 任务失败？

回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。

回答模板：

沿 trajectory 从目标理解、上下文、计划、工具选择、参数、工具结果和最终判断逐步定位。先判断失败发生在哪一步，再决定修 prompt、Skill、工具还是调度逻辑。

### Agent Observability 需要记录哪些信息？

回答思路：先定义问题，再说明核心机制、适用边界、风险和验证方式。

回答模板：

需要记录任务输入、上下文版本、计划、工具名、参数、返回结果、错误、耗时、token、成本和最终状态。高风险操作还要保存证据和审计日志。

### 为什么 Agent 评测不能只看最终准确率？

回答思路：先指出背后的核心约束，再解释收益，最后补充如果不这样做会带来的风险。

回答模板：

因为最终答对不代表过程安全可靠。Agent 可能调用了危险工具、多走了很多步、误读了中间结果或偶然成功。过程指标能暴露生产风险。

### 如何从 trajectory 反推需要修 Skill 还是修工具？

回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。

回答模板：

如果工具返回错误、结构不清或能力缺失，优先修工具；如果模型选错流程、漏步骤或误解约束，优先修 Skill、prompt 或上下文组织。
