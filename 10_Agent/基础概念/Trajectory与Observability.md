# Trajectory 与 Observability

## 一句话解释

Trajectory 是 Agent 完成任务过程中的完整轨迹；Observability 是记录、查看和分析这条轨迹的工程能力。

## Trajectory 包含什么

一次 Agent 任务通常不是单次模型调用，而是一串事件：

```text
用户输入
  -> 模型思考 / 计划
  -> 工具调用
  -> 工具返回
  -> 再次规划
  -> 文件修改
  -> 测试执行
  -> 最终回复
```

这些中间步骤组成 trajectory。

## 为什么需要 Observability

Agent 失败时，如果只看最终答案，很难知道问题在哪里。

可能原因包括：

- 用户意图理解错。
- 检索到错误上下文。
- 计划不合理。
- 工具选错。
- 工具参数错。
- 工具结果被误读。
- 执行中断。
- 最终汇总丢信息。

Observability 要帮助定位这些问题。

## 常见记录内容

- 每轮模型输入和输出。
- 计划变更。
- 工具调用名称、参数、返回。
- 错误栈和重试次数。
- 文件 diff。
- 外部 API 状态码。
- token、耗时、成本。
- 人工确认记录。
- 最终结果和验收状态。

## Agent 调试思路

```text
最终结果错
  -> 看 trajectory
  -> 定位首次偏离点
  -> 判断是上下文、规划、工具、执行还是验证问题
  -> 修 prompt / skill / tool / workflow / eval
```

关键不是只问“模型为什么错”，而是定位系统链路里第一个错误环节。

## 和 Harness 的关系

Harness 负责系统化跑评测；Trajectory 是评测中的关键证据。

对 Agent 来说，逐 case 的 trajectory 比单个最终分数更重要，因为它能解释：

- 为什么成功。
- 为什么失败。
- 失败发生在哪一步。
- 是否可以通过工具、上下文或流程修复。

## 常见误区

- 只记录最终答案。
- 工具调用失败被吞掉。
- 不保存中间状态。
- 没有 case id，无法追踪。
- 只看总准确率，不看路径质量。
- 失败归因只写“模型问题”。
