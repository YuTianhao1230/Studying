# SubAgent与Multi_Agent

## 知识点解析

### 概述

SubAgent 是由主 Agent 调度的专门子任务执行者；Multi-Agent 是多个 Agent 通过分工、通信和协作共同完成复杂任务的系统。

### 为什么需要 SubAgent

单个 Agent 同时处理所有事情会遇到几个问题：

- 上下文太长。
- 工具太多，选择困难。
- 任务之间互相干扰。
- 专业领域差异大。
- 并行能力不足。

SubAgent 的思路是把任务拆给更小、更专注的执行单元。

### 常见结构

#### Orchestrator-Workers

```text
主 Agent
  -> 拆分任务
  -> 分配给多个 Worker
  -> 汇总结果
  -> 输出最终答案
```

适合：

- 多文件代码审查。
- 多资料调研。
- 多模块实现。
- 多候选方案比较。

#### Specialist Agents

每个 Agent 负责一个专业领域：

- Research Agent：查资料。
- Coding Agent：写代码。
- Review Agent：审查代码。
- Test Agent：运行测试。
- Data Agent：分析数据。

#### Debate / Voting

多个 Agent 独立生成答案，再做投票或仲裁。

适合：

- 开放问题。
- 方案比较。
- 高风险判断。

### 主 Agent 的职责

- 理解用户目标。
- 拆解任务。
- 选择合适的 SubAgent。
- 控制上下文边界。
- 合并结果。
- 处理冲突。
- 负责最终交付质量。

### SubAgent 的职责

- 在窄领域内深入执行。
- 返回结构化结果。
- 不越权修改全局计划。
- 明确列出证据、假设和风险。

### 常见失败模式

- 过度拆分，沟通成本超过收益。
- SubAgent 之间信息不一致。
- 主 Agent 不做最终审查，直接拼接结果。
- 没有共享状态管理。
- 多个 Agent 同时改同一文件导致冲突。
- 缺少终止条件，循环委派。

### 设计原则

- 能用单 Agent 稳定完成时，不要强行多 Agent。
- SubAgent 职责要窄，输入输出要清晰。
- 主 Agent 必须保留最终决策权。
- 对并行任务要提前定义合并规则。
- 重要结论要带证据，不只带观点。

## 面试应对

### SubAgent 和普通工具调用有什么区别？

回答思路：抓住"一次性确定动作 vs 独立自主的执行体"这个本质差异，再落到上下文隔离的收益。

回答模板：

普通工具调用是主 Agent 发一个确定性动作、拿一个结果就回来，本身不做规划和决策；SubAgent 是一个有自己上下文、能自主规划和多步执行的独立执行体，主 Agent 把一个子目标丢给它，它内部可以自己调好几轮工具、反复纠错，最后只把结构化结论返回。它最大的价值是上下文隔离：SubAgent 内部的探索过程和大量中间信息不会污染主 Agent 的上下文，主 Agent 只拿到干净的结果。所以查一次数据库用工具调用就够了，但"审查整个模块并给出结论"这种需要独立探索的子任务才适合交给 SubAgent。

### 什么场景适合 Multi-Agent？

回答思路：给出"可拆分/需专业分工/需投票仲裁"的适用场景，再说简单任务用单 Agent 更稳。

回答模板：

适合三类场景：任务能自然拆成互相独立的子任务（比如多文件审查、多资料并行调研）、需要不同专业视角分工（研究、编码、审查、测试各一个 Agent）、或需要多方案独立生成再投票仲裁的高风险判断。反过来，简单的线性任务、步骤固定的流程用单 Agent 或 Workflow 更稳定，硬上多 Agent 只会增加通信成本和不一致风险。实际系统里我一般让 Workflow 或主 Agent 固定整体流程，只在确实需要并行或专业分工的环节才拆出 SubAgent。

### Orchestrator-Workers 模式如何工作？

回答思路：讲清主 Agent 拆分-分发-汇总、Worker 只管执行的分工，再点出接口和验证。

回答模板：

Orchestrator-Workers 是主从结构：主 Agent 负责理解目标、把任务拆成互相独立的子任务、分发给多个 Worker，再汇总它们的结果并做最终审查和交付；每个 Worker 只在自己窄领域内执行一个子任务，返回结构化结果，不去改全局计划。它适合能自然并行的任务，比如多文件代码审查、多资料并行调研。关键是子任务之间要尽量独立、Worker 的输入输出接口要清晰、结果要能被主 Agent 验证，否则汇总时容易出现信息打架。

### 多 Agent 系统如何避免互相冲突？

回答思路：从角色边界、共享状态和写权限三点讲，最后落到由 Orchestrator 收敛。

回答模板：

冲突主要来自多个 Agent 同时改同一份状态或给出不一致结论。我会从三点控制：一是明确角色边界，每个 Agent 只负责自己的子任务，不越界；二是管好共享状态，用统一的状态协议，写操作要加锁或串行，避免两个 Agent 同时改同一个文件；三是收敛决策权，最终结论由 Orchestrator 或明确规则来仲裁，Worker 只能提议不能直接拍板。这样即使中间有分歧，也能在汇总阶段统一收口。

### 多 Agent 的成本和风险是什么？

回答思路：把成本（token/延迟）和风险（不一致、错误传播、难调试）分开讲，再给使用边界。

回答模板：

成本上，多 Agent 意味着更多的 token 消耗、更多工具调用和更高的端到端延迟，因为每个 Agent 都要各自维护上下文、来回通信。风险上主要有四类：多个 Agent 意见冲突不好收敛、共享状态不一致、一个 Agent 的错误结论被下游当成事实继续传播（错误放大），以及链路变长后调试和复盘变难。所以我的原则是：能用单 Agent 或 Workflow 稳定完成的就别上多 Agent，只有任务确实能自然拆分、需要并行或不同专业视角时才用，而且必须保留主 Agent 的最终审查。
