# Computer Use

## 一句话解释

Computer Use 是让 Agent 像人一样操作电脑界面，包括看屏幕、移动鼠标、点击、输入、打开应用、使用浏览器和处理文件。

## 和普通工具调用的区别

普通 Tool Call 通常是结构化 API：

```text
search(query="xxx")
read_file(path="xxx")
```

Computer Use 面向 GUI 环境：

```text
观察屏幕截图
  -> 判断按钮位置
  -> 点击
  -> 输入文本
  -> 等待页面变化
  -> 再观察
```

它更接近人类操作，但也更脆弱。

## 常见能力

- 浏览器操作。
- 桌面应用操作。
- 表单填写。
- 文件下载和上传。
- 截图理解。
- UI 元素定位。
- 键盘鼠标控制。

## 为什么 Computer Use 重要

很多系统没有稳定 API，或 API 接入成本很高。Computer Use 可以让 Agent 通过已有 UI 完成任务。

适合：

- 网页自动化。
- 内部系统没有 API 的流程。
- 跨多个应用的办公任务。
- 人类原本通过浏览器完成的重复操作。

不适合：

- 高并发批处理。
- 严格稳定的生产链路。
- 高风险金融、权限、删除操作。
- UI 经常变化且没有容错的流程。

## 关键工程难点

- 页面加载不确定。
- 元素定位不稳定。
- 截图理解可能出错。
- 点击位置可能偏移。
- 登录态和权限复杂。
- 错误恢复困难。

## 设计原则

- 能用 API 就优先用 API。
- UI 自动化必须有明确检查点。
- 每次关键操作后重新观察页面状态。
- 对提交、删除、支付等动作设置人工确认。
- 保存截图和操作日志，方便复盘。

## 面试可能怎么问

1. Computer Use 和 API Tool Call 的区别是什么？
   - 回答思路：先分别定义两个概念，再从目标、机制、适用场景和工程取舍四个角度对比。
   - 回答模板：API Tool Call 是调用结构化接口，稳定、可校验、可控；Computer Use 是让 Agent 操作图形界面或浏览器，更通用但更脆弱。能用 API 时优先 API，只有没有接口或必须操作 GUI 时才用 Computer Use。
2. 什么场景适合用 Computer Use？
   - 回答思路：先给适用条件，再给不适用条件，最后说明真实系统里如何组合使用。
   - 回答模板：适合没有 API、必须操作网页/桌面、需要视觉识别或跨应用操作的场景。能用结构化 API 时不要优先用 Computer Use。
3. Computer Use 的主要风险是什么？
   - 回答思路：先给一句话定义，再说明它解决什么问题，最后补一个工程例子或常见风险。
   - 回答模板：主要风险是识别错 UI 元素、点击错按钮、页面状态判断错误、重复提交和越权操作。GUI 环境变化也会让流程失效，所以需要截图留痕、状态校验和高风险确认。
4. 如何验证 Agent 点击到了正确元素？
   - 回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。
   - 回答模板：点击前要用元素文本、位置、DOM 属性和截图交叉确认；点击后要检查 URL、页面状态、响应结果或视觉变化是否符合预期。关键操作最好保存截图和操作日志。
5. 为什么高风险操作需要人工确认？
   - 回答思路：先指出背后的核心约束，再解释收益，最后补充如果不这样做会带来的风险。
   - 回答模板：因为 GUI 操作可能不可逆，模型一旦误判按钮或页面状态，就可能造成真实损失。删除、支付、发消息、改权限、提交审批这类动作都应该先 dry-run，再由人确认。
