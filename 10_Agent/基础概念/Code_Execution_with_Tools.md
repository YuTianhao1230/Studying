# Code_Execution_with_Tools

## 知识点解析

### 概述

Code Execution with Tools 是让 Agent 在沙箱中写代码来组合调用工具，而不是每一步都把工具结果完整塞回模型上下文。

### 为什么出现这个模式

随着 MCP 和工具生态扩张，Agent 可能同时连接几十甚至上百个工具。传统直接工具调用会遇到两个问题：

- 工具定义太多，占满上下文。
- 大量中间结果反复进出模型，成本高、延迟高、还容易复制错。

例如：

```text
读取长文档 -> 模型收到全文
写入另一个系统 -> 模型又要把全文作为参数传出去
```

中间数据完全经过模型上下文，既浪费 token，也容易出错。

### 基本思路

把工具暴露成代码环境里的 API：

```text
Agent 写一段脚本
  -> 脚本调用多个工具
  -> 在沙箱中处理大数据
  -> 只把摘要、统计或最终结果返回给模型
```

### 适合场景

- 多工具组合调用。
- 大文档处理。
- 大表格处理。
- 数据清洗和转换。
- 批量 API 操作。
- 需要循环、过滤、聚合的任务。

### 优点

- 减少上下文占用。
- 降低模型复制大数据的错误。
- 提升执行效率。
- 让确定性逻辑由代码完成。
- 便于复现和调试。

### 风险

- 沙箱权限必须严格控制。
- 代码生成可能有 bug。
- 外部工具调用仍需权限和审计。
- 大规模写操作必须 dry-run 和人工确认。

### 和 MCP 的关系

MCP 负责把工具标准化暴露出来；Code Execution with Tools 是一种更高效的调用方式。

直接模式：

```text
模型 -> MCP Tool -> 工具结果 -> 模型
```

代码执行模式：

```text
模型 -> 写代码 -> 代码调用 MCP Tools -> 返回压缩结果 -> 模型
```

### 常见误区

- 把所有工具定义一次性塞进上下文。
- 让模型搬运大段中间数据。
- 没有沙箱隔离。
- 把不可控写操作放进自动执行脚本。
- 脚本执行后不保留日志。

## 面试应对

### 为什么直接工具调用在大规模 MCP 场景下会变慢？

回答思路：先指出背后的核心约束，再解释收益，最后补充如果不这样做会带来的风险。

回答模板：

当 MCP 工具很多时，模型需要阅读更长的工具列表和 schema，选择成本变高，误调用概率也会上升。工具返回的大量结果还会挤占上下文，所以需要工具分组、路由和 progressive disclosure。

### Code Execution with Tools 解决了什么问题？

回答思路：先定义问题，再说明核心机制、适用边界、风险和验证方式。

回答模板：

它让 Agent 不必把大量工具结果都塞回上下文，而是写脚本在沙箱里批量调用工具、过滤和聚合结果。适合大量文件搜索、数据处理、批量 API 查询这类任务，可以降低上下文成本并提高可复现性。

### 什么时候应该让 Agent 写脚本调用工具？

回答思路：先定义问题，再说明核心机制、适用边界、风险和验证方式。

回答模板：

当任务需要循环、批量处理、过滤、统计或组合多个工具结果时，适合让 Agent 写脚本。比如扫描上百个文件、批量校验链接、汇总日志。一次性简单查询则直接 Tool Call 更清晰。

### 这种模式有哪些安全风险？

回答思路：先定义问题，再说明核心机制、适用边界、风险和验证方式。

回答模板：

主要风险是脚本可能执行越权操作、访问敏感数据、写坏文件、进入无限循环或消耗过多资源。所以必须放在沙箱中执行，限制权限、网络、时间和文件写入范围，并保留执行日志。

### 如何减少工具结果对上下文的污染？

回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。

回答模板：

不要把原始大结果直接塞给模型，而是让脚本先过滤、聚合、排序和摘要，只返回关键统计、异常样本和必要证据。完整原始结果可以落盘，用路径或 ID 引用。
