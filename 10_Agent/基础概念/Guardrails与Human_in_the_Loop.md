# Guardrails与Human_in_the_Loop

## 知识点解析

### 概述

Guardrails 是 Agent 系统的安全边界和质量约束；Human-in-the-Loop 是在关键节点引入人工确认、审核或接管。

### 为什么需要 Guardrails

Agent 能调用工具和执行动作后，风险不再只是“回答错”，而是可能“做错事”。

典型风险：

- 删除文件。
- 修改权限。
- 发错消息。
- 泄露敏感信息。
- 调错接口。
- 生成错误代码并上线。
- 在错误上下文中继续执行。

Guardrails 的目标是降低这些风险。

### 常见 Guardrails

#### 输入校验

- 用户意图是否明确。
- 参数是否合法。
- 文件路径是否在允许范围内。
- 是否包含敏感信息。

#### 输出校验

- 格式是否符合 schema。
- 是否包含禁止内容。
- 是否有事实依据。
- 是否满足验收标准。

#### 工具权限

- 哪些工具可读。
- 哪些工具可写。
- 哪些工具需要确认。
- 哪些工具禁止自动执行。

#### 执行预算

- token 限制。
- 时间限制。
- 重试次数。
- 并发限制。
- 成本上限。

#### 人工确认

高风险操作前停下来，让人确认。

适合：

- 删除。
- 付款。
- 发外部消息。
- 改权限。
- 提交生产任务。
- 大规模批量修改。

### Human-in-the-Loop 的位置

```text
Agent 计划
  -> 人审计划
  -> Agent 执行
  -> 人审高风险动作
  -> Agent 验证
  -> 人审最终结果
```

不一定每一步都要人工参与，关键是把人放在风险最高的位置。

### 常见误区

- 只靠系统 Prompt 做安全控制。
- 高风险工具和低风险工具权限不分层。
- 没有 dry-run。
- 没有审计日志。
- 人工确认只问“是否继续”，不展示具体变更。
- 失败后自动重试高风险操作。

## 面试应对

### Agent 系统为什么需要 Guardrails？

回答思路：核心是 Agent 会真的影响外部状态，出错代价大，需要权限、校验和拦截兜底。

回答模板：

Agent 能调用工具并影响外部状态，错误可能造成数据泄露、越权操作或业务损失。Guardrails 用来限制权限、校验输入输出、拦截危险动作，并在必要时要求人工确认。

### 哪些操作必须 Human-in-the-Loop？

回答思路：给出"不可逆 / 影响外部世界 / 难恢复"的判断标准，再举典型动作。

回答模板：

涉及不可逆写操作、权限变更、删除、支付、发消息、上线发布、访问敏感数据的动作都应该有人确认。判断标准是风险高、影响外部世界、失败后难恢复。

### 如何设计工具权限分级？

回答思路：按只读/低风险写/高风险写/敏感操作分级，默认最小权限。

回答模板：

可以按只读、低风险写、高风险写、敏感操作分级。默认最小权限，高风险工具需要 allowlist、参数校验、dry-run、人工确认和审计日志。

### 如何防止 Agent 泄露敏感信息？

回答思路：从输入、上下文、工具返回、输出四层做控制，强调不能绕过系统权限。

回答模板：

需要从输入、上下文、工具返回和最终输出四层做控制，包括敏感字段识别、权限检查、最小上下文注入、日志脱敏和输出过滤。模型不能绕过系统级权限。

### 如何做高风险操作的 dry-run 和确认？

回答思路：讲清"先出动作和 diff 不执行、人确认后再执行、执行后留审计"。

回答模板：

先生成待执行动作、参数、影响范围和预期 diff，不真正执行；用户确认后再执行。执行后保存审计日志，失败时要能回滚或说明不可恢复范围。
