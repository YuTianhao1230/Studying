# Guardrails 与 Human-in-the-Loop

## 一句话解释

Guardrails 是 Agent 系统的安全边界和质量约束；Human-in-the-Loop 是在关键节点引入人工确认、审核或接管。

## 为什么需要 Guardrails

Agent 能调用工具和执行动作后，风险不再只是“回答错”，而是可能“做错事”。

典型风险：

- 删除文件。
- 修改权限。
- 发错消息。
- 泄露敏感信息。
- 调错接口。
- 生成错误代码并上线。
- 在错误上下文中继续执行。

Guardrails 的目标是降低这些风险。

## 常见 Guardrails

### 1. 输入校验

- 用户意图是否明确。
- 参数是否合法。
- 文件路径是否在允许范围内。
- 是否包含敏感信息。

### 2. 输出校验

- 格式是否符合 schema。
- 是否包含禁止内容。
- 是否有事实依据。
- 是否满足验收标准。

### 3. 工具权限

- 哪些工具可读。
- 哪些工具可写。
- 哪些工具需要确认。
- 哪些工具禁止自动执行。

### 4. 执行预算

- token 限制。
- 时间限制。
- 重试次数。
- 并发限制。
- 成本上限。

### 5. 人工确认

高风险操作前停下来，让人确认。

适合：

- 删除。
- 付款。
- 发外部消息。
- 改权限。
- 提交生产任务。
- 大规模批量修改。

## Human-in-the-Loop 的位置

```text
Agent 计划
  -> 人审计划
  -> Agent 执行
  -> 人审高风险动作
  -> Agent 验证
  -> 人审最终结果
```

不一定每一步都要人工参与，关键是把人放在风险最高的位置。

## 常见误区

- 只靠系统 Prompt 做安全控制。
- 高风险工具和低风险工具权限不分层。
- 没有 dry-run。
- 没有审计日志。
- 人工确认只问“是否继续”，不展示具体变更。
- 失败后自动重试高风险操作。

## 面试可能怎么问

1. Agent 系统为什么需要 Guardrails？
2. 哪些操作必须 Human-in-the-Loop？
3. 如何设计工具权限分级？
4. 如何防止 Agent 泄露敏感信息？
5. 如何做高风险操作的 dry-run 和确认？
