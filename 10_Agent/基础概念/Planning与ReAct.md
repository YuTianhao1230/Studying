# Planning与ReAct

## 知识点解析

### 概述

Planning 是 Agent 在执行前或执行中拆解任务、安排步骤的能力；ReAct 是把推理和行动交替进行的 Agent 模式，即 Reasoning + Acting。

### ReAct 是什么

ReAct 的核心循环：

```text
Thought -> Action -> Observation -> Thought -> ...
```

更工程化地说：

```text
分析当前状态
  -> 决定调用哪个工具
  -> 执行工具
  -> 读取工具结果
  -> 更新判断
  -> 继续或结束
```

### Planning 的类型

#### Upfront Planning

先生成完整计划，再执行。

适合：

- 需求明确。
- 步骤相对稳定。
- 需要用户先 review。

风险：

- 计划可能很快过期。
- 对未知环境假设过多。

#### Step-by-step Planning

每执行一步后根据结果重新规划。

适合：

- 调试。
- 代码库探索。
- 网页操作。
- 数据分析。

风险：

- 容易碎片化。
- 需要良好的终止条件。

#### Hierarchical Planning

先拆成大阶段，再在每个阶段内细化。

适合：

- 大型工程任务。
- 多 Agent 协作。
- 长周期自动化任务。

### 好计划的标准

- 目标明确。
- 每一步可验证。
- 有失败处理。
- 有终止条件。
- 能区分探索、修改、验证。
- 不把未知假设写成事实。

### 常见失败模式

- 只计划不执行。
- 计划太细，工具结果一变就失效。
- 计划没有验收标准。
- 遇到错误后继续按旧计划执行。
- 为简单任务引入复杂规划。

### 和 Workflow 的关系

- Workflow 是预定义流程。
- Planning 是 Agent 动态生成或更新流程。

生产系统常见组合：

```text
Workflow 固定边界
  -> Agent 在局部步骤内动态规划
  -> 关键节点由规则或人工确认
```

## 面试应对

### ReAct 模式是什么？

回答思路：一句话点明 Reasoning+Acting 的交替循环，再说它适合需要外部反馈的多步任务。

回答模板：

ReAct 是 Reasoning and Acting 的缩写，核心是让模型在“思考、行动、观察”之间循环。模型先判断当前状态，再调用工具执行动作，然后读取工具返回结果并更新判断。它适合搜索、调试、代码修改这类需要外部反馈的多步任务。

### Planning 和 Workflow 的区别是什么？

回答思路：点明"动态生成 vs 预先定义"，落到生产里两者怎么组合。

回答模板：

Planning 是 Agent 动态生成或更新计划的能力，强调根据当前状态和工具反馈调整下一步；Workflow 是工程师预先定义好的流程编排，强调稳定、可控和可复现。实际生产里我一般会用 Workflow 固定任务边界和关键节点，再让 Agent 在某些不确定的局部步骤里做 Planning，比如代码排查、资料检索或网页操作。

### 为什么 Agent 需要观察工具结果后再规划？

回答思路：从"初始信息不完整、工具结果会改变状态"来讲，配调试例子。

回答模板：

因为 Agent 的初始判断往往基于不完整信息，工具结果会改变当前状态。观察结果后再规划，可以避免沿着错误假设继续执行。例如代码调试时，运行测试后的报错会直接决定下一步该查数据、改逻辑还是调整环境。

### 如何避免 Agent 陷入无限循环？

回答思路：给出步数/超时/重复检测等硬约束，再补轨迹复盘。

回答模板：

我会设置最大步数、超时、重复动作检测和明确的完成条件；如果多轮没有产生新信息，就要求 Agent 总结阻塞原因或转人工处理。生产系统里还应该记录 trajectory，用于发现是 prompt 问题、工具问题还是终止条件设计问题。

### 什么场景适合先规划，什么场景适合边做边规划？

回答思路：按"目标明确、影响大"适合先规划，"信息不完整、强依赖反馈"适合边做边规划，复杂任务两者结合。

回答模板：

目标明确但步骤复杂、需要用户 review 或影响面较大时，适合先规划，例如代码重构或数据迁移。信息不完整、强依赖环境反馈时，适合边做边规划，例如排查报错、网页操作或多轮检索。复杂任务通常会结合两者：先有阶段性计划，每一步执行后根据观察结果修正。
