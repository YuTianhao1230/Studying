# Tool Call 与 Function Calling

## 一句话解释

Tool Call / Function Calling 是让大模型以结构化方式请求外部工具执行动作的机制，例如查数据库、读文件、调用 API、打开浏览器、运行代码。

## 为什么需要 Tool Call

LLM 本身只能生成文本，不能真正访问外部世界。Tool Call 让模型可以把“我要做什么”表达成结构化调用：

```json
{
  "tool": "search_files",
  "arguments": {
    "pattern": "**/*.py"
  }
}
```

真正执行工具的是外层 Orchestrator，而不是模型本身。

## 基本流程

```text
用户目标
  -> 模型判断需要工具
  -> 生成 tool call
  -> Orchestrator 校验参数
  -> 执行工具
  -> 工具结果返回给模型
  -> 模型继续推理或输出最终答案
```

## Tool Schema

工具需要给模型提供结构化描述，通常包括：

- 工具名。
- 工具说明。
- 参数名。
- 参数类型。
- 必填字段。
- 返回结果格式。
- 使用限制。

Schema 写得越清楚，模型越容易正确调用。

## 好的工具设计

- 名字清晰，动作明确。
- 参数少而精。
- 参数类型严格。
- 返回结构化数据，优先 JSON。
- 错误信息可诊断。
- 工具职责单一。
- 对高风险操作设置确认。

## 常见失败模式

- 参数名写错。
- 参数类型不匹配。
- 工具描述太模糊，模型不知道何时使用。
- 返回内容过长，污染上下文。
- 工具报错不可读，模型无法恢复。
- 高风险工具缺少权限和确认机制。

## Tool Call 和 MCP 的关系

Tool Call 是能力调用机制；MCP 是一种标准协议，用于统一发现和调用外部工具。

简单说：

```text
Tool Call：模型调用工具这件事
MCP：把工具标准化暴露给 Agent 的协议
```

## 面试可能怎么问

1. Function Calling 的基本流程是什么？
   - 回答思路：面试官想确认你是否理解“模型不直接执行函数”这个边界。回答时先定义 Function Calling，再讲清楚模型、Orchestrator、真实函数三者的分工，最后用一个工具调用例子说明完整链路。
   - 回答模板：Function Calling 是让大模型用结构化方式请求外部函数执行任务的机制。完整流程是：用户提出目标后，模型判断是否需要工具；如果需要，就根据工具 schema 生成函数名和参数；外层 Orchestrator 校验参数并真正执行函数；函数返回结构化结果；模型再基于这个结果继续推理或组织最终自然语言回答。这里最关键的边界是，模型本身不执行函数，它只是生成调用请求，真正执行动作的是外部系统。比如用户问“今天北京天气怎么样”，模型可以生成 `get_weather(city=\"北京\")` 的调用，天气服务返回真实结果后，模型再把结果解释给用户。
2. 工具 schema 应该怎么设计？
   - 回答思路：面试官想听你是否能把工具设计成“模型容易选、参数不容易错、系统容易校验”的形式。回答时从工具名、description、参数类型、必填字段、返回结构和权限约束展开。
   - 回答模板：工具 schema 的设计目标是降低模型误调用和参数错误。首先工具名要表达清楚动作，比如 `search_files` 比 `handle` 更好；其次 description 要说明什么时候用、什么时候不用；参数要有明确类型、必填字段、枚举范围和示例；返回值最好是结构化 JSON，包含状态、结果和错误信息。对于高风险工具，比如删除文件、发消息、改权限，还要在 schema 或外层策略里加入确认机制。一个好的 schema 不只是给模型看的，也是给 Orchestrator 做参数校验和权限控制用的。
3. 为什么工具返回要结构化？
   - 回答思路：面试官想确认你理解工具结果不是“给人看”优先，而是“给模型和系统继续处理”优先。回答时重点讲可解析、可校验、可组合、可审计。
   - 回答模板：工具返回结构化结果，是为了让模型和系统都能稳定理解结果。比如返回 JSON 里明确包含 `status`、`data`、`error`，模型就能判断调用是否成功，系统也能做日志、重试和指标统计。如果只返回一大段自然语言，模型可能漏读关键字段，也不方便后续节点继续处理。结构化返回还能降低上下文污染，只把必要字段交给模型，而不是把一整页日志塞进去。所以生产级工具调用里，输入参数和输出结果都应该尽量结构化。
4. 如何处理工具调用失败？
   - 回答思路：面试官想看你有没有工程化失败处理意识。回答时不要只说“重试”，要区分参数错误、权限错误、超时、服务异常、业务无结果，并说明不同错误对应不同策略。
   - 回答模板：我会先把工具失败分类型处理。参数错误通常让模型根据错误信息修正参数后重试；权限错误不能盲目重试，需要提示用户授权或停止；超时和临时服务异常可以有限次数重试并做退避；业务无结果则应该换查询条件或告诉用户没有找到。每次失败都要记录工具名、参数、错误码和耗时，方便后续排查。对于写操作或高风险操作，失败后还要保证幂等，避免重复执行造成副作用。
5. Tool Call 和 MCP 是什么关系？
   - 回答思路：面试官想听清楚“调用机制”和“工具协议”的区别。回答时先定义 Tool Call，再定义 MCP，然后说明 MCP 可以作为 Tool Call 的工具来源。
   - 回答模板：Tool Call 是模型发起工具调用这件事，也就是模型根据 schema 生成工具名和参数；MCP 是一种把外部工具、资源和 prompt 标准化暴露给 Agent 的协议。可以理解为 Tool Call 是调用动作，MCP 是工具接入和发现的标准。没有 MCP，也可以做 Tool Call，只是每个工具要单独适配；有了 MCP，Agent 可以用统一方式发现和调用很多外部能力。实际系统里，Skill 往往告诉模型什么时候该用某类 MCP 工具，而 Tool Call 负责发起具体调用。
