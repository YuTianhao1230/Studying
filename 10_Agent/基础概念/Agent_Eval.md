# Agent Eval

## 一句话解释

Agent Eval 是评估 Agent 是否能稳定完成任务的体系，不只评最终答案，还要评规划、工具调用、轨迹、成本、安全和可恢复性。

## 和普通模型评测的区别

普通模型评测常见形式：

```text
输入 -> 模型输出 -> 和标准答案比较
```

Agent 评测更复杂：

```text
目标
  -> 多轮模型调用
  -> 多次工具调用
  -> 中间状态变化
  -> 可能修改外部环境
  -> 最终结果
```

所以 Agent Eval 要评估完整执行过程。

## 常见评测维度

### 1. Task Success

最终任务是否完成。

例如：

- 文件是否正确修改。
- 测试是否通过。
- 数据是否正确导出。
- 页面操作是否完成。

### 2. Trajectory Quality

过程是否合理。

关注：

- 是否选对工具。
- 是否读取必要上下文。
- 是否绕路过多。
- 是否及时纠错。
- 是否遵守约束。

### 3. Tool Use Accuracy

工具调用是否正确。

关注：

- 工具选择。
- 参数准确性。
- 错误处理。
- 返回结果理解。

### 4. Safety

是否触发危险行为。

关注：

- 未授权写操作。
- 敏感信息泄露。
- 越权访问。
- 不该自动执行的动作。

### 5. Cost and Latency

Agent 是否高效。

关注：

- token 消耗。
- 工具调用次数。
- 运行耗时。
- 重试次数。
- 并发资源占用。

## 评测样例类型

- 正例：应该成功完成的任务。
- 负例：应该拒绝或要求确认的任务。
- 边界例：容易误判、误触发、路径复杂的任务。
- 回归例：历史失败 case。
- 对抗例：诱导越权、泄露、忽略规则的任务。

## 常见评测方法

- 规则检查：文件是否存在、字段是否正确、测试是否通过。
- LLM Judge：让模型按 rubric 评分。
- Trace Review：人工或模型审查 trajectory。
- Golden Set：固定任务集回归。
- A/B Test：比较两个 Agent、Prompt、Skill 或模型版本。

## 常见误区

- 只评最终答案，不看执行过程。
- 没有负例和安全例。
- LLM Judge 没有明确 rubric。
- 测试集和开发集混用。
- 成功标准含糊，导致评分不可复现。
- 不记录成本，导致系统上线后不可控。

## 面试可能怎么问

1. Agent Eval 和普通 LLM Eval 有什么区别？
   - 回答思路：先分别定义两个概念，再从目标、机制、适用场景和工程取舍四个角度对比。
   - 回答模板：先分别定义两个对象，再比较目标、机制、适用场景和风险。围绕 Agent Eval，关键是说明它们解决的问题不同。
2. 如何评估工具调用是否正确？
   - 回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。
   - 回答模板：我会从四层评估：工具是否选对、参数是否符合 schema、调用时机是否合理、工具结果是否被正确使用。最终还要用 execution-based grader 或状态检查验证任务是否真的完成。
3. 为什么要评估 trajectory？
   - 回答思路：先指出背后的核心约束，再解释收益，最后补充如果不这样做会带来的风险。
   - 回答模板：trajectory 记录了 Agent 从目标到最终输出的全过程。只看最终答案可能看不出它是否走了弯路、调用了危险工具、误读了工具结果或偶然成功。评估 trajectory 能定位失败原因，也能指导修 prompt、Skill、工具还是调度逻辑。
4. 如何设计 Agent 的负例和安全测试？
   - 回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。
   - 回答模板：我会覆盖无权限操作、恶意输入、冲突指令、工具失败、敏感数据、不可完成任务和诱导越权等场景。好的 Agent 不只是会完成任务，还要在不该做时拒绝、在不确定时澄清、在高风险操作前请求确认。
5. 如何比较两个 Agent 版本是否真的变好？
   - 回答思路：按“目标定义 -> 关键步骤 -> 风险控制 -> 指标验证”的顺序回答，避免只讲抽象原则。
   - 回答模板：要用固定任务集比较任务成功率、工具调用正确率、平均步数、成本、延迟、安全违规率和 bad case 类型。还要做 case-level diff，看新版本修复了哪些旧问题，又引入了哪些新问题。
