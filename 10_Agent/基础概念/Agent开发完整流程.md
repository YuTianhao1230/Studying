# Agent 开发完整流程

## 一句话总览

开发一个 Agent，本质上是在做一个由大模型驱动、能调用工具、能观察反馈、能被评测和约束的任务执行系统。

一个可用的 Agent 不是把 LLM 接上几个工具就结束，而是要把任务边界、工作流、工具协议、上下文、记忆、安全控制、轨迹观测和评测闭环都设计清楚。

## 整体流程

### 定义任务边界

第一步不是选框架，而是定义 Agent 到底要解决什么问题。

需要明确：

- 输入是什么：自然语言、文件、网页、数据库、代码仓库还是多模态内容。
- 输出是什么：答案、报告、代码变更、工单、执行结果还是结构化数据。
- 成功标准是什么：准确率、完成率、耗时、成本、安全合规、用户满意度。
- 失败边界是什么：哪些事情不能做，哪些动作必须人工确认。

如果任务可以用固定规则或普通 Workflow 稳定完成，就不一定需要 Agent。Agent 更适合开放任务、多步任务、依赖外部工具反馈的任务。

### 设计 Workflow

Workflow 是完整工作流，负责把任务拆成稳定节点。

典型结构包括需求解析、资料检索、方案生成、工具执行、结果校验和总结输出。这里的关键是：Workflow 不等于 Agent。Workflow 更偏确定性编排，Agent 更偏开放决策。实际工程里常见做法是用 Workflow 固定边界，在某些节点里调用 Agent 处理不确定问题。

### 设计 Agent Loop

Agent Loop 是 Agent 的核心循环，通常包括 Planning、Tool Call、Observation、Reflection 和 Final Response。

Planning 负责判断当前目标和下一步动作；Tool Call 负责选择工具并生成结构化参数；Observation 负责读取工具执行结果；Reflection 负责判断是否完成、是否需要修正；Final Response 负责输出最终结果。ReAct 就是这种思考、行动、观察交替进行的典型模式。

Loop 必须有最大步数、超时、失败退出和重复动作检测，否则很容易陷入无限循环。

### 设计 Tool Call 和 Function Calling

Tool Call 是模型调用外部工具的结构化机制。模型负责选择工具和组织参数，真正执行动作的是外部系统。

一个工具定义通常需要包括工具名、工具用途、输入参数 schema、返回结果格式、错误信息和使用限制。工具设计要克制。工具太多会增加上下文成本，也会让模型更容易选错。高风险工具，例如删除、发消息、改权限、提交任务，必须加权限控制和人工确认。

### 接入 MCP

MCP 解决的是工具、资源和 Prompt 的标准化接入问题。

可以这样理解：Tool Call 是一次调用动作，Tool 是真实可执行能力，MCP 是把工具标准化暴露给 Agent 的协议。当 Agent 需要接入多个外部系统，例如文件系统、数据库、浏览器、飞书、代码平台时，MCP 可以降低适配成本。

### 做 Context Engineering

Context Engineering 决定模型当前能看到什么信息，包括系统指令、用户目标、工具 schema、当前状态、历史轨迹摘要、相关文档和中间结果。

上下文不是越多越好。无关内容会增加 token 成本，也会干扰模型判断。好的上下文应该足够完成任务、足够短、结构清晰，并且把重要约束放在稳定位置。

### 设计 Memory

Memory 负责保存跨轮次、跨任务的长期信息，例如用户偏好、项目规则、历史决策、任务状态和工具使用经验。

Memory 不能无脑保存所有内容。要区分长期稳定知识和临时任务过程，避免污染未来上下文。

### 加 Guardrails 和 Human-in-the-Loop

Agent 有执行能力后，必须设计边界。常见 Guardrails 包括工具权限限制、参数校验、高风险动作确认、输出安全过滤、超时和最大步数、审计日志。

Human-in-the-Loop 适合放在不可逆、高成本、高风险节点，例如删除数据、发外部消息、提交生产任务、修改权限。

### 做 Observability 和 Trajectory

Trajectory 是 Agent 执行任务的全过程记录，包括模型输入、工具调用、工具返回、状态变化和最终输出。

Observability 的目标是让失败可复现、可诊断、可归因。没有轨迹记录，就很难判断 Agent 是规划错、工具选错、参数错、上下文错，还是模型能力不够。

### 设计 Agent Eval

Agent Eval 不能只看最终答案，要看全过程。常见指标包括任务完成率、工具调用正确率、平均步数、成本和延迟、错误恢复能力、安全违规率、人工接管率。

评测 Harness 负责把数据集、执行环境、打分器、日志和回归测试组织起来。上线前要有固定评测集，上线后要持续收集 bad case。

## 概念在流程中的位置

| 概念 | 发生作用的位置 | 解决的问题 |
| --- | --- | --- |
| Workflow | 任务编排阶段 | 固定流程、控制边界 |
| Agent | 开放决策节点 | 动态规划、工具选择、多步推理 |
| Tool Call | 执行阶段 | 让模型以结构化方式请求外部工具 |
| MCP | 工具接入阶段 | 标准化暴露工具、资源和 Prompt |
| Context Engineering | 每次模型调用前 | 控制模型当前看到的信息 |
| Memory | 跨任务阶段 | 保存长期稳定信息 |
| Guardrails | 全流程 | 控制权限、风险和失败退出 |
| Trajectory | 执行全过程 | 记录行为，支持诊断和评测 |
| Agent Eval | 测试和上线阶段 | 判断 Agent 是否真的可靠 |
| Harness | 评测工程层 | 组织数据、运行、打分和回归 |

## 面试应对

### 如果让你从 0 开发一个 Agent，你会怎么做？

回答思路：按任务边界、Workflow、Agent Loop、工具、上下文、记忆、安全、评测、上线的顺序回答。

回答模板：

我会先定义任务边界，明确输入、输出、成功标准和禁止动作。然后设计 Workflow，把稳定流程固定下来，只在需要动态决策的节点引入 Agent。Agent 内部用 plan、tool call、observe、reflect 的循环执行任务。接着设计工具 schema 和 MCP 接入方式，控制上下文和长期 Memory，再加上权限、超时、人工确认等 Guardrails。最后用 Harness 做 Agent Eval，记录 trajectory，评估完成率、工具调用正确率、成本、延迟和安全违规率。只有评测稳定后才会上线，并持续用 bad case 迭代。

### Workflow 和 Agent 在系统里怎么配合？

回答思路：强调 Workflow 负责确定性编排，Agent 负责开放决策。

回答模板：

Workflow 是完整任务流程，适合固化稳定步骤，比如解析输入、调用检索、执行校验和生成报告。Agent 是 Workflow 中处理不确定性的执行单元，适合做动态规划、工具选择和多步推理。真实系统里我不会让 Agent 完全自由运行，而是用 Workflow 控制边界，在局部节点让 Agent 发挥灵活性。

### 为什么 Agent 必须做评测和轨迹记录？

回答思路：说明 Agent 失败不只发生在最终答案，还可能发生在中间决策和工具调用。

回答模板：

Agent 的输出只是最后结果，真正的问题往往发生在中间过程，比如计划错、工具选错、参数错、上下文缺失或观察结果理解错。如果没有 trajectory，就很难复现和归因。评测也不能只看最终答案，要看工具调用正确率、平均步数、错误恢复、安全违规和成本。轨迹记录和 Harness 是把 Agent 从 demo 变成工程系统的关键。
