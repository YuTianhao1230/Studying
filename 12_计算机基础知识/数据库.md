# 数据库面试笔试要点

## 知识点解析

### 概述

数据库负责可靠地存储、查询和更新数据。面试中数据库问题通常围绕 SQL 能力、索引原理、事务隔离、锁机制、MVCC、日志恢复和性能优化展开。核心是理解“为什么查询快、为什么更新安全、为什么并发不会乱”。

### SQL 基础

SQL 的核心能力包括数据查询、过滤、聚合、排序、连接和子查询。常见执行逻辑可以理解为：

```text
FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY -> LIMIT
```

`WHERE` 在分组前过滤行，`HAVING` 在分组后过滤聚合结果。`INNER JOIN` 只保留匹配记录，`LEFT JOIN` 保留左表所有记录，右表没有匹配时补 NULL。

### 索引

索引是为了加速查询而维护的额外数据结构。数据库常用 B+ 树索引，因为 B+ 树高度低、查询稳定、叶子节点有序并通过链表连接，适合范围查询和磁盘页读取。

索引的代价是增加存储空间，并让写入、更新、删除变慢，因为数据变化时索引也要维护。

### 聚簇索引和非聚簇索引

聚簇索引的叶子节点直接存放整行数据，表数据按聚簇索引组织。MySQL InnoDB 中主键索引就是聚簇索引。非聚簇索引的叶子节点存放主键值，查到主键后可能需要回表查整行。

覆盖索引是指查询所需字段都在索引里，不需要回表。它能减少随机 IO，是常见 SQL 优化手段。

### 最左前缀原则

联合索引按照从左到右的字段顺序组织。查询条件需要从索引最左侧字段开始连续匹配，才能充分使用联合索引。例如索引 `(a, b, c)` 可以支持 `a`、`a,b`、`a,b,c`，但通常不能直接高效支持只按 `b` 查询。

### 事务 ACID

事务有四个基本特性：

- Atomicity 原子性：事务要么全部成功，要么全部失败。
- Consistency 一致性：事务前后数据库从一个一致状态转到另一个一致状态。
- Isolation 隔离性：并发事务之间不能互相产生不合理干扰。
- Durability 持久性：事务提交后结果要可靠保存。

### 隔离级别

常见隔离级别：

| 隔离级别 | 可能问题 | 说明 |
| --- | --- | --- |
| Read Uncommitted | 脏读、不可重复读、幻读 | 能读到未提交数据 |
| Read Committed | 不可重复读、幻读 | 只能读到已提交数据 |
| Repeatable Read | 幻读 | 同一事务内多次读结果稳定 |
| Serializable | 基本避免并发读写异常 | 串行化执行，性能最低 |

脏读是读到别人未提交的数据；不可重复读是同一行数据两次读取结果不同；幻读是同一范围内两次查询出现了新增或删除的记录。

### MVCC

MVCC 是多版本并发控制，通过维护数据的多个版本，让读操作尽量不阻塞写操作，写操作也尽量不阻塞读操作。InnoDB 中常见机制包括隐藏事务 ID、回滚指针、undo log 和 ReadView。快照读通过版本链和可见性判断读到符合当前事务视图的数据。

### 锁

数据库锁可以按粒度分为表锁、行锁；按模式分为共享锁和排他锁；按范围可涉及记录锁、间隙锁和临键锁。行锁并不意味着一定只锁一行，如果查询没有命中索引，可能导致锁范围扩大。

### 日志

数据库常见日志包括 undo log、redo log 和 binlog。

- undo log：用于事务回滚和 MVCC 版本链。
- redo log：保证崩溃恢复后的持久性。
- binlog：记录逻辑变更，用于主从复制和数据恢复。

InnoDB 通过 WAL，Write-Ahead Logging，先写日志再写数据页，提高写入性能并保证崩溃恢复能力。

### SQL 优化

SQL 优化一般从执行计划、索引、扫描行数、回表、排序、临时表和锁等待入手。常见方法包括：

- 给高选择性过滤条件建立索引。
- 避免在索引列上使用函数或隐式类型转换。
- 尽量使用覆盖索引减少回表。
- 避免 `SELECT *`。
- 大分页使用延迟关联或基于游标的翻页。
- 用 `EXPLAIN` 查看是否走索引、扫描行数和 join 类型。

## 笔试常考

### SQL 题型

- 分组聚合：按用户统计订单数、总金额、最大值、最小值。
- Top N：每个部门薪资前三、每类商品销量最高。
- 去重和窗口函数：`row_number`、`rank`、`dense_rank`。
- 连接查询：多表关联、找不存在记录、统计留存。
- 子查询和条件聚合：`CASE WHEN`、`COUNT DISTINCT`。

### 判断题

- 索引能提升查询性能，但会降低写入性能。
- 联合索引遵循最左前缀原则。
- 覆盖索引可以避免回表。
- MVCC 主要解决读写并发问题，不等于完全不需要锁。
- `WHERE` 过滤行，`HAVING` 过滤分组后的结果。

## 央国企与大厂查漏补缺

### 关系代数

关系代数是关系数据库理论基础，常见操作包括选择、投影、并、差、交、笛卡尔积、连接和除法。选择是按条件筛选行，投影是选取列，连接是把多个关系按条件组合。银行和央国企笔试可能用概念题考这些基本操作。

### 数据库范式

范式用于减少数据冗余和更新异常：

| 范式 | 核心要求 |
| --- | --- |
| 1NF | 字段不可再分，保证原子性 |
| 2NF | 在 1NF 基础上，非主属性完全依赖候选键 |
| 3NF | 在 2NF 基础上，非主属性不传递依赖候选键 |
| BCNF | 每个决定因素都必须是候选键 |

工程上不是范式越高越好。高范式减少冗余，但可能增加 join 成本；高并发读场景可能适当反范式，用冗余换查询性能。

### ER 模型

ER 模型用实体、属性、联系描述业务数据。转换成关系模型时，实体通常变成表，属性变成字段，一对多关系通常在多的一方加外键，多对多关系通常拆成中间表。笔试中常考 ER 图到关系模式的转换。

### DDL、DML、DCL、TCL

| 类型 | 常见语句 | 作用 |
| --- | --- | --- |
| DDL | `CREATE`、`ALTER`、`DROP`、`TRUNCATE` | 定义或修改数据库对象 |
| DML | `SELECT`、`INSERT`、`UPDATE`、`DELETE` | 查询和修改数据 |
| DCL | `GRANT`、`REVOKE` | 权限控制 |
| TCL | `COMMIT`、`ROLLBACK`、`SAVEPOINT` | 事务控制 |

`DELETE` 删除表中数据，可带条件，通常可回滚；`TRUNCATE` 清空整表，通常比 DELETE 快；`DROP` 删除表结构和数据。

### Oracle 常见文件

银行科技岗可能出现 Oracle 基础题。Oracle 数据库常见文件包括数据文件、控制文件和重做日志文件。数据文件存储实际数据；控制文件记录数据库结构和状态；重做日志文件记录变更，用于故障恢复。

### Redis 基础

Redis 是内存型键值数据库，常用于缓存、计数器、排行榜、分布式锁和会话存储。常见数据结构：

| 结构 | 典型场景 |
| --- | --- |
| String | 缓存、计数器、分布式锁 |
| Hash | 用户信息、对象字段 |
| List | 消息队列、时间线 |
| Set | 去重、共同好友 |
| ZSet | 排行榜、延迟队列 |

Redis 快的原因主要是内存访问、单线程避免锁竞争、IO 多路复用和高效数据结构。这里的单线程主要指命令执行主线程，现代 Redis 在网络 IO、持久化等方面也会使用后台线程。

### Redis 持久化和高可用

RDB 是周期性生成快照，恢复快，但可能丢失最近一段时间数据；AOF 记录写命令，数据更完整，但文件更大，恢复可能更慢。高可用常见方案包括主从复制、哨兵和 Redis Cluster。

### 缓存三大问题

| 问题 | 含义 | 常见解决 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的数据，请求打到数据库 | 缓存空值、布隆过滤器、参数校验 |
| 缓存击穿 | 热点 key 失效，大量请求同时打到数据库 | 互斥锁、逻辑过期、热点 key 不过期 |
| 缓存雪崩 | 大量 key 同时失效或 Redis 故障 | 过期时间加随机值、多级缓存、限流降级 |

### 分布式事务

分布式事务解决多个服务或多个数据库之间的一致性问题。常见方案包括 2PC、TCC、Saga 和本地消息表。金融场景更强调一致性和可追溯，常需要幂等、补偿、对账和人工兜底机制。

## 面试应对

### 为什么数据库索引常用 B+ 树？

回答思路：从磁盘 IO、树高、范围查询和叶子节点结构回答。

回答模板：

数据库索引常用 B+ 树，是因为它非常适合磁盘和范围查询场景。B+ 树非叶子节点只存 key，不存整行数据，所以一个页能放更多 key，树高更低，查询需要的磁盘 IO 更少。叶子节点存放数据或主键，并且按顺序通过链表连接，范围查询只要定位到起点后顺序扫描即可。相比二叉树，B+ 树更矮；相比哈希索引，B+ 树更适合范围查询和排序。

### 事务隔离级别怎么理解？

回答思路：先说并发异常，再说隔离级别从低到高解决哪些问题。

回答模板：

事务隔离级别本质是在并发性能和一致性之间做取舍。Read Uncommitted 可能读到未提交数据，会有脏读；Read Committed 只能读已提交数据，避免脏读，但同一事务内两次读同一行可能不同；Repeatable Read 保证同一事务内重复读取同一行结果一致，但理论上仍可能有幻读；Serializable 最严格，基本按串行方式执行，隔离性最好但并发性能最低。

### MVCC 是什么？

回答思路：说明多版本、快照读、读写不互相阻塞，再补 InnoDB 实现。

回答模板：

MVCC 是多版本并发控制，它通过保存数据的多个历史版本，让读操作基于事务开始时的快照读取数据，从而减少读写之间的阻塞。在 InnoDB 里，MVCC 依赖隐藏事务 ID、undo log 版本链和 ReadView 做可见性判断。这样普通快照读不用加锁也能读到一致视图，但更新、当前读和唯一性检查等场景仍然需要锁。

### SQL 慢查询怎么排查？

回答思路：从现象、执行计划、索引、数据量和锁等待逐层排查。

回答模板：

我会先确认慢查询的 SQL、耗时、调用频率和数据量，再用 EXPLAIN 看执行计划，重点看是否走索引、扫描行数、join 类型、是否有 filesort 或临时表。然后检查索引设计是否匹配过滤条件和排序条件，有没有函数、隐式转换、前导模糊匹配导致索引失效。如果 SQL 本身没问题，还要看锁等待、热点行、连接数和数据库资源。如果是大分页或大范围扫描，会考虑改成游标分页、覆盖索引或拆分查询。
