# 索引与查询优化

## 知识点解析

### 概述

本文整理 B+ 树索引、聚簇与非聚簇索引、覆盖索引、联合索引、索引失效、执行计划和慢 SQL 优化。

### B+ 树索引

B+ 树非叶子节点只存 key 和指针，叶子节点存数据或主键，并且叶子节点按顺序链表连接。它适合数据库索引，因为树高低、磁盘 IO 少、查询稳定，并且范围查询效率高。

### 聚簇索引和非聚簇索引

InnoDB 中主键索引是聚簇索引，叶子节点存整行数据。普通二级索引是非聚簇索引，叶子节点存主键值，查到主键后可能需要回表查询整行。

覆盖索引是指查询字段都能从索引中拿到，不需要回表。

### 联合索引和最左前缀

联合索引按字段顺序组织，例如 `(a, b, c)` 可以支持 `a`、`a,b`、`a,b,c` 的连续前缀匹配。跳过最左字段通常无法充分使用索引。

### 索引失效

常见索引失效场景：

- 在索引列上使用函数或表达式。
- 隐式类型转换。
- 前导模糊匹配，如 `LIKE '%abc'`。
- 联合索引不满足最左前缀。
- `OR` 条件中部分字段无索引。

### 联合索引怎么设计

索引字段顺序通常综合考虑：

1. 高频等值查询字段。
2. 选择性较高、能过滤大量数据的字段。
3. 范围查询字段通常放在等值字段之后。
4. 是否可以覆盖 SELECT 和 ORDER BY 所需字段。
5. 写入频率、索引大小和维护成本。

联合索引 `(a, b, c)` 的 B+ 树先按 `a` 排序，`a` 相同时再按 `b`、`c` 排序。因此跳过 `a` 后，`b` 在整棵树上不具备全局有序性。遇到范围条件后，后续字段通常难以继续用于缩小扫描范围，但仍可能用于索引下推或覆盖查询。

### EXPLAIN 关注项

| 字段 | 关注内容 |
| --- | --- |
| type | 访问类型，是否全表扫描 |
| key | 实际选择的索引 |
| rows | 预计扫描行数 |
| filtered | 条件过滤比例估计 |
| Extra | 是否回表、临时表、文件排序等 |

执行计划是优化器估计，不等于真实执行结果。必要时结合实际执行统计、慢查询日志和数据分布判断。

### 慢 SQL 排查

慢 SQL 排查要看执行计划、扫描行数、索引命中、回表、排序、临时表、锁等待和数据量。`EXPLAIN` 重点看 type、key、rows、Extra。

排查顺序：

```text
确认 SQL、参数和耗时分布
  -> 查看执行计划和实际扫描行数
  -> 检查索引与查询条件
  -> 检查回表、排序和临时表
  -> 检查锁等待、连接池和资源
  -> 改写或建索引后回归验证
```

### 常见考法与场景题

- 为什么 B+ 树比二叉搜索树、B 树或哈希更适合数据库索引。
- 给定 SQL 和候选索引，判断是否满足最左前缀。
- 判断函数、隐式转换和前导模糊匹配是否导致索引失效。
- 分析覆盖索引、回表、索引下推的区别。
- 设计联合索引支持 WHERE、ORDER BY 和 LIMIT。
- 给出慢 SQL，说明完整排查路径。

### 易错点

- “建了索引”不代表优化器一定选择它，小表或低选择性条件可能全表扫描更便宜。
- 索引不是越多越好，会增加写入、存储和优化器选择成本。
- 联合索引能否使用不能只看字段是否出现，还要看顺序、条件类型和查询目标。
- `LIKE 'abc%'` 可以利用前缀，`LIKE '%abc'` 通常无法使用普通 B+ 树定位。
- `SELECT *` 更难形成覆盖索引。

## 面试应对

### 为什么数据库索引用 B+ 树？

回答思路：磁盘 IO、树高、范围查询、稳定性。

回答模板：

数据库索引常用 B+ 树，是因为它适合磁盘页读取和范围查询。B+ 树非叶子节点只存 key 和指针，一个页能放更多 key，树高更低，查询需要的磁盘 IO 更少。所有数据都在叶子节点，查询路径长度稳定；叶子节点之间有链表，范围查询只要定位起点后顺序扫描即可。相比哈希索引，B+ 树更适合范围查询和排序。

### 慢 SQL 怎么排查？

回答思路：先执行计划，再索引和数据量，最后锁和资源。

回答模板：

我会先确认 SQL、耗时、调用频率和数据量，再用 EXPLAIN 看执行计划，重点看是否走索引、扫描行数、join 类型、是否有 filesort 或临时表。然后检查索引设计是否匹配 WHERE、JOIN、ORDER BY，有没有函数、隐式转换、前导模糊匹配导致索引失效。如果 SQL 本身没问题，还要看锁等待、热点行、连接池和数据库资源。

### 什么是覆盖索引？

回答思路：说明索引包含查询所需字段，因此可以避免回表。

回答模板：

覆盖索引是指 SQL 查询需要的字段都能直接从索引中取得，不需要再根据主键回表查询整行数据。它能减少随机 IO，提高查询性能。例如联合索引包含 `user_id` 和 `status`，查询只需要这两个字段时，就可能直接使用覆盖索引。

### 联合索引字段顺序怎么确定？

回答思路：结合查询模式、等值范围、选择性、排序和覆盖回答。

回答模板：

我会先根据真实高频 SQL 设计，而不是只看单列选择性。通常把常用等值条件放在前面，范围条件放在后面，再考虑 ORDER BY 和需要返回的字段是否能形成覆盖索引。还要评估索引大小和写入成本。最终会用实际数据和 EXPLAIN 验证扫描行数，避免只凭规则决定顺序。

### 回表、覆盖索引和索引下推有什么区别？

回答思路：分别说明取数据位置和过滤时机。

回答模板：

回表是通过二级索引找到主键后，再访问聚簇索引取得整行数据；覆盖索引表示查询所需字段都在当前索引中，可以完全避免回表；索引下推是在存储引擎扫描联合索引时，提前利用索引中的其他条件过滤记录，减少回表次数，但不一定完全避免回表。三者分别关注二次取数、字段覆盖和过滤时机。
