# 事务锁与MVCC

## 知识点解析

### 概述

本文整理事务 ACID、隔离级别、数据库锁、MVCC、快照读与当前读，以及 undo、redo、binlog 的作用。

### ACID

- Atomicity 原子性：事务要么全部成功，要么全部失败。
- Consistency 一致性：事务前后数据满足约束。
- Isolation 隔离性：并发事务互不产生不合理干扰。
- Durability 持久性：提交后的修改可靠保存。

### 隔离级别

| 隔离级别 | 可能问题 |
| --- | --- |
| Read Uncommitted | 脏读、不可重复读、幻读 |
| Read Committed | 不可重复读、幻读 |
| Repeatable Read | 理论上可能幻读 |
| Serializable | 基本避免并发异常 |

脏读是读到未提交数据；不可重复读是同一行两次读取结果不同；幻读是同一范围两次查询出现新增或删除记录。

### 锁

数据库锁可按粒度分为表锁、行锁；按模式分为共享锁和排他锁。InnoDB 还涉及记录锁、间隙锁、临键锁。查询没有命中索引时，可能导致锁范围扩大。

### MVCC

MVCC 是多版本并发控制，通过版本链和 ReadView 让读操作尽量不阻塞写操作。InnoDB 中 MVCC 依赖隐藏事务 ID、undo log 和可见性判断。普通快照读通常不加锁，当前读、更新和唯一性检查仍然需要锁。

### 日志

- undo log：用于回滚和 MVCC 版本链。
- redo log：用于崩溃恢复，保证持久性。
- binlog：记录逻辑变更，用于复制和恢复。

### 快照读与当前读

- 快照读读取符合 ReadView 的历史版本，普通 `SELECT` 通常属于快照读。
- 当前读读取最新版本并加锁，例如 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`。

MVCC 主要优化快照读；当前读仍需依赖锁保证并发正确性。

### InnoDB 常见锁

| 锁 | 锁定范围 | 典型用途 |
| --- | --- | --- |
| 记录锁 | 单条索引记录 | 锁定已存在的行 |
| 间隙锁 | 两条索引记录之间的间隙 | 防止范围内插入 |
| 临键锁 | 记录锁 + 前方间隙 | Repeatable Read 下防止幻读 |
| 意向锁 | 表级标记 | 表示事务准备持有行锁 |

InnoDB 行锁依赖索引。如果查询条件无法有效使用索引，扫描和锁定范围可能扩大。

### 常见考法与分析步骤

| 题型 | 怎么考 | 怎么解 |
| --- | --- | --- |
| 并发异常 | 给出两个事务执行顺序 | 按时间线标记每次读到的版本 |
| 隔离级别 | 判断会否脏读、不可重复读、幻读 | 先区分行值变化和结果集变化 |
| MVCC 可见性 | 给事务 ID、版本链和 ReadView | 按创建者与活跃事务判断 |
| 锁范围 | 等值、范围查询会锁哪里 | 看索引、隔离级别和查询类型 |
| 死锁 | 两事务按不同顺序更新 | 画等待关系，检查环 |
| 日志恢复 | 提交前后宕机如何恢复 | 区分 undo、redo、binlog 职责 |

分析事务题时：

1. 标出事务开始、读、写、提交时间。
2. 判断读取是快照读还是当前读。
3. 确定隔离级别和 ReadView 创建时机。
4. 判断需要读取哪个版本、是否加锁、是否等待。
5. 最后判断出现哪种并发异常。

### WAL 与两阶段提交

WAL 表示数据页落盘前先持久化 redo log。这样事务提交后即使脏页尚未写入磁盘，数据库也能通过 redo 恢复。

MySQL 为保持 redo log 和 binlog 一致，会使用两阶段提交思想协调二者，避免主库恢复状态与复制日志不一致。

### 易错点

- MVCC 不等于完全无锁，它主要服务快照读。
- 幻读关注范围结果集变化，不只是同一行值变化。
- Repeatable Read 下 InnoDB 会结合 MVCC 和临键锁处理幻读，但具体行为取决于快照读或当前读。
- undo 用于回滚和历史版本，redo 用于崩溃恢复，binlog 用于复制和时间点恢复。
- 行锁锁的是索引记录，不命中索引可能扩大扫描与锁范围。

## 面试应对

### MVCC 是什么？

回答思路：多版本、快照读、读写并发。

回答模板：

MVCC 是多版本并发控制，通过保存数据的多个历史版本，让读操作基于事务视图读取符合条件的版本，从而减少读写阻塞。在 InnoDB 中，MVCC 依赖隐藏事务 ID、undo log 版本链和 ReadView 做可见性判断。它主要服务快照读，不代表完全不需要锁，当前读、更新和唯一约束检查仍然需要锁。

### 事务隔离级别怎么理解？

回答思路：用并发异常串起来。

回答模板：

事务隔离级别是在并发性能和一致性之间做取舍。Read Uncommitted 可能脏读；Read Committed 避免脏读，但可能不可重复读；Repeatable Read 保证同一事务内重复读取同一行结果一致，但理论上仍可能幻读；Serializable 最严格，基本串行执行，并发性能最低。隔离越强，一致性越好，但并发性能通常越差。

### 脏读、不可重复读和幻读有什么区别？

回答思路：分别对应未提交数据、同一行变化和范围结果集变化。

回答模板：

脏读是读到了其他事务还没有提交的数据；不可重复读是同一事务内两次读取同一行，结果不同；幻读是同一事务内按相同范围条件查询，两次得到的记录集合不同。可以简单记为：脏读关注未提交数据，不可重复读关注同一行变化，幻读关注范围内记录数量变化。

### 快照读和当前读有什么区别？

回答思路：从读取版本和是否加锁回答。

回答模板：

快照读根据事务的 ReadView 从版本链中选择可见历史版本，普通 SELECT 通常属于快照读，可以减少读写阻塞。当前读要求读取最新版本，并对相关记录加锁，例如 SELECT FOR UPDATE、UPDATE 和 DELETE。MVCC 主要优化快照读，涉及更新或要求读取最新数据时仍然需要锁。

### undo、redo 和 binlog 分别做什么？

回答思路：按回滚、崩溃恢复和复制区分。

回答模板：

undo log 保存修改前的信息，用于事务回滚和 MVCC 历史版本；redo log 记录页修改，用于数据库崩溃后的恢复，支撑事务持久性；binlog 记录数据库逻辑变更，主要用于主从复制和时间点恢复。三者职责不同，不能互相简单替代。

### 数据库死锁怎么排查和处理？

回答思路：等待关系、事务范围、加锁顺序和重试。

回答模板：

我会先查看死锁日志，确认参与事务、持有锁、等待锁和具体 SQL，再还原两个事务的加锁顺序。常见原因是事务按不同顺序更新相同资源、范围过大或索引缺失导致锁范围扩大。修复时优先统一加锁顺序、缩短事务、补合适索引并减少锁定范围；数据库通常会回滚其中一个事务，应用还要对死锁错误做有限重试。
