# 分布式训练通信与故障排查

## 知识点解析

### 概述

分布式训练通过多卡、多机并行扩大模型规模或提升训练吞吐，但会引入通信、负载不均、数值一致性和故障恢复问题。排查时应先判断问题属于计算、通信、数据、存储还是调度，再结合吞吐、GPU 利用率、集合通信耗时和节点日志缩小范围。

### 并行策略

| 策略 | 切分对象 | 主要通信 | 适用场景 |
| --- | --- | --- | --- |
| 数据并行 DP/DDP | 每卡完整模型，切分数据 | 梯度 All-Reduce | 模型能放入单卡 |
| ZeRO/FSDP | 参数、梯度、优化器状态 | All-Gather、Reduce-Scatter | 单卡放不下模型状态 |
| 张量并行 TP | 单层矩阵 | All-Reduce、All-Gather | 单层参数或计算过大 |
| 流水线并行 PP | 不同层 | 阶段间激活点对点通信 | 模型层数多、跨卡切层 |
| 序列并行 SP | 序列维度 | 与 TP 配套的集合通信 | 长序列激活占用高 |
| 专家并行 EP | MoE 专家 | All-to-All | 稀疏 MoE 模型 |

混合并行需要同时考虑 GPU 拓扑。高频通信的 TP 通常放在同机高速互联内，跨机更多使用 DP 或 PP，减少慢网络上的通信量。

### 常见集合通信

- All-Reduce：聚合所有 Rank 的数据并把结果返回每个 Rank，DDP 梯度同步常用。
- Reduce-Scatter：先归约再把结果分片到不同 Rank，FSDP 和 ZeRO 常用。
- All-Gather：收集各 Rank 分片并拼成完整张量。
- Broadcast：一个 Rank 向其他 Rank 分发数据。
- All-to-All：每个 Rank 向所有 Rank 发送不同分片，MoE 专家路由常用。

NCCL 是 GPU 集合通信库。通信性能取决于消息大小、拓扑、带宽、延迟和通信算法。小消息更受延迟影响，大消息更受带宽影响。

### 通信与计算重叠

DDP 在反向传播中按 Bucket 聚合梯度。当后层梯度计算完成后，可以异步启动对应 Bucket 的 All-Reduce，同时继续计算前层梯度。Bucket 太大会推迟通信开始，太小则增加通信调用开销。

常见优化手段：

- 调整 Bucket 大小。
- 使用梯度累积，降低同步频率。
- 将高频通信限制在高速互联域内。
- 使用 Reduce-Scatter 和参数预取。
- 检查是否存在隐式同步，例如频繁调用 `.item()`。

### 吞吐和显存分析

训练吞吐可用 samples/s、tokens/s 或 MFU 衡量。显存主要由以下部分组成：

```text
参数
+ 梯度
+ 优化器状态
+ 激活
+ 临时通信 Buffer
+ 框架与内核占用
```

以 Adam 混合精度训练为例，除低精度参数外，通常还要保存梯度、FP32 主参数和两份优化器状态，因此不能只按“参数量乘 2 字节”估算训练显存。激活显存随 batch、序列长度、层数和隐藏维度增长，可通过 activation checkpointing 用计算换显存。

### 常见故障

#### 训练 Hang

常见原因：

- 某个 Rank 提前异常退出，其他 Rank 等待集合通信。
- 不同 Rank 进入了不同控制分支，调用通信算子的顺序不一致。
- DataLoader 某个 Worker 卡死或数据读取阻塞。
- 网络、RDMA 或 NCCL 通信异常。
- 保存 Checkpoint 时共享存储变慢。

排查顺序：

1. 确认所有 Rank 的最后日志位置。
2. 判断卡在前向、反向、通信、数据加载还是保存阶段。
3. 检查各 Rank 是否执行相同数量的 Step 和 Collective。
4. 开启 NCCL 调试日志并检查网络接口、拓扑和超时。
5. 用小规模、单机和单卡逐级缩小问题范围。

#### 慢节点与吞吐下降

同步训练的 Step 时间由最慢 Rank 决定。慢节点可能来自 GPU 降频、数据读取慢、CPU 抢占、网络重传、负载不均或某些样本序列过长。

应比较各 Rank 的：

- DataLoader 等待时间。
- 前向、反向和优化器耗时。
- Collective 耗时。
- GPU 利用率、功耗、显存和温度。
- 输入 Token 数和 Padding 比例。

#### OOM

先区分稳定 OOM 和偶发 OOM。固定 Step OOM 通常与配置或特定长样本有关；运行一段时间后 OOM 可能来自缓存、张量引用未释放、评测结果累积或显存碎片。

处理顺序：

1. 降低 micro batch 或最大序列长度。
2. 开启 activation checkpointing。
3. 使用 FSDP/ZeRO 切分模型状态。
4. 检查是否错误保留计算图。
5. 再考虑扩卡、CPU Offload 或更低精度。

### 数值与一致性问题

- 确保所有 Rank 使用一致的模型初始化和配置。
- 分布式采样器每个 Epoch 调用 `set_epoch`，避免每轮顺序完全相同。
- 梯度累积时只在同步 Step 做 All-Reduce。
- 恢复 Checkpoint 时同步模型、优化器、调度器、随机数状态和 DataLoader 进度。
- NaN 需要检查是单 Rank 数据异常还是所有 Rank 同时出现。

### Checkpoint 与故障恢复

可靠 Checkpoint 应包含：

- 模型参数和优化器状态。
- 学习率调度器、GradScaler。
- Global Step、Epoch 和数据游标。
- Python、NumPy、CPU 与 GPU 随机数状态。
- 并行拓扑、代码版本和训练配置。

分片 Checkpoint 要记录分片元数据，并在并行度变化时完成格式转换。写入时使用临时路径，全部成功后再原子标记为可用，避免恢复到半写入文件。

## 面试应对

### 分布式训练卡住了怎么排查？

回答思路：先定位阶段和 Rank，再检查控制流、数据、通信和存储。

回答模板：

我会先对齐所有 Rank 的最后日志和 Step，判断是单个 Rank 先异常，还是大家卡在同一个 Collective。然后把一个 Step 拆成数据加载、前向、反向、通信、优化器和 Checkpoint 阶段打点。如果不同 Rank 进入了不同分支或通信调用顺序不一致，很容易造成永久等待；如果某个 Rank 明显更慢，则继续检查长样本、DataLoader、GPU 状态和网络。必要时开启 NCCL 调试日志，并从多机缩到单机、再缩到单卡复现，逐层排除通信和业务代码问题。

### 如何选择数据并行、张量并行和流水线并行？

回答思路：先判断模型能否放入单卡，再结合通信频率、拓扑和流水线气泡。

回答模板：

如果模型和优化器状态能放进单卡，我会优先用 DDP，实现简单且扩展效率通常最好；放不下模型状态时先考虑 FSDP 或 ZeRO。单层矩阵就很大时需要张量并行，但它通信频繁，适合放在同机高速互联内。模型层数很多时可以用流水线并行跨设备切层，但要控制流水线气泡。大规模训练通常是多种并行组合，选择依据是显存是否够、通信量、GPU 拓扑和目标吞吐。

### 为什么分布式训练会出现慢节点拖累全局？

回答思路：说明同步训练的屏障效应，再给出定位指标。

回答模板：

同步训练中各 Rank 在梯度通信和参数更新前需要对齐，因此一个 Rank 变慢，其他 Rank 即使提前完成也只能等待。慢节点可能来自数据读取、超长样本、GPU 降频、网络异常或负载不均。我会比较各 Rank 的数据等待、前后向、Collective 耗时和 GPU 指标，找到差异出现在哪一阶段，再针对性处理，而不是只看全局平均 GPU 利用率。
