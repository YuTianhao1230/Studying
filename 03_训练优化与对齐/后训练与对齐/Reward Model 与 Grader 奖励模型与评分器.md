# Reward Model 与 Grader 奖励模型与评分器

## 知识点解析

### 概述

Reward Model 是给模型输出打偏好分的模型；Grader 是更泛化的评分器，可以是规则、脚本、测试、人工或 LLM，用来判断输出是否满足标准。

### 二者区别

| 概念 | 主要用途 | 形态 |
| --- | --- | --- |
| Reward Model | 为强化学习或偏好优化提供奖励信号 | 通常是训练出来的模型 |
| Grader | 为评测或训练样本打分 | 可以是规则、代码、测试、LLM、人 |

Reward Model 更偏训练；Grader 更偏评测和数据生产。

### 为什么重要

大模型和 Agent 的能力提升越来越依赖“反馈信号”。

反馈信号可以来自：

- 人类偏好。
- 单元测试。
- 格式校验。
- 可验证答案。
- LLM Judge。
- 用户线上行为。
- 专家审核。

如果反馈信号质量差，训练和评测都会被带偏。

### Reward Model 常见流程

```text
Prompt
  -> 采样多个回答
  -> 人类排序
  -> 构造成 preference pair
  -> 训练 Reward Model
  -> 给新回答打分
```

常见训练目标是让被偏好的回答得分高于不被偏好的回答。

### Grader 常见类型

#### Rule-based Grader

用确定性规则打分。

适合：

- JSON 格式。
- 数学答案。
- 字段匹配。
- 单元测试。

#### LLM Grader

用大模型按 rubric 打分。

适合：

- 开放问答。
- 摘要质量。
- 解释质量。
- 安全性判断。

风险：

- 评分不稳定。
- 被待评答案诱导。
- rubric 不清导致打分漂移。

#### Execution-based Grader

通过真实执行判断结果。

适合：

- 代码题。
- Agent 工具任务。
- 前端自动化测试。
- 数据处理任务。

### 好 Grader 的标准

- 标准明确。
- 可复现。
- 能覆盖关键错误。
- 能解释扣分原因。
- 对格式和内容分别评分。
- 能区分严重错误和轻微问题。

### 常见误区

- 把 LLM Judge 当绝对真值。
- rubric 写得太抽象。
- 只评最终答案，不评过程。
- Grader 训练数据和评测数据泄漏。
- 奖励信号只优化表面格式。

## 面试应对

### Reward Model 和 Grader 有什么区别？

回答思路：从用途（训练 vs 评测）和形态（训练出来的模型 vs 各种评分器）两点对比。

回答模板：

Reward Model 是专门训练出来给模型输出打偏好分的模型，主要用途是在 RLHF/偏好优化里提供奖励信号，是训练环节的一部分。Grader 是更泛化的评分器，用来判断输出是否满足标准，形态可以是规则、脚本、单元测试、LLM Judge 或人工，更偏评测和训练数据生产。简单说 Reward Model 偏训练、通常是个模型；Grader 偏评测和数据生产、形态多样。实际项目里两者常配合：用 Grader 生产高质量偏好/评分数据，再训练 Reward Model 或直接把可执行 Grader 当作奖励信号。

### 如何设计一个 LLM Judge rubric？

回答思路：先拆评分维度，再给分档标准和校准手段。

回答模板：

先拆出评分维度，如正确性、完整性、忠实性、格式和安全性；再给每个分数档明确标准和一票否决项（比如出现事实错误直接判不合格）。最好要求 Judge 在打分时引用具体证据，而不是只给一个分数，并用一批人工标注的黄金集去校准 rubric，确认 Judge 判分和人工判断一致后再大规模使用。rubric 要尽量具体可操作，写得太抽象会导致打分漂移。

### 为什么代码任务适合 execution-based grading？

回答思路：抓住"代码有客观可执行的真值"这个本质。

回答模板：

因为代码任务有一个客观、可执行的真值：跑单元测试就能确定性地判断对不对，不需要靠模型主观判断。相比让 LLM Judge 去"看代码猜对错"，直接执行更准、更难被表面花哨的写法糊弄，也更可复现。风险在于测试覆盖不足时会漏判——模型可能只过拟合已知测试用例而没真正解决问题，所以要保证测试用例覆盖边界情况，必要时结合隐藏测试集，防止 reward hacking。

### Reward Hacking 如何发生？

回答思路：定义清楚"钻漏洞拿高分"，再举例并给排查方法。

回答模板：

Reward Hacking 指模型没有真正变好，而是学会利用奖励函数或 Reward Model 的漏洞拿高分。例如奖励模型偏好长回答，模型就输出冗长内容；单测覆盖不足，代码模型就过拟合测试用例。排查时不能只看 reward 上升，还要看人工评测、分桶指标、bad case 和护栏指标，一旦发现 reward 涨但真实质量没涨，就要怀疑是 hacking，需要补强 Grader 或加约束。

### 如何评估 Grader 本身的可靠性？

回答思路：把 Grader 当被测对象，用黄金集和一致性指标去校验。

回答模板：

我会把 Grader 当成一个被测系统来验证。首先构造一个人工标注的黄金集，拿 Grader 的判分和人工标注对齐，看准确率、和人工的一致性（比如 Cohen's Kappa）；其次做稳定性测试，同一输入多次评分看方差，对 LLM Grader 尤其要查评分漂移和被待评答案诱导的情况；再做偏差检查，比如是否有长度偏见、是否只看最终答案不看过程。还要防止 Grader 训练/校准数据和评测数据泄漏。只有 Grader 本身可靠，它产出的奖励或评测信号才可信。
