# MLOps与模型生产化

## 知识点解析

### 概述

MLOps 是把模型从实验室带到生产环境的一整套工程体系，覆盖数据、训练、评测、部署、监控、回滚和持续迭代。

### 为什么大厂 JD 重视 MLOps

模型效果只是上线前的一部分。真实业务还关心：

- 能否稳定训练。
- 能否复现结果。
- 能否安全上线。
- 能否监控质量下降。
- 能否快速回滚。
- 能否解释指标变化。

大厂算法工程师常常不是只训练模型，而是要负责模型生命周期。

### 标准链路

```text
数据采集
  -> 数据清洗
  -> 数据版本
  -> 训练实验
  -> 模型评测
  -> 模型注册
  -> 灰度发布
  -> 线上监控
  -> A/B 测试
  -> 回滚 / 放量 / 迭代
```

### 核心模块

#### 数据版本

记录训练数据来源、过滤规则、采样策略和时间范围。

否则模型效果变化时无法判断是模型变了，还是数据变了。

#### 实验追踪

记录：

- 代码 commit。
- 数据版本。
- 模型配置。
- 超参数。
- 随机种子。
- 指标曲线。
- checkpoint。

#### 模型注册

模型上线前需要注册元信息：

- 模型版本。
- 训练配置。
- 评测结果。
- 适用场景。
- 依赖资源。
- 回滚版本。

#### 灰度与回滚

不能直接全量上线。

常见方式：

- 小流量灰度。
- 按用户分桶。
- 按地域 / 业务线灰度。
- 监控护栏指标。
- 异常自动回滚或人工回滚。

#### 线上监控

关注：

- 输入分布变化。
- 特征缺失。
- 模型输出分布。
- 业务指标。
- 延迟和错误率。
- 资源使用。

### 常见 Drift

- Data Drift：输入数据分布变了。
- Feature Drift：特征分布变了。
- Concept Drift：输入和标签之间的关系变了。
- Training-Serving Skew：训练和线上特征处理不一致。

### 面试回答框架

如果被问“如何把模型上线”，可以这样回答：

```text
我会先固定数据版本、代码版本和训练配置，保证实验可复现。
然后在离线评测和回归集上验证模型效果，并保存 bad case。
上线时通过模型注册、灰度发布和 A/B 测试控制风险。
线上持续监控业务指标、模型输出分布、特征漂移、延迟和错误率。
如果护栏指标异常，先回滚，再基于日志和 bad case 做归因。
```

### 常见误区

- 只保存模型文件，不保存数据和代码版本。
- 只看离线指标，不做线上监控。
- 没有灰度和回滚。
- 没有训练-serving 一致性检查。
- 线上指标异常时无法定位数据、模型还是系统问题。

## 面试应对

### MLOps 要解决的核心问题是什么？

回答思路：从可复现、可发布、可观测和可回滚四个目标定义，不只罗列工具。

回答模板：

MLOps 是对数据、代码、训练、评测、模型发布和线上运行进行生命周期管理的工程体系。它要保证一次实验能由明确的数据版本、代码 Commit、配置和随机种子复现；通过模型注册、自动检查和灰度发布安全上线；通过质量、数据和系统指标发现退化；出现问题时能定位影响版本并快速回滚。核心不是堆工具，而是建立可追溯、可验证的交付闭环。

### 一个模型从训练完成到全量上线要经过哪些步骤？

回答思路：按产物注册、离线门禁、部署验证、灰度观察和放量回滚顺序回答。

回答模板：

训练完成后，我会先注册模型及其数据、代码、配置和评测结果，再执行离线质量、性能、安全和兼容性门禁。部署到预发环境后做接口、资源和回归验证，然后按用户或流量分桶灰度，持续观察业务指标、模型质量、延迟、错误率和资源护栏。指标满足放量条件才逐步扩大流量；任何关键护栏越界都应停止放量或自动回滚到已验证版本。

### 如何区分 Data Drift、Concept Drift 和 Training-Serving Skew？

回答思路：分别说明输入分布、条件关系和处理链不一致，并给出对应证据。

回答模板：

Data Drift 是线上输入或特征分布相对训练期发生变化；Concept Drift 是相同输入与目标标签之间的关系发生变化；Training-Serving Skew 则是训练和线上使用了不同的特征计算、预处理或依赖版本。前两类需要结合分布统计和延迟标签判断，后一类可以通过同样本离在线特征对账定位。三者的修复方式不同，不能只看到线上指标下降就直接重训。

### 线上模型指标突然下降时如何止损和定位？

回答思路：先保护业务，再沿版本、数据、系统和模型四条证据链排查。

回答模板：

我会先确认告警口径和影响范围，必要时停止放量、切回稳定版本或启用降级，先控制业务损失。随后按时间线核对模型、数据、特征、Prompt、代码和依赖是否变更，并分层检查输入分布、特征缺失、输出分布、错误率、延迟和资源指标。通过样本回放和版本对照判断问题来自数据漂移、训练服务偏差、模型质量还是系统故障。修复后要在回归集和小流量灰度中验证，并把触发条件沉淀为自动门禁或监控。
