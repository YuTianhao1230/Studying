# AI系统设计

## 知识点解析

### 概述

AI 系统设计关注如何把模型能力变成稳定、可扩展、可观测且成本可控的线上系统。答题时既要描述数据、模型和服务链路，也要给出流量、延迟、吞吐、容量、一致性、安全和故障恢复约束，并解释每个技术选择解决了什么问题。

#### 高频问题

1. 设计一个模型评测平台，你会如何拆模块？
2. 设计一个 [RAG](<../../02_大模型/应用与问题/RAG.md>) 问答系统，需要哪些组件？
3. 设计一个多[模型路由](<模型路由.md>)系统，如何选择模型？
4. 设计一个 [Agent](<../../08_Agent/基础概念/Agent.md>) 系统，如何管理工具、状态、记忆和错误恢复？
5. 设计一个在线推荐/排序系统，训练、[召回](<../../09_搜索推荐广告/召回粗排精排重排.md>)、排序、重排如何衔接？
6. 设计一个图片/视频理解系统，数据、模型、推理和评测如何组织？
7. 如何设计离线训练到线上部署的 MLOps 流程？
8. 如何保证模型版本、数据版本、prompt 版本可追溯？
9. 如何做灰度发布和回滚？
10. 如何设计监控指标，发现模型效果退化？
11. 如何在成本、延迟、效果之间做 tradeoff？
12. 系统出现线上事故时，你如何定位和止损？

### 核心知识点

- 系统分层：数据层、训练层、评测层、服务层、监控层、治理层。
- 评测平台：任务管理、样本管理、模型接入、指标计算、结果存储、case 分析、报表。
- RAG 系统：文档解析、切片、embedding、向量库、召回、rerank、生成、引用、反馈闭环。
- Agent 系统：planner、executor、tool registry、memory、state machine、guardrail、trace。
- [MLOps](<MLOps与模型生产化.md>)：数据版本、模型注册、实验追踪、CI/CD、灰度、回滚和持续迭代。
- [Serving](<../推理工程/Serving.md>) 可观测性：日志、指标、trace、样本回放、错误分类和告警。
- 成本优化：模型分层、缓存、路由、小模型优先、批处理、异步任务。
- 可靠性：幂等、重试、超时、限流、降级、隔离、权限控制。

模型路由的专项说明见 [模型路由.md](<模型路由.md>)；召回、粗排、精排和重排的专项说明见 [召回粗排精排重排.md](<../../09_搜索推荐广告/召回粗排精排重排.md>)。

#### 回答要点

- 系统设计题要先明确目标、流量、延迟、准确率、成本、数据规模和可靠性要求。
- 评测平台的核心不是只算分，而是保证可复现、可对比、可定位、可追溯。
- RAG 的效果瓶颈通常来自知识解析质量、召回覆盖率、排序准确性和上下文组织。
- Agent 系统必须重视状态管理和失败恢复，否则多步任务会在工具异常、格式错误、上下文膨胀时失控。
- 灰度发布要有明确监控指标、回滚条件和版本隔离，不能只看平均效果。

### 通用答题框架

系统设计题可以按以下顺序展开：

```text
需求与边界
  -> 容量估算与 SLO
  -> 核心数据流
  -> 模块和接口
  -> 存储与一致性
  -> 扩展性与成本
  -> 可靠性与安全
  -> 可观测性与回滚
```

容量估算至少应明确峰值 QPS、平均输入输出长度、单实例吞吐、目标 p99、并发数、GPU 数量和缓存命中率。粗略实例数可以表示为：

$$
\text{实例数}\ge
\frac{\text{峰值请求速率}}{\text{单实例稳定吞吐}}
\times\text{冗余系数}.
$$

估算不要求数字绝对准确，但必须说明假设，并预留突发流量和故障容量。

### 服务接口与基础设施

- REST 适合通用请求响应和外部接口；gRPC 适合内部高性能、强类型服务通信。
- 负载均衡根据实例健康状态、并发数或预计 Token 成本分发请求，不能只做简单轮询。
- Kubernetes 负责容器编排、服务发现、滚动发布、自动扩缩容和故障重建；模型服务还需要结合 GPU 拓扑、显存和模型加载时间设置调度策略。
- 队列用于削峰和异步任务，但实时请求不能无限排队，应设置超时、最大队列长度和拒绝策略。
- 限流保护系统容量，熔断阻止故障依赖持续拖垮主链路，降级保证核心功能仍然可用。

### 案例：RAG 问答系统

#### 需求

支持企业知识问答，回答必须带引用，用户只能访问有权限的文档，目标 p95 小于 3 秒。

#### 离线链路

```text
文档接入
  -> 解析与清洗
  -> 按语义和结构切片
  -> 元数据与权限标注
  -> Embedding
  -> 向量索引和关键词索引
  -> 版本化发布
```

#### 在线链路

```text
鉴权
  -> Query 改写
  -> 混合召回
  -> 权限过滤
  -> Rerank
  -> 上下文组织
  -> LLM 生成
  -> 引用校验
  -> 结果返回
```

关键指标包括 Recall@K、重排 NDCG、答案正确率、引用支持率、拒答准确率、p95/p99 和单请求成本。出现错误答案时，应逐层判断是解析、召回、排序、上下文还是生成问题。

### 案例：模型评测平台

平台由任务管理、数据集版本、模型适配器、执行队列、指标计算、结果存储和案例分析组成。任务配置必须记录代码版本、模型版本、Prompt、解码参数、数据版本和随机种子。

执行层使用队列分发任务，Worker 定期写入进度和心跳；单个 case 的结果幂等落盘，支持失败重试和断点续跑。大任务按 case 分片，避免单 Worker 失败导致整批重跑。平台还需要支持：

- 并发和配额控制，避免评测任务打满模型服务。
- 超时、重试和错误分类，区分模型错误、平台错误与外部依赖错误。
- 多版本结果对齐和 diff case。
- 指标置信区间、分桶结果和回归阈值。
- 任务、数据与结果的权限隔离。

### 案例：高并发 LLM 推理服务

该场景在系统设计总览中重点关注组件边界和容量权衡：

- 网关与路由层负责鉴权、准入、流量隔离和模型选择，不承担 GPU 执行。
- 调度层负责队列、优先级与批处理，把请求映射到可用推理容量。
- 推理运行时负责模型执行和 [KV Cache](<../推理工程/KV_Cache与Prefill_Decode.md>)，不承担业务权限判断。
- 配置与状态层管理模型、Prompt、Tokenizer 和路由版本，避免实例间版本漂移。

完整请求流、服务监控和过载治理见 [Serving](<../推理工程/Serving.md>)；批处理与缓存的机制细节分别见 [Batching](<../推理工程/Batching.md>) 和 [KV Cache 与 Prefill/Decode](<../推理工程/KV_Cache与Prefill_Decode.md>)。

容量规划需要区分 Prefill 和 Decode：

- Prefill 更偏计算密集，主要受输入长度和算力影响。
- Decode 更偏显存带宽和 KV Cache，主要受并发数和输出长度影响。

因此不能只按 QPS 估算 GPU，还要结合输入输出 Token 分布、TTFT/TPOT SLO 和并发缓存规模。系统应限制最大上下文和最大输出 Token，避免少量超长请求占满显存；高优请求可使用独立队列或预留容量，过载时在切换小模型、缩短上下文、关闭非核心工具、转异步任务和限制输出长度之间按业务损失选择。

### 可观测性边界

系统设计总览只确定观测责任边界：每个组件都要输出 Metrics、Logs 和 Traces，并统一携带请求 ID、模型与配置版本，以区分网关、检索、模型、工具和存储故障。系统指标与模型质量指标必须分开建模，因为“服务无报错”不代表“模型效果正常”。

LLM 服务的指标、日志、Trace 与排障方法见 [Serving](<../推理工程/Serving.md>)；模型质量、数据漂移和生产生命周期监控见 [MLOps 与模型生产化](<MLOps与模型生产化.md>)。

### 故障域与发布边界

设计时应把网关与路由、检索与外部工具、推理集群、状态存储划为独立故障域，分别设置容量上限、超时、隔离和降级边界，避免单个慢依赖、异常模型版本或重试风暴扩散到整条链路。跨域状态必须保留模型、Prompt、Tokenizer、特征和索引版本的对应关系，才能判断影响范围并恢复一致状态。

请求级止损与服务排障见 [Serving](<../推理工程/Serving.md>)；部署门禁、灰度、版本放量和回滚流程见 [MLOps 与模型生产化](<MLOps与模型生产化.md>)。

### 常见追问

- 如何设计评测任务的断点续跑？
- 如何支持多个模型服务供应商？

- Agent 工具调用死循环怎么处理？

## 面试应对

### AI 系统设计题应该怎么开始？

回答思路：先澄清约束并估算容量，再进入架构，避免直接罗列组件。

回答模板：

我会先明确用户场景、输入输出、峰值 QPS、目标延迟、准确率、成本和可用性要求，再估算单实例吞吐和所需容量。架构上按数据、模型、服务、存储和治理拆分，明确同步与异步边界、状态归属和故障域。随后重点讨论瓶颈、扩容方式、版本一致性和降级选择；具体请求流与服务观测落到 [Serving](<../推理工程/Serving.md>)，灰度和回滚落到 [MLOps 与模型生产化](<MLOps与模型生产化.md>)。

### 如何设计一个高并发 LLM 推理服务？

回答思路：围绕路由、调度、Prefill/Decode、KV Cache、容量和降级回答。

回答模板：

我会先明确峰值 QPS、输入输出长度分布、TTFT/TPOT、可用性和成本上限，再把系统拆成网关路由、调度、推理运行时与配置状态层。容量要分别估算 Prefill 算力和 Decode 带宽、KV Cache，并给超长请求和高优流量设置独立边界，避免局部过载扩散。扩容或降级选择要同时满足 p99 与质量要求；具体请求流、监控和过载治理见 [Serving](<../推理工程/Serving.md>)，灰度回滚见 [MLOps 与模型生产化](<MLOps与模型生产化.md>)。

### 如何设计一个可追溯的模型评测平台？

回答思路：从版本化、任务执行、幂等落盘、指标计算和 Case 分析形成闭环。

回答模板：

我会把平台拆成数据集版本、模型适配器、任务编排、执行 Worker、结果存储、指标计算和 Case 分析。每次任务固定代码、数据、模型、Prompt、解码参数和随机种子；大任务按 Case 分片，结果以稳定主键幂等落盘，并通过心跳、超时和有限重试支持断点续跑。结果层既保存汇总指标，也保留逐 Case 输出、错误类型和耗时，便于版本对比、置信区间计算和回归定位。权限、并发配额和审计日志则保证平台可控运行。

### RAG 系统回答错误时如何分层定位？

回答思路：沿解析、召回、权限过滤、重排、上下文和生成逐层检查证据。

回答模板：

我会先固定请求、索引版本、Prompt 和模型版本，再看正确证据是否被解析并进入索引。如果证据不在候选集，问题在解析、切片、Embedding 或召回；候选中有但排序靠后，要检查 Rerank；证据已进入上下文却答错，再看上下文组织、Prompt 和生成。还要单独验证权限过滤与引用支持率，避免越权内容被召回或答案没有证据支撑。分层指标应同时包含 Recall@K、NDCG、答案正确率、引用支持率和拒答准确率。

### 线上 AI 系统发生故障时如何止损？

回答思路：按发现、隔离、降级、回滚、定位和复盘回答，先恢复服务再查根因。

回答模板：

我会先按网关与路由、检索与工具、推理集群、状态存储划分影响范围，隔离故障域并阻止重试或流量继续扩散。随后核对模型、Prompt、Tokenizer、特征和索引版本，判断是容量耗尽、依赖故障还是版本不一致。请求级止损和 Trace 排障见 [Serving](<../推理工程/Serving.md>)，修复后的门禁、灰度和回滚见 [MLOps 与模型生产化](<MLOps与模型生产化.md>)。
