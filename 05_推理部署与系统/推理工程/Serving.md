# Serving

## 知识点解析

### 概述

Serving 是把模型能力部署成可被业务稳定调用的在线服务，包括接口、扩缩容、监控、限流、灰度、回滚和故障处理。

### Serving 和推理有什么区别

推理是模型计算：

```text
输入 -> 模型 -> 输出
```

Serving 是线上服务系统：

```text
用户请求
  -> 网关
  -> 权限 / 限流
  -> 模型服务
  -> 监控 / 日志
  -> 返回结果
```

推理关注模型怎么算，Serving 关注服务怎么稳定地对外提供能力。

### Serving 系统通常包括什么

- API Server：HTTP、gRPC、OpenAI-compatible API。
- Model Runtime：vLLM、TensorRT-LLM、xLLM 等推理运行时。
- Scheduler：请求调度和 batching。
- Load Balancer：负载均衡。
- Autoscaler：自动扩缩容。
- Monitor：延迟、吞吐、错误率、GPU 使用率监控。
- Logger：请求、响应、错误、trace。
- Config Manager：模型版本、参数、灰度配置。
- Guardrail：输入输出安全检查。

### 关键指标

- 可用性：服务是否稳定可调用。
- 延迟：P50、P95、P99。
- 吞吐：QPS、tokens/s。
- 成本：单请求成本、GPU 利用率。
- 质量：模型回答准确率、格式正确率、用户满意度。
- 稳定性：超时率、失败率、重试率。

### 常见线上问题

- 请求排队导致 P99 延迟升高。
- KV cache 占满导致 OOM。
- 上游请求量突增导致超时。
- 模型版本不一致导致输出异常。
- tokenizer 或 prompt 模板版本不匹配。
- 输出解析失败。
- 服务重启后冷启动耗时过长。

## 面试应对

### 模型 Serving 系统怎么设计？

回答思路：先讲清 Serving 和裸推理的区别，再按请求链路把核心模块串起来。

回答模板：

推理只关心"输入过模型出输出"，Serving 关心的是怎么把这个能力稳定地对外提供。我会按请求链路来设计：前面是 API Server（HTTP/gRPC 或 OpenAI 兼容接口）接收请求，经过网关做鉴权和限流；核心是 Model Runtime（比如 vLLM、TensorRT-LLM）加上 Scheduler 做请求调度和 batching；外围有 Load Balancer 和 Autoscaler 做负载均衡与自动扩缩容，Monitor、Logger 做延迟/吞吐/错误率监控和 trace，Config Manager 管模型版本和灰度配置，再加 Guardrail 做输入输出安全检查。目标是在满足延迟 SLA 的前提下，把吞吐和成本做到最优、并保证可灰度、可回滚。

### 推理服务如何做限流和降级？

回答思路：从保护 GPU 资源出发，给出限流手段和降级策略。

回答模板：

限流是为了保护后端 GPU 资源不被突增流量打爆导致雪崩。常见做法是在网关层按 QPS 或并发数做限流、用优先级队列区分核心和非核心业务，再用 token budget 控制单位时间处理的总 token 量。降级则是在压力过大时主动牺牲部分体验保可用：比如缩短最大生成长度、关掉部分昂贵功能、把请求路由到更小的备用模型，或者对超出容量的请求直接返回排队/拒绝而不是让所有请求一起超时。核心原则是宁可让部分请求优雅降级，也不要整个服务被拖垮。

### 如何监控一个 LLM 服务？

回答思路：按可用性/延迟/吞吐/成本/质量/稳定性几组指标铺开。

回答模板：

我会分几组指标来监控。基础的是可用性和稳定性：服务是否可调、超时率、失败率、重试率；性能上看延迟的 P50/P95/P99 和吞吐 QPS、tokens/s；成本上看单请求成本和 GPU 利用率。LLM 特有的是质量指标：回答准确率、格式正确率、用户满意度，这些通常靠采样离线评估或 LLM Judge 补充。除了打点还要有请求/响应/错误的日志和 trace，方便出问题时快速定位。最后针对常见故障（P99 抖动、KV cache OOM、上游突增、版本不一致）设置告警阈值。

### P99 延迟突然升高怎么排查？

回答思路：先确认现象真实性，再从排队、显存、上游流量、版本几个高频原因分层定位。

回答模板：

我先确认是全局升高还是某些请求长尾拉高，排除监控口径问题。然后分层查：最常见是请求排队，看是不是流量突增或 batch 调度导致排队变长；其次看显存，KV cache 占满会触发抢占或 OOM，让延迟飙升；再看上游是不是有超长 prompt 或输出长度异常的请求拖慢整批；还要确认最近有没有发版，模型版本、tokenizer 或 prompt 模板不匹配也可能导致重算或解析失败。定位后对应处理：扩容、调 batch 参数、限制最大长度或回滚版本。

### 如何做模型灰度发布和回滚？

回答思路：讲清小流量验证—逐步放量—异常回滚的闭环。

回答模板：

我会用 Config Manager 管理模型版本，先把新版本部署成独立实例，只切一小部分流量（比如 1%~5%）做灰度，同时对齐新老版本的延迟、错误率和质量指标（准确率、格式正确率、bad case）。指标正常就逐步放量到 100%，任何一项关键指标劣化就立刻把流量切回老版本回滚。关键是老版本在灰度期间保持在线、可秒级切回，并且发布过程要保证 tokenizer 和 prompt 模板版本随模型一起切换，避免版本错配导致输出异常。
