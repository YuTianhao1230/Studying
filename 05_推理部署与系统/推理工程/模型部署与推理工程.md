# 模型部署与推理工程

## 知识点解析

### 概述

模型部署与推理工程关注如何把离线模型转换成稳定、低延迟且成本可控的线上服务。核心包括模型导出与加载、请求调度、[Batching](<Batching.md>)、[KV Cache](<KV_Cache与Prefill_Decode.md>)、[量化](<量化.md>)、并行推理、容量规划、灰度发布、监控和故障恢复，并需要在效果、吞吐、延迟与成本之间做明确取舍。

#### 高频问题

1. 训练和推理有什么差异？为什么推理工程是独立问题？
2. 大模型推理延迟由哪些部分构成？
3. Prefill 和 Decode 阶段有什么区别？
4. KV cache 是什么？它如何影响显存和吞吐？
5. Batch、Dynamic Batching、Continuous Batching 分别是什么？
6. TensorRT、[vLLM](<vLLM.md>)、TensorRT-LLM、xLLM 一类推理框架通常解决什么问题？
7. 量化有哪些方式？INT8、INT4、FP8 的收益和风险是什么？
8. 如何评估推理服务的性能？QPS、吞吐、P50/P95/P99、TTFT、TPOT 分别是什么？
9. 线上服务如何做限流、重试、超时、降级？
10. 模型输出需要结构化解析时，如何提升稳定性？
11. 多模态推理中图片/视频预处理会带来哪些性能和一致性问题？
12. 如何定位线上模型服务偶发失败？

### 核心知识点

- 推理阶段：请求接入、预处理、tokenize、prefill、decode、postprocess。
- 性能指标：QPS、吞吐、并发、延迟分位数、TTFT、TPOT、显存占用、GPU 利用率。
- [Serving](<Serving.md>) 技术：动态批处理、连续批处理、PagedAttention、KV cache 管理、speculative decoding。
- 压缩加速：量化、蒸馏、剪枝、[算子](<算子.md>)融合、FlashAttention、CUDA Graph。
- 稳定性：超时、重试、幂等、限流、熔断、降级、灰度、监控告警。
- 结构化输出：JSON schema、正则校验、约束解码、重试修复、parser 容错。
- 多模态推理：图像 resize、patch/token 数、视频抽帧、FPS、分辨率、输入顺序。

#### 回答要点

- Prefill 处理完整上下文，计算量大但可并行；Decode 每次生成一个 token，强依赖 KV cache。
- KV cache 用空间换时间，避免重复计算历史 token 的 K/V，但会随 batch 和序列长度增加显存压力。
- TTFT 衡量首 token 延迟，TPOT 衡量后续 token 生成速度，二者对应不同优化方向。
- 量化能降低显存和提升吞吐，但可能损害精度，尤其对小模型、长尾能力和数值敏感任务影响更明显。
- 线上推理问题需要保留 request、response、参数、模型版本、错误码、耗时分解，才能复现和定位。

## 面试应对

### 大模型推理延迟由哪些部分组成？

回答思路：按请求链路拆分，并区分 TTFT 和 TPOT。

回答模板：

端到端延迟包括排队、预处理和 Tokenize、Prefill、逐 Token Decode、后处理以及网络传输。TTFT 主要受排队、输入长度和 Prefill 影响，TPOT 主要受 Decode 阶段的显存带宽、KV Cache 和并发调度影响。排查时我会记录各阶段耗时和输入输出 Token 数，而不是只看一个总延迟。

### 如何评估和优化推理服务？

回答思路：同时覆盖质量、延迟、吞吐、显存、成本和稳定性。

回答模板：

我会在固定模型、硬件和请求分布下测量 TTFT、TPOT、p50/p95/p99、Token 吞吐、并发、显存和错误率，并按输入输出长度分桶。优化时先定位瓶颈，再选择 Continuous Batching、KV Cache 管理、量化、算子融合或并行策略。所有性能优化都要重新验证任务质量和长尾请求，不能只报告峰值吞吐。

### 结构化输出失败率高怎么处理？

回答思路：从提示、约束解码、校验、重试和模型能力分层回答。

回答模板：

我会先统计失败类型，区分语法错误、字段缺失、类型错误和内容不合法。输入侧提供清晰 Schema 和少量示例，生成侧优先使用 Function Calling 或约束解码，输出后做严格校验。可修复错误使用有限重试或解析修复，不可修复错误返回明确失败。还要保存模型、Prompt 和解析器版本，避免把后处理问题误判成模型能力问题。
