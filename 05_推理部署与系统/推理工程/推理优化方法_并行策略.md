# 推理优化方法_并行策略

## 知识点解析

### 概述

推理优化是为了在保证效果的前提下，让模型推理更快、更省显存、更稳定；并行策略是把模型、数据或计算拆到多张 GPU / 多台机器上执行。

### 推理优化主要优化什么

核心目标通常有三个：

- 降低延迟：用户更快拿到结果。
- 提升吞吐：单位时间处理更多请求或 token。
- 降低成本：使用更少 GPU、显存和机器资源。

常见指标：

- TTFT：首 token 延迟。
- TPOT：每个输出 token 的生成时间。
- QPS：每秒请求数。
- Throughput：每秒处理 token 数。
- GPU 利用率。
- 显存占用。
- 错误率和超时率。

### 大模型推理的两个阶段

```text
输入 prompt
  -> Prefill：一次性处理输入上下文
  -> Decode：逐 token 生成输出
```

Prefill：

- 处理完整输入。
- 计算量大，但并行度较高。
- 输入越长，prefill 越慢。

Decode：

- 每次生成一个 token。
- 强依赖 [KV cache](<KV_Cache与Prefill_Decode.md>)。
- 容易受访存和调度影响。

### 常见推理优化方法

#### Batching

[Batching](<Batching.md>) 通过合并请求提高 GPU 利用率与吞吐，静态、动态、Continuous Batching 及长度分桶的机制与取舍见专题卡。

#### KV Cache

[KV Cache 与 Prefill/Decode](<KV_Cache与Prefill_Decode.md>) 用显存换取历史 Key/Value 的复用，承担降低自回归重复计算的角色，容量估算与分页管理见专题卡。

#### FlashAttention

优化 [Attention](<../../02_大模型/基础架构/Self-Attention.md>) 的计算和显存访问。

核心价值：

- 减少中间 attention matrix 的显存占用。
- 提升 GPU 访存效率。

#### 算子与算子融合

[算子与算子融合](<算子.md>) 从 Kernel Launch 和中间 Tensor 读写侧优化执行效率，具体融合机制、收益边界与慢算子定位见专题卡。

#### 量化

[量化](<量化.md>) 通过降低权重或激活精度换取显存、带宽和吞吐收益，精度类型、方案选择与质量风险见专题卡。

#### Speculative Decoding

[Speculative Decoding](<Speculative_Decoding.md>) 通过草拟与验证减少目标模型的串行 Decode 步数，适用条件、严格采样机制与收益评估见专题卡。

#### Prompt / Context 优化

减少输入 token 数也能直接优化推理成本。

方法：

- 压缩 prompt。
- 删除无用上下文。
- [RAG](<../../02_大模型/应用与问题/RAG.md>) 只放高相关片段。
- 控制 max_tokens。

### 并行策略

#### Data Parallelism，数据并行

多张 GPU 各自处理不同请求或不同 batch。

```text
GPU0: request batch A
GPU1: request batch B
GPU2: request batch C
```

特点：

- 模型在每张卡上都有完整副本。
- 实现简单。
- 适合模型能完整放进单卡的场景。

限制：

- 如果单卡放不下模型，就不能只靠数据并行。

#### Tensor Parallelism，张量并行

把单层里的大矩阵计算拆到多张 GPU。

例如一个 Linear 层权重很大，可以按列或按行切分：

```text
W = [W0, W1, W2, W3]
GPU0 算 W0
GPU1 算 W1
GPU2 算 W2
GPU3 算 W3
```

特点：

- 适合单卡放不下模型或单层计算太大的场景。
- 每层都可能需要通信。

限制：

- 通信开销高。
- 对网络带宽和拓扑敏感。

#### Pipeline Parallelism，流水线并行

把模型不同层放在不同 GPU 上。

```text
GPU0: Layer 0-7
GPU1: Layer 8-15
GPU2: Layer 16-23
GPU3: Layer 24-31
```

特点：

- 适合层数很多、模型很大的场景。
- 每个 micro-batch 像流水线一样经过不同 GPU。

限制：

- 有 pipeline bubble，GPU 可能等待。
- 推理场景下 decode 逐 token 生成，流水线调度更复杂。

#### Sequence Parallelism，序列并行

把序列长度维度拆到不同 GPU 上。

适合：

- 长上下文训练或推理。
- attention 或 norm 在序列维度上占用较大。

限制：

- 实现复杂。
- 通信模式要求高。

#### Expert Parallelism，专家并行

主要用于 [MoE](<../../02_大模型/基础架构/MoE.md>) 模型，把不同专家放到不同 GPU。

```text
Router
  -> Expert 1 on GPU0
  -> Expert 2 on GPU1
  -> Expert 3 on GPU2
```

特点：

- 每个 token 只激活部分专家。
- 可以扩大模型总参数量，同时控制每次计算量。

限制：

- token 分发会产生 all-to-all 通信。
- 负载不均衡会影响吞吐。

### 训练并行和推理并行的差异

训练并行：

- 需要前向、反向、梯度同步。
- 还要处理优化器状态和激活保存。

推理并行：

- 只做前向。
- 更关注 KV cache、请求调度、decode 延迟和服务稳定性。

## 面试应对

### 推理时如何选择数据并行、张量并行和流水线并行？

回答思路：先判断单卡能否放下模型，再按吞吐、单请求延迟、通信和拓扑选择。

回答模板：

如果模型能放进单卡且目标是提高总吞吐，我优先做数据并行，多副本独立处理请求，通信最少。如果单卡放不下，通常先在高速互联节点内使用张量并行，把每层矩阵计算切到多卡，但每层都需要集合通信。流水线并行按层切分，适合模型更大或跨节点部署，不过在线小 Batch 下容易产生流水线 Bubble。实际选择还要结合 GPU 拓扑、KV Cache、并发和延迟 SLO。

### Prefill 和 Decode 应分别优先优化什么？

回答思路：Prefill 侧重计算和长序列 Attention，Decode 侧重带宽、KV Cache 和调度。

回答模板：

Prefill 一次处理大量输入 Token，通常优先关注计算吞吐、FlashAttention、长序列切分和 Chunked Prefill，以降低 TTFT。Decode 每步只处理一个新 Token，更容易受权重与 KV Cache 读取、Batch 调度和串行依赖限制，因此优先考虑 Continuous Batching、Paged KV Cache、量化和 Speculative Decoding。优化前应分别测 TTFT 与 TPOT，避免用同一种手段处理两个不同瓶颈。

### 为什么增加 GPU 数量不一定降低推理延迟？

回答思路：说明计算切分收益会被集合通信、同步、流水线空泡和小负载利用率抵消。

回答模板：

模型并行虽然减少了单卡计算和显存压力，但会引入 All-Reduce、All-to-All、跨阶段传输和同步等待。小 Batch 或短序列下，每卡计算量不足，通信和 Kernel Launch 可能反而占主导；流水线并行还会有 Bubble，专家并行会受负载不均影响。因此扩卡前要看计算通信比和互联拓扑，扩卡后按相同请求分布比较 p99、吞吐和单 Token 成本。

### 训练并行和推理并行的关注点有什么不同？

回答思路：对比计算阶段、内存构成、通信目标和核心指标。

回答模板：

训练包含前向、反向和优化器更新，显存重点是参数、梯度、优化器状态和激活，核心指标通常是每秒训练 Token 与扩展效率。推理只有前向，但自回归 Decode 引入不断增长的 KV Cache 和在线请求调度，核心指标变成 TTFT、TPOT、吞吐、尾延迟和成本。因此训练中合适的并行切分不能直接照搬到推理，推理还要结合请求长度分布和服务 SLO 重新选择。
