# AI系统设计

## 知识点解析

### 概述

AI 系统设计关注如何把模型能力变成稳定、可扩展、可观测且成本可控的线上系统。答题时既要描述数据、模型和服务链路，也要给出流量、延迟、吞吐、容量、一致性、安全和故障恢复约束，并解释每个技术选择解决了什么问题。

#### 高频问题

1. 设计一个模型评测平台，你会如何拆模块？
2. 设计一个 RAG 问答系统，需要哪些组件？
3. 设计一个多模型路由系统，如何选择模型？
4. 设计一个 Agent 系统，如何管理工具、状态、记忆和错误恢复？
5. 设计一个在线推荐/排序系统，训练、召回、排序、重排如何衔接？
6. 设计一个图片/视频理解系统，数据、模型、推理和评测如何组织？
7. 如何设计离线训练到线上部署的 MLOps 流程？
8. 如何保证模型版本、数据版本、prompt 版本可追溯？
9. 如何做灰度发布和回滚？
10. 如何设计监控指标，发现模型效果退化？
11. 如何在成本、延迟、效果之间做 tradeoff？
12. 系统出现线上事故时，你如何定位和止损？

### 核心知识点

- 系统分层：数据层、训练层、评测层、服务层、监控层、治理层。
- 评测平台：任务管理、样本管理、模型接入、指标计算、结果存储、case 分析、报表。
- RAG 系统：文档解析、切片、embedding、向量库、召回、rerank、生成、引用、反馈闭环。
- Agent 系统：planner、executor、tool registry、memory、state machine、guardrail、trace。
- MLOps：数据版本、模型注册、实验追踪、CI/CD、灰度、回滚、线上监控。
- 可观测性：日志、指标、trace、样本回放、错误分类、告警。
- 成本优化：模型分层、缓存、路由、小模型优先、批处理、异步任务。
- 可靠性：幂等、重试、超时、限流、降级、隔离、权限控制。

#### 回答要点

- 系统设计题要先明确目标、流量、延迟、准确率、成本、数据规模和可靠性要求。
- 评测平台的核心不是只算分，而是保证可复现、可对比、可定位、可追溯。
- RAG 的效果瓶颈通常来自知识解析质量、召回覆盖率、排序准确性和上下文组织。
- Agent 系统必须重视状态管理和失败恢复，否则多步任务会在工具异常、格式错误、上下文膨胀时失控。
- 灰度发布要有明确监控指标、回滚条件和版本隔离，不能只看平均效果。

### 通用答题框架

系统设计题可以按以下顺序展开：

```text
需求与边界
  -> 容量估算与 SLO
  -> 核心数据流
  -> 模块和接口
  -> 存储与一致性
  -> 扩展性与成本
  -> 可靠性与安全
  -> 可观测性与回滚
```

容量估算至少应明确峰值 QPS、平均输入输出长度、单实例吞吐、目标 p99、并发数、GPU 数量和缓存命中率。粗略实例数可以表示为：

```text
实例数 >= 峰值请求速率 / 单实例稳定吞吐 * 冗余系数
```

估算不要求数字绝对准确，但必须说明假设，并预留突发流量和故障容量。

### 服务接口与基础设施

- REST 适合通用请求响应和外部接口；gRPC 适合内部高性能、强类型服务通信。
- 负载均衡根据实例健康状态、并发数或预计 Token 成本分发请求，不能只做简单轮询。
- Kubernetes 负责容器编排、服务发现、滚动发布、自动扩缩容和故障重建；模型服务还需要结合 GPU 拓扑、显存和模型加载时间设置调度策略。
- 队列用于削峰和异步任务，但实时请求不能无限排队，应设置超时、最大队列长度和拒绝策略。
- 限流保护系统容量，熔断阻止故障依赖持续拖垮主链路，降级保证核心功能仍然可用。

### 案例：RAG 问答系统

#### 需求

支持企业知识问答，回答必须带引用，用户只能访问有权限的文档，目标 p95 小于 3 秒。

#### 离线链路

```text
文档接入
  -> 解析与清洗
  -> 按语义和结构切片
  -> 元数据与权限标注
  -> Embedding
  -> 向量索引和关键词索引
  -> 版本化发布
```

#### 在线链路

```text
鉴权
  -> Query 改写
  -> 混合召回
  -> 权限过滤
  -> Rerank
  -> 上下文组织
  -> LLM 生成
  -> 引用校验
  -> 结果返回
```

关键指标包括 Recall@K、重排 NDCG、答案正确率、引用支持率、拒答准确率、p95/p99 和单请求成本。出现错误答案时，应逐层判断是解析、召回、排序、上下文还是生成问题。

### 案例：模型评测平台

平台由任务管理、数据集版本、模型适配器、执行队列、指标计算、结果存储和案例分析组成。任务配置必须记录代码版本、模型版本、Prompt、解码参数、数据版本和随机种子。

执行层使用队列分发任务，Worker 定期写入进度和心跳；单个 case 的结果幂等落盘，支持失败重试和断点续跑。大任务按 case 分片，避免单 Worker 失败导致整批重跑。平台还需要支持：

- 并发和配额控制，避免评测任务打满模型服务。
- 超时、重试和错误分类，区分模型错误、平台错误与外部依赖错误。
- 多版本结果对齐和 diff case。
- 指标置信区间、分桶结果和回归阈值。
- 任务、数据与结果的权限隔离。

### 案例：高并发 LLM 推理服务

请求先经过网关完成鉴权、限流和模型路由，再进入调度器。调度器按模型、上下文长度和优先级组织 continuous batching，后端推理引擎管理 KV Cache 和 GPU 执行。

容量规划需要区分 Prefill 和 Decode：

- Prefill 更偏计算密集，主要受输入长度和算力影响。
- Decode 更偏显存带宽和 KV Cache，主要受并发数和输出长度影响。

系统应限制最大上下文和最大输出 Token，避免少量超长请求占满显存。高优请求可使用独立队列或预留容量。降级方案包括切换小模型、缩短上下文、关闭非核心工具、返回异步任务或限制输出长度。

### 可观测性

建议同时建设三类信号：

| 类型 | 关注内容 |
| --- | --- |
| Metrics | QPS、并发、p50/p95/p99、错误率、Token 吞吐、GPU 利用率、队列长度 |
| Logs | 请求 ID、模型版本、错误码、重试、关键耗时，敏感内容需脱敏 |
| Traces | 网关、检索、模型、工具和存储各阶段耗时与依赖关系 |

监控应区分系统指标和模型质量指标。服务没有报错不代表模型效果正常，因此还需要采样回放、线上质量评测、分布漂移和安全违规监控。

### 发布与故障处理

上线采用小流量灰度，先检查错误率、延迟和资源，再检查任务质量和业务指标。发布必须保留模型、Prompt、特征和索引版本的对应关系，确保可以整体回滚。

事故处理顺序：

1. 确认影响范围和用户症状。
2. 止损：回滚、限流、降级或隔离故障依赖。
3. 根据最近变更、指标、日志和 Trace 缩小范围。
4. 修复后使用流量回放和回归集验证。
5. 补监控、测试和操作手册，避免同类问题重复发生。

### 常见追问

- 如何设计评测任务的断点续跑？
- 如何支持多个模型服务供应商？
- 如何避免 RAG 检索到错误知识还被模型强行引用？
- Agent 工具调用死循环怎么处理？
- 模型平台如何处理权限和数据合规？

## 面试应对

### AI 系统设计题应该怎么开始？

回答思路：先澄清约束并估算容量，再进入架构，避免直接罗列组件。

回答模板：

我会先明确用户场景、输入输出、峰值 QPS、目标延迟、准确率、成本和可用性要求，再估算单实例吞吐和所需容量。架构上按数据、模型、服务、存储和监控拆分，说明请求主链路以及异步链路。随后重点讨论瓶颈、扩容方式、超时重试、限流降级、数据和模型版本，以及灰度回滚。最后用指标、日志、Trace 和质量回归说明系统如何被持续运营，而不只是画出静态架构图。

### 如何设计一个高并发 LLM 推理服务？

回答思路：围绕路由、调度、Prefill/Decode、KV Cache、容量和降级回答。

回答模板：

请求先经过网关做鉴权、限流和模型路由，再进入按模型和长度分组的调度队列，通过 continuous batching 提升 GPU 利用率。推理层要分别关注 Prefill 的计算瓶颈和 Decode 的显存带宽、KV Cache 瓶颈，并限制最大上下文和输出长度。容量按峰值请求、Token 吞吐和冗余系数估算，监控 p99、队列长度、GPU 利用率、KV Cache 使用率和错误率。过载时可以切换小模型、缩短上下文、降低最大输出或转异步处理，并通过灰度和版本隔离保证可回滚。
