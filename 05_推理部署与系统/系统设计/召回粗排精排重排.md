# 召回、粗排、精排与重排

## 知识点解析

### 概述

召回、粗排、精排、重排是一套分层筛选机制，用来从海量候选中逐步选出最相关、最可靠、最适合展示或送入大模型上下文的内容。

一句话：

```text
召回解决“找得到”，粗排解决“先筛掉明显不相关”，精排解决“排得准”，重排解决“最终可用”。
```

在传统搜索推荐里，候选可能是商品、视频、广告、网页；在 AI 产品里，候选也可以是文档 chunk、代码片段、工具、[Skill](<../../10_Agent/基础概念/Skill.md>)、历史记忆、视频帧或 OCR 区域。

### 召回是什么

召回是从海量候选中快速找出一批“可能相关”的内容。

它的目标不是最终排序最精确，而是尽量不漏掉正确候选：

```text
海量候选
  -> 快速召回 top 100 / top 1000
  -> 保证正确候选在里面
```

不同 AI 场景里的召回对象：

| 场景 | 召回对象 |
| --- | --- |
| [RAG](<../../02_大模型/应用与问题/RAG.md>) | 文档 chunk、网页、知识片段 |
| AI Coding | 文件、函数、类、测试、历史错误 |
| [Agent](<../../10_Agent/基础概念/Agent.md>) | 工具、Skill、[Memory](<../../10_Agent/基础概念/Memory.md>)、历史轨迹 |
| 多模态 | 图片、视频片段、关键帧、OCR 区域 |
| 搜索推荐 | 网页、商品、帖子、视频、广告 |

### 常见召回策略

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 关键词召回 | BM25、倒排索引 | 精确匹配强，适合术语、编号、错误码、人名 | 语义泛化弱 |
| 向量召回 | Embedding + ANN | 语义匹配强，能处理同义表达 | 容易召回语义相似但事实不相关内容 |
| 规则召回 | 根据权限、标签、类型、业务规则过滤 | 稳定、可控 | 覆盖有限 |
| 图召回 | 基于用户、物品、代码调用、知识图谱扩展 | 适合关系型候选 | 构建和维护成本高 |
| Query Rewrite | 改写、扩展、拆解 query | 改善召回覆盖 | 改写错会引入噪声 |
| 多路召回 | BM25 + 向量 + 规则 + 图/热门 | 覆盖更全 | 需要融合、去重和调权 |

RAG 常见组合：

```text
BM25 top 50
  + embedding top 100
  + metadata / 权限过滤
  -> 合并去重
  -> rerank
```

### 粗排是什么

粗排是在召回结果上做快速筛选。

召回结果可能有几百到几千个，如果全部交给复杂 reranker 或 LLM，成本和延迟太高。粗排通常用轻量规则或轻量模型先筛掉明显不相关的候选。

常见粗排信号：

- 关键词命中数。
- embedding 相似度。
- 文档更新时间。
- 权限和业务标签。
- 用户上下文匹配。
- 文件路径或标题匹配。
- 候选长度是否过长。

粗排目标：

```text
召回 top 1000
  -> 粗排 top 100
```

### 精排是什么

精排是用更强模型对候选做更细粒度打分，目标是把真正相关、真正能回答问题的候选排到前面。

常见精排模型：

- Cross-Encoder reranker。
- BGE / [Qwen](<../../02_大模型/模型细节/Qwen千问架构.md>) Reranker。
- LLM-as-reranker。
- 业务排序模型。
- 规则 + 模型混合打分。

为什么精排比向量召回更准：

```text
向量召回：
  query 和 doc 分别编码，再算相似度。

Cross-Encoder 精排：
  query 和 doc 一起输入模型，让模型直接判断相关性。
```

后者能理解更细粒度条件，例如“生产权限”不能匹配成“测试权限”，“Qwen3-VL 视频输入”不能匹配成普通 Qwen 文本模型。

### 重排是什么

重排是在精排结果基础上加入最终展示或上下文构造规则。

它不只看相关性，还看最终可用性：

- 去重：同一文档相邻 chunk 合并。
- 多样性：避免全是同一来源。
- 权限：最终输出前再确认权限。
- 安全：过滤敏感、过期、低可信内容。
- 业务规则：优先官方文档、最新版本、用户所在部门文档。
- 长度预算：控制进入 prompt 的 token 数。
- 引用顺序：按答案组织而不是按分数机械排列。

在 RAG 里：

```text
精排 top 10
  -> 去重 / 合并相邻 chunk
  -> 过滤冲突或低可信来源
  -> 按答案逻辑组织 top 5
  -> 放入 prompt
```

### RAG 里的完整链路

```text
知识库全量 chunk
  -> 多路召回 top 200
  -> 粗排过滤 top 50
  -> cross-encoder / LLM reranker 精排 top 10
  -> 重排：去重、压缩、权限、安全、引用组织
  -> top 5 放入 prompt
  -> LLM 基于证据回答
```

这个链路里，每层解决的问题不同：

| 层级 | 目标 | 更关注 |
| --- | --- | --- |
| 召回 | 不漏正确证据 | Recall@K、覆盖率、速度 |
| 粗排 | 快速降候选量 | 延迟、明显错误过滤 |
| 精排 | 把正确证据排前面 | MRR、NDCG、Precision@K |
| 重排 | 最终上下文可用 | 去重、权限、引用、token budget |

### 精排为什么重要

向量召回只看 embedding 相似，不等于能回答问题。

例子：

```text
用户问：如何申请 A 系统的生产权限？

向量召回可能找回：
- A 系统介绍
- A 系统测试环境权限
- A 系统生产权限审批流程
- B 系统生产权限流程
```

这些都“语义相似”，但真正能回答的是“A 系统生产权限审批流程”。精排模型会把 query 和候选文档一起看，判断哪个片段真正支持答案。

### 在 AI Coding 里的对应

```text
用户说：帮我修这个测试失败

召回：
  搜相关错误日志、测试文件、被测函数、最近改动。

粗排：
  排除明显无关文件和依赖目录。

精排：
  选择最可能导致失败的函数、配置和测试断言。

重排：
  按阅读/修改顺序组织上下文，避免把无关大文件塞给模型。
```

### 在多模态关键帧里的对应

```text
视频任务
  -> 召回候选时间窗口 / 候选帧 / OCR 区域 / Video Primitive
  -> 粗排去掉明显未加载或无关片段
  -> 精排比较边界前、当前、后帧
  -> 重排/组织证据，输出关键帧时间和理由
```

对关键帧任务，召回漏掉正确时间窗口，后面 [VLM](<../../06_视觉多模态与生成模型/多模态模型/VLM与Vision_Instruction_Tuning.md>) 再强也没用；精排不准，就会把“相似但不是首次完成”的帧排在前面。

### 评估指标

| 阶段 | 常用指标 | 含义 |
| --- | --- | --- |
| 召回 | Recall@K、Hit Rate、覆盖率 | 正确候选有没有被找回来 |
| 粗排 | 过滤后 Recall、延迟、候选压缩率 | 是否快速减少候选且不误杀正确项 |
| 精排 | MRR、NDCG、Precision@K、Pairwise Accuracy | 正确候选是否排得靠前 |
| 重排 | 引用支持率、去重率、上下文 token 数、安全违规率 | 最终上下文是否可用 |
| 端到端 | 答案正确率、Faithfulness、p95/p99、成本 | 产品最终效果 |

排查顺序：

```text
答案错
  -> 正确证据是否被召回？
  -> 是否被粗排误杀？
  -> 是否被精排排进 top K？
  -> 重排后是否仍在 prompt 里？
  -> 模型是否忠实使用证据？
```

### 常见错误

- 召回和精排混为一谈。
- 只用向量召回，不做 BM25，导致编号、术语、错误码召回差。
- 召回 top K 太小，正确证据根本进不来。
- rerank 模型和业务 query 分布不匹配。
- 重排只看相关性，不看权限、时效、冲突和 token budget。
- 只看端到端答案，不拆分 Recall@K、NDCG、Faithfulness。

## 面试应对

### 召回、粗排、精排、重排有什么区别？

回答思路：按候选规模逐层缩小讲，强调召回重覆盖、精排重准确。

回答模板：

召回是从海量候选里快速找出一批可能相关的内容，目标是尽量别漏掉正确结果，所以更关注 Recall@K 和速度。粗排是在召回结果上用轻量模型或规则快速筛掉明显不相关的候选。精排会用更复杂的模型，比如 cross-encoder、reranker 或 LLM，对 query 和候选做更细粒度匹配，目标是把最相关的结果排到前面。重排是在最终展示或送入上下文前加入去重、多样性、权限、安全、长度预算等业务规则。简单说，召回解决“找得到”，精排解决“排得准”，重排解决“最终可用”。

### 为什么 RAG 里通常要做 rerank？

回答思路：说明向量相似不等于能回答问题，rerank 用更强匹配模型纠正排序。

回答模板：

RAG 里做 rerank 是因为第一阶段召回通常追求速度和覆盖，尤其向量召回只看语义相似，可能把“看起来相关但不能回答问题”的片段排在前面。Reranker 会把用户问题和候选文档放在一起做更细粒度匹配，判断这个片段是否真的能支撑答案。这样可以把正确证据排进最终上下文，减少噪声和幻觉。工程上常见做法是 BM25 加向量多路召回 top 100 或 top 200，再用 reranker 精排到 top 5 到 top 10 放进 prompt。

### 多路召回为什么比单一路召回更稳？

回答思路：关键词保精确匹配，向量保语义泛化，规则保业务约束。

回答模板：

多路召回更稳，是因为不同召回方式覆盖的问题不一样。BM25 和倒排索引擅长精确匹配，适合错误码、接口名、人名、版本号；向量召回擅长语义匹配，可以处理同义表达和自然语言问题；规则和 metadata 过滤能保证权限、业务线、时间范围这些硬约束。单一路召回容易有盲区，多路召回先提高覆盖，再通过去重、融合和 rerank 控制噪声。

### 如果正确证据没进最终上下文，怎么排查？

回答思路：按召回、粗排、精排、重排逐层定位。

回答模板：

我会先看正确证据有没有进召回 top K。如果没有，问题在文档解析、chunk、关键词索引、embedding、query rewrite 或权限过滤。召回到了但粗排后没了，就看粗排规则是不是误杀，比如时间、标签、长度过滤过严。粗排保住但 rerank 排得靠后，说明 reranker 和业务相关性不匹配，或者 query-doc 匹配特征不足。rerank 排前但最终 prompt 没有，就看重排、去重、上下文预算和引用组织是否把它挤掉。这样能把“RAG 答错”拆成具体链路问题。
